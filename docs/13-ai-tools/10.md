# 배포·인프라 도구 지형도 — 무엇에 올릴까

**① 한 줄 정의**
내가 만든 앱을 인터넷에 띄워 '남이 볼 수 있는 주소'를 갖게 하는 도구들(프론트 호스팅·서버 호스팅·컨테이너·자동 배포·모니터링)을 **한 지형도에 펼쳐 놓고**, 비전공 디렉터가 **무엇 위에 올리고 무엇은 나중으로 미룰지**를 길라잡이 판정(🟢🟡🔵⚪)으로 정리하는 페이지입니다.

**② 왜 중요한가 (디렉터 관점)**
아무리 잘 만들어도 **내 컴퓨터(localhost) 안에만 있으면 세상에는 존재하지 않는 것**입니다. 배포는 "코딩 AI"와 더불어 비전공 첫 서비스의 **두 개뿐인 🟢 메인** 중 하나입니다(다른 하나가 코딩 AI). 안 올리면 아무도 못 보고, 포트폴리오로도 못 쓰니까요.

그런데 막상 배포 도구를 검색하면 Vercel·Netlify·Render·Fly·Railway·Docker·Kubernetes·GitHub Actions·Sentry… 이름이 폭탄처럼 쏟아집니다. 디렉터의 무기는 이걸 **"내 앱이 어떤 종류냐"라는 질문 하나로 갈라서 거의 다 무시하는 능력**입니다. 정적·Next.js 프론트면 답은 사실상 정해져 있고(Vercel), 24시간 켜져 있어야 하는 서버는 또 다른 칸이며, Docker·쿠버네티스 같은 단어는 대부분 비전공 첫 서비스에서 **몰라도 되는** 영역입니다.

이 지형도를 머리에 넣어 두면, AI가 "Docker로 컨테이너화하고 쿠버네티스에 올리세요"라고 답할 때 "그건 ⚪ 지금 내 규모엔 과해요, Vercel에 그냥 올려 주세요"라고 **되받아칠 수** 있습니다. 잘못된 배포 선택은 단순한 불편이 아니라 **요금 폭탄·새벽 장애 호출·복잡도 지옥**으로 직결되므로, 첫 선택을 가볍게 가는 것이 곧 실력입니다.

**③ 비유**
배포 도구를 고르는 건 **'내 가게를 어디에 차릴까'**를 정하는 것과 같습니다.

- **Vercel·Netlify(프론트 호스팅)** = **목 좋은 상가에 입점**. 인테리어(내 코드)만 들고 가면 전기·수도·간판(서버·HTTPS·CDN)은 건물이 다 해 줍니다. 가장 손쉬운 출발.
- **Render·Fly·Railway(서버 호스팅)** = **24시간 불 켜진 주방을 임대**. 손님이 없어도 불이 켜져 있어야 하는 식당(상시 서버)을 차릴 때. 임대료(상시 비용)가 듭니다.
- **Docker(컨테이너)** = **'주방 통째로 포장한 이사 박스'**. 내 컴퓨터에서 잘 돌던 환경을 박스에 그대로 담아, 어느 건물에 갖다 놔도 똑같이 작동하게 만드는 표준 규격 컨테이너. "내 컴퓨터에선 됐는데요?"를 없애는 도구.
- **CI/CD(자동 배포)** = **'코드 올리면 알아서 가게가 새 단장되는 자동 시스템'**. 내가 글(코드)을 GitHub에 올리기만 하면, 검수→번역(빌드)→오픈(배포)이 자동으로 굴러갑니다.
- **모니터링** = **가게에 단 CCTV·화재경보기**. 손님이 넘어졌는지(에러), 불이 났는지(서버 다운), 전기료가 폭증하는지(비용)를 내가 잠든 사이에도 지켜보고 알려 줍니다.

**④ 최소한 알 것**

먼저 도구를 **다섯 칸(layer)**으로 나눕니다. 머릿속 폴더 5개면 충분합니다.

| 칸 | 무엇을 하나 | 대표 도구 | 비유 |
|---|---|---|---|
| 프론트 호스팅 | 정적·Next.js 화면을 올린다 | Vercel, Netlify, Cloudflare Pages | 목 좋은 상가 입점 |
| 서버 호스팅 | 24시간 켜진 백엔드를 올린다 | Render, Fly.io, Railway | 상시 주방 임대 |
| 컨테이너 | 환경을 박스로 표준화 | Docker | 주방 이사 박스 |
| 자동 배포(CI/CD) | 올리면 알아서 빌드·배포 | GitHub Actions, Vercel 내장 | 자동 새단장 시스템 |
| 모니터링 | 죽음·에러·비용을 감시·알림 | Sentry, Vercel Analytics, UptimeRobot | CCTV·화재경보기 |

이제 **각 도구의 길라잡이 판정**입니다. 아이콘 뜻 — 🟢 메인(지금 바로) / 🟡 대안(상황 되면) / 🔵 나중에(필요해질 때) / ⚪ 몰라도 됨(개념만).

| 도구·주제 | 무엇에 쓰나 | 비전공자 판정 | 한 줄 이유 |
|---|---|---|---|
| **Vercel** | Next.js·정적 프론트 배포 | 🟢 메인 | Next.js를 만든 회사. GitHub 연결만으로 자동 배포·HTTPS. 우리 기본값 |
| Netlify | 정적·JAMstack 프론트 | 🟡 대안 | Vercel과 거의 동급. 정적 위주면 좋은 선택지 |
| Cloudflare Pages | 정적 프론트 + 엣지 | 🔵 나중에 | 트래픽·전세계 속도가 중요해질 때 |
| Render | 상시 서버·DB·크론 | 🟡 대안 | '항상 켜진 서버'가 필요한 백엔드일 때 무난 |
| Railway | 상시 서버·DB 빠른 셋업 | 🟡 대안 | 셋업이 쉬워 초보 친화적. Render와 비슷 결 |
| Fly.io | 전세계 분산 서버 | 🔵 나중에 | 글로벌 저지연이 필요할 때. 입문 난도 약간 높음 |
| **Supabase** | DB·인증·스토리지 | 🟢 메인 | 우리 기본 백엔드. 별도 서버 임대 없이 시작 |
| Docker | 환경을 컨테이너로 | ⚪ 몰라도 됨 | 개념만. Vercel·Supabase 쓰면 직접 다룰 일 거의 없음 |
| 쿠버네티스(k8s) | 컨테이너 수십 개 관리 | ⚪ 몰라도 됨 | 대기업 규모용. 비전공 첫 서비스엔 과함 |
| GitHub Actions / CI·CD | 자동 빌드·배포·테스트 | 🔵 나중에 | Vercel이 자동배포를 이미 해 줌. 고급 자동화는 나중 |
| Sentry(에러 추적) | 실시간 에러 알림 | 🟡 대안 | 사용자가 생기면 큰 무기. 무료 티어로 시작 |
| UptimeRobot(가동 감시) | 사이트 다운 알림 | 🟡 대안 | "내 사이트 살아 있나?"를 5분마다 점검 |
| Vercel Analytics | 방문·성능 측정 | 🔵 나중에 | 사람이 들어오기 시작하면 켠다 |

!!! tip "비전공자 기본값(default) 한 줄 요약"
    **프론트 = Vercel · 백엔드/DB = Supabase**, 이 조합 하나가 첫 서비스의 90%를 덮습니다.
    여기에 **자동 배포는 Vercel이 공짜로 끼워서** 해 주므로 CI/CD를 따로 배울 필요가 없고, **Docker·쿠버네티스는 "그런 게 있다"만 알면** 충분합니다. 상시 서버(Render·Fly·Railway)는 *"Supabase로 안 되는 무거운 백엔드(예: 영상 처리, 항상 도는 봇)"가 생겼을 때* 비로소 펴 보세요. 모니터링은 **사람이 들어오기 시작한 날** 무료 티어부터 켜면 됩니다.

**서버리스 vs 상시 서버 — 딱 한 가지만 구분.** Vercel·Supabase는 '서버리스'라 **손님이 올 때만 잠깐 켜졌다 꺼지는** 방식입니다(안 쓰면 비용 거의 0, 대신 첫 호출이 살짝 느린 '콜드 스타트'). Render·Fly·Railway의 상시 서버는 **24시간 불을 켜 두는** 방식입니다(항상 빠르지만 임대료가 늘 나감). "항상 켜져 있어야 하는 무언가(상시 동작 봇, 웹소켓 실시간 연결)"가 핵심이 아니라면, 비전공 디렉터는 **서버리스(Vercel+Supabase)부터** 가는 게 정석입니다.

**⑤ AI에게 이렇게 시켜라**

```text
나는 비전공 청년이고, [한 줄 서비스 설명: 예) "Next.js로 만든 포트폴리오 +
문의폼(Supabase 저장)"]을 인터넷에 올리려고 해. 나는 코드를 직접 짜기보다
AI에게 시키고 결과를 판별하는 '디렉터'야.

내 앱을 '어디에 어떻게 배포할지' 정해줘. 단, 조건이 있어:
1) 가능하면 가장 단순한 기본값으로 가줘 — Docker·쿠버네티스 같은 건
   '지금 내 규모에 정말 필요한 경우'가 아니면 쓰지 마.
2) 프론트/백엔드/DB를 각각 어디에 올릴지 표로:
   - 추천 도구와 그 이유(내 서비스 맥락에 맞춰서)
   - 서버리스로 충분한지, 굳이 '상시 서버'가 필요한 부분이 있는지
   - 예상되는 무료 티어 한도와 '요금이 새는' 시나리오(있으면 경고)
3) GitHub에 올리면 자동 배포되는 흐름(로컬 → GitHub → 배포)을
   비전공자가 따라할 단계로 풀어줘.
4) 환경변수(비밀키)는 코드에 박지 말고 배포 플랫폼 설정에 넣는 방법으로.
   Supabase를 쓴다면 anon 키는 공개돼도 되고 보호는 RLS로 한다는 전제로,
   service_role 키만 서버 환경변수로 숨기는 구성으로 잡아줘.

가격·정확한 한도는 변할 수 있으니 단정하지 말고 '공식 문서 확인'으로 표시해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **오버 엔지니어링(가장 흔함).** AI는 "확장성을 위해 Docker로 컨테이너화하고 쿠버네티스에…"로 직행하는 경향이 큽니다. 사용자가 0명인 포트폴리오에 **수천만 명용 인프라**를 얹는 셈입니다. 디렉터는 "지금 사용자/트래픽 규모"를 못 박고 "그 규모에 정말 필요한 최소 구성만"을 요구해야 합니다.
- **서버리스와 상시 서버를 섞어 설명.** Vercel은 '서버리스'라 24시간 켜진 서버가 없는데, AI가 전통 서버 기준으로 "서버를 재시작하세요" 같은 엉뚱한 조언을 하기도 합니다. '콜드 스타트(첫 호출 지연)'와 '함수 타임아웃'을 모르고 진단하면 멀쩡한 코드를 헤집습니다.
- **대소문자·경로 함정.** 내 컴퓨터(Windows/Mac)에선 되는데 **Vercel(리눅스)에선 빌드 실패**하는 대표 원인이 파일명 대소문자입니다(`Image.png`를 코드에선 `image.png`로 부르는 식). AI는 이걸 잘 경고하지 않습니다. "내 PC에선 되는데 배포만 하면 깨져요"의 단골 범인.
- **'빌드 실패'와 '실행 중 에러'를 뭉뚱그림.** 배포는 *번역(build) → 가동(run)* 두 단계인데, AI가 둘을 안 가르고 답합니다. "빌드 로그에서 멈췄는지, 떠 있는데 500이 나는지"부터 갈라야 합니다.
- **비밀키를 코드에 박는 안내.** AI가 API 키·`service_role` 키를 코드나 깃에 넣게 시키는 경우가 있습니다. **비밀키는 배포 플랫폼의 환경변수 설정**에 넣고, 코드엔 `.env.example`(자리표시자)만 둡니다. 단, **Supabase의 anon 키는 공개돼도 되는 키**(브라우저에 나가도 됨)이고 보호는 **RLS(행 수준 보안)**로 합니다 — "anon 키가 새면 큰일"은 틀린 설명입니다. 진짜 숨길 것은 `service_role` 키이고, 이건 **서버에서만** 씁니다.
- **'최신 화제 도구'가 정답이라는 환상.** AI는 새로 뜬 배포 도구를 권하곤 하지만, 비전공자에겐 **자료 많고 안정적인 도구(Vercel·Supabase)**가 거의 항상 낫습니다. 막혔을 때 검색해서 답이 나오는지가 더 중요합니다.

**⑦ 검증하는 법**

코드가 아니라 **'배포가 정말 됐는지·내 선택이 건강한지'**를 확인하는 페이지입니다.

1. **'시크릿 창'으로 진짜 공개 주소를 연다.** 로그인 안 된 다른 브라우저(또는 휴대폰 데이터)에서 배포 URL을 엽니다. 내 PC가 아닌 곳에서도 떠야 진짜 배포된 것입니다. (localhost는 나만 봅니다.)
2. **빌드 로그를 본다.** Vercel 대시보드에서 최근 배포의 로그를 열어 **`Build Completed`(또는 성공 표시)**를 확인합니다. 빨간 'Build Failed'면 *번역 단계*에서 막힌 것 — 대개 코드/대소문자/의존성 문제입니다.
3. **F12 → Network로 404·500을 확인한다.** 페이지는 떴는데 데이터가 안 보이면, 개발자도구 Network 탭에서 빨간 줄(에러)을 찾습니다. 화면 깨짐 vs 데이터 없음을 구분하는 핵심.
4. **🟢로 고른 도구가 'Vercel + Supabase' 둘을 크게 벗어나는가?** 벗어난다면(예: 첫 서비스에 Docker·k8s) "왜 이게 지금 필요한지" 한 문장으로 말할 수 있어야 합니다. 못 하면 그건 "AI가 권해서" 붙인 것 — 빼세요.
5. **요금 알림을 켰는가?** 무료 티어 한도 초과 시 '조용히 멈추거나' 과금되는 시나리오가 있습니다. 플랫폼의 사용량 알림/한도 설정을 켜 두는 것이 새벽 요금 폭탄의 예방주사입니다. *(정확한 한도·가격은 변하므로 공식 문서 확인 권장.)*

    수강생 준호가 "포트폴리오 사이트 다 만들었는데, 배포는 Docker로 컨테이너 만들어서 AWS EC2 서버 빌리고 쿠버네티스로 관리하면 되죠?"라며 블로그에서 본 단어들을 늘어놓습니다. 디렉터의 눈으로 지형도를 펼쳐 봅니다. "준호야, 그 사이트가 24시간 켜져서 뭔가를 계속 돌려야 해?" "아뇨, 그냥 제 작업물 보여주는 정적 사이트랑 문의폼이요." → 그러면 답은 한 칸으로 줄어듭니다. **GitHub에 코드를 올리고 → Vercel에 GitHub를 연결하면 끝.** 빌드·HTTPS·자동 배포·전세계 CDN을 Vercel이 공짜로 해 주고, 문의폼은 Supabase 테이블 하나(anon 키는 공개, RLS로 보호)면 됩니다. Docker(⚪)도 쿠버네티스(⚪)도 EC2(🔵)도 **지금 준호에겐 전혀 필요 없습니다** — 그건 손님 수천 명용 가게를 차리는 장비인데, 준호는 아직 개업도 안 했으니까요. 준호의 '도구 4개짜리 막막한 계획'이 **"GitHub 푸시 → Vercel 자동 배포"** 한 줄로 바뀌는 순간, 막혔던 출시가 오늘 오후의 일이 됩니다. 그게 지형도를 가진 디렉터의 힘입니다.
