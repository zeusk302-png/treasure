# Redis 연동 — 캐시·세션·속도

**① 한 줄 정의**
Redis는 데이터를 디스크가 아니라 **메모리(RAM)에 통째로 올려두고 키-값 한 쌍으로 즉시 꺼내 쓰는, 번개처럼 빠른 임시 저장소**입니다. 캐시·세션·레이트리밋·큐 같은 "빨라야 하고, 잠깐만 있으면 되는" 데이터를 맡깁니다.

**② 왜 중요한가 (디렉터 관점)**
디렉터에게 "느려요"는 가장 자주 듣는 민원입니다. 이때 보통 두 갈래의 처방이 있습니다. 하나는 **서버·DB를 더 크게 늘리는 것**(돈이 많이 듦), 다른 하나는 **같은 답을 한 번만 만들고 재사용하는 것**(가성비 최고)입니다. Redis는 두 번째 처방의 대표 도구입니다. 또한 "로그인이 자꾸 풀려요", "버튼을 빠르게 연타하면 가입이 수십 번 돼요", "이메일 발송이 화면을 멈추게 해요" 같은 민원도 결국 **세션·레이트리밋·큐** 문제이고, 이 셋의 단골 해법이 Redis입니다.

디렉터가 코드를 다 짤 필요는 없습니다. 다만 AI가 "Redis 붙이면 됩니다"라고 했을 때 **"이 데이터를 메모리에 둬도 되는 건가? 사라지면 큰일 나는 데이터 아닌가? 만료(TTL)는 몇 초로?"** 같은 옳은 질문을 던질 수 있어야 합니다. 그 판단력이 있으면 AI의 제안을 검증할 수 있고, 없으면 "DB에 둬야 할 결제 기록을 메모리에 뒀다가 서버 재시작에 날리는" 사고를 그대로 통과시킵니다.

**③ 비유**
DB(예: Supabase/PostgreSQL)가 **지하 대형 창고**라면, Redis는 **계산대 옆 손이 닿는 선반**입니다. 창고는 모든 물건을 안전하게 영구 보관하지만 매번 지하까지 내려갔다 오면 느립니다. 그래서 자주 찾는 물건(인기 상품, 방금 본 가격, 로그인한 손님의 번호표)을 계산대 선반에 잠깐 꺼내 둡니다. 선반은 좁고(메모리는 비쌈) 정전되면 비워지지만(휘발성), 대신 손만 뻗으면 즉시 잡힙니다. 핵심 원칙은 **"창고에 있어야 할 원본은 창고에, 선반엔 사본·임시·번호표만"** 입니다. 선반(Redis)이 통째로 사라져도 창고(DB)만 멀쩡하면 가게는 다시 돌아가야 합니다 — 이 설계가 안 되어 있으면 Redis를 잘못 쓴 것입니다.

**④ 최소한 알 것**

Redis가 잘하는 4가지 용도:

| 용도 | 무엇 | 비유 | 사라지면? |
|---|---|---|---|
| 캐시(cache) | 비싼 DB조회/계산 결과를 잠깐 저장해 재사용 | 인기 메뉴 미리 만들어 보온대에 | 괜찮음(DB에서 다시 만들면 됨) 🟢 |
| 세션(session) | "이 사람이 방금 로그인한 그 사람"이라는 번호표·상태 | 단골손님 번호표 장부 | 로그인 풀림(보통 감수 가능) 🟡 |
| 레이트리밋(rate limit) | "1분에 5번까지만" 호출 횟수 세기 | 입장 횟수 도장 찍기 | 잠깐 제한 느슨해짐 🟡 |
| 큐(queue) | 오래 걸리는 일을 줄 세워 뒤에서 처리 | 주방 앞 주문 전표 꽂이 | 처리 대기 작업 유실 위험 🔴 |

기억할 핵심 성질:

- **인메모리(in-memory)**: 데이터가 RAM에 있어 빠르지만, 기본적으로 **휘발성**(서버·인스턴스가 꺼지면 사라질 수 있음). 디스크 저장(영속성) 옵션이 있지만 "DB 대체"가 아니라 "빠른 보조"로 봅니다.
- **키-값(key-value)**: `user:42:session → {...}` 처럼 **이름표(키)** 로 값을 즉시 꺼냅니다. SQL 같은 복잡한 조회는 못 합니다. 단순·고속 전용.
- **TTL(Time To Live)**: "이 값은 60초 뒤 자동 삭제" 같은 **만료 시간**을 줄 수 있습니다. 캐시·세션·레이트리밋이 전부 이 기능 위에 섭니다.
- **🟢 무료로 시작하는 법**: 서버를 직접 깔지 말고 **관리형(서버리스) Redis**를 쓰세요. 대표가 **Upstash**(서버리스 Redis, HTTP로도 호출되어 Vercel 같은 서버리스/엣지 환경과 궁합이 좋음). 그 외 Redis Cloud, Railway, Render 등. 무료 등급은 작은 프로젝트에 충분하지만 **용량·일일 요청 수 한도와 가격은 시점에 따라 바뀌므로 반드시 공식 문서 확인을 권장**합니다.
- **언제 안 써도 되나(⚪)**: Vercel을 쓰면 정적 페이지 캐시(CDN)는 이미 됩니다. Next.js의 데이터 캐시·`revalidate`로 충분한 경우도 많습니다. **"진짜 병목이 DB 반복 조회인가, 세션 공유인가"를 먼저 확인**하고, 그제서야 Redis를 꺼내는 게 순서입니다.

**⑤ AI에게 이렇게 시켜라**

```text
[역할] 너는 Next.js + Supabase로 만든 내 웹앱의 백엔드 멘토야.
나는 비전공 디렉터라 코드를 다 짜기보다 옳은 결정을 하고 싶어.

[상황] 메인 페이지가 "인기 상품 목록"을 띄우는데, 매 방문마다 Supabase에
같은 무거운 쿼리를 날려서 느려. Upstash Redis(무료 서버리스)로 캐시를 붙이고 싶어.

[해줘]
1) 먼저 코드부터 짜지 말고, 이 데이터에 캐시를 둬도 되는지 점검 질문부터 해줘:
   - 이 목록은 몇 분에 한 번 바뀌어도 괜찮은 데이터인가?(가격·재고처럼 틀리면 안 되는 거면 캐시 짧게/주의)
   - 적절한 TTL(만료시간)은 몇 초/몇 분이 좋을까? 그 이유도.
2) 그다음 Upstash Redis를 붙이는 절차를 단계로:
   - 환경변수는 .env.example에 자리표시자로만 두고 .gitignore에 .env 넣는 것까지
   - "캐시에 있으면 그걸 주고, 없으면 DB조회 후 캐시에 저장(TTL)" 패턴(cache-aside) 코드
3) 상품 데이터가 수정되면 옛 캐시가 남아 '수정했는데 화면은 옛날'이 되는 문제(stale data)를
   어떻게 막을지(무효화 전략)도 같이 설명해줘.
4) 코드엔 '무엇'뿐 아니라 '왜 이렇게 했는지'를 한국어 주석으로 달아줘.
비밀키(Redis 토큰)는 절대 코드에 직접 박지 말고 서버 환경변수로만 쓰는 것 지켜줘.
```

> 팁: 모델은 **최신·최강 Claude**(예: Opus 4.8 = `claude-opus-4-8`, 가벼운 작업엔 Haiku 4.5 = `claude-haiku-4-5`)를 기본으로 권장합니다. 설계 판단이 중요한 이런 작업은 상위 모델이 함정을 더 잘 짚습니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **영속성 착각 — "Redis에 저장했으니 안전하다"**: Redis는 기본이 휘발성입니다. AI가 결제 기록·회원 정보·주문처럼 **사라지면 안 되는 원본**을 Redis에만 저장하는 코드를 줄 수 있습니다. 원본은 **항상 DB(Supabase)**, Redis엔 사본·임시·번호표만. "Redis가 통째로 비워져도 서비스가 복구되나?"가 점검 질문입니다.
- **캐시 무효화 누락(stale data)**: 캐시 켜기는 쉽지만, **데이터가 바뀌었는데 옛 캐시를 계속 보여주는** 문제를 자주 빠뜨립니다. "수정했는데 사이트엔 옛날 내용"이 전형적 증상. AI가 "캐시 추가했어요"라고만 하면 **"바뀌면 캐시는 어떻게 갱신돼?"** 를 꼭 되물으세요.
- **TTL을 안 주거나 너무 길게**: 만료가 없으면 메모리가 영영 차고, 너무 길면 옛 데이터가 오래 남습니다. **가격·재고처럼 틀리면 안 되는 데이터는 캐시를 짧게 하거나 안 씁니다.**
- **비밀키를 코드/프런트에 노출**: Redis 접속 토큰은 **service_role급 비밀값**입니다. 절대 브라우저 코드나 깃에 박지 말고 **서버 환경변수**로만. (참고: Supabase에서도 anon 키는 공개 가능·RLS로 보호하지만, service_role과 Redis 토큰은 서버 전용 비밀입니다.)
- **세션을 서버 메모리(전역변수)에 저장**: Vercel 같은 서버리스는 인스턴스가 여러 개라 한 서버 메모리에 세션을 두면 "다음 요청은 딴 서버라 로그인 풀림"이 납니다. 그래서 세션을 **공용 저장소(Redis)** 에 두는 것입니다 — 이게 Redis 세션의 존재 이유입니다.
- **비용·한도 무시**: "무료니까 무한"이 아닙니다. 일일 요청 수·용량 한도가 있고, 캐시 키를 무한정 쌓으면 한도를 넘깁니다. **TTL로 자동 청소**가 기본. 가격·한도는 시점에 따라 변하니 단정 말고 공식 문서를 확인하세요.

**⑦ 검증하는 법**

1. **속도가 실제로 빨라졌나**: 브라우저 **F12 → Network 탭**에서 같은 페이지를 두 번 새로고침해 보세요. 두 번째(캐시 적중)가 첫 번째보다 응답 시간이 눈에 띄게 짧으면 캐시가 일하고 있는 것입니다.
2. **"수정 → 반영" 테스트(무효화 점검)**: DB에서 데이터를 바꿔 보고, 화면이 **의도한 시간(TTL) 안에 새 값으로 바뀌는지** 확인하세요. 영영 옛날 값이면 무효화가 빠진 것입니다.
3. **"Redis 꺼져도 사나" 테스트(영속성 점검)**: 관리형 대시보드에서 캐시를 비우거나(flush) 잠깐 끊었을 때 **앱이 죽지 않고 DB에서 다시 만들어 내는지** 확인하세요. 흰 화면·에러로 죽으면 원본을 Redis에만 의존한 설계입니다.
4. **비밀키 점검**: 깃 저장소와 브라우저에서 보이는 코드(F12 → 소스)에 Redis 토큰이 노출되지 않았는지, `.env`가 `.gitignore`에 있는지 확인하세요.
5. **AI에게 자기검증 시키기**: "이 캐시 코드에서 (1)원본을 Redis에만 의존하는 곳, (2)무효화가 빠진 곳, (3)TTL이 없는 키, (4)비밀키가 노출된 곳이 있는지 비판적으로 점검해줘"라고 별도 세션에서 다시 물어보세요.

!!! example "💡 예시로 이해하기"
    동네 카페 예약 사이트를 만들었습니다. 메인에 "오늘의 추천 메뉴 9개"가 뜨는데, 누가 들어올 때마다 Supabase에 무거운 쿼리를 날려 평점·재고를 계산하니 점심시간만 되면 빙글빙글 돕니다. 디렉터는 AI에게 "추천 메뉴는 5분에 한 번만 바뀌어도 충분하니 Upstash Redis에 60초 TTL 캐시를 두자"고 시킵니다. 이제 첫 손님이 만든 답을 60초 동안 모두에게 그대로 내주니 DB는 거의 쉬고 화면은 빨라집니다. 단, 사장이 "오늘 라떼 품절"을 누르면 옛 캐시가 60초간 "재고 있음"으로 남아 헷갈리겠죠. 그래서 디렉터는 "재고처럼 틀리면 안 되는 값은 캐시를 짧게 하거나, 수정 시 그 키를 즉시 지우게(무효화) 해줘"라고 한 줄 덧붙입니다. 핵심은 변하지 않습니다 — **원본(메뉴·재고)은 창고(Supabase)에, 빠른 사본(추천 목록)은 선반(Redis)에, 그리고 선반이 비워져도 가게는 멀쩡히 돌아간다.** 이 한 문장을 지키는지가 Redis를 옳게 쓴 증거입니다.
