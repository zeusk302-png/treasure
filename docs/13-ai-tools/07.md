# 결제 연동 — Stripe로 구독·결제

**① 한 줄 정의**
Stripe(스트라이프)는 **내가 직접 카드번호를 만지지 않고도** 손님에게 돈을 받게 해주는 '결제 대행 도구'이고, 핵심은 **결제 페이지(Checkout)에 돈 받는 일을 통째로 맡기고, 진짜 입금됐는지는 웹훅(서버 통보)으로만 확인**하는 것입니다.

**② 왜 중요한가 (디렉터 관점)**
결제는 **여러분이 AI에게 시키는 일 중 가장 위험한 한 가지**입니다. 글자가 깨진 화면은 부끄러운 정도지만, 결제 코드가 틀리면 *돈을 안 낸 사람이 상품을 가져가거나, 비밀 키가 새서 요금 폭탄을 맞거나, 같은 손님에게 두 번 청구*되는 진짜 사고가 납니다. 그리고 AI는 이런 코드를 "동작은 하는데 안전하지 않은" 모습으로 아주 자신 있게 써줍니다.

디렉터의 무기는 코드를 짜는 능력이 아니라 **'이 결제 코드가 안전한지 판별하는 질문 세 개'**입니다. (1) 비밀 키가 서버에만 있나? (2) "결제됐다"를 브라우저 화면이 아니라 웹훅으로 확인하나? (3) 같은 통보가 두 번 와도 두 번 청구 안 되나? 이 세 질문을 던질 줄 알면, 코드를 한 줄도 못 읽어도 위험한 결제 코드를 걸러낼 수 있습니다. 이건 곧 **돈을 받는 사업(6권)의 안전장치**입니다.

**③ 비유**
Stripe는 **식당 입구의 '카드 단말기 대행업체'**입니다. 옛날에는 식당 주인이 손님 카드번호를 직접 받아 적었다면(=위험천만), Stripe를 쓰면 손님이 단말기(Checkout 페이지)에 직접 카드를 긁고, 주인은 카드번호를 **구경도 못 합니다**. 그 대신 결제가 끝나면 단말기 회사가 주인에게 **"방금 12번 테이블에서 3만 원 결제됐습니다"라는 전화(웹훅)**를 겁니다.

여기서 초보가 저지르는 치명적 실수: **손님이 "저 결제했어요!"라고 말하는 걸 믿고 음식을 내주는 것**. 손님 말(브라우저 화면)이 아니라 **단말기 회사의 전화(웹훅)**가 와야만 음식을 내줘야 합니다. 화면은 손님이 개발자도구로 얼마든지 조작할 수 있지만, 단말기 회사의 전화는 위조할 수 없으니까요.

**④ 최소한 알 것**

| 개념 | 한 줄 설명 | 디렉터가 기억할 것 |
|---|---|---|
| Stripe | 글로벌 결제 대행(PG). 카드·구독 처리 | 내가 카드번호를 직접 다루지 않음 |
| Checkout | Stripe가 만들어주는 결제 페이지 | 결제 화면을 직접 안 짜도 됨 |
| 테스트 키 | `pk_test_…` / `sk_test_…` (샌드박스) | 개발·연습은 무조건 이것만 |
| 라이브 키 | `pk_live_…` / `sk_live_…` (실제 돈) | 실서비스 전환 시에만, 매우 조심 |
| Publishable 키 | `pk_…` 공개 가능(브라우저에 나가도 됨) | 공개 키라서 노출 OK |
| Secret 키 | `sk_…` 절대 비밀(서버에만) | 새면 요금 폭탄. 깃허브 금지 |
| 웹훅(Webhook) | 결제 성공을 Stripe가 내 서버에 통보 | "진짜 입금" 판단의 유일한 근거 |
| 웹훅 서명 검증 | 그 통보가 진짜 Stripe가 보낸 건지 확인 | 안 하면 가짜 통보로 사기당함 |
| 멱등성(Idempotency) | 같은 통보가 두 번 와도 한 번만 처리 | 안 하면 두 번 청구·중복 발송 |
| 일회성 vs 구독 | 한 번 결제 vs 매달 자동 청구 | SaaS는 구독, 굿즈는 일회성 |

**언제 쓰나 (길라잡이)**
- 🟢 **메인**: 해외 손님 대상, 구독(SaaS), 글로벌 카드 결제가 필요할 때 → Stripe
- 🟡 **대안(한국)**: 국내 손님 위주, 한국 카드·간편결제(네이버페이·카카오페이·계좌이체)가 중요하면 → **토스페이먼츠 / 포트원(구 아임포트)**. 사업자등록·국내 정산이 쉬움
- 🔵 **나중에**: 세금계산서·정기 구독 환불·플랜 변경 같은 운영 흐름
- ⚪ **몰라도 됨**: 결제 표준(PCI-DSS)의 내부 규격 — Stripe가 대신 책임져 줌

!!! warning "키는 절대 코드·깃허브에 박지 말 것"
    `sk_…`(시크릿 키)가 깃허브에 한 줄이라도 올라가면, 자동 봇이 몇 분 안에 긁어가 여러분 명의로 결제를 일으킬 수 있습니다. **모든 키는 `.env`(환경변수)에, `.gitignore`로 제외**하고, 저장소에는 자리표시자만 담긴 `.env.example`만 올립니다. 이건 Supabase `service_role` 키와 똑같은 원칙입니다(참고: Supabase `anon` 키는 공개 가능, 보호는 RLS로).

**⑤ AI에게 이렇게 시켜라**

```text
역할: 너는 결제 보안에 깐깐한 시니어 개발자야.
목표: 내 Next.js 앱에 Stripe로 "월 9,900원 구독" 결제를 붙여줘.

반드시 지킬 보안 제약(어기면 안 됨):
1) 시크릿 키(sk_...)는 서버(서버 라우트/Edge Function)에서만 쓰고,
   절대 브라우저로 나가는 코드나 깃허브에 노출하지 마. .env에 두고 .gitignore.
2) 결제 화면은 Stripe Checkout으로 만들어(결제 폼을 내가 직접 짜지 않게).
3) "구독 시작/결제 성공"은 브라우저 리다이렉트 화면이 아니라
   Stripe '웹훅(checkout.session.completed)'을 받아서만 확정해.
4) 웹훅은 서명 검증(constructEvent + STRIPE_WEBHOOK_SECRET)을 반드시 하고,
   같은 이벤트가 두 번 와도 한 번만 처리하도록 멱등 처리(이벤트 id 기록)도 넣어.
5) 처음에는 테스트 키(pk_test_/sk_test_)와 테스트 카드(4242...)로만 동작하게.

산출물: (a) 결제 시작 서버 라우트 (b) 웹훅 수신 라우트
        (c) 권한을 켜는 부분(돈 낸 사람만 기능 ON)
모든 코드에 '왜 이렇게 했는지'를 비전공자가 알아듣게 한국어 주석으로 달아줘.
마지막에 위 5개 제약을 지켰는지 체크리스트로 정리해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**
AI가 결제에서 자주 저지르는 사고는 거의 정해져 있습니다.

1. **화면 말만 믿고 확정** — 결제 성공 페이지(`/success`)로 돌아온 것만 보고 주문을 확정. 손님이 그 주소를 직접 쳐서 들어가면 **돈 안 내고도 상품 획득**. 반드시 웹훅으로만 확정해야 합니다.
2. **웹훅 서명 검증 누락** — 누구나 내 웹훅 주소로 "결제됐어요" 가짜 신호를 보낼 수 있는데, 서명 검증(`STRIPE_WEBHOOK_SECRET`)을 빼먹으면 그걸 믿어버립니다.
3. **멱등성 무시** — Stripe는 통보가 **한 번만 온다고 보장하지 않습니다.** 같은 이벤트가 두 번 와도 처리는 한 번만 되도록 이벤트 id를 기록해 두지 않으면, 메일이 두 번 가거나 권한이 꼬입니다.
4. **시크릿 키 노출** — `sk_test_`/`sk_live_`나 웹훅 시크릿을 프론트 코드·깃허브에 박음. 라이브 키면 곧장 금전 피해.
5. **테스트 키와 라이브 키 혼동** — 연습한다며 실수로 라이브 키를 써서 **진짜 카드에 진짜 청구**. 또는 그 반대로 실서비스에 테스트 키를 둬서 돈이 안 들어옴.
6. **'해피 패스'만 만듦** — AI는 '결제 성공' 흐름만 짜고, **결제 실패·환불·구독 해지·카드 만료**를 자주 빠뜨립니다. 구독은 특히 "해지하면 권한이 꺼지나?"까지 챙겨야 합니다.

**⑦ 검증하는 법**
비전공자도 눈과 도구로 확인할 수 있습니다.

1. **테스트 카드로 결제 시도** — Stripe 테스트 모드에서 카드번호 `4242 4242 4242 4242`(만료일은 미래 아무 날, CVC 아무 3자리)로 결제해 봅니다. 실제 돈은 한 푼도 안 나갑니다.
2. **Stripe 대시보드에서 확인** — Stripe 관리자 화면 → Payments / Webhooks 탭에서 방금 결제와 **웹훅이 200(성공)으로 전달됐는지** 눈으로 봅니다. 빨간 실패가 있으면 그 줄을 AI에게 그대로 붙여 넣습니다.
3. **'화면만 믿는지' 공격 테스트** — 결제를 안 한 채로 성공 페이지 주소(`/success`)를 브라우저에 직접 쳐서 들어가 봅니다. **그래도 권한이 켜지면 위험**(웹훅으로 확정 안 하고 화면을 믿는 것). 안 켜지면 정상.
4. **깃허브·브라우저에 키 검색** — 저장소에서 `sk_`로 검색해 한 건도 안 나와야 하고, 브라우저 개발자도구(F12) → Network에서 결제 요청을 봐도 `sk_…`가 보이면 안 됩니다(`pk_…`만 보여야 정상).
5. **체크리스트로 자가 점검** — "키는 서버에만 / 웹훅으로만 확정 / 서명 검증 / 멱등 처리 / 테스트 키"의 5칸이 다 ✅인지 AI에게 점검시킵니다.

!!! example "💡 예시로 이해하기"
    수료생 민지가 '월 9,900원 글쓰기 도구'를 만들어 팔기로 했습니다. AI에게 "결제 붙여줘"라고만 했더니, 결제 성공 페이지로 돌아오면 바로 프리미엄 기능을 켜주는 코드가 나왔습니다. 동작은 잘 됩니다 — 테스트 카드로 결제하니 기능이 켜졌죠. 그런데 민지가 디렉터의 질문 세 개를 던집니다. "이거 결제 안 하고 `/success` 주소만 쳐도 켜지는 거 아냐?" 직접 해보니 **정말로 켜졌습니다.** 돈 한 푼 안 내고 프리미엄을 쓸 수 있었던 겁니다.
    민지는 ⑤번 프롬프트로 다시 시켜 **웹훅으로만 확정**하도록 고쳤습니다. 이제 `/success`를 직접 쳐도 권한이 안 켜지고, 오직 Stripe가 "진짜 9,900원 들어왔다"고 전화(웹훅)를 걸어줄 때만 켜집니다. 민지는 코드를 한 줄도 새로 쓰지 않았지만, **'무엇을 의심하고 어떻게 검증할지'를 알았기에** 돈 새는 구멍을 막았습니다. 이것이 디렉터의 일입니다.
