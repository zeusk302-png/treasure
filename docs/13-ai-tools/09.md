# 자동화·연결 — n8n·Zapier·MCP로 도구 잇기

**① 한 줄 정의**
자동화·연결 도구(n8n·Zapier·Make)는 **"A에서 무슨 일이 생기면(트리거) → B·C에서 이걸 해라(액션)"**를 코드 없이 이어 붙이는 배관 공사이고, MCP는 한 발 더 나아가 **AI 모델이 그 도구·데이터를 직접 손에 쥐고 쓰게 해주는 표준 콘센트**입니다.

**② 왜 중요한가 (디렉터 관점)**
혼자 만든 서비스에서 진짜 시간을 잡아먹는 건 화면 개발이 아니라 **"문의가 오면 슬랙에 띄우고, 구글시트에 적고, 환영 메일을 보내고…" 같은 손노동의 반복**입니다. 이걸 사람이 계속 하면 자정에도 알림을 놓치고, 빠뜨리고, 지칩니다. 자동화 도구는 이 반복을 기계에 넘겨, 혼자서도 직원 여럿이 일하는 것처럼 보이게 만듭니다.

디렉터에게 더 중요한 건 **"무엇을 직접 코드로 짜고, 무엇을 기성 자동화에 맡길까"의 판단**입니다. 결제 알림 하나 받겠다고 백엔드 서버를 새로 띄울 필요는 없습니다. 반대로 초당 수천 건이 흐르는 핵심 로직을 Zapier 같은 종량제 도구에 맡기면 요금 폭탄을 맞습니다. **어디까지가 배관 공사로 충분하고, 어디부터가 직접 지어야 할 집인지**를 가르는 것 — 그게 이 페이지의 핵심입니다. 그리고 MCP를 알면, 자동화의 "조건 분기"를 사람이 일일이 그리는 대신 **AI에게 도구를 쥐어주고 "알아서 판단해 실행하라"**고 맡기는 한 단계 위의 그림을 그릴 수 있습니다.

**③ 비유**
자동화 도구는 **공장 컨베이어 벨트**입니다. 한쪽 끝에 물건(데이터)을 올리면, 정해진 라인을 따라 "여기서 도장 찍고, 여기서 포장하고, 여기서 분류" 하며 자동으로 흘러갑니다. 사람은 라인을 한 번 설계할 뿐, 물건마다 손대지 않습니다.

- **트리거(trigger)**는 벨트를 돌리는 시작 버튼 — "신청서가 들어왔다", "매일 아침 9시가 됐다".
- **액션(action)**은 라인 중간의 작업대 — "메일 보내기", "시트에 한 줄 추가".
- **웹훅(webhook)**은 벨트끼리 잇는 연결관 — "내 서비스야, 일 생겼어!" 하고 다른 벨트에 신호를 쏘는 전화선입니다.

그럼 **MCP**는? 컨베이어 벨트는 사람이 라인을 미리 그려둬야 합니다. MCP는 그 공장에 **눈과 손을 가진 숙련공(AI)을 들여보내, 도구함(데이터베이스·검색·파일)을 직접 열어 쓰게 하는 표준 규격의 손잡이**입니다. 모든 도구 손잡이가 같은 규격이라, 숙련공은 처음 보는 공장에서도 "아, 이건 데이터 조회 손잡이군" 하고 바로 집어 씁니다.

**④ 최소한 알 것**

먼저 자동화 도구 셋의 성격 차이:

| 도구 | 한 줄 성격 | 강점 | 주의 |
|---|---|---|---|
| Zapier | 가장 쉬운 클라우드 자동화 | 연동 앱 수가 압도적, 클릭만으로 완성 | 실행 횟수 종량제 — 양 많아지면 비싸짐 |
| Make (구 Integromat) | 시각적 흐름도형 자동화 | 분기·반복·복잡한 흐름을 그림으로 | 처음엔 노드가 많아 어지러움 |
| n8n | 오픈소스 자가호스팅 끝판왕 | 직접 서버에 올리면 거의 무제한·저렴, 코드 노드로 확장 | 직접 설치·운영 부담(또는 클라우드판 유료) |

핵심 부품 용어:

- **트리거 / 액션** — "언제(시작 신호) → 무엇을(할 일)". 모든 자동화의 뼈대.
- **웹훅(webhook)** — 어떤 사건이 생기면 정해둔 주소(URL)로 데이터를 쏘는 "역(逆)호출". 폴링(계속 물어보기)보다 즉각적이고 효율적. *(자세히는 7권 자동화 권 참고.)*
- **폴링(polling)** — 반대로 "새 거 있어? 새 거 있어?" 하고 주기적으로 물어보는 방식. 웹훅이 안 될 때의 대안.
- **조건 분기 / 필터** — "금액이 10만 원 넘으면 사장에게도 알림" 같은 if 갈림길.
- **멱등성(idempotency)** — 같은 신호가 두 번 와도 결과가 한 번과 같게. 웹훅은 종종 중복 발사되므로 "이미 처리한 건인지" 확인 장치가 필요. *(보안·결제에서 다시 만나는 개념.)*

MCP(Model Context Protocol)란:

- **한 줄 정의** — AI 모델이 외부 도구·데이터에 접근하는 방식을 통일한 **공개 표준(콘센트 규격)**. 도구마다 제각각이던 연결을 "MCP 서버"라는 같은 모양의 플러그로 통일.
- **왜 생겼나** — 예전엔 AI에 도구를 붙이려면 도구마다 맞춤 코드를 짰습니다. MCP는 "도구 쪽이 MCP 서버로 자기를 노출하면, 어떤 AI든 같은 방식으로 꽂아 쓴다"로 바꿔, **N×M 짝짓기 지옥을 N+M으로** 줄였습니다.
- **무엇을 할 수 있나** — AI에게 DB 조회, 파일 읽기/쓰기, 사내 검색, 외부 API 호출 같은 "손"을 줍니다. AI가 답만 생성하던 것에서 **직접 행동(도구 실행)하는** 단계로.
- **모델 권장** — MCP로 AI가 도구를 골라 쓰는 "에이전트형" 작업은 판단력이 중요하므로 **최신·최강 Claude**(예: Opus 4.8 = `claude-opus-4-8`, 균형형은 Sonnet 4.6 = `claude-sonnet-4-6`)를 권장. 빠른·가벼운 처리는 Haiku 4.5(`claude-haiku-4-5`).

**무엇을 AI/자동화에 맡길까 — 판단 기준**

- 🟢 **메인(맡겨라)** — 규칙이 분명하고 반복되는 일: 알림 전달, 시트 기록, 환영 메일, 정해진 리포트 생성. 실수해도 되돌리기 쉬운 일.
- 🟡 **대안(조건부)** — 판단이 약간 필요한 일: 문의 내용 요약·분류(여기서 LLM 호출), 우선순위 매기기. AI 판단을 사람이 사후 확인할 수 있게.
- 🔵 **나중에** — 흐름이 자주 바뀌거나 양이 폭증할 일: 일단 수동/간단 자동화로 검증 후 정교화.
- ⚪ **맡기지 마라** — 돈·권한·삭제가 걸린 비가역 동작을 사람 확인 없이 자동 실행: 환불 자동 승인, 데이터 일괄 삭제, 외부에 자동 공개. 반드시 사람 승인 단계(휴먼 인 더 루프)를 끼운다.

**⑤ AI에게 이렇게 시켜라**

```text
나는 비전공자고, 1인 서비스 운영자야. 코드를 직접 짜기보다 기성 자동화로 빠르게 잇고 싶어.

[상황] 내 랜딩페이지의 신청 폼(Supabase 테이블에 한 줄 저장됨)에 새 신청이 들어오면,
1) 우리 팀 슬랙 채널에 "새 신청: {이름} / {이메일}" 알림을 띄우고
2) 구글시트 'leads' 탭에 한 줄로 기록하고
3) 신청자에게 환영 메일을 자동 발송

하고 싶어. 다음을 단계별로 알려줘:
- Zapier / Make / n8n 중 내 상황(아직 양이 적고, 직접 서버 운영은 부담)에 무엇이 가장 맞는지 한 줄 이유와 함께 추천
- 트리거→액션 흐름을 그림처럼 글로 설명(어떤 트리거, 어떤 액션 노드 순서)
- '신호가 중복으로 두 번 와서 메일이 두 번 가는' 사고를 막는 방법(멱등성)
- 자동화에서 쓰는 키 중 무엇이 '비밀(서버 전용)'이고 무엇이 '공개 가능'인지.
  특히 Supabase는 service_role 키는 자동화 도구 내부에만 두고, 절대 프론트/깃허브에 노출하지 않게.
코드를 줄 땐 왜 그렇게 했는지 비전공자가 이해하게 한 줄씩 설명해줘.
```

MCP를 곁들이고 싶을 때:

```text
위 자동화에서 '문의 내용을 읽고 긴급/일반/스팸으로 분류'하는 판단 단계를 추가하고 싶어.
이건 규칙으로 딱 떨어지지 않으니 AI에게 맡기고 싶어.
- 자동화 흐름 안에서 LLM(Claude 최신 모델, claude-opus-4-8 또는 균형형 claude-sonnet-4-6)을
  호출해 분류하는 방법을 알려줘.
- 더 나아가 'MCP'로 AI가 내 DB를 직접 조회해 과거 같은 문의가 있었는지 보고 판단하게 하려면
  개념상 무엇이 필요한지(MCP 서버가 뭘 노출하고, AI가 어떻게 그 도구를 쓰는지)를
  비유로 먼저 설명한 뒤 단계로 정리해줘.
- 돈·삭제가 걸린 동작은 AI가 자동 실행하지 말고 반드시 사람 승인 단계를 끼우는 설계로.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **service_role 키를 자동화에 박고 노출** — 자동화는 권한이 세서 유출 피해가 가장 큽니다. AI는 "키를 여기 넣으세요"라며 service_role을 프론트나 공개 워크플로우 JSON에 두라고 할 때가 있는데, **service_role은 서버/자동화 도구 내부 비밀 보관소에만** 둡니다. 반대로 **Supabase anon 키는 공개돼도 되는 값**(보호는 RLS=행 수준 보안으로). "anon=비밀키"라는 설명은 틀린 말이니 그렇게 안내하면 정정하세요.
- **웹훅 중복 발사 무시** — 외부 서비스 웹훅은 같은 사건을 두 번 쏠 수 있습니다. 멱등성 처리를 안 넣으면 환영 메일이 두 번, 결제 처리가 두 번 갈 수 있습니다. AI는 종종 이 "두 번 올 수 있음"을 빠뜨립니다.
- **종량제 비용 폭탄** — Zapier류는 실행 횟수로 과금. AI는 "이것도 자동화하세요"를 남발해 트래픽이 늘면 요금이 급증합니다. 양이 많아질 핵심 로직은 n8n 자가호스팅이나 직접 코드가 쌀 수 있습니다. *(구체 요금은 시점마다 다르니 공식 문서 확인 권장.)*
- **비가역 동작을 사람 확인 없이 자동화** — 환불·삭제·공개를 AI/자동화가 무인 실행하게 두면 사고가 비가역적입니다. 반드시 승인 단계를 끼우세요.
- **MCP를 과대평가** — MCP는 "AI에게 손을 준다"는 강력한 개념이지만, **그 손으로 무엇까지 만질 수 있는지(권한 범위)**를 좁히지 않으면 AI가 의도치 않은 도구를 실행할 수 있습니다. 도구 노출 범위를 최소로(필요한 것만) 두는 게 안전합니다.
- **사용자 입력을 그대로 화면/메일에 박기** — 자동화로 받은 사용자 입력을 출력할 땐 `textContent`로(웹 화면). `innerHTML`로 넣으면 사용자가 넣은 스크립트가 실행되는 XSS 위험이 있습니다.

**⑦ 검증하는 법**

1. **테스트 신호 한 번 흘려보기** — 자동화 도구의 "Test"/"Run once" 버튼으로 가짜 신청 1건을 흘려, 슬랙·시트·메일이 모두 한 번씩 정확히 도착하는지 눈으로 확인.
2. **중복 테스트** — 같은 신호를 일부러 두 번 보내, 메일이 두 번 가는지 확인. 두 번 간다면 멱등성 장치(이미 처리한 ID 기록)가 필요.
3. **실행 로그 보기** — 모든 도구에는 실행 기록(history/executions)이 있습니다. 성공/실패와 각 단계 입출력을 펼쳐, 어느 노드에서 멈췄는지 확인. 실패 단계만 짚으면 AI에게 정확히 질문할 수 있습니다.
4. **키 노출 점검** — 워크플로우를 내보낸 JSON·깃허브에 service_role 같은 비밀키가 평문으로 들어가 있지 않은지 검색해 확인.
5. **승인 단계 동작 확인** — 비가역 동작 앞에 사람 승인 단계를 넣었다면, 승인 전에는 실제로 실행이 멈추는지 테스트.

    수강생 민지가 손뜨개 클래스 신청 랜딩페이지를 만들었습니다. 처음엔 신청이 들어올 때마다 본인이 직접 슬랙을 보고, 구글시트에 옮겨 적고, "신청 감사합니다" 메일을 손으로 보냈습니다. 하루 두세 건일 땐 괜찮았는데, 인스타에 한 번 떠서 하루 80건이 몰리자 새벽까지 손으로 옮기다 몇 건을 빠뜨려 환불 항의를 받았죠. 민지는 Zapier로 컨베이어 벨트를 깔았습니다 — "Supabase에 새 신청 저장(트리거) → 슬랙 알림 → 시트 한 줄 추가 → 환영 메일(액션 3개)". 이제 신청 80건이 와도 손 하나 까딱 안 합니다. 한 달 뒤, 문의가 늘자 "이건 환불 문의 / 이건 일정 문의 / 이건 스팸"을 나누는 일이 또 손노동이 됐습니다. 규칙으로 딱 안 떨어지니, 민지는 흐름 중간에 Claude(`claude-sonnet-4-6`) 호출을 끼워 문의를 자동 분류하게 했습니다. 더 욕심이 나자 MCP로 AI가 과거 신청 DB를 직접 조회해 "이 사람 지난달에도 환불했네 → 우선 처리" 같은 판단까지 하게 만들었죠. 단, 환불 승인만큼은 AI가 자동 실행하지 못하게 사람 승인 버튼을 끼워뒀습니다. 손노동이 컨베이어 벨트가 되고, 그 벨트에 판단하는 숙련공(AI)이 들어선 셈입니다.
