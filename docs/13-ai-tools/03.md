# Figma → 코드 — 디자인을 코드로 옮기기

**① 한 줄 정의**
Figma는 **화면을 그리는 도구(디자인 툴)**이고, 'Figma → 코드'란 그 그림(디자인)을 **AI나 자동 도구의 힘으로 실제 HTML/CSS/React 코드로 바꾸는 작업**입니다.

**② 왜 중요한가 (디렉터 관점)**
바이브코딩으로 만든 화면은 자주 '동작은 하는데 못생긴' 상태에 머뭅니다. 글자만 줄줄이, 여백은 들쭉날쭉, 색은 제멋대로 — 기능은 멀쩡한데 첫인상에서 신뢰를 잃습니다. 디렉터의 무기는 **"내 머릿속 화면을 AI에게 정확히 전달하는 능력"**입니다. 말로 "예쁘게 만들어줘"라고 하면 AI는 매번 다른 걸 내놓지만, **그림(디자인)을 보여주면** AI가 "이 간격, 이 색, 이 배치"를 눈으로 보고 따라 만들 수 있습니다. 즉 Figma는 디렉터가 AI에게 주는 **가장 정확한 명세서**입니다. 또한 디자인이 한곳(Figma)에 정리돼 있으면, 화면을 고칠 때 "어디를 어떻게 바꿀지"를 그림에서 먼저 합의하고 코드는 그다음에 손대므로, AI가 멀쩡한 코드를 헤집어 새 버그를 만드는 일을 줄일 수 있습니다.

**③ 비유**
Figma는 **집을 짓기 전의 설계 도면**입니다. 도면 없이 "거실 넓게, 부엌은 햇빛 잘 들게" 말로만 시키면 목수(AI)는 매번 다른 집을 짓습니다. 반대로 치수와 배치가 적힌 도면을 건네면 목수는 그대로 짓기만 하면 됩니다. 'Figma → 코드'는 **도면을 목수에게 건네는 행위**이고, AI는 그 도면을 보고 벽을 세우는 목수입니다. 그리고 'Dev Mode(개발자 모드)'는 도면 위에 **치수선·자재 목록을 자동으로 적어주는 기능** — "이 여백은 16px, 이 색은 #2563eb"처럼 코드가 알아들을 값으로 번역해 줍니다.

**④ 최소한 알 것**

세 가지 길이 있습니다. 상황에 맞게 고르세요.

| 길 | 무엇 | 언제 쓰나 | 난이도 |
|---|---|---|---|
| 🟢 스크린샷 → 코드 | 디자인을 캡처해 AI에게 이미지로 붙여넣고 "이대로 만들어" | 가장 빠름. 화면 한두 개를 그럴듯하게 옮길 때 | 매우 낮음 |
| 🟡 Dev Mode 값 베끼기 | Figma 'Dev Mode'에서 자동 생성된 색·여백·폰트 값을 복사해 AI에게 전달 | 색·간격을 디자인과 똑같이 맞춰야 할 때 | 낮음 |
| 🔵 Figma MCP 연동 | AI 코딩 도구가 Figma에 직접 접속해 디자인 데이터를 읽음 | 화면이 여러 개·반복 작업·정확도가 중요할 때 | 중간 |

핵심 용어:

- **Figma**: 브라우저에서 도는 무료(기본) 디자인 협업 툴. 화면을 '프레임(Frame)' 단위로 그립니다.
- **Dev Mode(개발자 모드)**: 디자인 요소를 클릭하면 색·여백·글자크기 등을 **코드가 쓰는 값으로 보여주는** 보기 모드. 디자인을 코드로 자동 변환해 주는 마법은 아니고, **값을 정확히 알려주는 사전**에 가깝습니다.
- **MCP(Model Context Protocol)**: AI 도구가 외부 서비스(여기선 Figma)에 **표준 방식으로 연결**되는 통로. 'Figma MCP'를 켜면 AI가 사람이 캡처를 붙이지 않아도 디자인을 직접 읽습니다. (MCP 전반은 같은 권 [자동화·연결](09.md) 참고)
- **디자인 토큰(Design Token)**: 색·간격·폰트 같은 값에 `primary`, `spacing-4` 처럼 **이름을 붙여 재사용**하는 약속. 토큰이 있으면 AI가 "여기저기 다른 파란색" 대신 "정해진 파란색 하나"를 일관되게 씁니다.

판단 기준: **화면 1~2개면 스크린샷, 색·여백을 픽셀 단위로 맞춰야 하면 Dev Mode, 여러 화면을 반복 변환하면 MCP.** 어느 길이든 AI가 만든 결과는 100% 똑같이 나오지 않으니, '거의 같게 만들고 사람이 마지막 손질'이 현실입니다.

**⑤ AI에게 이렇게 시켜라**

스크린샷 → 코드 (가장 흔한 길, 디자인 이미지를 채팅에 첨부한 뒤):

```text
첨부한 디자인 이미지대로 화면을 만들어줘. 우리 스택은 Next.js + Tailwind CSS야.
규칙:
1) 이미지의 레이아웃·여백·색·글자 크기를 최대한 그대로 따라줘. 색은 눈대중 말고
   가능한 한 정확한 HEX 값으로.
2) 모바일에서도 깨지지 않게 반응형으로 만들어줘(좁은 화면에서 어떻게 쌓이는지도 설명).
3) 버튼·입력창 같은 요소는 의미 있는 이름의 컴포넌트로 나눠줘.
4) 사용자가 입력한 값을 화면에 출력할 땐 innerHTML이 아니라 textContent를 써줘
   (XSS 방지). 보안상 그렇게 한 이유도 주석으로 달아줘.
5) 코드만 주지 말고, 디자인의 어느 부분을 코드의 어디로 옮겼는지 한 줄씩 설명해줘.
아직 못 맞춘 부분(폰트가 없거나 아이콘이 빠진 곳)은 추측하지 말고 따로 목록으로 알려줘.
```

Dev Mode 값까지 정확히 맞출 때:

```text
이 화면을 Figma 디자인과 픽셀 단위로 맞추고 싶어. 아래는 Figma Dev Mode에서
복사한 값이야. 이 값들을 그대로 써서 만들어줘(임의로 바꾸지 마):
- 배경색: #0f172a, 본문 글자색: #e2e8f0, 강조색(버튼): #2563eb
- 제목 폰트 크기: 28px / 굵기 700, 본문: 16px / 굵기 400
- 카드 안쪽 여백: 24px, 카드 사이 간격: 16px, 모서리 둥글기: 12px
이 값들을 Tailwind 설정의 디자인 토큰(색·간격)으로 등록해서 화면 전체가
같은 값을 재사용하게 해줘. 한 곳만 바꾸면 전체가 따라 바뀌도록.
```

Figma MCP를 막 연결한 뒤 (AI 코딩 도구 안에서):

```text
연결된 Figma 파일에서 'Pricing' 프레임을 읽어 그대로 코드로 만들어줘.
- 디자인에 있는 색·간격·폰트는 추측하지 말고 Figma에서 읽은 실제 값을 써.
- 프레임 안의 반복되는 카드는 하나의 재사용 컴포넌트로 만들고, 내용만 데이터로 받게 해.
- Figma에 없는 동작(클릭 시 일어나는 일)은 네가 지어내지 말고, 비워두고 나에게 물어봐.
다 만든 뒤, 디자인과 결과가 다른 부분이 있으면 표로 정리해서 알려줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **"픽셀 맞게 똑같이 만들었습니다"라는 거짓 자신감.** AI는 결과가 디자인과 꽤 다른데도 자신 있게 "그대로 만들었다"고 말합니다. 눈으로 비교 전엔 믿지 마세요.
- **반응형(모바일) 무시.** 데스크톱 화면만 보고 만들어 휴대폰에서 글자가 넘치거나 버튼이 깨집니다. 항상 "모바일에서 어떻게 되는지"를 함께 시키세요.
- **하드코딩된 색·여백 난립.** 같은 파란색을 코드 곳곳에 다른 값(`#2563eb`, `#2664ec`…)으로 흩뿌려, 나중에 색 하나 바꾸기가 지옥이 됩니다. → 디자인 토큰으로 모으게 시키세요.
- **있지도 않은 폰트·아이콘을 'AI가 상상으로' 채움.** 디자인에 없는 요소를 그럴듯하게 지어냅니다. "없는 건 지어내지 말고 목록으로 알려줘"를 항상 붙이세요.
- **이미지를 통째로 한 덩어리 코드로.** 화면 전체를 쪼개지 않은 거대한 한 파일로 토해내, 고치기 어렵습니다. "의미 있는 컴포넌트로 나눠줘"를 명시하세요.
- **Figma MCP 연결 자체의 함정.** 토큰(접근 권한 키)이 필요하고, 이는 **비밀값**입니다. 깃허브나 코드에 박지 말고 환경변수로 관리하세요(보안 원칙은 [안전·보안 권](../04-security/index.md)).
- **저작권·라이선스 착각.** 인터넷에서 주운 디자인 시안이나 유료 템플릿을 그대로 베끼면 저작권 문제가 됩니다. 내 디자인이거나 사용 허락된 것만 코드로 옮기세요([윤리·법·저작권 권](../09-ethics-law/index.md)).

**⑦ 검증하는 법**

1. **나란히 놓고 눈으로 비교**: 디자인 이미지와 만든 화면을 좌우로 띄워 놓고, 여백·색·정렬을 훑습니다. 의외로 가장 강력한 검증입니다.
2. **모바일 확인**: 브라우저 F12 → 기기 모드(휴대폰 아이콘)로 좁은 화면을 켜고, 글자 넘침·버튼 깨짐·가로 스크롤이 생기는지 봅니다.
3. **색 정확도**: F12 → Elements에서 요소를 클릭해 실제 적용된 색이 디자인 값(예 `#2563eb`)과 같은지 확인합니다. 스포이드(색 추출) 도구로 디자인과 화면의 같은 지점 색을 찍어 비교해도 좋습니다.
4. **일관성 점검**: AI에게 "이 화면에서 쓰인 색·여백·글자크기 값을 전부 목록으로 뽑아줘"라고 시켜, 비슷한데 미묘하게 다른 값(난립)이 없는지 봅니다.
5. **'다른 점' 표 받기**: AI에게 "디자인과 결과가 다른 부분을 표로"라고 시키고, 그 표를 디자인과 대조해 거짓이 없는지 교차 확인합니다.

!!! example "💡 예시로 이해하기"
    카페 사장님이 메뉴판 소개 페이지를 만들고 싶다고 합니다. 디자이너 친구가 Figma로 '예쁜 메뉴 카드 3개가 가로로 놓인 화면'을 그려줬어요. 디렉터인 우리는 그 화면을 캡처해 AI에게 붙이고 ⑤의 첫 프롬프트를 그대로 시킵니다. AI가 화면을 만들어 오면, 디자인 이미지와 결과를 나란히 띄워 봅니다. "어, 카드 사이 간격이 디자인은 넉넉한데 결과는 다닥다닥 붙었네." 이때 Figma Dev Mode를 열어 카드 클릭 → '간격 16px'을 확인하고, AI에게 "카드 사이 간격을 16px로 정확히 맞추고, 그 값을 토큰으로 등록해줘"라고 다시 시킵니다. 말로 "간격 좀 넓혀줘"라고 했다면 AI는 또 눈대중으로 어림했겠지만, **그림에서 읽은 정확한 숫자(16px)**를 건넸기 때문에 한 번에 맞습니다. 디렉터가 코드를 한 줄도 안 쳤지만, '정확한 명세서'를 건넸기에 결과는 디자인과 같아집니다 — 이것이 'Figma → 코드'의 핵심입니다.
