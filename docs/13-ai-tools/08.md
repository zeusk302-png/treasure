# 검색 연동 — Algolia·Meilisearch로 빠른 검색

**① 한 줄 정의**
검색 엔진(Algolia·Meilisearch 등)은 데이터를 미리 **검색 전용으로 정리(색인, index)** 해 두고, 사용자가 친 글자마다 **오타까지 봐주며 관련도 순으로** 결과를 즉시 내주는 도구입니다. DB의 `LIKE '%검색어%'` 가 "책을 1쪽부터 끝까지 훑는 것"이라면, 검색 엔진은 "책 뒤 찾아보기 색인을 보고 곧장 그 쪽으로 점프하는 것"입니다.

**② 왜 중요한가 (디렉터 관점)**
검색은 거의 모든 사이트가 결국 만나는 기능입니다. 쇼핑몰의 상품 검색, 블로그의 글 검색, 사내 문서의 자료 찾기 — 처음엔 데이터가 적어 `LIKE`로도 멀쩡히 돌아갑니다. 그래서 AI에게 "검색 기능 만들어줘"라고 하면 대부분 `WHERE title LIKE '%검색어%'` 같은 코드를 줍니다. 문제는 **데이터가 쌓이면 이게 조용히 무너진다**는 것입니다. 글이 10개일 땐 0.01초, 10만 개가 되면 몇 초씩 걸리며 사이트 전체를 끌어내립니다. 게다가 `LIKE`는 **오타를 못 봐주고**(`아이폰`→`아이푼` 검색 시 0건), **관련도 정렬이 없고**(제목에 든 것과 본문 구석에 든 것을 똑같이 취급), **한글 조사·띄어쓰기에 약합니다**.

디렉터의 무기는 "지금 `LIKE`로 충분한가, 아니면 전문 검색을 도입할 때인가"를 **타이밍으로 판단**하는 것입니다. 너무 일찍 도입하면 안 써도 될 외부 도구·비용·복잡도를 떠안고, 너무 늦으면 "검색이 느려요·검색해도 안 나와요" 민원이 쌓입니다. 또 AI가 "Algolia 붙이면 됩니다"라고 했을 때 **"색인은 언제·어떻게 갱신돼?", "검색 API 키를 프런트에 노출해도 되는 거 맞아?", "오타교정·랭킹은 기본으로 켜져 있어?"** 같은 옳은 질문을 던질 수 있어야 합니다. 그 질문을 못 하면, "글을 수정했는데 검색 결과는 옛날 그대로"이거나 "관리자용 비밀 키가 브라우저에 노출된" 사고를 그대로 통과시킵니다.

**③ 비유**
도서관에서 책을 찾는 두 가지 방법을 떠올려 보세요. 첫째, **사서가 서가를 1번 책장부터 한 권씩 다 들춰보며** 찾아주는 방법(`LIKE` 전체 훑기) — 책이 100권이면 빠르지만 100만 권이면 평생 못 찾습니다. 둘째, **미리 만들어 둔 '주제별·제목별 찾아보기 카드함'(색인)** 을 보고 곧장 해당 서가로 가는 방법(검색 엔진) — 책이 몇 권이든 카드함만 보면 즉시 위치를 압니다.

검색 엔진의 진짜 똑똑함은 이 카드함이 **"아이푼"이라고 잘못 적어도 "혹시 아이폰?"이라며 맞는 카드를 꺼내 주고**(오타교정), **제목에 든 책을 본문에 살짝 언급된 책보다 위에 보여 주는**(랭킹) 데 있습니다. 그리고 새 책이 들어오면 누군가 카드를 새로 꽂아 줘야 카드함에서 찾을 수 있듯, **데이터가 바뀌면 색인을 갱신**해 줘야 검색에 반영됩니다 — 이 "카드 꽂기(색인 동기화)"를 빠뜨리는 게 가장 흔한 함정입니다.

**④ 최소한 알 것**

먼저, 왜 `LIKE`보다 전문 검색(full-text search)이 나은가:

| 비교 항목 | DB `LIKE '%말%'` | 전문 검색 엔진 |
|---|---|---|
| 속도(데이터 많을 때) | 전체를 훑어 점점 느려짐(seq scan) | 미리 만든 색인으로 즉시 |
| 오타교정 | 없음(`아이푼` → 0건) | 있음(`아이푼` → "아이폰?") |
| 관련도 랭킹 | 없음(맞으면 다 동급) | 있음(제목·인기·최신 가중치) |
| 부분어·동의어 | 약함 | 강함(어간 추출·동의어 사전) |
| 자동완성·실시간 | 직접 구현해야 | 기본 제공(타이핑마다 결과) |
| 한글 처리 | 조사·띄어쓰기에 약함 | 형태소·토크나이저로 보완 |

두 대표 도구 비교 — 🟢 메인 / 🟡 대안 기준:

| 항목 | Algolia (호스팅 SaaS) | Meilisearch (오픈소스) |
|---|---|---|
| 운영 방식 | 회사가 다 운영(서버 신경 끔) | 직접 서버에 설치하거나 클라우드 호스팅 |
| 도입 난이도 | 가장 쉬움(가입→키→붙이기) 🟢 | 비교적 쉬움(설치 한 번 필요) 🟡 |
| 비용 구조 | 무료 등급 후 사용량 과금(검색·레코드 수) | 자체 호스팅이면 서버비만, 클라우드는 별도 |
| 데이터 주권 | 데이터가 외부(Algolia)에 올라감 | 내 서버에 둘 수 있음(민감 데이터 유리) |
| 한국어 | 잘 됨(설정으로 보완) | 잘 됨(기본 다국어 토크나이저) |
| 대표 강점 | 안정성·부가기능·문서 풍부 | 무료·자기 통제·가벼움 |

> 한 줄 길잡이: **빨리·안정적으로·운영 부담 없이** 붙이려면 🟢 **Algolia**, **비용을 아끼고·데이터를 내 손에** 두려면 🟡 **Meilisearch**. (둘 다 가격·한도는 시점에 따라 바뀌니 **공식 문서 확인 권장**.) 검색량이 적고 단순하면 🔵 **나중에** — PostgreSQL/Supabase의 내장 전문 검색으로 버티다 정말 필요할 때 도입해도 됩니다.

색인·연동 흐름(둘 다 큰 그림은 같음):

1. **무엇을 검색할지 정한다** — 예: 상품(제목·설명·태그·가격). 검색에 필요한 필드만 골라 색인에 보냅니다(비밀 필드는 빼고).
2. **색인을 만든다(initial index)** — 기존 데이터를 한 번 통째로 검색 엔진에 올립니다("카드함 처음 만들기").
3. **계속 동기화한다(sync)** — 데이터가 추가·수정·삭제될 때마다 색인도 같이 갱신합니다. 보통 서버에서 DB 변경 시점에(또는 자동화 도구로) 색인을 업데이트합니다.
4. **검색 UI를 붙인다** — 프런트의 검색창이 검색 엔진에 직접 질의해 타이핑마다 결과를 받습니다.

핵심 보안 한 가지(필독): 검색 엔진은 보통 **키가 두 종류**입니다.

- **검색 전용(search-only) 키** — 읽기만 가능. **브라우저(프런트)에 노출해도 되는** 공개 키입니다(Supabase의 anon 키와 같은 성격: 공개 가능하되 권한이 좁음).
- **관리자(admin/master) 키** — 색인 생성·수정·삭제까지 가능한 **비밀 키**입니다. **절대 프런트에 두지 말고 서버 환경변수에만** 둡니다(Supabase의 service_role과 같은 성격).

**⑤ AI에게 이렇게 시켜라**

```text
[역할] 너는 Next.js + Supabase로 만든 내 웹앱의 검색 기능 멘토야.
나는 비전공 디렉터라 코드를 다 짜기보다 옳은 결정을 내리고 검증하고 싶어.

[상황] 지금 상품 검색을 Supabase에 LIKE '%검색어%'로 하고 있는데,
상품이 늘면서 느려지고 오타("아이푼")를 못 봐줘서 검색해도 안 나온다는 민원이 있어.
전문 검색 엔진 도입을 고민 중이야.

[해줘]
1) 먼저 코드부터 짜지 말고, 도입 타이밍부터 판단해줘:
   - 지금 데이터 양·검색 빈도를 봤을 때, PostgreSQL/Supabase 내장 전문 검색으로
     버틸 수 있는지 vs 외부 엔진(Algolia/Meilisearch)이 필요한지 기준으로 짚어줘.
2) 도입한다면 Algolia(호스팅)와 Meilisearch(오픈소스)를 내 상황 기준으로 비교해줘:
   - 운영 부담, 비용 구조, 데이터가 외부로 나가도 되는지(민감 데이터 여부), 한국어 처리.
   - 가격·한도 같은 시점성 수치는 단정하지 말고 "공식 문서 확인 권장"으로 표시해줘.
3) 고른 엔진으로 붙이는 절차를 단계로:
   - 색인에 보낼 필드 고르기(비밀 필드는 제외), 초기 색인 만들기,
     데이터가 바뀔 때 색인을 동기화하는 방법(언제·어디서 갱신되는지 명확히).
   - 오타교정(typo tolerance)과 관련도 랭킹(제목 가중치 등)을 켜는 설정도.
4) 보안: 검색 전용 키(프런트 공개 가능)와 관리자 키(서버 전용 비밀)를 명확히 구분해줘.
   관리자 키는 .env.example에 자리표시자로만 두고 .gitignore에 .env 넣는 것까지.
   프런트에는 절대 관리자 키를 두지 마.
5) 검색 결과를 화면에 그릴 때 사용자 검색어/결과는 textContent로 출력해줘(innerHTML 금지, XSS 방지).
6) 코드엔 '무엇'뿐 아니라 '왜 이렇게 했는지'를 한국어 주석으로 달아줘.
```

> 팁: 모델은 **최신·최강 Claude**(예: Opus 4.8 = `claude-opus-4-8`, 가벼운 작업엔 Haiku 4.5 = `claude-haiku-4-5`)를 기본으로 권장합니다. "도입할까 말까", "어느 엔진이 내 상황에 맞나" 같은 설계 판단은 상위 모델이 함정을 더 잘 짚습니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **`LIKE`를 기본값으로 주고 끝 — 확장성 경고를 안 함**: AI는 "검색 만들어줘"에 `LIKE '%검색어%'`를 주고 "데이터가 많아지면 느려지고 인덱스를 못 타며 오타·랭킹이 없다"는 한계를 먼저 말해 주지 않는 경향이 있습니다. **"이게 10만 건일 때도 괜찮아? 오타·랭킹은?"** 을 디렉터가 먼저 물어야 합니다.
- **색인 동기화 누락(stale index)** — 가장 흔한 사고: 초기 색인은 만들었는데 **데이터가 바뀔 때 색인을 갱신하는 코드를 빠뜨립니다.** 증상은 "글을 새로 썼는데 검색에 안 나옴", "삭제한 상품이 검색엔 아직 보임". AI가 "검색 붙였어요"라고 하면 **"데이터가 추가·수정·삭제될 때 색인은 어떻게·언제 갱신돼?"** 를 반드시 되물으세요.
- **관리자(admin) 키를 프런트에 노출**: 검색을 빨리 붙이려고 색인 수정까지 되는 **관리자 키를 브라우저 코드에 박는** 치명적 실수. 누구나 F12로 키를 꺼내 색인을 통째로 지울 수 있습니다. **프런트엔 검색 전용 키만, 관리자 키는 서버 환경변수에만.** ("anon 키는 공개 가능"과 헷갈리지 마세요 — 검색 전용 키만 공개 가능이고, 관리자 키는 service_role급 비밀입니다.)
- **민감 데이터를 통째로 색인에 올림**: 검색에 필요 없는 비밀번호 해시·내부 메모·개인정보까지 색인에 보내면, 외부 SaaS(Algolia)에 데이터가 그대로 나가고 검색 결과로 새어 나올 수 있습니다. **검색에 필요한 필드만, 비밀 필드는 제외.** 민감 데이터가 많으면 데이터를 내 서버에 둘 수 있는 **Meilisearch 자체 호스팅**을 검토하세요.
- **오타교정·랭킹이 기본으로 켜진 줄 착각**: 엔진에 따라 기본 설정만으로는 한국어 오타·랭킹·동의어가 약할 수 있습니다. **"오타교정(typo tolerance)·관련도 가중치(제목 우선 등)·한국어 토크나이저를 켰는지"** 를 확인해야 합니다.
- **과한 조기 도입(over-engineering)**: 글 50개짜리 사이트에 외부 검색 엔진·색인 파이프라인·추가 비용을 얹는 건 과합니다. **데이터·검색량이 작으면 DB 내장 전문 검색으로 충분**하고, 정말 느려지거나 오타·랭킹이 필요해질 때 도입하는 게 순서입니다.
- **자동완성·디바운스 누락으로 과금·부하 폭증**: 타이핑마다 검색을 날리면 글자 수만큼 요청이 갑니다. **디바운스(타이핑이 잠깐 멈추면 한 번만 호출)** 가 없으면 요청 수가 폭증해 비용·부하가 늘 수 있습니다.

**⑦ 검증하는 법**

1. **속도·관련도 눈으로 확인**: 검색창에 흔한 단어를 쳐 보고, 결과가 **즉시(체감상 0.x초)** 뜨는지, **가장 관련 높은 것이 맨 위**인지 보세요. 제목에 든 항목이 본문 구석에 든 것보다 위에 오면 랭킹이 일하는 것입니다.
2. **오타교정 테스트**: 일부러 한 글자 틀려서(`아이푼`, `노틉북`) 검색해 보세요. 그래도 맞는 결과가 나오면 오타교정이 켜진 것, 0건이면 꺼졌거나 `LIKE`인 것입니다.
3. **"추가·수정·삭제 → 검색 반영" 테스트(동기화 점검)**: 새 데이터를 추가하고 바로 검색해 보세요. 안 나오면 색인 동기화가 빠진 것입니다. 삭제한 항목이 계속 검색되면 삭제 동기화가 빠진 것입니다.
4. **키 노출 점검(보안)**: 브라우저 F12 → 소스/네트워크에서 검색 요청에 쓰이는 키가 **검색 전용 키**인지 확인하세요. **색인을 수정·삭제할 수 있는 관리자 키가 프런트에 보이면 즉시 사고**입니다. 깃 저장소에 키가 박혀 있지 않은지, `.env`가 `.gitignore`에 있는지도 확인하세요.
5. **민감 필드 누출 점검**: 검색 결과(F12 → Network 응답)에 비밀번호·내부 메모·개인정보 같은 **검색에 불필요한 필드가 딸려 오지 않는지** 확인하세요.
6. **XSS 점검**: 검색어에 `<script>alert(1)</script>` 를 넣어 보세요. 글자 그대로 보이면 안전(`textContent`), 알림창이 뜨면 `innerHTML`로 잘못 출력한 것입니다.
7. **AI에게 자기검증 시키기**: "이 검색 코드에서 (1)색인 동기화가 빠진 곳, (2)프런트에 노출된 관리자 키, (3)색인에 들어간 불필요·민감 필드, (4)오타교정·랭킹이 꺼진 곳, (5)디바운스 없는 검색 호출을 비판적으로 점검해줘"라고 별도 세션에서 다시 물어보세요.

!!! example "💡 예시로 이해하기"
    중고 책 거래 사이트를 만들었습니다. 처음엔 책이 200권뿐이라 `WHERE title LIKE '%검색어%'` 로도 잘 돌아갔습니다. 그런데 1년 뒤 책이 12만 권이 되자 검색창에 글자를 칠 때마다 빙글빙글 돌고, 손님이 `해리포터`를 `헤리포터`로 쳤더니 "결과 없음"이 떴습니다. 디렉터는 AI에게 묻습니다. "지금 DB 내장 검색으로 더 버틸 수 있어, 아니면 검색 엔진을 붙일 때야? 붙인다면 운영 부담 없는 Algolia랑 비용 아끼는 Meilisearch 중 내 상황엔 뭐가 맞아?" 비교 끝에 빨리·안정적으로 가려고 Algolia를 골랐습니다. 색인에는 **제목·저자·태그·가격만** 보내고(판매자 연락처 같은 민감 정보는 제외), 프런트 검색창엔 **검색 전용 키**만 두고 색인을 고치는 **관리자 키는 서버 환경변수에만** 숨겼습니다. 이제 `헤리포터`라고 쳐도 "혹시 해리포터?"하며 결과가 즉시 뜨고, 제목에 든 책이 본문에만 언급된 책보다 위에 옵니다. 마지막으로 디렉터는 함정 하나를 더 챙깁니다 — "새 책을 등록하면 검색에 바로 나와? 판 책을 지우면 검색에서도 사라져?"를 직접 테스트해 **색인 동기화**가 도는지 눈으로 확인합니다. 핵심은 한 문장입니다 — **원본은 DB에, 빠른 찾아보기 카드함(색인)은 검색 엔진에, 그리고 데이터가 바뀌면 카드도 같이 갱신된다.** 이게 지켜지는지가 검색을 옳게 붙인 증거입니다.
