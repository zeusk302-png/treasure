# 외부 서비스 연동 — 이메일·슬랙·시트·결제를 안전하게 잇기

**1) 한 줄 정의**

외부 서비스 연동은 이메일·슬랙·구글시트·결제 같은 바깥 도구를 n8n의 전용 노드와 '자격증명(credential)'으로 안전하게 연결하는 것이다.

**2) 왜 중요한가 (디렉터 관점)**

자동화의 가치는 대부분 "내 사이트 밖 도구와 엮일 때" 나온다. 핵심은 연결 자체가 아니라 **키를 어떻게 보관하느냐**다. 자격증명 기능은 키를 워크플로우 본문이 아니라 별도 금고에 저장해 한 번 등록하면 여러 워크플로우가 참조한다. 디렉터는 AI가 키를 평문으로 흘리지 않았는지, 권한을 과하게 주지 않았는지 검증해야 한다.

**3) 비유**

회사 출입카드다. 직원마다 비밀번호를 종이에 적어 돌리는 대신(평문 하드코딩), 중앙에서 카드(자격증명)를 발급하고 필요한 문에만 권한을 준다. 카드 한 장을 회수하면 모든 접근이 한 번에 끊긴다.

**4) 최소한 알 것**

- 자격증명은 **한 번 저장 → 여러 워크플로우가 참조**한다. 키를 노드마다 복붙하지 않는다.
- **최소 권한 원칙**: 메일만 보낼 거면 메일 읽기·삭제 권한까지 주지 않는다.
- 개발용 키와 운영용 키를 분리한다(섞으면 테스트가 실데이터를 건드린다).
- OAuth 연결 시 요청하는 권한 범위(scope)를 꼭 확인한다.

| 있는 것 | 한 줄 해설 | 판정 |
|---|---|---|
| 자격증명(credential) 저장소 | 키를 금고에 보관, 노드가 참조 | 🟢메인 |
| 전용 노드(Gmail·Slack 등) | 서비스별 검증된 연동 블록 | 🟢메인 |
| HTTP Request 노드로 직접 호출 | 전용 노드 없을 때만 | 🔵나중 |
| 노드에 키 평문 입력 | 절대 금지 | ⚪몰라도됨(=하지 말 것) |

**5) AI에게 이렇게 시켜라**

```text
n8n에서 Slack/이메일/구글시트를 연동하려 해.
(1) 키를 노드 본문에 직접 넣지 말고 자격증명(credential)으로 저장하는 방법
(2) 이 작업에 꼭 필요한 최소 권한(scope)만 무엇인지 — 과한 권한은 빼줘
(3) 개발용과 운영용 자격증명을 분리하는 구조
(4) 자격증명 하나를 여러 워크플로우가 재사용하는 방법
키를 평문으로 넣는 예시는 절대 주지 말고, 권한 체크리스트도 함께.
```

**6) 흔한 함정 · AI가 틀리는 것**

AI는 빠른 동작을 위해 키를 노드 필드에 평문으로 넣거나, "일단 다 되게" OAuth 권한 범위를 과하게 요청한다(최소 권한 위반). 또 개발 키와 운영 키를 같은 것으로 써서 테스트가 실데이터를 망가뜨리게 한다.

!!! warning
    워크플로우를 내보내기(export)하거나 공유할 때 자격증명이 함께 새지 않는지 확인하라. 키가 들어간 JSON을 그대로 공개 저장소에 올리는 것은 권4에서 다룬 키 노출 사고와 동일한 위험이다.

**7) 검증하는 법**

1. 자격증명 화면에서 "연결 테스트"를 눌러 인증이 통과하는지 확인한다.
2. 해당 키로 의도한 작업(메일 1통 발송)만 되고, 의도 밖 작업(메일 삭제)은 권한이 없어 막히는지 확인한다.
3. 워크플로우 JSON을 열어 키 문자열이 본문에 노출돼 있지 않은지 확인한다.

**8) 더 깊이**

- n8n Credentials 공식 문서 — 자격증명 저장·관리(1차 출처)
- 각 서비스(Slack·Google)의 OAuth scope 공식 문서 — 최소 권한 확인(1차 출처)
