# 트리거 1 — 웹훅(Webhook): '무슨 일이 생긴 순간' 깨어나는 자동화

**1) 한 줄 정의**

웹훅은 외부 서비스가 미리 약속된 내 URL로 데이터를 "밀어 보내면" 그 즉시 자동화가 깨어나는 트리거다.

**2) 왜 중요한가 (디렉터 관점)**

대부분의 실시간 연동(결제 완료, 새 가입, 폼 제출)은 웹훅으로 일어난다. 디렉터는 "내가 30초마다 확인하러 가는 것(폴링)"과 "일이 생기면 상대가 알려주는 것(웹훅)"의 차이를 알아야, AI가 만든 연동이 실시간으로 도는지 아니면 비효율적으로 계속 확인하는 구조인지 판별할 수 있다.

**3) 비유**

집 초인종이다. 내가 1분마다 문을 열어 손님이 왔나 확인(폴링)하는 대신, 손님이 초인종을 누르면(웹훅) 그제서야 나간다. 신호가 올 때만 움직이니 효율적이다.

**4) 최소한 알 것**

- 웹훅은 **받는 쪽이 URL을 만들어 상대에게 알려주는** 방식이다.
- 같은 신호가 두 번 올 수 있다(네트워크 재시도). 즉 **중복은 정상이다.**
- 테스트용 URL과 운영용 URL은 다르다. 혼동하면 "테스트는 되는데 실서비스는 안 됨"이 생긴다.
- 누가 보낸 신호인지 확인하는 **서명 검증**이 없으면 아무나 가짜 신호를 보낼 수 있다.

**5) AI에게 이렇게 시켜라**

```text
n8n Webhook 노드로 외부 서비스의 이벤트를 받으려 해.
다음을 반드시 포함해서 설계해줘:
(1) 같은 이벤트가 두 번 와도 한 번만 처리되게 하는 중복 방지(멱등성) 방법
(2) 보낸 쪽이 진짜인지 확인하는 서명 검증 방법
(3) 테스트 URL과 운영(Production) URL의 차이와 전환 시 주의점
"한 번만 호출된다"고 가정하지 말고, 중복·위조·실패를 전제로 짜줘.
```

**6) 흔한 함정 · AI가 틀리는 것**

AI는 웹훅이 "딱 한 번 호출되고 끝난다"고 가정해 중복 처리를 빠뜨린다. 그 결과 같은 결제가 두 번 기록되거나 같은 메일이 두 번 나간다. 또 테스트 URL을 운영에 그대로 남기거나, 서명 검증을 생략해 누구나 가짜 데이터를 밀어 넣을 수 있는 구조를 만든다.

!!! warning
    웹훅 URL은 사실상 "열린 문"이다. 서명 검증 없이 공개되면 외부에서 가짜 이벤트를 주입할 수 있다. 결제·인증 관련 웹훅은 반드시 서명을 검증하라.

**7) 검증하는 법**

1. 외부 서비스의 "테스트 이벤트 보내기" 기능으로 신호를 한 번 쏜다.
2. n8n 실행 기록에서 페이로드(들어온 데이터)가 찍혔는지 확인한다.
3. 같은 이벤트를 일부러 두 번 보내, 결과가 한 번만 생기는지(중복 방지 작동) 확인한다.
4. 잘못된 서명으로 보낸 요청이 거부되는지 확인한다.

**8) 더 깊이**

- n8n Webhook 노드 공식 문서 — 설정·테스트/운영 URL(1차 출처)
- 연동할 서비스의 웹훅 서명 검증 가이드(해당 서비스 공식 문서)
