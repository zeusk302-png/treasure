# 표 하나 너머 — 데이터 모델링과 관계의 기초

**1) 한 줄 정의**
데이터 모델링이란 **무엇을 어떤 표(테이블)로 나누고, 그 표들을 어떻게 연결할지**를 미리 설계하는 일이다.

**2) 왜 중요한가(디렉터 관점)**
데이터 구조는 집의 골조다. 골조를 잘못 세우면 나중에 벽지 하나 바꾸려다 집이 흔들린다. 모든 걸 한 표에 욱여넣으면, 사용자 이름 하나 바꿀 때 그 이름이 적힌 100군데를 전부 고쳐야 한다. 디렉터가 "표를 어떻게 나눌까"를 먼저 정하지 않으면, AI가 임시방편 구조를 만들고 그 위에 기능이 쌓여 되돌리기 어려워진다.

**3) 비유**
도서관이 책을 한 더미에 쌓지 않고 "책 목록"과 "대출 기록"을 따로 관리하는 것과 같다. 회원 정보는 회원 표에 한 번만 두고, 대출 기록은 "누가(회원번호) 어떤 책을" 식으로 번호로만 연결한다. 회원이 이사 가도 회원 표 한 곳만 고치면 된다.

**4) 최소한 알 것**

| 개념 | 한 줄 해설 |
|---|---|
| 테이블 | 같은 종류의 데이터 묶음(회원, 댓글) |
| 기본키(PK) | 각 행을 구별하는 고유 번호(예: user_id) |
| 외래키(FK) | 다른 표를 가리키는 연결고리(댓글의 user_id) |
| 1:N 관계 | 한 명의 회원이 여러 댓글을 가짐 |
| 정규화 | 같은 정보를 한 곳에만 두어 중복을 없앰 |

**5) AI에게 이렇게 시켜라**

```text
[댓글 + 진도체크] 기능에 필요한 데이터 구조를 설계해줘. 코드 말고 먼저 표로:
- 어떤 테이블이 필요한지, 각 테이블의 컬럼과 타입
- 기본키와 외래키, 그리고 테이블 간 관계(1:N 등)
- 같은 정보가 두 군데 중복되는 곳이 있으면 지적하고 나누는 안 제시
모든 표를 한 테이블에 합치는 안은 피하고, 왜 나눴는지 한 줄씩 설명해줘.
```

**6) 흔한 함정·AI가 틀리는 것**

!!! warning "God 테이블·외래키 누락"
    AI는 빠른 동작을 위해 모든 걸 한 테이블에 몰아넣는 'God 테이블'을 만들거나, 정보를 여러 곳에 중복으로 적어 두는(비정규화) 코드를 자주 준다. 또 테이블을 나눠도 외래키 연결을 빠뜨려, 나중에 "이 댓글 누가 썼지?"를 추적할 수 없게 만든다.

**7) 검증하는 법**

1. AI가 만든 구조에서 "같은 정보(예: 사용자 이름)가 두 표에 동시에 적혀 있는가?"를 본다. 있으면 중복이다.
2. 각 표마다 "이 행을 구별하는 고유 번호(PK)가 있는가?"를 확인한다.
3. 연결이 필요한 표끼리 외래키로 이어져 있는지, "이 댓글의 작성자를 어떻게 찾아?"라고 물어 확인한다.

**8) 더 깊이**

!!! tip
    설계가 끝나면 AI에게 ERD(개체-관계 다이어그램)를 글이나 그림으로 그려 달라고 해 한눈에 본다. 이 사이트는 users ↔ comments(user_id) 1:N 관계를 실제 스키마와 1:1로 대응시켜 공개한다.
