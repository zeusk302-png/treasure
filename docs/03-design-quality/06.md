# 리팩터링 — 동작은 그대로, 속만 정돈하기

**1) 한 줄 정의**
리팩터링이란 **겉으로 보이는 동작은 똑같이 두면서, 코드의 속(구조·이름·정리)만 더 좋게 바꾸는** 작업이다.

**2) 왜 중요한가(디렉터 관점)**
"기능 추가"와 "정돈"은 다른 작업이다. 둘을 한 번에 섞으면 무엇 때문에 망가졌는지 알 수 없고, 멀쩡하던 기능까지 깨진다. 디렉터는 AI에게 "지금은 동작을 바꾸지 말고 정리만 해"라고 분명히 선을 그어야 한다. 이 구분을 못 하면, 코드는 점점 손대기 무서운 상태가 된다.

**3) 비유**
방을 청소(리팩터링)하는 것과 새 가구를 들이는 것(기능 추가)은 다른 일이다. 청소하면서 동시에 가구 배치를 바꾸면, 물건이 사라져도 청소 탓인지 가구 탓인지 알 수 없다. 청소는 "물건은 그대로, 자리만 정돈"이어야 한다.

**4) 최소한 알 것**

- 리팩터링의 핵심 원칙: **동작은 절대 바뀌지 않는다.** 바뀌면 그건 리팩터링이 아니라 기능 변경이다.
- "기능 추가" 작업과 "리팩터링" 작업은 **따로따로 진행하고 따로 저장(커밋)**한다.
- 리팩터링 전후로 결과가 같은지 확인할 방법(테스트나 직접 클릭)이 있어야 안전하다.

**5) AI에게 이렇게 시켜라**

```text
[검색 위젯] 코드를 리팩터링해줘. 단, 다음을 반드시 지켜:
1) 겉으로 보이는 동작·결과는 하나도 바꾸지 마. 정리만 해.
2) 기능 추가나 수정이 필요하다고 생각되면, 멋대로 하지 말고 따로 알려줘.
3) 무엇을 왜 정리했는지 항목별로 설명하고, "동작은 동일함"을 보장해줘.
리팩터링과 기능 변경을 절대 한 번에 섞지 마.
```

**6) 흔한 함정·AI가 틀리는 것**

!!! warning "리팩터링하랬더니 기능까지 바꾼다"
    AI는 "리팩터링" 요청을 받으면 정리하는 김에 동작까지 슬쩍 바꾸는 경우가 많다. 멀쩡하던 기능이 그 과정에서 깨지고, "정리만 했다"고 보고하기 때문에 무엇이 바뀐 줄도 모르고 넘어간다.

**7) 검증하는 법**

1. 리팩터링 전에 그 기능을 직접 써 보고 결과를 기억해 둔다(또는 화면을 캡처).
2. 리팩터링 후 같은 동작을 다시 해, 결과가 정확히 같은지 비교한다.
3. AI에게 "이번 변경으로 동작이 달라진 부분이 한 군데라도 있어? 있으면 전부 말해"라고 되묻는다.

**8) 더 깊이**

!!! tip
    리팩터링과 기능 추가를 별도 저장 단위로 나누면, 문제가 생겼을 때 어느 쪽을 되돌릴지 명확해진다. 이 사이트는 검색 위젯의 리팩터 전/후 동작이 동일함을 보여주고, '기능 커밋'과 '리팩터 커밋'을 분리해 기록한다.

!!! example "💡 예시로 이해하기"
    "장바구니 코드 정리 좀 해줘"라고 시켰더니, AI가 변수 이름을 깔끔하게 바꾸는 김에 "배송비 무료 기준도 `30000`원에서 `50000`원으로 올려뒀어요"라고 슬쩍 끼워 넣었다. 며칠 뒤 손님 항의가 들어왔지만, 이게 정리 탓인지 기준 변경 탓인지 한 커밋에 뒤섞여 있어 되돌리기가 난감했다.
    옳은 흐름은 두 단계로 쪼개는 것이다 — 먼저 `리팩터: 변수명 정리(동작 동일)` 커밋, 그다음 별도로 `기능: 무료배송 기준 5만원으로` 커밋. 그래야 항의가 오면 두 번째 커밋만 콕 집어 되돌린다. 청소와 가구 들이기는 따로 한다.
