# 인덱스 — 왜 빨라지고, 언제 안 듣나

**① 한 줄 정의**
인덱스(index)는 **자주 찾는 열에 미리 만들어 두는 '정렬된 찾아보기(색인)'**로, 데이터베이스가 모든 행을 처음부터 끝까지 훑지 않고 **곧장 원하는 행으로 점프**하게 해 검색을 극적으로 빠르게 만듭니다.

**② 왜 중요한가 (디렉터 관점)**
인덱스는 **디렉터가 상용에서 가장 먼저 마주치는 성능의 핵심**입니다. 회원이 10명일 때는 아무도 못 느끼지만, 10만 명이 되면 '이메일로 로그인'이 갑자기 느려집니다. 무서운 점은 **개발 단계(데이터가 적을 때)에는 멀쩡하다가, 사용자가 늘어난 뒤 실서비스에서 터진다**는 것입니다. 이때 "사이트가 느려요"라고만 던지면 AI는 멀쩡한 코드를 헤집어 새 버그를 만들기 쉽습니다. 하지만 디렉터가 "그 열에 인덱스 걸었어? EXPLAIN으로 전체 훑기 하는지 봐줘"라고 물을 수 있으면, 원인을 정확히 짚고 진짜 해법(코드 수정이 아니라 인덱스 한 줄)으로 데려갈 수 있습니다.

또 하나, 인덱스는 **공짜가 아닙니다**. "느리니까 모든 열에 인덱스 다 걸어"는 틀린 지시입니다. 인덱스는 저장 공간을 먹고, 데이터를 넣고 고칠 때마다 인덱스도 같이 갱신해야 해서 **쓰기가 느려집니다**. '어디에 걸지'와 '어디에 안 걸지'를 함께 아는 것이 디렉터의 균형 감각입니다.

**③ 비유**
두꺼운 전공 책에서 '광합성'이라는 단어가 어디 나오는지 찾는다고 해봅시다. 색인이 없으면 1쪽부터 마지막 쪽까지 한 장씩 넘겨야 합니다(=전체 훑기, Seq Scan). 그런데 책 맨 뒤에 **'찾아보기'(가나다순 색인)**가 있으면, '광합성 → 142, 287쪽'처럼 단어에서 쪽수로 **바로 점프**합니다. 인덱스가 바로 이 찾아보기입니다.

단, 공짜가 아니라는 것도 이 비유로 보입니다. 찾아보기를 만들려면 **추가 종이(저장 공간)**가 들고, 책 내용을 한 줄이라도 고쳐 쪽 번호가 밀리면 **찾아보기도 다시 손봐야**(쓰기 비용) 합니다. 그래서 좋은 책은 '자주 찾는 핵심 용어'만 색인에 넣지, 책에 나오는 모든 단어를 색인으로 만들지는 않습니다. 인덱스도 똑같습니다.

**④ 최소한 알 것**

| 개념 | 쉬운 설명 | 디렉터가 기억할 것 |
|---|---|---|
| 인덱스(index) | 자주 찾는 열의 '찾아보기' | 검색을 빠르게, 쓰기를 약간 느리게 |
| Seq Scan(전체 훑기) | 1행부터 끝까지 다 봄 | 데이터 많은데 이게 나오면 위험 신호 |
| Index Scan(인덱스 점프) | 색인 타고 바로 점프 | 이게 나오면 인덱스가 '듣고' 있는 것 |
| `EXPLAIN` | "이 쿼리 어떻게 실행할지" 계획서 | 추측 말고 이걸로 확인 |
| `EXPLAIN ANALYZE` | 계획 + 실제로 재본 시간 | 진짜 느린 곳을 숫자로 봄 |
| 복합 인덱스 | 두 개 이상 열을 묶은 색인 | 열 '순서'가 중요(아래 함정 참고) |
| 쓰기 오버헤드 | 입력·수정 때 인덱스도 갱신 | 인덱스가 많을수록 쓰기 느려짐 |

**어떤 열에 인덱스를 걸까 (판단 기준)**

- 🟢 **자주 `WHERE`로 거르는 열** — 로그인할 때의 `email`, 글을 회원별로 볼 때의 `user_id`
- 🟢 **자주 `ORDER BY`로 정렬하는 열** — 글 목록의 `created_at`(작성일순)
- 🟢 **`JOIN`으로 연결하는 열(외래키)** — `orders.user_id` 같은 연결 고리
- 🟡 **자주 검색하지만 종류가 적은 열** — `status`('대기/완료' 2종)는 인덱스 효과가 작을 수 있음(상황 보고 결정)
- ⚪ **거의 검색·정렬 안 하는 열** — 인덱스를 걸어봤자 헛수고, 쓰기만 느려짐
- ⚪ **`UPDATE`가 매우 잦은 열** — 인덱스 갱신 비용이 검색 이득보다 클 수 있음

> 참고: 기본키(PK)와 `UNIQUE` 제약이 걸린 열에는 **대개 인덱스가 자동으로 생깁니다.** "로그인 이메일이 느려요"의 의외의 해법이 "이메일을 `UNIQUE`로 만들면 인덱스가 따라온다"인 경우도 많습니다(DB마다 다르니 확인 권장).

**인덱스가 '안 듣는' 대표 상황 (Seq Scan으로 떨어짐)**

- 거른 열을 **가공**하면 색인을 못 탐 — `WHERE lower(email) = ...`, `WHERE date(created_at) = ...`처럼 함수로 감싸면 원래 색인을 못 씀
- **앞이 와일드카드인 검색** — `LIKE '%광합성%'`(앞에 `%`)은 색인을 못 탐. `LIKE '광합성%'`(뒤에만 `%`)은 탈 수 있음
- **표가 너무 작을 때** — DB가 "어차피 다 봐도 빠르네" 하고 일부러 전체 훑기를 고름(정상)
- **거의 다 걸리는 조건** — 조건에 90%가 해당하면 색인 점프보다 통째로 읽는 게 빨라서 색인을 버림
- **복합 인덱스인데 첫 열을 안 씀** — `(user_id, created_at)` 인덱스인데 `created_at`만으로 검색하면 못 탐

**⑤ AI에게 이렇게 시켜라**

```text
[상황] Supabase(Postgres)를 쓰는 회원제 사이트야. 회원이 늘면서
'이메일로 로그인' 조회와 '특정 회원의 글 목록(작성일 내림차순)'이 느려졌어.

[부탁] 코드부터 고치지 말고 아래 순서로 진단·처방해줘.
1) 어떤 검색이 자주 일어나는지 먼저 정리해줘
   (로그인=users.email 조회, 글목록=posts.user_id로 거른 뒤 created_at 정렬).
2) 각 쿼리에 EXPLAIN ANALYZE를 어떻게 붙여 실행하고,
   결과에서 'Seq Scan'과 'Index Scan' 중 무엇이 보이면
   인덱스를 타는지/못 타는지 한국어로 설명해줘.
3) 인덱스를 추가한다면 어떤 열에 거는 게 맞는지,
   복합 인덱스라면 열 순서를 왜 그렇게 잡는지 이유와 함께
   CREATE INDEX 문을 줘. 주석으로 '왜 이 열인지'도 달아줘.
4) 인덱스를 걸면 무엇이 빨라지고 무엇이(쓰기·용량) 느려지는지
   비용도 같이 알려줘. "모든 열에 다 걸자"는 하지 마.
5) WHERE에서 lower()나 date() 같은 함수로 열을 감싸서
   인덱스를 못 타게 만드는 부분이 있으면 짚어줘.

[제약] anon 키는 공개돼도 되지만 보호는 RLS로 한다는 전제는 유지해줘.
service_role 키가 들어가는 쿼리는 서버에서만 돈다고 가정해.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **느린데 인덱스를 떠올리지 못함.** AI는 "느려요"를 들으면 코드(반복문·정렬 로직)부터 만지작거리고, 진짜 원인인 '인덱스 없는 검색'을 마지막에야 의심하는 경향이 있습니다.
- **반대로 모든 열에 덕지덕지.** "성능 좋게 해줘"라고 하면 거의 안 찾는 열까지 인덱스를 걸어, **쓰기(입력·수정)를 오히려 느리게** 만들고 용량을 키웁니다. 쓰기 비용·용량 비용은 거의 먼저 언급하지 않습니다.
- **함수로 감싸 인덱스를 죽임.** `WHERE lower(email) = $1`처럼 짜놓고 `email`에만 인덱스를 걸어, 정작 그 인덱스를 못 타게 만듭니다(이럴 땐 표현식 인덱스가 필요).
- **복합 인덱스 열 순서를 거꾸로.** `(created_at, user_id)`로 만들어 놓고 `user_id`로 거르는 쿼리가 색인을 제대로 못 쓰는 경우. **자주 등호(`=`)로 거르는 열을 앞에** 두는 게 일반 원칙입니다.
- **개발 환경에서 빨라서 '해결됨'으로 착각.** 데이터가 적으면 Seq Scan도 빠릅니다. **데이터를 많이 넣은 상태에서 다시 측정**하지 않으면 함정에 그대로 빠집니다.
- **N+1을 인덱스로 착각.** 목록 100개에 쿼리를 101번 날리는 'N+1 문제'는 인덱스로 안 풀립니다(조인·일괄조회로 풉니다). "인덱스 추가했는데도 안 빨라져요"의 진짜 범인일 때가 많습니다.

**⑦ 검증하는 법**

추측이 아니라 **측정**으로 확인합니다.

1. **느린 쿼리 앞에 `EXPLAIN ANALYZE`를 붙여** 실행합니다. (Supabase는 대시보드의 SQL Editor 또는 쿼리 성능 도구에서 가능 — 메뉴 위치는 버전마다 다르니 확인 권장.)
2. 결과에서 **`Seq Scan`**(전체 훑기)인지 **`Index Scan`/`Index Only Scan`**(색인 점프)인지 봅니다. 데이터가 많은데 `Seq Scan`이면 인덱스 추가 후보입니다.
3. **인덱스를 추가한 뒤 같은 쿼리를 다시 `EXPLAIN ANALYZE`** 해서, `Seq Scan`이 `Index Scan`으로 바뀌고 실행 시간(`actual time`)이 줄었는지 **숫자로 비교**합니다.
4. **꼭 데이터를 충분히 넣은 상태에서** 잽니다(예: 더미 회원 수만 건). 적은 데이터로는 차이가 안 보입니다.
5. 인덱스를 건 뒤 **입력·수정이 너무 느려지지 않았는지**도 확인합니다(쓰기 비용 점검). 빨라진 검색만 보고 만족하면 반쪽짜리입니다.

!!! example "💡 예시로 이해하기"
    중고거래 앱을 만들었습니다. 출시 첫 주, 회원 30명일 때는 로그인이 눈 깜짝할 새 됩니다. 석 달 뒤 회원 8만 명, 갑자기 로그인 화면에서 "빙글빙글"이 3초씩 돕니다. 디렉터가 한 일은 코드를 안 건드린 것입니다. 대신 로그인 쿼리(`SELECT * FROM users WHERE email = $1`) 앞에 `EXPLAIN ANALYZE`를 붙여 돌렸더니 **`Seq Scan on users`**, 실행 시간 2,900ms가 찍혔습니다. 8만 줄을 매번 처음부터 다 훑고 있던 것입니다. `CREATE INDEX idx_users_email ON users(email);` 한 줄을 추가하고 같은 쿼리를 다시 재니 **`Index Scan`**, 1.2ms. 약 2,400배 빨라졌습니다. 코드 한 줄도 안 고치고요. 다만 여기서 멈추지 않고, 회원가입(쓰기) 속도가 눈에 띄게 느려지지 않았는지도 확인했습니다 — 이메일은 어차피 가입 시 한 번만 쓰고 로그인 때마다 검색하니, 검색 이득이 쓰기 비용을 압도하는 '인덱스 걸기 딱 좋은 자리'였습니다.
