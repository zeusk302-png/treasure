# 캐시·읽기복제·스케일 — 사용자가 늘면

**① 한 줄 정의**
사용자가 늘어 데이터베이스(DB)가 비명을 지를 때, **자주 쓰는 답을 가까이 저장해 두고(캐시), 읽기 일을 사본에게 나눠 주고(읽기 복제본), 연결을 미리 만들어 돌려쓰고(커넥션 풀), 같은 질문을 반복하지 않게(N+1 제거)** DB의 부하를 더는 네 가지 기술입니다.

**② 왜 중요한가 (디렉터 관점)**
혼자 쓸 땐 멀쩡하던 사이트가 사용자가 몰리는 순간 느려지거나 멈추는 일은, 비전공 디렉터가 상용에서 가장 자주 만나는 사고입니다. 그리고 그 병목은 거의 항상 **가장 느린 한 곳, 즉 DB**에서 먼저 터집니다. 디렉터가 직접 캐시 서버를 깔거나 복제본을 운영할 필요는 없습니다. 하지만 "느려요"라는 한 덩어리 불만을 받았을 때, **"이건 같은 질문을 반복해서 그런가(N+1)? 자주 쓰는 답을 캐싱하면 되나? 읽기가 너무 많아 복제본이 필요한가? 아니면 연결을 너무 자주 새로 맺어서인가(커넥션 풀)?"** 로 원인을 네 갈래로 쪼갤 수 있어야 합니다. 그래야 AI에게 "느린 거 고쳐줘"가 아니라 "이 목록 화면에서 N+1이 있는지부터 봐줘"처럼 **정확히 지시**할 수 있습니다. 더 중요한 건 멈출 카드를 아는 것입니다 — AI는 "확장하려면 샤딩하세요" 같은 과한 처방을 곧잘 내놓는데, 대부분의 비전공자 프로젝트는 **캐시 한 줄과 N+1 제거만으로 충분**합니다. 무엇이 가성비 좋은 첫 카드인지 아는 것이 디렉터의 무기입니다.

**③ 비유**
바쁜 식당으로 생각해 봅시다. 주방(DB)은 하나뿐인데 주문(요청)이 밀려듭니다.

- **캐시**는 인기 메뉴를 주문마다 처음부터 만들지 않고 미리 몇 인분 만들어 **보온대(가까운 빠른 저장소)**에 올려 두는 것입니다. 손님이 시키면 보온대에서 바로 내주니 빠릅니다. 단, 보온대 음식은 시간이 지나면 식으니(=오래된 데이터) "언제 새로 만들지"가 핵심 고민입니다.
- **읽기 복제본**은 "메뉴판 보여 주세요"(읽기) 같은 요청만 처리하는 **안내 데스크 직원을 여럿 두는 것**입니다. 주문을 실제로 조리(쓰기)하는 주방은 하나로 두되, 단순 조회는 여러 사본이 나눠 답합니다.
- **커넥션 풀**은 손님이 올 때마다 전화선을 새로 까는 대신, **미리 깔아 둔 전화선 몇 개를 돌려 쓰는 것**입니다. 연결을 맺고 끊는 일 자체가 의외로 비싸거든요.
- **N+1 문제**는 라면 100그릇을 시킨 손님에게 면을 한 번에 가져오지 않고 **그릇마다 주방까지 101번을 왕복**하는 어리석은 점원입니다. 한 번에 받아 오면(일괄 조회/조인) 끝날 일을 쪼개서 주방을 녹초로 만듭니다.

**④ 최소한 알 것**

| 기술 | 무엇을 더는가 | 한 줄 핵심 | 디렉터 판단 기준 |
|---|---|---|---|
| 캐시(Redis 등) | DB·계산 부하 | 한 번 만든 답을 가까이 저장해 재사용 | "이 데이터, 자주 바뀌나? 안 바뀌면 캐싱" |
| 읽기 복제본(read replica) | 읽기 부하 | 쓰기는 원본, 읽기는 사본 여러 개가 나눠 답함 | "읽기가 쓰기보다 압도적으로 많은가?" |
| 커넥션 풀 | 연결 생성 비용 | 연결을 미리 만들어 두고 돌려 씀 | "서버리스인가? 그럼 풀러(pooler) 필수" |
| N+1 제거 | 쿼리 횟수 | 반복문 안 개별 조회를 일괄/조인 한 번으로 | "목록 화면이 항목 수만큼 느려지나?" |

- **캐시의 진짜 난제는 '저장'이 아니라 '무효화'**입니다. 컴퓨터과학의 두 난제 중 하나가 "캐시를 언제 버리고 새로 만들지"라는 말이 있을 정도입니다. 데이터가 바뀌었는데 옛 캐시를 계속 보여 주는 것(stale data, 오래된 데이터)이 가장 흔한 버그입니다.
- **TTL(Time To Live)** = 캐시를 몇 초/몇 분 살려 둘지. 가격·재고처럼 틀리면 안 되는 데이터는 짧게(또는 캐시 안 함), 소개글·공지처럼 잘 안 바뀌는 건 길게.
- **읽기 복제본엔 '복제 지연(replication lag)'**이 있습니다. 원본에 막 쓴 데이터가 사본에 도달하기까지 짧은 틈이 있어, "방금 쓴 글이 새로고침하면 안 보이는" 현상이 생길 수 있습니다.
- **Redis**(인메모리 키-값 저장소)는 캐시의 대표 도구이자 세션 저장·큐·실시간 순위표에도 씁니다. RAM에 두기 때문에 빠르지만, 끄면 날아갈 수 있는 성격(설정에 따라 다름)이라 **'원본'이 아니라 '빠른 사본'**으로 다루는 게 안전합니다.
- **Supabase/Postgres 환경**: 읽기 복제본·커넥션 풀러(pooler)는 플랫폼이 제공하는 기능을 켜는 식이 많습니다(요금제·제공 여부는 **공식 문서로 확인 권장**). Vercel 같은 서버리스에서 Postgres에 붙을 땐 **연결이 폭증하기 쉬워 커넥션 풀러를 거치는 것이 거의 필수**입니다.

**⑤ AI에게 이렇게 시켜라**

```text
역할: 너는 성능을 진단하는 백엔드 엔지니어다.
상황: 우리는 Supabase(Postgres) + Next.js를 쓰고, 게시판 목록 화면이
사용자가 늘면서 느려졌다. 데이터는 게시글 100개, 각 글에 작성자·댓글수가 붙는다.

작업: 코드를 바로 고치지 말고, 아래 순서로 '진단'부터 해줘.
1) 이 화면에 N+1 쿼리(목록을 돌며 글마다 작성자·댓글을 따로 조회)가
   있는지 먼저 확인하고, 있으면 'JOIN 또는 일괄 조회 한 번'으로 바꾸는 방법.
2) 그래도 느리면 무엇을 캐시할 수 있는지: 어떤 데이터가 '자주 안 바뀌어'
   캐시 후보인지, 각 데이터의 적절한 TTL(몇 초/몇 분)과,
   글이 수정/삭제되면 캐시를 어떻게 무효화할지까지 함께 제안해줘.
3) Supabase에 서버리스에서 붙을 때 커넥션 풀러를 써야 하는지,
   읽기 복제본이 필요한 규모인지(읽기:쓰기 비율 기준)도 알려줘.

제약: anon 키는 공개돼도 RLS로 보호되니 비밀이 아니다 — 비밀로 취급해
       엉뚱하게 막지 마. 캐시에 '사용자별 개인 데이터'를 공용 캐시로
       저장해 남에게 보이는 사고가 나지 않도록 주의해줘.
출력: 각 제안마다 '왜 그렇게 했는지' 이유를 한 줄씩 붙여줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **N+1을 먼저 의심하지 않음.** 개발 환경엔 데이터가 적어 빨라서 문제가 안 보입니다. AI는 "인덱스를 추가하세요"로 직행하지만, 인덱스를 아무리 걸어도 **쿼리를 101번 던지면 느립니다.** "느린데 인덱스로도 안 빨라진다"의 진짜 원인이 N+1인 경우가 많습니다.
- **캐시 무효화를 빠뜨림.** AI는 캐시를 켜는 코드는 쉽게 주지만 "데이터가 바뀌면 캐시를 어떻게 새로고침할지"를 자주 누락합니다. 그 결과 "수정했는데 사이트엔 옛날 내용"이라는 전형적 버그가 납니다.
- **개인 데이터를 공용 캐시에 넣음.** "내 주문 내역"처럼 사람마다 다른 데이터를 공용 캐시로 저장하면 **남의 정보가 다른 사람에게 보이는** 보안 사고가 됩니다. 캐시 대상은 '공개·공통' 데이터인지 반드시 확인.
- **읽기 복제본을 만능으로 권함.** 복제본은 '읽기'만 분산합니다. 쓰기가 병목이거나 복제 지연을 감당 못 하는 화면(방금 쓴 걸 바로 보여 줘야 하는)엔 부적합한데 AI가 구분 없이 권하기도 합니다.
- **서버리스의 연결 폭증을 모름.** "DB에 그냥 connect 하세요" 식 코드를 주는데, 서버리스에선 함수가 동시에 수백 개 떠 연결이 폭증해 DB가 "연결이 너무 많다"며 거부합니다. **커넥션 풀러 경유**가 핵심인데 자주 빠뜨립니다.
- **anon 키를 비밀 취급해 캐시·복제 설정을 망침.** anon 키는 공개돼도 RLS로 보호되는 값입니다. 이를 service_role(서버 전용 비밀)과 혼동하면 엉뚱한 곳을 막아 기능이 깨집니다.

**⑦ 검증하는 법**

1. **데이터를 많이 넣고 다시 재 보기.** 개발용 데이터 10개가 아니라 **수천 개를 넣은 상태**에서 화면을 열어 보세요. 항목 수에 비례해 느려지면 N+1 신호입니다.
2. **F12 → Network 탭**으로 화면 하나를 여는 데 요청이 몇 개 나가는지 보세요. 목록 항목 수만큼 비슷한 요청이 줄줄이 찍히면 N+1입니다(한 번으로 줄어야 정상).
3. **Supabase 대시보드의 쿼리 성능/로그**에서 같은 쿼리가 짧은 시간에 수십·수백 번 반복되는지 확인합니다. AI에게 `EXPLAIN ANALYZE` 결과를 붙여 "전체 훑기(Seq Scan)인지, 호출 횟수가 과한지" 해석을 시켜도 됩니다.
4. **캐시 검증**: 데이터를 바꾼 뒤 화면 반영에 시간이 걸리면 캐시가 도는 증거입니다. 반대로 "분명 수정했는데 옛날 게 보인다"면 무효화가 빠진 것 — TTL과 무효화 로직을 점검하세요.
5. **부하 그래프**: Supabase/Vercel 대시보드에서 사용자가 몰리는 시간대에 **응답 시간(latency)과 DB 요청 수**가 치솟는지 봅니다. 캐시/N+1 수정 후 같은 그래프가 낮아졌는지 비교하면 효과를 눈으로 확인할 수 있습니다.

!!! example "💡 예시로 이해하기"
    동네 맛집 정보를 모은 사이트를 만들었다고 합시다. 처음엔 친구 몇 명만 써서 쌩쌩했는데, 지역 카페에 소문이 나 하루 만에 방문자가 수백 명으로 늘자 메인 화면이 5초씩 걸리기 시작합니다. 디렉터는 "느려요"를 통째로 던지는 대신 네 갈래로 쪼갭니다. F12 Network를 열어 보니 가게 목록 30개를 띄우는 데 요청이 **31개**나 나갑니다 — 목록 한 번 + 가게마다 평점 따로 한 번씩. **N+1입니다.** AI에게 "평점을 일괄 조회 한 번으로 합쳐 줘"라고 시키니 요청이 2개로 줄고 화면이 1초로 빨라집니다. 그래도 메인의 '오늘의 추천 가게'는 모두에게 똑같고 하루에 한 번만 바뀌므로, **TTL 10분짜리 캐시**를 걸어 DB를 아예 거치지 않게 합니다. 단, "내가 찜한 가게" 목록은 사람마다 다르니 공용 캐시에 넣지 않습니다(넣었다면 남의 찜이 내게 보였을 겁니다). 마지막으로, 방문자가 거의 다 '구경(읽기)'만 하고 글은 가끔 올라오므로 — 즉 읽기가 쓰기를 압도하므로 — 더 커지면 읽기 복제본이 답이 될 거라고 메모해 둡니다. "느려요" 한 마디가 `N+1 31→2 + 추천목록 10분 캐시`라는 구체적 처방으로 바뀌는 순간, 서버를 한 푼도 더 늘리지 않고 문제가 풀립니다.
