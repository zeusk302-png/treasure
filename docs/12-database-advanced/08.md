# Supabase/Postgres 심화 — RLS·정책·함수·실시간

**① 한 줄 정의**
Supabase는 Postgres 데이터베이스에 **로그인·API·실시간**을 얹은 도구이고, 그 핵심 안전장치가 **RLS(Row Level Security, 행 수준 보안)** — "이 줄(행)은 *누가* 읽고 쓸 수 있는가"를 **DB 안에서** 강제해 '내 데이터만 보이게' 만드는 규칙입니다.

**② 왜 중요한가 (디렉터 관점)**
바이브코딩으로 만든 앱에서 **가장 자주, 가장 크게 터지는 사고**가 바로 RLS를 안 켠 것입니다. 화면은 멀쩡합니다. 로그인도 되고, 내 글도 잘 보입니다. 그런데 뒤에서는 **아무나 F12를 열어 남의 글·회원 명단·전화번호·결제 내역을 통째로 긁어갈 수 있는** 상태일 수 있습니다. AI는 "빨리 동작하게" 만드는 데 최적화돼 있어서, 데모를 띄우려고 RLS를 *끄거나*, 아예 *안 켜거나*, "나중에 켜자"며 미루는 코드를 자주 내놓습니다.

디렉터가 코드를 한 줄도 못 짜도 괜찮습니다. 하지만 **"모든 테이블에 RLS가 켜져 있나? 정책(policy)을 보여줘"** 한 문장을 던지고, 돌아온 답을 읽고 판별할 줄 알아야 합니다. 이것은 코딩 실력이 아니라 **안전을 묻는 습관**입니다. "예쁘게 되는 것"과 "안전하게 되는 것"은 전혀 다른 일이고, 디렉터의 일은 후자를 지키는 것입니다.

**③ 비유**
RLS는 **개인 사물함이 줄지어 있는 탈의실**과 같습니다. 탈의실(테이블) 자체는 누구나 들어옵니다. 하지만 사물함 하나하나(행)에는 **각자의 열쇠(로그인한 본인)**가 있어서, 내 열쇠로는 *내 사물함만* 열립니다. RLS를 **안 켜면** 어떻게 될까요? 사물함에 문이 아예 없는 상태 — 누구든 손 뻗어 남의 가방을 뒤질 수 있습니다.

또 다른 비유로, anon 키와 service_role 키의 차이는 **출입증 vs 마스터키**입니다. anon 키는 건물 1층 로비까지 들여보내 주는 **공개 출입증**입니다(브라우저에 그대로 나가도 됩니다 — 어차피 RLS라는 사물함 자물쇠가 막아줍니다). 반면 service_role 키는 **모든 사물함을 다 여는 관리인 마스터키**라서, 이게 새 나가면 RLS고 뭐고 전부 무력화됩니다. 그래서 마스터키는 절대 손님 손(브라우저·GitHub)에 쥐여주지 않고 **서버 금고(환경변수)에만** 둡니다.

**④ 최소한 알 것**

| 개념 | 한 줄 설명 | 디렉터가 점검할 것 |
|---|---|---|
| RLS (행 수준 보안) | "이 행은 누가 읽고/쓰나"를 DB가 직접 강제 | **모든 테이블에 켜져 있는가** |
| 정책 (policy) | RLS 안에서 동작하는 구체 규칙(읽기/생성/수정/삭제별로) | 너무 활짝 열려 있지 않은가 |
| anon 키 | 공개 가능한 출입증. 브라우저에 나가도 됨 | (공개돼도 OK — RLS가 막음) |
| service_role 키 | 모든 RLS를 무시하는 마스터키 | **서버·환경변수에만**, GitHub 절대 금지 |
| DB 함수 (function) | DB 안에 저장해 둔 작은 계산·로직 | 복잡한 권한 검사·집계에 사용 |
| 트리거 (trigger) | "이 일이 생기면 자동으로 저걸 해라" | 가입 시 프로필 자동 생성 등 |
| 실시간 (Realtime) | DB가 바뀌면 화면이 자동 갱신(새로고침 없이) | 채팅·알림·라이브 점수판 |

정책을 읽을 때 핵심 키워드 두 가지만 알면 됩니다.

- **`USING`** — *읽기/수정/삭제* 시 "이 행을 건드려도 되나?"를 판정하는 조건.
- **`WITH CHECK`** — *생성/수정* 시 "이런 값으로 새로 넣어도 되나?"를 판정하는 조건.
- 위험 신호: `USING (true)`는 "조건 없이 전부 허용" — 누구나 다 본다는 뜻이라 공개 데이터가 아니면 사고입니다.
- 안전 패턴: `USING (auth.uid() = user_id)` — "로그인한 본인의 행만" 이라는 뜻(`auth.uid()`는 현재 로그인 사용자의 ID).

작업 우선순위(길라잡이):

- 🟢 **메인**: 모든 테이블에 RLS 켜기 + '읽기는 정해진 대상만, 쓰기는 본인/관리자만' 정책.
- 🟡 **대안**: 공개 게시물처럼 정말 모두에게 열 데이터는 읽기만 `USING (is_published = true)`로 한정 공개.
- 🔵 **나중에**: 실시간 구독, DB 함수로 집계 최적화.
- ⚪ **몰라도 됨**: 정책 SQL 문법을 손으로 외우는 것(AI에게 시키고 *읽고 판별*하면 됨).

**⑤ AI에게 이렇게 시켜라**

```text
Supabase + Next.js로 회원제 메모 앱을 만들고 있어. memos 테이블(id, user_id,
title, content, is_public, created_at)에 대해, 비전공자도 읽고 검증할 수 있게
RLS 정책을 만들어줘. 규칙은 이렇게 해줘:

1) 모든 테이블에 RLS를 반드시 켜라(enable).
2) 읽기: 본인(auth.uid() = user_id)의 메모, 그리고 is_public = true 인 메모는 누구나.
3) 생성: 로그인한 사용자만, 단 user_id 칸은 반드시 본인(auth.uid())이어야 함
   (남의 명의로 못 쓰게 WITH CHECK 사용).
4) 수정/삭제: 본인 메모만.

그리고 각 정책이 '무엇을 막는지' 한국어 주석으로 한 줄씩 달아줘.
마지막에, anon 키와 service_role 키 중 무엇을 브라우저에 두고 무엇을 서버에만
둬야 하는지, 왜 그런지 비전공자에게 설명하는 문단을 붙여줘.
service_role 키는 절대 프론트엔드 코드나 .env의 NEXT_PUBLIC_ 변수에 넣지 마.
```

추가로 검증을 시키는 프롬프트(디렉터의 진짜 무기):

```text
방금 만든 Supabase 프로젝트의 모든 테이블에 대해 점검표를 만들어줘.
각 테이블마다: RLS가 켜져 있는가(Y/N), 어떤 정책이 걸려 있는가,
USING (true) 처럼 전부 열린 위험한 정책이 있는가, service_role 키가
혹시 프론트 코드나 NEXT_PUBLIC_ 환경변수에 들어가 있지 않은가를
표로 정리하고, 위험한 항목은 빨간 표시와 함께 고칠 SQL을 제안해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **"anon 키는 비밀이니 숨기세요"** — *틀린 설명입니다.* anon 키는 공개돼도 되는 출입증입니다. 진짜 숨겨야 하는 건 service_role 키입니다. AI가 anon 키를 비밀처럼 다루라고 하면 개념을 잘못 알고 있는 신호이니, 같이 나온 RLS 설명도 의심하세요.
- **RLS를 안 켜거나 끔** — "데모가 안 떠서" RLS를 잠깐 끄고 그대로 두는 일이 비일비재합니다. 화면은 멀쩡해도 데이터는 발가벗겨진 상태입니다.
- **`USING (true)`로 활짝 열기** — "일단 되게" 하려고 모든 행을 모두에게 여는 정책. 비공개 데이터엔 곧 사고.
- **권한을 화면에서만 숨김** — "삭제 버튼을 안 보이게 했어요"는 보안이 아닙니다. 버튼이 안 보여도 누구나 직접 요청을 보낼 수 있으므로, 권한은 반드시 **DB(RLS)에서** 막아야 합니다.
- **`WITH CHECK` 빠뜨리기** — 읽기만 막고 생성/수정 시 "남의 user_id로 끼워 넣기"를 안 막으면, 본인인 척 남의 데이터를 조작할 수 있습니다.
- **service_role 키를 데모 속도 때문에 프론트에 박음** — 모은 명단·결제 내역이 통째로 털립니다. 자동화(n8n 등)에서도 이 키는 서버에서만.
- **트리거를 과신** — "가입하면 프로필 자동 생성" 같은 트리거가 조용히 실패하면 빈 프로필이 생기기도 합니다. 자동 동작은 한 번 직접 테스트하세요.

**⑦ 검증하는 법**

1. **RLS 켜짐 확인**: Supabase 대시보드 → Table Editor에서 각 테이블 옆에 RLS가 **Enabled**로 떠 있는지 눈으로 확인. 꺼져 있으면 경고가 보입니다.
2. **정책 읽기**: Authentication → Policies(또는 SQL Editor)에서 정책 목록을 보고, `USING (true)`처럼 활짝 열린 게 없는지, 본인 한정(`auth.uid() = user_id`)인지 확인.
3. **로그아웃 테스트**: 로그아웃(또는 anon 상태)으로 비공개 데이터에 접근을 시도해, **빈 결과 또는 거부**가 나오는지 확인. 데이터가 그대로 보이면 RLS 사고입니다.
4. **두 계정 교차 테스트**: A 계정으로 글을 쓰고, B 계정으로 로그인해 A의 비공개 글이 **안 보이는지** 확인. 가장 확실한 실전 점검입니다.
5. **키 위치 확인**: 코드와 환경변수에서 `service_role`을 검색해, 프론트엔드나 `NEXT_PUBLIC_`로 시작하는 변수에 *없는지* 확인. 있으면 즉시 회수·교체.
6. **실시간 동작**: 실시간 구독을 썼다면 두 개의 브라우저 창을 띄워, 한쪽에서 데이터를 바꿀 때 다른 쪽이 새로고침 없이 갱신되는지 확인. (단, 실시간으로 흘러나가는 행도 RLS의 통제를 받는지 같이 점검.)

!!! example "💡 예시로 이해하기"
    동아리 회비 장부 앱을 만들었다고 합시다. `members` 테이블에 이름·전화번호·납부액이 들어 있습니다. 데모는 완벽합니다 — 내가 로그인하면 내 정보가 잘 뜨고, 회장이 로그인하면 전체가 뜹니다. 그런데 어느 날 한 부원이 F12 개발자도구를 열고, 브라우저에 그대로 노출된 **anon 키**로 `members` 테이블을 직접 조회해 봅니다. RLS가 꺼져 있었다면? **전체 부원의 전화번호 명단이 그대로** 응답으로 돌아옵니다. 여기서 핵심은 "anon 키가 노출돼서" 털린 게 아니라는 점입니다. anon 키는 원래 공개되는 출입증이고, 잘못은 **사물함에 자물쇠(RLS)를 안 단 것**입니다. 정책을 `USING (auth.uid() = user_id)` (본인 행만) + 회장 역할만 전체 읽기로 고치고, 로그아웃 상태와 다른 부원 계정으로 각각 "남의 번호가 안 보이는지" 두 번 테스트하면, 같은 anon 키가 노출돼도 명단은 안전합니다. 디렉터가 던질 한 문장은 이것뿐입니다 — *"이 테이블 RLS 켜져 있어? 정책 보여줘."*
