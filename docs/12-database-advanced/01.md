# 관계형 모델 — 테이블·행·열·관계

**① 한 줄 정의**
관계형 모델은 우리 앱의 모든 기억(회원·상품·주문)을 **엑셀처럼 줄 맞춘 표(테이블) 여러 장**으로 나눠 담고, 그 표들을 **공통 번호(키)로 서로 연결**해 다루는 데이터 정리 방식입니다.

**② 왜 중요한가 (디렉터 관점)**
AI에게 "쇼핑몰 만들어줘"라고 하면 AI는 화면(코드)만 그럴듯하게 뽑고, 그 뒤에 깔리는 **데이터 구조**는 대충 만들기 일쑤입니다. 그런데 화면은 나중에 마음껏 바꿔도 되지만, **데이터 구조를 잘못 잡으면 회원 5천 명이 쌓인 뒤엔 되돌리기가 지옥**입니다. 디렉터가 코드를 한 줄도 못 짜도, "이 표는 무슨 한 건을 뜻하지? 이 표와 저 표는 어떻게 연결돼 있지? 한 칸에 여러 값을 쉼표로 욱여넣지 않았나?"만 읽어낼 수 있으면 AI의 설계가 **튼튼한지 모래성인지**를 판별할 수 있습니다. 관계형 모델을 읽는 눈은 곧 'AI가 만든 기억 창고의 도면을 검수하는 눈'입니다. 이 권 전체(정규화·인덱스·트랜잭션·SQL)가 모두 이 한 장의 개념 위에 쌓입니다.

**③ 비유**
관계형 데이터베이스는 **여러 명이 동시에 보고 고치는, 칸이 다 정해진 클라우드 엑셀 파일 묶음**입니다. 파일 묶음 안에는 시트가 여러 장 있죠. '회원' 시트, '상품' 시트, '주문' 시트. 각 시트는 **표(테이블)** 한 장입니다. 표의 **한 줄(행)**은 '회원 한 명', '상품 한 개', '주문 한 건' 처럼 **딱 한 건**을 뜻하고, 표의 **세로 칸(열)**은 '이름·이메일·가입일' 같은 **항목의 종류**입니다. 그리고 시트끼리는 출석부의 '학번'처럼 **뜻 없는 고유 번호**로 서로를 가리킵니다. 주문 시트의 한 줄이 "회원 #7번이 상품 #3번을 샀다"라고 적어두면, 회원 이름이 김민수든 김민수가 둘이든 헷갈리지 않습니다.

**④ 최소한 알 것**

| 용어 | 쉬운 말 | 예 (쇼핑몰) |
|---|---|---|
| 테이블(table) | 표 한 장 / 엑셀 시트 한 장 | `members`, `products`, `orders` |
| 행(row, 레코드) | 표의 한 줄 = '한 건' | 회원 한 명, 주문 한 건 |
| 열(column, 필드) | 표의 세로 칸 = 항목 종류 | 이름, 이메일, 가격, 재고 |
| 기본키(PK, primary key) | 그 줄을 절대 헷갈리지 않게 가리키는 고유 번호 | `members.id`, `products.id` |
| 외래키(FK, foreign key) | 다른 표의 기본키를 가리키는 '연결고리' | `orders.member_id` → `members.id` |

관계의 세 가지 모양:

- **1:1 (일대일)** — 한 건이 다른 표의 한 건과만 짝. 예: 회원 1명 ↔ 회원 상세설정 1줄. (드뭅니다.)
- **1:N (일대다)** — 한 건이 여러 건을 거느림. 예: **회원 1명 → 주문 여러 건**. 이때 외래키는 **'다(N)' 쪽 표**에 둡니다(`orders`에 `member_id`). 가장 흔한 관계.
- **N:M (다대다)** — 양쪽이 서로 여럿. 예: **주문 1건에 상품 여럿, 상품 1개도 여러 주문에 등장**. 이건 표 둘로는 못 풀고, 사이에 **중간 표(연결 테이블)** `order_items`를 둡니다.

**왜 한 표에 다 안 넣고 쪼개나?** — 핵심은 **중복을 없애 '한 군데만 고치면 끝'**으로 만들기 위해서입니다. 주문 표에 회원 이름·주소를 통째로 베껴 적으면, 회원이 이사할 때 옛 주문 100건의 주소가 옛날 주소로 어긋나 남습니다. 회원 정보는 `members` 표에 **딱 한 줄**만 두고, 주문은 `member_id`로 **가리키기만** 하면 한 번 고침이 전체에 반영됩니다. (왜·언제 쪼개는지의 깊은 원리는 다음 페이지 [정규화](02.md)에서.)

**⑤ AI에게 이렇게 시켜라**

```text
온라인 쇼핑몰의 데이터베이스 구조를 Supabase(PostgreSQL) 기준으로 설계해줘.
필요한 기능: 회원 가입, 상품 등록, 한 주문에 여러 상품 담기.

조건:
1) 회원·상품·주문을 별도 테이블로 나누고, 한 주문에 여러 상품이 들어가는
   다대다(N:M) 관계는 중간 테이블(예: order_items)로 풀어줘.
2) 모든 테이블의 기본키는 '뜻 없는 고유 id'(uuid 또는 bigint)로 해줘.
   사람 이름이나 이메일처럼 바뀔 수 있는 값은 기본키로 쓰지 마.
3) 외래키는 '다(N)' 쪽 테이블에 두고, 무엇이 무엇을 가리키는지 표로 정리해줘.
4) 한 칸에 여러 값을 쉼표로 욱여넣지 말고(예: '독서,영화'), 관계로 풀어줘.

각 테이블의 열 목록, 기본키/외래키, 그리고 회원-주문-상품이 어떻게 연결되는지를
비전공자가 이해하게 한 줄씩 설명도 붙여줘. CREATE TABLE 문도 함께.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **사람 이름·이메일을 기본키로 삼기.** 이름은 겹치고(김민수 둘), 이메일은 바뀝니다. 키는 반드시 **뜻 없는 고유 번호(id·UUID)**여야 합니다. AI는 빠른 설계랍시고 이메일을 키로 쓰는 실수를 자주 합니다.
- **한 칸에 여러 값 욱여넣기.** `취미: '독서,영화,등산'`, `상품들: '1,3,5'` 같은 쉼표 묶음. 당장은 편하지만 "영화를 좋아하는 회원만 찾기"가 지옥이 되고, 중간 표로 풀었어야 할 N:M을 망가뜨립니다.
- **다대다(N:M)를 중간 표 없이 풀려는 시도.** "주문 1건에 상품 여럿"을 `orders` 표 한 칸에 상품을 몰아넣어 버립니다. 반드시 `order_items` 같은 **연결 테이블**이 필요합니다.
- **외래키 방향 헷갈림.** 1:N에서 외래키는 항상 **'다(N)' 쪽**에 둡니다(`orders`에 `member_id`). 거꾸로 `members`에 주문들을 적으려 하면 한 칸에 여러 값 함정으로 돌아갑니다.
- **'가짜 DB'로 만들고 다 됐다 하기.** 진짜 Supabase 테이블이 아니라 코드 안 임시 배열로 데이터를 흉내 내고 완성이라 보고하는 경우. 새로고침하면 다 날아갑니다.

**⑦ 검증하는 법**

1. **'한 줄이 무엇인가' 묻기.** 각 표를 가리키며 "이 표의 한 줄은 무슨 한 건이야?"에 한 문장으로 답이 나오면(회원 한 명 / 주문 한 건) 표가 깔끔히 나뉜 것입니다. "회원이면서 주문이기도 한 줄"이 나오면 섞인 설계입니다.
2. **중복 베끼기 찾기.** 같은 정보(회원 이름·주소 등)가 **두 표 이상에 베껴 적혀 있나?** 있으면 위험. "회원이 주소를 바꾸면 옛 주문은 어떻게 돼?"라고 물어 답이 막히면 중복 설계입니다.
3. **Supabase 대시보드 눈으로 확인.** Table Editor에서 표 목록이 실제로 보이는지, 한 건 입력 → 새로고침 → 남아 있는지(진짜 DB) 확인. `member_id` 같은 열에 진짜 다른 표의 id가 들어가 있는지도 봅니다.
4. **외래키 자리 점검.** "1:N 관계에서 외래키를 '다' 쪽 표에 뒀어?", "N:M은 중간 테이블로 풀었어?" 두 질문에 'yes + 어디에'가 명확히 나와야 합니다.

!!! example "💡 예시로 이해하기"
    동네 카페가 주문을 종이 장부 한 권에 다 적었다고 합시다. 한 줄에 "2026-06-19 / 김민수 / 010-1234-5678 / 서면 무슨아파트 / 아메리카노 2, 라떼 1 / 12,500원". 김민수가 단골이라 100줄이 쌓였는데 이사를 갔습니다. 주소를 고치려면 **100줄을 다 찾아 고쳐야** 하고, 한 줄이라도 빠뜨리면 옛 주소로 배달이 갑니다. 게다가 "라떼를 한 번이라도 시킨 사람" 집계는 한 칸에 쑤셔 넣은 '아메리카노 2, 라떼 1' 글자를 일일이 눈으로 읽어야 합니다. 관계형 모델은 이 장부를 세 장으로 쪼갭니다. **회원 표**(김민수는 #7번, 주소 한 줄), **상품 표**(아메리카노 #1, 라떼 #2, 가격 한 줄), 그리고 **주문 표 + 주문상품 표**(주문 #55는 회원 #7번이 했고, 거기에 상품 #1 두 잔·상품 #2 한 잔). 이제 김민수가 이사하면 회원 표 **딱 한 줄**만 고치면 과거·미래 주문 전부에 반영되고, "라떼 마신 사람"은 주문상품 표에서 상품 #2를 가리키는 줄만 추려 단번에 셉니다. 표를 나누는 건 일을 늘리는 게 아니라, **나중에 고칠 일을 한 군데로 모으는** 일입니다.
