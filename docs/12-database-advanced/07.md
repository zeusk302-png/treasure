# 스키마 설계와 마이그레이션 — 바뀌는 요구를 안전하게

**① 한 줄 정의**
**스키마**는 우리 데이터베이스의 '설계 도면'(어떤 표가 있고, 각 표에 어떤 칸이 어떤 형태로 있는지)이고, **마이그레이션**은 이미 사람이 살고 있는 집을 부수지 않고 그 도면을 차근차근 바꿔 가는 '공사 기록부'입니다.

**② 왜 중요한가 (디렉터 관점)**
바이브코딩에서 화면(코드)은 마음에 안 들면 다시 그리면 그만입니다. 새로고침하면 깨끗하게 갈아엎을 수 있죠. 그런데 **데이터 구조는 다릅니다.** 회원 5천 명, 주문 3만 건이 이미 쌓인 표의 모양을 바꾸는 건, 사람이 살고 있는 집의 기둥과 배관을 옮기는 리모델링 공사입니다. 짐을 들어내고 벽을 부수는 동안에도 가족은 그 집에서 밥을 먹고 잠을 자야 하죠.

디렉터가 이걸 알아야 하는 이유는, AI가 변경을 **너무 가볍게** 말하기 때문입니다. "컬럼 하나 추가하면 돼요"라는 한 마디 뒤에는 (1) 이미 쌓인 옛 데이터 3만 건을 어떻게 채울지, (2) 그 칸을 쓰는 코드를 전부 어떻게 고칠지, (3) 잘못되면 어떻게 되돌릴지가 숨어 있습니다. AI는 이 세 개를 자주 빠뜨립니다. 디렉터는 코드를 짜는 사람이 아니라, **"이 변경, 운영 데이터를 깨지 않고 안전하게 할 수 있어?"라고 멈춰 세워 묻는 사람**입니다. 그 한 번의 질문이 며칠짜리 데이터 사고를 막습니다.

**③ 비유**
집을 떠올려 봅시다. **벽지·가구(화면 코드)**는 주말에 혼자서도 바꿉니다. 마음에 안 들면 다시 바꾸면 되죠. 하지만 **기둥 위치나 배관(스키마)**을 바꾸려면 이미 들어찬 짐을 다 들어내고, 벽을 부수고, 그 배관에 연결된 모든 수도꼭지(데이터를 쓰는 코드)를 다시 이어야 합니다.

여기서 **마이그레이션**은 그 공사를 '한꺼번에 와장창'이 아니라 **순서대로 적어 둔 공사 일지**입니다. "3월 1일: 화장실에 수도관 하나 추가(기존 배관은 그대로 둠)", "3월 3일: 새 수도꼭지 연결", "3월 5일: 옛 배관 철거". 이렇게 단계를 기록해 두면, 똑같은 공사를 다른 집(개발 서버 → 운영 서버)에 그대로 재현할 수 있고, 3월 3일에 사고가 나면 "3월 1일 상태로 되돌리기"가 가능합니다. **백업**은 공사 전에 찍어 둔 '집 전체 사진'입니다. 벽을 완전히 잘못 부쉈을 때, 그 사진으로 원래 모습을 복원할 수 있는 마지막 안전장치죠.

**④ 최소한 알 것**

| 용어 | 한 줄 뜻 | 디렉터가 챙길 점 |
|---|---|---|
| 스키마(schema) | DB의 설계 도면(표·칸·형태·관계) | 처음에 신중히. 화면보다 바꾸기 어렵다 |
| 마이그레이션(migration) | 스키마를 단계별로 바꾸는 변경 기록 파일 | 손으로 직접 고치지 말고 '기록되는 변경'으로 |
| `ADD COLUMN`(컬럼 추가) | 표에 새 칸 추가 | 보통 안전. 단 기본값·기존 데이터 채움 확인 |
| `DROP COLUMN`(컬럼 삭제) | 칸 통째로 제거 | 위험. 그 데이터는 영영 사라짐. 백업 필수 |
| `NOT NULL`(빈 칸 금지) | 그 칸은 반드시 값이 있어야 함 | 옛 데이터에 빈 칸이 있으면 추가가 실패한다 |
| `DEFAULT`(기본값) | 값을 안 넣으면 자동으로 채울 값 | 새 컬럼 추가 시 옛 줄을 무엇으로 채울지 |
| 백업(backup) | 현재 데이터 전체 사본 | 큰 변경 직전엔 무조건. 복원도 연습해 둘 것 |
| 롤백(rollback) | 변경을 되돌리기 | "잘못되면 되돌릴 수 있나?"의 답 |
| 무중단(zero-downtime) | 사용자 끊김 없이 바꾸기 | 운영 서비스는 멈추지 않고 바꿔야 한다 |

**좋은 스키마 설계의 출발점 (초기에 30분 더 쓰면 나중에 며칠을 번다):**

- 모든 표에 **뜻 없는 고유 번호(id, 보통 UUID)**를 기본키로. 이메일·이름처럼 사람이 바꿀 수 있는 값은 키로 쓰지 않는다.
- 한 칸에 여러 값을 쉼표로 욱여넣지 않는다(취미: '독서,영화,등산' ✗). 나중에 골칫거리.
- 같은 정보를 여러 표에 베껴 적지 않는다(중복은 모든 데이터 사고의 근원). → [정규화](02.md) 참고.
- **나중에 칸을 추가하기 쉬운 구조인가?**를 먼저 본다. 칸 추가는 비교적 안전하지만, 칸 삭제·이름 변경·표 쪼개기는 큰 공사다.

**컬럼 변경의 '안전 등급' (외울 만한 직관):**

- 🟢 **쉬움/안전**: 새 컬럼 추가(`NULL` 허용 또는 `DEFAULT` 있음), 새 표 추가, 인덱스 추가.
- 🟡 **주의**: `NOT NULL` 컬럼 추가(옛 데이터 채움 필요), 큰 표에 인덱스 추가(잠깐 느려질 수 있음), 데이터 타입 변경.
- 🔵 **위험/단계 필요**: 컬럼 이름 변경, 컬럼 삭제, 표 쪼개기·합치기. → 반드시 무중단 단계로 나눠서.

**⑤ AI에게 이렇게 시켜라**

```text
나는 Next.js + Supabase(PostgreSQL)로 운영 중인 사이트가 있어.
지금 'profiles' 표에 회원 5천 명이 이미 들어 있는데,
'phone'(전화번호) 칸을 새로 추가하려고 해.

코드부터 바꾸지 말고, 먼저 '안전한 마이그레이션 계획'을 세워줘.
다음 4가지를 비전공자도 알게 단계별로 설명해줘:

1) 이미 들어 있는 5천 명의 'phone' 칸은 어떤 값으로 채워야 하나?
   (NULL 허용으로 갈지, 기본값을 줄지, 왜 그렇게 하는지)
2) 이 변경 때문에 수정해야 하는 기존 코드는 어디인지 목록으로.
3) 변경을 Supabase 마이그레이션 파일로 만드는 방법(직접 손으로
   테이블을 고치지 말고 '기록되는 변경'으로 하고 싶어).
4) 잘못됐을 때 되돌리는(롤백) SQL과, 변경 전에 백업하는 방법.

운영 데이터를 절대 깨지 않는 게 1순위야. 위험한 명령(DROP,
조건 없는 UPDATE/DELETE)이 들어가면 미리 경고해줘.
```

> 팁: 한 발 더 나아가 "이 변경을 **무중단으로** 하려면 어떤 순서로 해야 해?(예: 컬럼 먼저 추가 → 코드 배포 → 옛 컬럼 나중에 제거)"를 덧붙이면, AI가 운영 서비스를 멈추지 않는 단계별 계획을 내놓습니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **"나중에 추가하면 돼요"의 함정.** AI는 칸 추가를 가볍게 말하지만, 실제론 *옛 데이터를 어떻게 채울지*와 *그 칸을 쓰는 코드 전부 수정*을 자주 누락합니다. "추가는 됐는데 옛 회원 5천 명은 전화번호 칸이 비어 있어 코드가 에러"가 전형적입니다.
- **`NOT NULL`을 그냥 붙인다.** 이미 빈 칸이 있는 표에 "이 칸은 반드시 값이 있어야 함"을 거는 순간 변경 자체가 실패합니다. AI는 옛 데이터를 먼저 채우는(또는 기본값을 주는) 단계를 건너뛰곤 합니다.
- **운영 DB에서 바로 손으로 고친다.** AI가 "Supabase 대시보드에서 이 컬럼 지우세요"라고 하면 기록이 안 남아 다른 환경(개발↔운영)과 어긋나고, 되돌릴 수도 없습니다. 변경은 **마이그레이션 파일**로 남겨야 합니다.
- **위험한 SQL을 무심코.** `DROP COLUMN`, `DROP TABLE`, 조건(`WHERE`) 없는 `UPDATE`/`DELETE`는 데이터를 통째로 날립니다. AI가 이런 명령을 슬쩍 끼워 넣어도 디렉터가 못 읽으면 못 막습니다. → [SQL 읽기](05.md).
- **백업 없이 큰 변경.** "이론상 안전해요"를 믿고 백업을 건너뛰는 것. 백업은 변경이 *실패할 때*가 아니라, 변경은 성공했는데 *논리가 틀렸을 때*(예: 잘못된 값으로 일괄 변환)를 위한 보험입니다.
- **롤백을 안 만든다.** "되돌리는 방법"을 미리 준비하지 않으면, 사고가 났을 때 손이 떨립니다.

**⑦ 검증하는 법**
큰 변경 직전, **세 가지를 반드시** 확인하세요. 하나라도 흐릿하면 변경을 멈춥니다.

1. **데이터**: "이미 쌓인 옛 데이터는 어떻게 옮기나?(채울 값·변환 규칙)" → 답이 없으면 변경 금지.
2. **코드**: "이 변경으로 깨지는 기존 코드는 어디인가?" → 목록이 안 나오면 변경 금지.
3. **되돌리기**: "잘못되면 백업으로 복원하거나 롤백할 수 있나?" → 둘 다 없으면 변경 금지.

그리고 실제로 눈으로 확인하는 절차:

- **개발 환경에서 먼저.** 운영(실제 사용자) DB가 아니라 복제본/개발 DB에서 마이그레이션을 먼저 돌려 봅니다. Supabase는 로컬/스테이징 프로젝트로 리허설할 수 있습니다.
- **마이그레이션 파일이 남았는지.** 손으로 고친 게 아니라 `supabase/migrations/` 폴더 같은 곳에 변경 기록 파일이 생겼는지 봅니다(있어야 다른 환경에 재현·되돌리기 가능).
- **위험 단어 검색.** 변경 SQL에 `DROP`, `WHERE` 없는 `UPDATE`/`DELETE`가 있는지 눈으로 훑습니다. 있으면 "이거 정말 전부에 적용되는 거 맞아?"로 멈춰 세웁니다.
- **백업 확인.** Supabase 대시보드의 백업(또는 `pg_dump`로 받은 사본)이 변경 *직전* 시점에 있는지. 가격·자동 백업 주기는 플랜마다 다르니 **현재 정책 확인 권장**.
- **새로고침 테스트.** 변경 후 옛 데이터 한 줄(예: 가장 오래된 회원)을 화면에서 열어 봅니다. 새 칸이 빈 값이어도 화면이 안 깨지는지 — 깨지면 코드가 새 칸의 빈 값을 처리 못 하는 것.

!!! example "💡 예시로 이해하기"
    온라인 원두 쇼핑몰을 운영 중인데, 사장님이 "회원별로 '단골 등급(silver/gold)'을 보여주고 싶다"고 합니다. AI에게 그냥 "members 표에 grade 칸 추가해줘"라고 하면, AI는 `ALTER TABLE members ADD COLUMN grade text NOT NULL;`을 던질 수 있습니다. 그런데 이미 회원 5천 명이 있고 그들의 grade는 비어 있으니, "이 칸은 반드시 값이 있어야 함(NOT NULL)"이라는 조건 때문에 이 명령은 **실패**하거나, 통과해도 옛 회원들이 줄줄이 에러를 냅니다. 디렉터는 여기서 멈춰 묻습니다. "옛 회원 5천 명의 grade는 뭐로 채울 거야? 'silver'를 기본값으로 줄까?" 그러면 안전한 버전이 나옵니다 — `ADD COLUMN grade text DEFAULT 'silver'`(기존 5천 명은 자동으로 silver로 채워짐), 마이그레이션 파일로 기록, 변경 전 백업, 잘못되면 `DROP COLUMN grade`로 롤백. 똑같은 "칸 하나 추가"인데, 디렉터의 질문 한 줄이 '운영 데이터 사고'를 '안전한 30분 작업'으로 바꿉니다.
