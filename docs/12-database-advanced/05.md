# SQL 실전 — SELECT·JOIN·집계·서브쿼리

**① 한 줄 정의**
SQL은 데이터베이스에게 "이 표에서 / 이런 조건인 줄을 / 이렇게 합치고 / 이렇게 세서 / 이 순서로 / 이만큼만" 보여달라고 시키는 '읽기 주문서'이며, **SELECT·WHERE·ORDER BY·LIMIT·JOIN·GROUP BY·서브쿼리** 일곱 부품만 알면 AI가 짠 조회 쿼리의 '의도'를 읽고 검증할 수 있습니다.

**② 왜 중요한가 (디렉터 관점)**
앞 페이지들에서 "테이블을 어떻게 나눌지(설계·정규화)"를 배웠다면, 이 페이지는 **나눠 둔 데이터를 다시 사람이 보고 싶은 모양으로 꺼내 오는 법**입니다. 디렉터가 매일 마주치는 요구는 거의 다 '읽기'입니다 — "이번 달 매출 합계 보여줘", "주문이 많은 회원 상위 10명", "댓글이 하나도 없는 글만". 이걸 코드로 직접 짜진 못해도, AI가 내놓은 SQL을 읽고 *"이건 이번 달만 거르네", "이건 합계가 아니라 개수네", "WHERE가 빠져서 전부 다 긁어오네"* 를 판별할 수 있으면, 잘못된 숫자가 화면에 박히기 전에 멈춰 세울 수 있습니다.

특히 **읽기 SQL은 '틀려도 조용히' 틀린다**는 점이 위험합니다. DELETE는 데이터가 사라져 바로 티가 나지만, JOIN을 잘못 걸어 매출이 3배로 부풀려진 SELECT는 빨간 에러 하나 없이 멀쩡한 숫자처럼 보입니다. 디렉터의 일은 코드를 짜는 게 아니라 **'그 숫자가 진짜 맞는 숫자인지' 의심하고 확인하는 것**입니다. SQL을 읽을 줄 알면 그 의심에 근거가 생깁니다.

**③ 비유**
SQL 한 문장은 **카페 주문**과 똑같은 순서로 읽으면 됩니다. "어느 진열대에서(FROM 주문 표) / 아이스만(WHERE 조건) / 영수증의 회원 정보랑 붙여서(JOIN) / 회원별로 묶어 잔 수를 세고(GROUP BY + COUNT) / 많이 산 순으로(ORDER BY) / 위에서 10명만(LIMIT)" 달라는 주문서입니다. 바리스타(DB)는 이 주문을 **정해진 순서대로** 처리합니다. 그리고 **서브쿼리**는 "어제 평균보다 많이 판 음료만 골라줘"처럼, *주문 안에 또 다른 작은 주문*을 끼워 넣는 것 — 먼저 작은 주문(어제 평균)을 계산해서 그 답을 바깥 주문의 조건으로 쓰는, 주문서 안의 주문서입니다.

**④ 최소한 알 것**

읽기 SQL의 6개 핵심 부품:

| 부품 | 뜻 (한 줄) | 예 |
|---|---|---|
| `SELECT … FROM` | 어느 표에서 어떤 열을 보여줘 | `SELECT name, price FROM products` |
| `WHERE` | 이런 조건인 줄만 거른다 | `WHERE price > 10000` |
| `ORDER BY` | 어떤 순서로 정렬 (`ASC` 오름/`DESC` 내림) | `ORDER BY created_at DESC` |
| `LIMIT` | 위에서 몇 줄만 (페이지네이션의 핵심) | `LIMIT 10` |
| `JOIN … ON` | 공통 연결고리로 두 표를 합쳐 본다 | `JOIN members ON orders.member_id = members.id` |
| `GROUP BY` + 집계 | 같은 값끼리 묶어 세거나 더한다 | `GROUP BY member_id` |

집계 함수(묶은 한 무더기를 숫자 하나로 요약):

| 함수 | 뜻 | 흔한 쓰임 |
|---|---|---|
| `COUNT(*)` | 줄(건수)을 센다 | 회원 수, 주문 건수 |
| `SUM(컬럼)` | 합계 | 매출 합계 |
| `AVG(컬럼)` | 평균 | 평균 단가 |
| `MAX` / `MIN` | 최댓값 / 최솟값 | 최고가, 최초 가입일 |

JOIN 두 종류만 구분하면 충분:

| 종류 | 한 줄 | 쓸 때 |
|---|---|---|
| `INNER JOIN` | 양쪽 표에 **모두 있는** 줄만 | "주문이 있는 회원"만 보고 싶을 때 |
| `LEFT JOIN` | 왼쪽 표는 **다 남기고**, 짝 없으면 오른쪽은 빈칸 | "주문이 0건인 회원도 포함"할 때 |

`WHERE`(묶기 전 거름)와 `HAVING`(묶은 뒤 거름)의 차이도 알아두면 좋습니다. "1만 원 넘는 주문만"은 `WHERE`, "합계가 100만 원 넘는 회원만"은 묶은 결과를 거르므로 `HAVING`입니다.

처리 순서(읽을 때 머릿속으로 이 순서로 따라가면 안 헷갈림): **FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT**. 적는 순서(SELECT가 맨 앞)와 실제 실행 순서가 다르다는 점만 기억하세요.

!!! tip "디렉터가 외울 안전 습관"
    조회는 항상 **작게 시작해서 키운다.** 먼저 `SELECT * FROM 표 LIMIT 5`로 "이 표에 뭐가 들었나" 눈으로 보고, 그다음 WHERE를 붙이고, 마지막에 JOIN·집계를 얹습니다. 한 번에 거대한 쿼리를 받지 말고 "한 단계씩 결과를 보여주며 쌓아줘"라고 시키면 어디서 틀렸는지 잡기 쉽습니다.

**⑤ AI에게 이렇게 시켜라**

```text
[역할] 너는 Supabase(PostgreSQL)를 쓰는 내 프로젝트의 SQL 도우미야.
[표 구조]
- members(id, name, email, created_at)
- orders(id, member_id, amount, created_at, status)   # status는 'paid'|'cancelled'
[원하는 결과]
"이번 달(2026-06)에 결제 완료(status='paid')된 주문 기준으로,
 회원별 총 결제액이 큰 상위 10명"을 뽑고 싶어. 단, 주문이 0건인 회원은 빼.

[지켜줘]
1) 한 번에 큰 쿼리를 주지 말고, (a)먼저 결과를 확인할 작은 쿼리,
   (b)거기에 조건/집계를 단계별로 얹는 쿼리 순서로 설명해줘.
2) 각 줄이 무슨 뜻인지 비전공자가 읽게 한국어 주석으로 풀어줘.
3) INNER JOIN인지 LEFT JOIN인지, 왜 그걸 골랐는지 한 줄로 말해줘.
4) 이 쿼리가 '읽기 전용'이라 데이터를 바꾸지 않는다는 걸 명시해줘.
5) 결과 줄 수가 상식적으로 맞는지(회원 수보다 많을 수 없는지) 검증법도 알려줘.
```

> 한 단계 더: 받은 쿼리에 대해 *"이 JOIN 때문에 한 회원의 주문이 여러 건이면 매출이 중복으로 더해질 위험은 없어? GROUP BY를 어디서 하는지로 설명해줘"* 라고 되물으면, 집계 중복(가장 흔한 SQL 버그)을 AI 입으로 점검하게 만들 수 있습니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **집계가 중복 부풀려짐(가장 흔함).** 회원 1명에 주문 3건인데 JOIN 후 GROUP BY 전에 다른 표를 또 JOIN하면, 줄이 곱해져 매출이 2~3배로 뻥튀기됩니다. 에러 없이 '그럴듯한 큰 숫자'가 나와 더 위험합니다.
- **`INNER` vs `LEFT` 혼동.** "주문 없는 회원도 포함"이 요구인데 INNER JOIN을 쓰면 주문 0건 회원이 결과에서 통째로 사라집니다. "신규 회원이 왜 리포트에 안 보여요?"의 단골 원인.
- **`WHERE`에 NULL 비교.** `status != 'cancelled'`로 거르면 status가 비어있는(NULL) 줄까지 같이 빠집니다. NULL은 `=`/`!=`로 비교되지 않고 `IS NULL`/`IS NOT NULL`을 써야 한다는 걸 AI가 종종 놓칩니다.
- **`SELECT *` 남발.** 필요한 두 열만 있으면 되는데 모든 열을 끌어와 느려지고, JOIN 시 같은 이름 열(둘 다 `id`)이 섞여 헷갈립니다.
- **`LIMIT`만 있고 `ORDER BY`가 없음.** "상위 10명"이라면서 정렬을 안 하면, DB가 주는 순서는 보장되지 않아 매번 다른 10줄이 나올 수 있습니다. "상위/최신 N개"엔 반드시 `ORDER BY`가 짝으로 따라와야 합니다.
- **읽기인 줄 알았는데 쓰기.** "데이터 좀 보여줘"라고 했는데 AI가 `UPDATE`/`DELETE`를 끼워 넣는 경우. 조회 요청에 `INSERT/UPDATE/DELETE/DROP/TRUNCATE`가 보이면 즉시 멈추세요.
- **숫자/날짜 형식.** 금액을 문자열로 더하거나, 한국 시간(KST)이 아닌 UTC 기준으로 "이번 달"을 잘라 하루씩 어긋나는 일이 잦습니다.

**⑦ 검증하는 법**

1. **줄 수의 상식 점검.** 회원이 100명인데 "회원별 매출" 결과가 5천 줄이면 JOIN이 중복된 것입니다. 결과 줄 수가 '원래 표의 줄 수'와 어긋나면 의심하세요.
2. **합계 교차 검증.** `GROUP BY`로 회원별 합을 냈다면, 그 값들을 다 더한 총합이 *"WHERE만 걸고 SUM 한 전체 합계"* 와 같아야 합니다. 다르면 중복·누락이 있다는 신호입니다.
3. **샘플 한 줄 손으로 따라가기.** 결과 맨 윗줄 회원 하나를 골라 `WHERE member_id = '그 id'`로 원본 주문을 직접 조회해, 집계값이 손으로 더한 값과 같은지 확인합니다.
4. **`LIMIT 5`로 먼저 본다.** 큰 쿼리를 돌리기 전에 같은 조건으로 5줄만 떠 형태를 눈으로 확인합니다. Supabase **SQL Editor**나 **Table Editor**에서 바로 됩니다.
5. **읽기 전용인지 단어 검색.** 실행 전 쿼리에서 `INSERT`·`UPDATE`·`DELETE`·`DROP`·`TRUNCATE`·`ALTER` 단어가 하나라도 있으면 그건 더 이상 '조회'가 아닙니다. 조회라면 `SELECT`로 시작하는 한 문장이어야 합니다.
6. **RLS를 잊지 말기.** Supabase에서 브라우저(anon 키)로 같은 쿼리를 돌리면 **행 수준 보안(RLS) 정책 때문에 SQL Editor에서보다 적게 보일 수 있습니다.** SQL Editor는 보통 정책을 우회하므로, "관리자용 화면엔 다 보이는데 사용자 화면엔 일부만 보인다"는 버그가 아니라 RLS가 정상 작동하는 것일 수 있습니다.

!!! example "💡 예시로 이해하기"
    동네 빵집 사장님이 "이번 달 단골 베스트 10명 뽑아서 쿠폰 보내자"고 합니다. 디렉터는 이걸 SQL 주문서로 번역합니다. *주문 표(orders)에서(FROM) / 6월에 결제 완료된 것만 거르고(WHERE status='paid' AND 6월) / 회원 정보랑 붙여서(JOIN members) / 회원별로 묶어 결제액을 더하고(GROUP BY member_id, SUM(amount)) / 많이 산 순으로 줄 세워(ORDER BY 합계 DESC) / 위 10명만(LIMIT 10).*

    AI가 깔끔한 쿼리를 내놨습니다. 그런데 결과를 보니 1등 단골의 매출이 480만 원 — 사장님이 "그 손님 그렇게 많이 안 샀는데?" 합니다. 디렉터는 검증법대로 그 회원 한 명만 `WHERE member_id`로 직접 조회해 봅니다. 실제 주문은 12건, 합계는 160만 원. **정확히 3배.** 알고 보니 AI가 회원의 '배송지 표'까지 JOIN했고, 그 회원의 배송지가 3개라 주문 한 건이 3번씩 세어진 것이었습니다. JOIN을 하나 빼자 160만 원으로 맞습니다. 코드를 한 줄도 직접 안 고쳤지만, "이 숫자 진짜 맞아?"라는 의심 하나와 "샘플 한 줄 손으로 따라가기" 한 번이, 단골에게 엉뚱한 등급의 쿠폰이 나갈 뻔한 사고를 막았습니다.
