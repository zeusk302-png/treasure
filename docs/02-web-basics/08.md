# 정적 사이트의 진실 — '프론트·백·DB' 비유 바로잡기

**① 한 줄 정의**
정적 사이트에는 사실상 **'내 백엔드'가 없습니다.** Supabase를 붙인 것은 내 서버를 만든 게 아니라 **'남의 백엔드를 빌린 것'** 입니다.

**② 왜 중요한가 (디렉터 관점)**
"모든 사이트는 프론트·백·DB 3층 구조"라는 통념은 정적 사이트에서 **거짓이 됩니다**. 이 교정을 못 하면, AI가 모든 사이트에 똑같은 3층 구조를 적용해 불필요한 서버를 짓거나, 반대로 빌린 백엔드(Supabase)의 보안 책임(RLS)을 "남의 일"로 착각합니다. 이 페이지는 권2의 마지막 교정이자 권3·권4로 가는 다리입니다.

**③ 비유**
정적 사이트는 **인쇄해 벽에 붙인 포스터**입니다. 누가 봐도 같은 내용이고, 따로 "주방"이 없습니다. 여기에 방명록을 붙인 건, 포스터 옆에 **남의 가게(Supabase)로 연결되는 우편함**을 단 것입니다. 그 가게의 운영 규칙(누가 글을 읽고 쓰나 = RLS)은 여전히 내가 정하고 검증해야 합니다.

**④ 최소한 알 것**

| 구분 | 정적 본문 | 동적 위젯(진도·댓글) |
|---|---|---|
| 내 백엔드 | 없음 | 없음(빌림) |
| DB 요청 | 0건 | Supabase로 요청 |
| 보안 책임 | 거의 없음 | RLS는 **내 책임** |

- "백엔드가 없다"는 "보안 신경 안 써도 된다"가 아니다 — 빌린 부분의 규칙은 내 몫.

**⑤ AI에게 이렇게 시켜라**

```text
내 사이트는 정적 사이트(예: MkDocs/Next.js 정적 빌드)이고, 데이터는
Supabase를 빌려 쓰고 있어. 이 구조에서 '프론트/백/DB' 중 실제로 내가 운영하는
서버가 무엇이고, 무엇이 빌린 것인지 표로 정리해줘. 그리고 빌린 부분에서
내가 직접 책임져야 하는 보안 설정(예: RLS)이 무엇인지 알려줘.
모든 사이트가 3층 구조라는 전제로 답하지 마.
```

**⑥ 흔한 함정 / AI가 틀리는 것**
AI는 **모든 사이트에 3층(프론트·백·DB) 구조를 동일하게 적용**합니다. 정적 사이트인데 별도 서버를 짓게 하거나, 빌린 백엔드의 보안 책임(RLS 설정·검증)을 "Supabase가 알아서 해준다"고 잘못 안심시킵니다.

**⑦ 검증하는 법**
F12 → Network에서 두 페이지를 대조합니다. **본문 페이지 = DB 요청 0건**, **진도체크 페이지 = Supabase로 요청 발생**. 이 차이가 곧 "어디까지가 정적이고 어디서부터 빌린 백엔드인지"의 경계선입니다.

!!! example "💡 예시로 이해하기"
    동네 카페가 종이 전단지를 만들어 게시판에 붙였습니다(정적 사이트). 전단지엔 "주방"이 없습니다 — 누가 봐도 같은 내용이고 서버랄 게 없죠. 그런데 전단지 옆에 "후기 남겨주세요" 우편함을 달면서, 그 우편함을 **옆 가게 사장님(Supabase)에게 관리해 달라고 맡겼습니다**. 여기서 흔한 착각: "우편함은 옆 가게가 관리하니 보안도 그쪽 책임"이라고 안심하는 것. 아닙니다. "후기는 누구나 읽되, 남의 후기를 지우는 건 본인만"이라는 **규칙(RLS)은 전단지 주인인 내가 직접 설정하고 확인**해야 합니다. 이 규칙을 안 걸어두면 누구나 남의 후기를 지우는 사고가 납니다. F12 → Network로 보면 전단지 본문은 DB 요청 0건, 후기 영역만 Supabase로 요청이 나가는 게 바로 그 경계선입니다.
