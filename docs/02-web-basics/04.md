# API가 뭔가 — 주방에 음식을 주문하는 창구

**① 한 줄 정의**
**API**는 한 프로그램이 다른 프로그램에 "이걸 해줘/이걸 줘"라고 요청하는 약속된 **주문 창구**입니다. 진도체크·댓글·검색은 모두 Supabase의 API를 부르는 일입니다.

**② 왜 중요한가 (디렉터 관점)**
"직접 만들까, 남의 API를 부를까"가 설계의 절반입니다. 결제·지도·번역처럼 남이 잘 만들어 둔 것은 API로 빌리는 게 빠르고 안전합니다. 다만 빌리는 순간 **요청 한도·요금·실패 가능성**이라는 청구서가 따라옵니다. 디렉터는 "이 API가 공짜인지, 한 달에 몇 번까지인지, 실패하면 어떻게 되는지"를 먼저 물어야 합니다.

**③ 비유**
식당의 주문 창구입니다. 손님은 주방에 직접 들어가지 않고 정해진 메뉴판(API 명세)대로 주문합니다. 메뉴에 없는 건 안 되고, 너무 자주 시키면 "오늘 주문 한도 초과"가 뜨고, 일부 메뉴는 유료입니다.

**④ 최소한 알 것**
- API = 정해진 형식으로 요청하면 정해진 형식(보통 JSON)으로 응답.
- 빌릴 때 따라오는 3가지: **요청 한도(rate limit)·요금·실패 처리**.
- 응답은 대부분 JSON이라는 텍스트 데이터로 온다.

**⑤ AI에게 이렇게 시켜라**

```text
이 기능을 외부 API로 구현할지, 직접 만들지 비교해줘. 외부 API를 쓴다면
'무료 한도, 초과 시 요금, 요청 실패하면 어떻게 되는지'를 표로 정리하고,
키는 코드에 직접 박지 말고 환경변수로 분리하는 전제로 설계해줘.
공식 문서 링크도 함께 줘. 추정한 한도/요금이면 '추정'이라고 표시해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**
AI는 요청 한도·요금·실패 가능성을 빠뜨리고, **키를 코드에 그대로 박은 예제**를 주기 쉽습니다. 데모에선 동작하지만 그대로 공개 저장소에 올리면 사고가 납니다.

!!! warning "Tving 사태의 실제 원인"
    널리 알려진 키 유출 사고의 핵심 원인은 키 자체가 아니라, **키를 `.env`로 분리하지 않고 코드에 하드코딩한 채 공개 저장소(예: GitHub)에 그대로 올린 것**이었습니다. API 키는 항상 환경변수로 분리하고, 공개 저장소에 올라가지 않게 관리하세요. (자세한 대응은 권4)

**⑦ 검증하는 법**
F12 → Network 탭에서 진도체크·댓글 동작 시 **Supabase로 가는 요청과 JSON 응답**을 직접 펼쳐봅니다. 요청 URL·헤더에 anon 키만 보이는지(정상), JSON 응답 구조가 어떤지 눈으로 확인합니다.
