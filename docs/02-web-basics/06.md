# 렌더링 방식 — 미리 만들어 두느냐, 주문받고 만드느냐

**① 한 줄 정의**
**렌더링 방식**은 화면(HTML)을 *언제, 어디서* 만드느냐의 선택입니다. 크게 SSG(미리)·SSR(요청 때 서버에서)·CSR(브라우저에서)·ISR(미리 만들되 주기적 갱신) 네 가지가 있습니다.

**② 왜 중요한가 (디렉터 관점)**
이 선택이 **속도·비용·검색 노출**을 동시에 좌우합니다. 자주 안 바뀌는 본문을 매 요청마다 새로 만들면(SSR) 느리고 비쌉니다. 반대로 사용자마다 달라야 하는 진도체크를 미리 만들어 두면(SSG) 말이 안 됩니다. 디렉터는 "내 페이지가 *어떤 성격*인가"를 보고 방식을 정해 AI에게 지시해야 합니다.

**③ 비유**
- **SSG**: 미리 구워둔 빵(아침에 다 만들어 진열). 가장 빠르고 쌈.
- **SSR**: 주문받고 굽는 빵(매번 신선하지만 기다림·인건비).
- **CSR**: 손님이 받아가 집에서 데움(서버는 재료만, 조립은 브라우저가).
- **ISR**: 미리 굽되 N시간마다 새로 구움(둘의 절충).

**④ 최소한 알 것**

| 방식 | 만드는 시점 | 잘 맞는 경우 | 검색 노출 |
|---|---|---|---|
| SSG | 빌드 때 미리 | 잘 안 바뀌는 본문 | 매우 좋음 |
| SSR | 요청 올 때 서버 | 매번 신선해야 함 | 좋음 |
| CSR | 브라우저에서 | 로그인 후 개인화면 | 약함 |
| ISR | 미리+주기 갱신 | 가끔 바뀌는 인기글 | 좋음 |

**⑤ AI에게 이렇게 시켜라**

```text
이 페이지의 성격은 [예: 자주 안 바뀌는 안내 본문 / 사용자마다 다른 개인 화면]이야.
SSG, SSR, CSR, ISR 중 '내 경우'에 가장 맞는 방식을 하나 고르고, 왜 그게
맞는지 속도·비용·검색노출 관점에서 이유를 말해줘. 정의만 나열하지 말고
내 페이지에 대한 구체적 권고를 줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**
AI는 네 방식의 **정의만 나열하고 "그래서 내 경우엔 무엇"** 인지를 안 줍니다. 결정을 디렉터에게 떠넘기거나, 가장 흔한 기본값을 묻지도 않고 적용합니다.

**⑦ 검증하는 법**
이 사이트 한 곳에 네 방식이 섞여 있습니다: 본문 = 정적(SSG), 진도/댓글 = 동적, 인기글 = ISR. F12 → Network에서 본문 페이지는 HTML이 통째로 오는지, 동적 위젯은 별도 데이터 요청이 추가로 가는지 비교해 보세요.
