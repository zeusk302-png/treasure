# 검색에 잡히게 하기 2 — 구조화 데이터(JSON-LD)와 2026년에 사라진 것

**(1) 한 줄 정의**

구조화 데이터(JSON-LD)란 페이지 안에 검색엔진이 읽기 좋은 '설명 라벨'을 숨겨 넣어, 검색 결과에 별점·작성자·로고 같은 풍부한 모양(리치결과)으로 뜨게 하는 표준 표기법이다.

**(2) 왜 중요한가 (디렉터 관점)**

같은 검색결과라도 리치결과로 뜨면 눈에 더 띄어 클릭률이 오른다. 하지만 더 중요한 건 **효과 없는 라벨을 붙이지 않는 판단**이다. 검색엔진이 지원을 끊은 스키마를 넣어달라는 건 시간 낭비이고, AI는 과거 데이터로 학습해 이미 폐지된 것을 여전히 추천하기 쉽다. 디렉터가 "이건 지금도 효과가 있나?"를 물을 줄 알아야 한다.

**(3) 비유**

상품에 붙이는 영양성분표 같은 표준 라벨이다. 검색엔진은 이 라벨을 읽어 진열대를 더 예쁘게 꾸며준다. 그런데 마트가 "이제 그 칸의 라벨은 안 봅니다"라고 정책을 바꿨다면, 그 라벨을 계속 붙여봐야 진열에 아무 변화가 없다.

**(4) 최소한 알 것**

| 스키마 | 한 줄 해설 | 판정 |
|---|---|---|
| Article | 글/문서 페이지 표시 | 🟢 메인 |
| Organization | 운영 주체·로고 표시 | 🟢 메인 |
| WebSite | 사이트 검색창 등 | 🟢 메인 |
| FAQPage | 질문·답변 펼침 | ⚪ 넣지 않음 — 리치결과 폐지 |

!!! warning
    **시점성 정보 — 반드시 확인.** FAQ 리치결과는 2026-05-07부로 폐지된 것으로 알려져 있다(원본 기획서 기준). 검색 리치결과 정책은 자주 바뀌므로, 집필·적용 시점에 Google Search Central 공식 문서에서 날짜와 함께 재확인할 것. "FAQ 스키마 넣어줘"가 효과 0일 수 있다.

**(5) AI에게 이렇게 시켜라**

```text
Next.js 사이트에 구조화 데이터(JSON-LD)를 넣으려고 해.
1) Article, Organization, WebSite 스키마를 각 페이지/사이트에 맞게 넣어줘
2) FAQPage 스키마는 넣지 마. 그 이유(리치결과 지원 여부)를 2026년 기준으로
   Google 공식 문서에서 확인 가능한지, 아니면 네 추정인지 명시해줘
3) 네가 추천하는 스키마가 '지금도 검색 리치결과로 지원되는지'를
   각각 '공식문서 확인 가능 / 추정 / 시점에 따라 변동'으로 표시해줘
```

**(6) 흔한 함정 · AI가 틀리는 것**

!!! warning
    AI의 학습 데이터는 과거라서, 폐지된 **FAQPage 스키마를 여전히 추천**한다(2026 기준 틀린 조언). 또 존재하지 않거나 오타가 섞인 스키마 속성을 진짜처럼 적기도 한다. 구조화 데이터 정책은 검색엔진이 수시로 바꾸는 영역이라, AI의 단언을 그대로 믿으면 안 된다.

**(7) 검증하는 법**

1. Google의 Rich Results Test에 페이지 URL을 넣어 인식되는 스키마와 경고를 확인.
2. Search Console의 '리치결과' 보고서에서 실제로 어떤 유형이 잡히는지 본다.
3. 적용하려는 스키마가 현재 지원되는지 Google Search Central 공식 문서에서 날짜와 함께 확인.

**(8) 더 깊이**

- Google Search Central: 구조화 데이터 일반 가이드라인 (developers.google.com/search/docs/appearance/structured-data) — 1차 출처 (정책은 시점성 정보)
- schema.org 공식 어휘 사전 (schema.org) — 1차 출처
