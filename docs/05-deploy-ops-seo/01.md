# 로컬 → GitHub → Vercel: 코드가 세상에 나가는 길 (자동배포 파이프라인)

**(1) 한 줄 정의**

자동배포 파이프라인이란 내가 코드를 GitHub에 올리면(`git push`), 그 신호를 받아 Vercel이 자동으로 빌드 → 검증 → 배포까지 한 번에 돌리는 컨베이어 벨트다.

**(2) 왜 중요한가 (디렉터 관점)**

"배포"는 한 번 누르는 버튼이 아니라 매번 도는 자동 공정이다. 디렉터가 이 흐름을 모르면 "AI가 배포했다고 했는데 사이트는 옛날 그대로"인 상황에서 어디가 막혔는지 짚지 못한다. 빌드가 실패하면 새 버전이 안 올라갈 뿐, 이전 버전은 멀쩡히 살아 있다는 점을 알아야 "사이트가 안 죽었다"를 침착하게 확인할 수 있다.

**(3) 비유**

공장 컨베이어 벨트다. 원재료(코드)를 입구(`git push`)에 올리면, 검사대(빌드·테스트)를 통과한 것만 매장 진열대(라이브 사이트)에 오른다. 불량이면 벨트가 멈추고, 진열대엔 어제 팔던 정상 제품이 그대로 남는다.

**(4) 최소한 알 것**

- `git push` → GitHub → Vercel 자동 감지 → 빌드 → (성공 시) 배포, 이 4단계가 한 줄로 이어진다.
- 빌드 실패 시 새 버전은 게시되지 않고 직전 성공 버전이 라이브로 유지된다.
- 각 배포에는 고유 ID와 미리보기 URL이 생긴다.

**(5) AI에게 이렇게 시켜라**

```text
지금 GitHub 저장소가 Vercel과 어떻게 연결돼 자동배포되는지 단계별로 설명해줘.
1) git push부터 라이브 반영까지 거치는 단계를 순서대로
2) 빌드가 실패하면 라이브 사이트가 어떻게 되는지
3) 코딩 지식 없이 '이번 배포가 성공했는지' Vercel 대시보드에서 확인하는 절차를
클릭 순서로 알려줘. 추측이면 '추측'이라고 표시해.
```

**(6) 흔한 함정 · AI가 틀리는 것**

!!! warning
    AI는 "main에 push하면 배포돼요"까지만 말하고, **빌드 실패 시 이전 버전이 그대로 살아 있다**는 점을 강조하지 않는다. 그래서 초보 디렉터는 빌드가 깨진 줄도 모르고 "왜 반영이 안 되지?"라며 코드를 더 헤집는다. 또 AI는 빌드 로그를 읽어보라고 안내하기보다 추측으로 코드를 고치려 든다.

**(7) 검증하는 법**

1. Vercel 대시보드 → Deployments 탭을 연다.
2. 가장 최근 배포 상태가 Ready(초록)인지 Error(빨강)인지 본다.
3. 커밋 메시지·해시가 방금 올린 것과 일치하는지 확인한다.
4. 라이브 URL을 새로고침(캐시 무시)해 변경이 실제 반영됐는지 눈으로 본다.

**(8) 더 깊이**

- Vercel Deployments 공식 문서 (vercel.com/docs) — 1차 출처
- Git 공식 문서의 push 개념 (git-scm.com) — 1차 출처

!!! example "💡 예시로 이해하기"
    금요일 오후 5시, 디렉터가 AI에게 "메인 배너 문구 바꿔줘"라고 시키고 `git push`를 눌렀다. 1분 뒤 "배포 완료했어요"라는 답을 믿고 퇴근하려는데, 라이브 사이트는 옛날 문구 그대로다. Vercel 대시보드 Deployments 탭을 열어보니 맨 위 배포가 빨간 `Error` 상태 — 빌드 로그에 `Module not found: './Banner'`라는 한 줄이 떠 있다(AI가 파일명을 `banner`로 잘못 import).
    여기서 핵심: 새 버전은 안 올라갔지만 손님이 보는 사이트는 안 죽었다. 30분 전 초록 `Ready` 배포가 그대로 라이브로 살아 있기 때문이다. 디렉터는 당황해서 코드를 더 헤집을 게 아니라, "빌드가 깨졌고 이전 버전이 살아 있다"만 침착하게 확인하면 된다.
