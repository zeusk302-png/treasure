# 무너졌을 때 알아채기 — 모니터링·로그·에러추적과 즉시 롤백

**(1) 한 줄 정의**

모니터링은 사이트가 무너진 걸 '알아채는' 장치(Vercel 로그 + Sentry 같은 에러추적)이고, 롤백은 방금 올린 배포가 문제일 때 '직전 멀쩡한 버전으로 즉시 되돌리는' 복구 버튼이다.

**(2) 왜 중요한가 (디렉터 관점)**

상용 사이트의 차이는 '안 무너지는 것'이 아니라 '무너진 걸 빨리 알고 빨리 되돌리는 것'에 있다. 디렉터가 모니터링이 없으면 손님이 항의할 때까지 고장을 모른다. 또 "AI가 에러를 try/catch로 삼켜" 화면엔 멀쩡해 보이지만 기능은 죽은 '조용한 실패'를 알아챌 수 있어야 한다.

**(3) 비유**

가게에 화재경보기(에러추적)와 CCTV(로그)를 달아두는 일이다. 불이 나면 즉시 울려야지, 손님이 "타는 냄새 나요"라고 말해줄 때까지 모르면 늦다. 롤백은 "방금 바꾼 메뉴가 문제니 어제 메뉴로 즉시 되돌리기" 버튼이다.

**(4) 최소한 알 것**

| 도구 | 한 줄 해설 | 판정 |
|---|---|---|
| Vercel 로그 | 서버에서 무슨 일이 있었는지 기록 | 🟢 메인 |
| Sentry(에러추적) | 실제 사용자가 만난 에러를 모아 알림 | 🟡 대안/보강 |
| Instant Rollback | 직전 배포로 클릭 한 번에 복구 | 🟢 메인 |
| `git revert` 재배포 | 코드를 되돌려 다시 배포 | 🔵 나중/느린 복구 |

!!! tip
    Instant Rollback은 코드를 건드리지 않고 '이미 검증됐던 직전 배포'로 즉시 돌아간다. 급할 땐 git revert보다 이게 빠르고 안전하다.

**(5) AI에게 이렇게 시켜라**

```text
내 Next.js + Vercel 사이트에 모니터링과 롤백 체계를 갖추려고 해.
1) Vercel 로그에서 에러를 확인하는 방법
2) Sentry 같은 에러추적을 붙일 때, 에러를 try/catch로 '삼키지' 말고
   반드시 기록·알림이 가도록 하는 원칙
3) 방금 배포가 문제일 때 Vercel Instant Rollback으로 직전 버전으로
   되돌리는 클릭 절차 (git revert 재배포 말고 이것부터)
코딩 지식 없이 따라 할 수 있게 클릭 순서로 알려줘.
```

**(6) 흔한 함정 · AI가 틀리는 것**

!!! warning
    AI는 (1) 에러를 `try/catch`로 잡고 아무 기록 없이 넘겨 **조용한 실패**(화면은 멀쩡, 기능은 죽음)를 만들고, (2) 롤백을 'git revert 후 재배포'로만 안내해 빠른 Instant Rollback을 빠뜨린다. 또 "에러 없음"과 "의도대로 동작"을 구분하지 못한 채 "정상입니다"라고 보고한다.

!!! warning
    이 페이지의 '복구'는 코드/배포 되돌리기까지다. **삭제된 데이터를 어제 시점으로 되살리는 백업·복구는 별개 주제**이며, 데이터 백업이 없으면 운영 안전망은 반쪽이다(권5 보강 주제 A1로 별도 회수 권장).

**(7) 검증하는 법**

1. 일부러 에러를 발생시키는 테스트 페이지를 만들어, 그 에러가 Vercel 로그/Sentry에 실제로 잡히는지 확인.
2. 에러추적 대시보드에 알림이 오는지(이메일/슬랙) 확인.
3. 깨진 배포를 일부러 올린 뒤 Instant Rollback으로 직전 버전이 즉시 복구되는지 라이브로 확인.
