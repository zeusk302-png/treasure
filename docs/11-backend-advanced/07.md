# 캐싱 전략 — 무엇을 어디에 저장해 둘까

**① 한 줄 정의**
캐싱(caching)은 **한 번 만든 결과를 다음에 또 쓰려고 가까운 곳에 잠깐 보관**해, 같은 일을 매번 다시 하지 않게 만드는 기술입니다.

**② 왜 중요한가 (디렉터 관점)**
"사이트가 느려요"의 해법은 대부분 둘 중 하나입니다. **(1) 일을 더 빨리 하거나, (2) 일을 아예 안 하거나.** 캐싱은 두 번째, 즉 "이미 한 일은 두 번 하지 마"입니다. 코드를 한 줄도 안 고치고도 응답 속도가 몇 배 빨라지고, 서버·DB가 받는 부하가 확 줄어 비용까지 내려갑니다. 그래서 캐싱은 디렉터가 AI에게 "성능을 개선해줘"라고 막연히 시키기 전에 **"이 결과는 캐시할 수 있는 종류인가?"를 먼저 판단하는 무기**입니다.

동시에 캐싱은 **양날의 검**입니다. 잘못 쓰면 "분명히 고쳤는데 화면엔 옛날 게 그대로 떠요" "A 사용자가 B 사용자의 정보를 봐요" 같은 무서운 버그를 만듭니다. 디렉터의 진짜 역할은 캐시를 *켜는 것*이 아니라, **무엇을·어디에·얼마나 오래 저장할지, 그리고 언제 비울지**를 결정하고, AI가 만든 캐싱이 그 결정과 맞는지 검증하는 것입니다. 컴퓨터과학에 "정말 어려운 건 두 가지뿐 — 캐시 무효화와 이름 짓기"라는 농담이 괜히 있는 게 아닙니다.

**③ 비유**
캐시는 **자주 쓰는 물건을 책상 위에 꺼내 두는 것**입니다. 매번 창고(DB)까지 걸어가 가져오면 느리니, 오늘 쓸 것들은 손 닿는 책상 위(메모리)에 올려둡니다. 빠르지만 책상은 좁아서(용량이 작아서) 다 못 올리고, 책상에 둔 게 **창고의 진짜 내용과 어긋날 수 있다**는 게 함정입니다. 누가 창고의 재고를 바꿨는데 책상 위 메모지는 옛 숫자 그대로라면, 그 메모지를 보고 일하면 틀립니다.

계층은 **편의점 vs 동네마트 vs 대형 물류창고**로도 그려집니다. 집 앞 편의점(브라우저 캐시)에 있으면 1초, 동네마트(CDN)면 1분, 멀리 물류창고(원본 서버·DB)까지 가면 1시간. 같은 물건이라면 당연히 가장 가까운 데서 꺼내 씁니다. 캐싱 전략이란 **"이 물건을 어느 단계까지 미리 깔아둘까"를 정하는 일**입니다.

**④ 최소한 알 것**

캐시는 한 군데가 아니라 **여러 계층(layer)**에 겹겹이 깔립니다. 요청이 사용자 → 서버로 가는 길목마다 "혹시 답 가지고 있어?"를 물어보고, 가진 데가 있으면 거기서 끝납니다.

| 계층 | 어디에 있나 | 무엇을 캐시 | 누가 제어 | 주의점 |
|---|---|---|---|---|
| 브라우저 캐시 | 사용자 PC·폰 | 이미지·CSS·JS·API 응답 | `Cache-Control` 헤더 | 한 번 잘못 캐시되면 사용자별로 안 지워짐 |
| CDN | 전 세계 엣지 서버 | 정적 파일, 공개 페이지 | 헤더·revalidate 설정 | 사용자 맞춤 데이터 캐시하면 정보 유출 위험 |
| 서버 메모리 | 그 서버 1대 안 | 자주 쓰는 계산 결과 | 코드(변수·맵) | 서버 여러 대면 캐시가 제각각·재시작 시 사라짐 |
| 외부 캐시(Redis 등) | 별도 캐시 서버 | 세션·집계·조회 결과 | 코드 + TTL | 운영·연결 관리 필요(→ 13권 연동에서 실습) |
| DB 자체 캐시 | 데이터베이스 안 | 쿼리 결과 등 | DB가 자동 | 우리가 직접 손대는 일은 드묾 |

핵심 용어 몇 가지:

- **TTL(Time To Live)** — "이 캐시는 N초/분/시간만 유효" 하는 유통기한. 지나면 자동으로 버리고 원본에서 새로 가져옵니다.
- **캐시 적중(hit) / 빗나감(miss)** — 캐시에 답이 있어 바로 준 게 hit, 없어서 원본까지 다녀온 게 miss. **적중률(hit rate)**이 캐싱이 잘 되는지의 점수표입니다.
- **무효화(invalidation)** — 원본이 바뀌었으니 낡은 캐시를 버리는 것. 캐싱에서 **가장 어려운 부분**.
- **TTL 만료 vs 능동 무효화** — 그냥 시간 지나길 기다릴지(간단·약간 낡을 수 있음), 데이터가 바뀌는 순간 캐시를 직접 지울지(정확·복잡).

캐시해도 되는 것 / 안 되는 것 판단 기준(디렉터 체크리스트):

- 🟢 **캐시 적극 추천** — 잘 안 바뀌고, 모두에게 같고, 무거운 것(공개 게시글 목록, 인기글 집계, 환율·날씨, 이미지·폰트).
- 🟡 **짧은 TTL로 캐시** — 자주 보지만 약간 낡아도 되는 것(메인 피드, 조회수).
- 🔵 **사용자별로 나눠서만** — 사람마다 다른 것(장바구니, 내 알림). 키에 사용자 ID를 꼭 포함.
- ⚪ **캐시 금지** — 항상 최신·민감해야 하는 것(잔액, 결제 직전 가격, 권한 판정). 캐시했다간 큰 사고.

**⑤ AI에게 이렇게 시켜라**

```text
[맥락] 나는 Next.js + Supabase로 만든 커뮤니티 사이트를 운영해.
'인기글 목록' API가 매 요청마다 DB에서 무거운 집계 쿼리를 돌려서 느려.
이 데이터는 모든 사용자에게 똑같고, 5분쯤 낡아도 괜찮아.

[요청] 캐싱을 도입하고 싶은데, 먼저 코드부터 짜지 말고 아래 순서로 안내해줘.
1) 이 데이터를 '어느 계층(브라우저 / CDN / 서버 메모리 / Redis)'에
   캐시하는 게 맞는지, 각 선택의 장단점을 비전공자도 알게 비교.
2) 추천 TTL과 그 이유.
3) 가장 무서운 함정인 '캐시 무효화'를 어떻게 처리할지
   (그냥 TTL 만료를 기다릴지 / 글이 등록되는 순간 캐시를 비울지) 옵션 제시.
4) 그다음에야 추천안의 코드를 주되, 각 줄에 '왜 이렇게 했는지' 주석을 한국어로.

[제약]
- 사용자마다 다른 데이터(내 알림, 장바구니)는 절대 한 덩어리로 캐시하지 마.
- 잔액·결제 가격처럼 항상 최신이어야 하는 값은 캐시 후보에서 제외해.
- 캐시 키에 무엇을 넣어야 사용자끼리 데이터가 안 섞이는지 설명해줘.
```

> 팁: 막연히 "캐시 적용해줘"라고 하면 AI는 가장 흔한 코드를 던지고 무효화를 통째로 빠뜨립니다. **"무엇을·어디에·얼마나·언제 비울지" 네 가지를 질문에 박아 넣는 것**이 디렉터의 핵심 기술입니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **무효화를 빼먹는다.** AI는 "캐시 넣기"는 잘하지만 "낡으면 비우기"는 자주 빠뜨립니다. 그 결과가 그 유명한 **"배포했는데 옛 화면이 계속 떠요"**(5권에서 다루는 단골 사고). 캐시를 켰다면 *반드시* "이건 언제 비워지나?"를 되물으세요.
- **사용자별 데이터를 공용으로 캐시한다.** 캐시 키에 사용자 ID를 안 넣어, **A의 장바구니·알림·이름이 B에게 보이는** 심각한 정보 유출. CDN에 로그인 사용자 맞춤 페이지를 통째로 캐시하면 같은 사고가 더 크게 납니다.
- **민감/실시간 값을 캐시한다.** 잔액, 재고 수량, 결제 직전 가격, 권한 판정 결과를 캐시했다가 "돈은 빠졌는데 잔액은 그대로" 같은 사고.
- **TTL을 무한이나 0으로 둔다.** 너무 길면 영영 안 바뀌고, 0이면 캐시한 의미가 없습니다. AI가 제안한 TTL이 데이터 성격과 맞는지 사람이 판단해야 합니다.
- **서버 메모리 캐시를 서버 여러 대 환경에서 믿는다.** 서버가 2대면 캐시도 2개라 사용자마다 다른 답을 봅니다. Vercel 같은 서버리스는 함수가 매번 새로 떠서 메모리 캐시가 잘 안 남습니다 — 이럴 때 **공유 캐시(Redis)**가 필요해지고, 그 연동을 **13권**에서 다룹니다.
- **캐시를 "지웠다"고 착각.** 브라우저·CDN은 한 번 잘못 캐시되면 사용자 쪽에서 안 지워지는 경우가 많습니다. 파일 이름에 버전을 붙이는 식(`app.v2.js`)으로 우회한다는 점을 모르고 "캐시 비웠으니 됐다"고 넘어갑니다.

!!! warning "보안 한 줄"
    캐시는 **데이터를 복제해 여러 곳에 흩뿌리는 일**입니다. 따라서 "누가 봐도 되는 데이터인가?"가 캐시 가능 여부의 1순위 질문입니다. 공개 데이터만, 또는 사용자별로 키를 분리해서만 캐시하세요. (참고: Supabase의 anon 키는 브라우저에 노출돼도 되는 공개 키이고 보호는 RLS로 합니다 — 캐시 여부와 별개로 데이터 보호는 RLS가 책임집니다.)

**⑦ 검증하는 법**

1. **속도로 확인** — 같은 페이지/API를 **연속 두 번** 호출해 봅니다. 두 번째가 눈에 띄게 빠르면(첫 호출은 miss, 두 번째는 hit) 캐시가 동작하는 신호입니다. F12 → **Network 탭**에서 응답 시간과 `Cache-Control`·`X-Cache`(또는 `age`) 헤더를 확인하세요.
2. **무효화로 확인(가장 중요)** — 원본 데이터를 일부러 바꾼 뒤, **TTL 안에서는 옛 값, TTL이 지나면(또는 비운 직후) 새 값**이 뜨는지 봅니다. "고쳤는데 영영 안 바뀐다"면 무효화가 빠진 것입니다.
3. **사용자 섞임 점검** — 서로 다른 두 계정(또는 시크릿 창)으로 같은 화면을 열어, **개인 정보가 절대 안 섞이는지** 확인합니다. 장바구니·알림·이름이 상대 것으로 보이면 캐시 키 분리 실패입니다.
4. **민감값 제외 확인** — 잔액·가격처럼 최신이어야 할 값이 캐시에 걸리지 않았는지, 바꾼 즉시 반영되는지 봅니다.

!!! example "💡 예시로 이해하기"
    당신의 커뮤니티 사이트 메인에 "오늘의 인기글 TOP 10"이 있습니다. 이걸 띄우려면 DB가 수천 개 글의 조회수·좋아요를 한꺼번에 세는 무거운 계산을 합니다. 처음엔 방문자 한 명이 들어올 때마다 이 계산을 매번 다시 돌려서, 사람이 몰리는 저녁이면 사이트가 버벅였습니다. 디렉터인 당신은 묻습니다. "이 목록은 **모두에게 같고**, **1~2분 낡아도 아무도 모른다**. 그럼 매번 셀 필요가 없잖아?" 그래서 결과를 **TTL 2분짜리 캐시**에 올려둡니다. 이제 2분 동안 들어온 수백 명은 DB를 한 번도 안 건드리고 **책상 위 메모지(캐시)**를 그대로 봅니다 — 첫 한 명만 창고에 다녀오고 나머지는 즉답. 단, 누군가 새 글을 올려 순위가 확 바뀌어도 최대 2분은 옛 순위가 보일 수 있죠. 당신은 이게 괜찮은 거래라고 판단합니다(인기글은 2분 늦어도 무방). 반면 같은 사이트의 "내 포인트 잔액"은? "사람마다 다르고, 1초도 낡으면 안 된다"이니 **캐시 후보에서 빼**고 항상 DB에서 직접 읽게 둡니다. 캐싱 전략이란 결국 이렇게 **데이터 하나하나를 두고 '캐시해도 되나 / 얼마나 / 언제 비우나'를 판정하는 안목**입니다.
