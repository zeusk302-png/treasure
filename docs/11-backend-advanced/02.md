# REST API 설계 — 자원·메서드·상태코드

**① 한 줄 정의**
REST API는 **"무엇(자원)을 URL 명사로, 무엇을 한다(동작)를 HTTP 메서드 동사로"** 일관되게 표현하는 서버 사용 설명서이고, 서버는 그 결과를 **상태코드(숫자 신호)**로 돌려줍니다.

**② 왜 중요한가 (디렉터 관점)**
디렉터는 화면(프론트)과 데이터(백엔드)를 잇는 **계약서**가 깔끔한지를 봐야 합니다. API가 잘 설계돼 있으면 "글 목록 가져와"는 `GET /posts`, "3번 글 지워"는 `DELETE /posts/3`처럼 **AI에게 시킬 말이 곧 주소가 됩니다.** 반대로 설계가 엉성하면(`GET /getPostsAndDeleteOld?id=3` 같은) 한 엔드포인트가 여러 일을 섞어 하게 되고, AI도 사람도 "이걸 부르면 무슨 일이 나는지" 예측할 수 없습니다. 게다가 우리가 부트캠프에서 쓰는 **Supabase가 내부적으로 주는 게 사실상 REST API(PostgREST)** 입니다. 테이블 `posts`를 만들면 `/rest/v1/posts`라는 주소가 자동으로 생깁니다. 그래서 REST의 문법을 알면, AI가 짜준 API 코드를 읽고 "이건 규칙을 지킨 설계인가, 나중에 터질 설계인가"를 **눈으로 판별**할 수 있습니다. 코드를 못 짜도, 계약서가 잘 쓰였는지는 읽을 수 있어야 디렉터입니다.

**③ 비유**
잘 만든 **레스토랑 메뉴판**과 같습니다. 메뉴 항목(자원)은 명사로 적혀 있습니다 — `주문(/orders)`, `손님(/customers)`, `테이블(/tables)`. 손님이 하는 행동(메서드)은 정해진 동사뿐입니다 — **보여줘(GET), 새로 만들어(POST), 통째로 바꿔(PUT), 일부만 고쳐(PATCH), 지워(DELETE)**. 손님은 주방이 어떻게 돌아가는지 전혀 몰라도, "3번 테이블 주문 보여주세요(GET /tables/3/orders)"를 정확히 전달할 수 있습니다. 주방(서버)은 일을 처리한 뒤 **불빛으로 답합니다** — 초록불(2xx, 잘 됐어요), 노란불(4xx, 손님이 주문을 잘못 했어요), 빨간불(5xx, 주방에 불이 났어요). 메뉴판이 일관되면 손님도 종업원도 헷갈리지 않습니다. REST는 이 메뉴판을 일관되게 쓰는 약속입니다.

**④ 최소한 알 것**

**HTTP 메서드 (동사 — "무엇을 할까")**

| 메서드 | 의미 | 메뉴판 비유 | 멱등성* |
|---|---|---|---|
| GET | 조회(읽기만, 변화 없음) | "보여줘" | 예 (몇 번 봐도 그대로) |
| POST | 새로 생성 | "새로 만들어" | 아니오 (두 번 누르면 두 개 생김) |
| PUT | 통째로 교체 | "이걸로 전부 바꿔" | 예 (같은 걸로 덮으면 결과 같음) |
| PATCH | 일부만 수정 | "이 부분만 고쳐" | 보통 예 (설계에 따라) |
| DELETE | 삭제 | "지워" | 예 (이미 지운 걸 또 지워도 결과 같음) |

> *멱등성(idempotency): **같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질.** 네트워크가 끊겨 "보냈나? 다시 보내자" 할 때 안전한지를 가릅니다. POST(생성)는 멱등이 아니라서 결제 "결제하기" 버튼 중복 클릭이 위험한 것입니다.

**자원 중심 URL (명사로, 계층으로)**

- 좋은 예: `/posts`(글 목록), `/posts/3`(3번 글), `/posts/3/comments`(3번 글의 댓글들)
- 나쁜 예: `/getPosts`, `/createPost`, `/deletePostById?id=3` — **동사를 URL에 넣지 않습니다.** 동사는 메서드가 담당합니다.
- 복수형 명사를 권장: `/users`(여러 명), `/users/42`(그중 42번).

**상태코드 (서버의 신호등 — "어떻게 됐어")**

| 무리 | 뜻 | 대표 코드 | 누구 책임? |
|---|---|---|---|
| 2xx | 성공 | 200(OK), 201(생성됨), 204(됐는데 보낼 내용 없음) | — |
| 4xx | 요청한 쪽 잘못 | 400(형식 틀림), 401(로그인 안 함), 403(권한 없음), 404(없는 주소), 422(검증 실패), 429(너무 자주 부름) | **클라이언트(내가 보낸 것)** |
| 5xx | 서버 쪽 잘못 | 500(서버 터짐), 502/503/504(게이트웨이·과부하·시간초과) | **서버(받는 쪽)** |

핵심 갈림: **4xx면 "내가 보낸 주소·데이터"를 먼저 의심**, **5xx면 "서버·배포·환경변수 로그"를 먼저** 봅니다.

**버전과 페이지네이션 (오래 가는 API의 표식)**

- **버전**: 주소에 버전을 박습니다 — `/v1/posts`, `/v2/posts`. 이미 그 API를 쓰는 앱이 있는데 모양을 바꾸면 다 깨지므로, **옛 버전은 살려두고 새 버전을 따로** 냅니다.
- **페이지네이션**: 글이 1만 개인데 한 번에 다 주면 느리고 무겁습니다. **나눠서** 줍니다 — `?page=2&limit=20`(2페이지, 20개씩) 또는 `?cursor=abc&limit=20`(커서 방식). 응답에 "전체 몇 개, 다음 페이지 있음" 같은 정보를 함께 담는 게 좋은 설계입니다.

**잘 설계된 API의 표식 (체크리스트)**

- URL이 **명사**다(동사가 안 보인다).
- 같은 일은 항상 **같은 메서드**다(삭제는 늘 DELETE).
- 상태코드가 **정직**하다(실패인데 200을 주지 않는다).
- 응답이 **예측 가능한 모양**(JSON 구조)이고 에러도 일정한 형식이다.
- 목록은 **페이지네이션**이 있고, 변경에 대비한 **버전**이 있다.

**⑤ AI에게 이렇게 시켜라**

```text
블로그용 백엔드 API를 REST 원칙에 맞게 설계해줘. 다음을 표로 정리해줘:
- 자원: 글(posts), 댓글(comments)
- 각 자원에 대해 'CRUD 동작 → HTTP 메서드 + URL + 성공 상태코드'를 한 줄씩
- URL은 동사를 넣지 말고 명사·계층 구조로(예: /posts/3/comments)
- 목록 조회에는 페이지네이션(page, limit) 쿼리 파라미터를 포함
- 실패 상황(없는 글 조회, 검증 실패, 권한 없음)에 각각 어떤 상태코드를
  돌려줘야 하는지와 그 이유도 적어줘
규칙을 어긴 흔한 안티패턴(예: GET /deletePost?id=3)이 왜 나쁜지도 한 줄씩 알려줘.
코드보다 '설계 표'를 먼저 보여주고, 내가 OK하면 그때 코드를 짜줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **동사를 URL에 박는 비-RESTful 설계**: `GET /getPost`, `POST /deletePost` 같은 코드를 아무렇지 않게 내놓습니다. 동작은 메서드가, 자원은 URL이 담당해야 합니다.
- **상태코드를 거짓말로**: 에러가 났는데 `200 OK`에 `{"error": "..."}`를 담아 보내는 설계. 프론트가 "성공했네" 하고 넘어가 버립니다. **실패는 4xx/5xx로 정직하게** 줘야 합니다.
- **404 만능 처방**: AI는 404를 "페이지가 없다"로만 봅니다. 실제로는 주소 오타·배포 누락·API 경로 틀림·라우팅 설정 모두 404가 됩니다. 500도 코드만 의심하지만 Supabase 연결 끊김·환경변수 누락·외부 서비스 장애도 500입니다.
- **모든 API를 REST로 착각**: REST가 흔할 뿐 전부는 아닙니다. GraphQL·RPC·tRPC도 많습니다. "API = REST"라고 단정하면 의심하세요.
- **인증을 설계에서 빠뜨림**: `DELETE /posts/3`을 만들면서 "누구나 부를 수 있는지"를 안 따지면, 남이 내 글을 지웁니다. **누가 부를 수 있는가는 설계의 일부**입니다(→ 인증/인가는 03.md, 보안은 08.md).
- **PUT과 PATCH 혼동**: PUT은 통째 교체(빠진 필드는 비워짐), PATCH는 일부만 수정. 닉네임만 바꾸려고 PUT을 쓰면 다른 필드가 날아갈 수 있습니다.

**⑦ 검증하는 법**

- **브라우저 F12 → Network 탭**을 열고 사이트를 조작해 보세요. 각 요청의 **Method(GET/POST/…)와 Status(200/404/…)**가 줄줄이 찍힙니다. "글 삭제" 버튼을 눌렀을 때 정말 `DELETE`가 나가고 `200`/`204`가 오는지, 아니면 엉뚱하게 `GET`이 나가는지 눈으로 확인합니다.
- **상태코드로 책임 가르기 연습**: 빨간 줄(실패)을 보고 4xx면 "내가 보낸 주소·데이터"부터, 5xx면 "서버·로그"부터 봅니다.
- **AI에게 자기 설계를 채점시키기**: "방금 만든 API 표를 REST 체크리스트(URL 명사인가·메서드 일관·상태코드 정직·페이지네이션·버전)로 스스로 채점하고, 어긴 항목이 있으면 고쳐줘."
- Supabase를 쓴다면, 테이블 하나에 대해 자동 생성된 `/rest/v1/<테이블>` 주소를 호출해 보고, GET이 행 목록을 JSON으로 주는지 확인합니다(이때 anon 키는 브라우저에 노출돼도 되는 **공개 키**이고, 진짜 보호는 RLS로 합니다 — service_role 키는 절대 프론트에 두지 않습니다).

!!! example "💡 예시로 이해하기"
    중고거래 앱을 만든다고 해봅시다. 자원은 "상품(products)"입니다. 디렉터는 메뉴판을 이렇게 그립니다 — 목록 보기는 `GET /products?page=1&limit=20`(첫 페이지 20개), 자세히 보기는 `GET /products/15`, 새 상품 올리기는 `POST /products`(성공하면 `201 생성됨`), 가격만 내리기는 `PATCH /products/15`(통째 교체인 PUT이 아니라 일부만!), 팔려서 내리기는 `DELETE /products/15`(성공하면 `204`). 어느 날 친구가 "내 상품이 안 지워져요!"라고 합니다. F12 Network 탭을 같이 열어 보니 삭제 버튼이 `DELETE /products/15`를 보냈고 응답은 `403`. 4xx니까 서버 잘못이 아니라 **요청한 쪽 문제** — 그것도 403은 "로그인은 했는데 권한이 없다"는 뜻입니다. 알고 보니 남의 상품을 지우려 한 것이었죠. "안 지워져요"라는 한 덩어리가 `DELETE에 403 = 내 상품이 아니라서 막힌 것`이라는 한 문장으로 좁혀지는 순간, 고칠 곳이 분명해집니다.
