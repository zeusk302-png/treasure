# 서버란 무엇인가 — 요청을 받아 응답하는 기계

**① 한 줄 정의**
서버는 **누군가의 요청을 받아(request) → 그 일을 처리하고(process) → 결과를 돌려주는(response)** 일을 끝없이 반복하는 프로그램입니다. 거창한 기계가 아니라, "물어보면 답하는 창구"가 항상 켜져 있는 상태입니다.

**② 왜 중요한가 (디렉터 관점)**
02권에서 "손님(브라우저)과 주방(서버)"을 배웠다면, 이 권은 그 **주방 안으로 들어가는 문**입니다. 비전공 디렉터에게 서버가 중요한 이유는 딱 하나입니다 — **"이 일은 브라우저에서 해도 되는 일인가, 서버에서 해야만 하는 일인가"를 판단**할 줄 알아야 AI에게 올바른 설계를 시킬 수 있기 때문입니다. 이 판단을 못 하면 AI는 비밀 API 키를 브라우저 코드에 박아 넣거나(누구나 훔쳐볼 수 있음), 결제 금액 계산을 손님이 조작할 수 있는 곳에 두는(가격을 0원으로 바꿔치기 가능) 설계를 천연덕스럽게 내놓습니다. 디렉터는 코드를 짜지 않아도 **"그건 서버에서 해"** 한마디로 이런 사고를 막는 사람입니다. 또 하나 — "서버가 죽었어요"와 "서버 코드에 버그가 있어요"와 "서버를 아예 안 띄웠어요"는 완전히 다른 문제인데, 셋을 구분할 줄 알면 AI에게 던지는 질문이 정확해지고 답도 정확해집니다.

**③ 비유**
서버는 **24시간 영업하는 안내데스크 직원**입니다. 손님(브라우저)이 와서 "3번 자료 주세요"라고 쪽지(요청)를 내밀면, 직원은 창고에서 찾아오거나(데이터베이스 조회) 계산을 하거나(처리) 해서 결과를 쪽지에 적어 돌려줍니다(응답). 중요한 건 이 직원이 **자리를 비우면 안 된다**는 점입니다. 손님은 언제 올지 모르니까요. 그리고 직원이 일하려면 **데스크와 전기**가 필요한데, 이게 바로 뒤에 나올 '런타임'입니다. 안내데스크 자체(서버 코드)는 매뉴얼일 뿐이고, 그 매뉴얼을 읽고 실제로 손님을 응대할 **사람(런타임)**이 있어야 비로소 창구가 열립니다.

**④ 최소한 알 것**

서버의 본질은 단순한 한 줄 루프입니다: **"요청 올 때까지 기다린다 → 받으면 처리한다 → 답을 보낸다 → 다시 기다린다"**. 이걸 누가, 어떻게 켜 두느냐가 갈래입니다.

| 용어 | 쉬운 뜻 | 디렉터가 기억할 것 |
|---|---|---|
| 요청 (request) | 손님이 보낸 "이거 해줘" 쪽지 | 누가 보냈는지·무엇을 원하는지 담겨 있음 |
| 처리 (process) | 서버가 실제로 하는 일 | 계산·DB 조회·외부 API 호출 등 |
| 응답 (response) | 서버가 돌려주는 결과 | 상태코드(200/404/500) + 내용 |
| 런타임 (runtime) | 서버 코드를 실제로 '돌리는' 엔진 | 코드(매뉴얼)와 별개. 없으면 코드는 그냥 글자 |
| Node.js | 자바스크립트를 서버에서 돌리는 런타임 | "브라우저 밖에서 JS 실행" |

**런타임을 한 번 더 쉽게**: 코드는 `.js` 파일에 적힌 **글자**일 뿐입니다. 이 글자를 읽어서 실제로 컴퓨터를 움직이게 하는 **재생기**가 런타임입니다. 음악으로 치면 악보(코드)와 연주자/스피커(런타임)의 관계입니다. 같은 악보라도 연주자가 없으면 소리가 안 납니다.

- 🟢 **Node.js** — 바이브코딩에서 가장 흔히 만나는 서버 런타임. 자바스크립트를 서버에서 실행. Next.js·Vercel이 다 이 위에서 돕니다. *(버전은 LTS 사용 권장 — 현재 LTS가 무엇인지는 확인 권장)*
- 🟡 **Python / Deno / Bun** — 대안 런타임. Python은 AI·데이터 쪽에서 많이 씀.
- 🔵 **PHP / Ruby / Go / Java** — 회사·레거시에서 만날 수 있음. 지금 당장은 몰라도 됨.

이제 핵심 갈림길 — **상시 서버 vs 서버리스(함수)**:

| 구분 | 상시 서버 (always-on) | 서버리스 함수 (serverless) |
|---|---|---|
| 비유 | 24시간 불 켜진 가게(직원 상주) | 손님이 벨 누르면 그때 직원 출근 |
| 켜져 있나 | 항상 켜져 있음 | 요청 올 때만 잠깐 깸 |
| 비용 | 안 써도 24시간치 임대료 | 실제 처리한 만큼만(쓴 만큼 과금) |
| 콜드 스타트 | 거의 없음(이미 깨어 있음) | 첫 요청 때 잠깐 굼뜸(직원이 출근하는 시간) |
| 항상 도는 작업 | 가능(예: 24시간 감시·소켓 연결) | 어려움(요청 끝나면 잠듦) |
| 대표 예 | 직접 띄운 EC2·임대 서버 | Vercel 함수, AWS Lambda, Supabase Edge Functions |

비전공 디렉터의 기본값은 **🟢 서버리스(함수)**입니다. Vercel에 Next.js를 올리면 여러분의 백엔드 코드는 자동으로 "요청 올 때만 깨는 함수"로 돕니다. 따로 서버를 켜 두고 관리(재시작·보안패치·모니터링)할 필요가 없어 초보에게 압도적으로 편합니다.

**언제 직접(상시) 서버가 필요한가** — 아래에 해당할 때만 고민하세요:
- **항상 켜져 있어야 하는 연결**: 실시간 채팅의 WebSocket, 게임 서버처럼 손님과 계속 줄을 잡고 있어야 할 때.
- **오래 걸리는 작업**: 서버리스 함수는 보통 실행 시간 제한이 있습니다(예: 수십 초~몇 분, 플랫폼·요금제별 상이 — 확인 권장). 5분짜리 영상 변환을 한 함수 안에서 끝내려 하면 시간 초과로 죽습니다. → 이런 일은 06권의 '큐'로 쪼개거나 별도 서버로.
- **무거운 상시 백그라운드 작업**: 1초마다 센서를 읽는 등 쉴 새 없이 도는 일.

대부분의 청년 프로젝트(포트폴리오·소상공인 사이트·간단한 SaaS)는 **서버리스 + BaaS(예: Supabase)** 조합으로 직접 서버 없이 충분합니다. 이 갈림길은 09권에서 더 깊이 다룹니다.

**⑤ AI에게 이렇게 시켜라**

```text
나는 비전공자고 Next.js를 Vercel에 올려서 운영할 거야. 다음 기능들을 만들 건데,
각 기능이 "브라우저(클라이언트)에서 해야 할 일"인지 "서버에서 해야 할 일"인지
표로 분류해줘. 그리고 서버에서 해야 하는 것 중에서, Vercel 서버리스 함수로
충분한 것과 '상시 서버가 필요할 수 있는 것'을 따로 표시해줘.

기능 목록:
1) 외부 결제 API 호출(비밀 키 사용)
2) 사용자가 입력한 글 화면에 보여주기
3) 실시간 채팅(메시지가 바로바로 보여야 함)
4) 업로드한 이미지 1장 썸네일로 줄이기
5) 매일 새벽 3시에 데이터 백업

분류 이유도 한 줄씩 비전공자가 이해하게 설명하고,
비밀 키는 절대 브라우저 코드에 넣으면 안 되는 이유를 강조해줘.
```

이렇게 시키면 AI가 막연히 코드부터 쏟아내는 대신, **"무엇을 어디서 처리할지"라는 설계 판단**을 먼저 내놓습니다. 디렉터가 검토할 거리가 생깁니다.

**⑥ 흔한 함정 / AI가 틀리는 것**
- **비밀 키를 클라이언트에 박는다.** AI는 "결제 API 호출"을 손쉽게 브라우저 코드에 넣어버리곤 합니다. 브라우저 코드는 누구나 F12로 들여다볼 수 있으니 비밀 키가 통째로 새어 나갑니다. **비밀 키를 쓰는 일은 반드시 서버**에서. (Supabase로 치면 `service_role` 키는 절대 브라우저로 내보내지 말 것 — 이건 서버 전용 비밀입니다. 반대로 `anon` 키는 **공개돼도 되는** 키이고, 보호는 RLS(행 수준 보안)로 합니다. "anon=비밀키"라는 설명은 틀립니다.)
- **상시 서버를 당연한 듯 전제한다.** AI가 "서버를 24시간 켜 두고 cron으로…"처럼 전통 서버 기준으로 설명하면서, 여러분이 쓰는 Vercel은 **서버리스라 24시간 켜진 서버가 없다**(콜드 스타트·실행시간 제한)는 사실을 빼먹는 경우가 잦습니다.
- **세 가지 '서버 문제'를 뭉뚱그린다.** "서버가 죽었다(런타임 다운)" vs "서버 코드 버그로 500 에러" vs "서버를 아예 배포 안 함"은 원인도 해결도 다른데 AI가 한 덩어리로 답하기 쉽습니다.
- **실행시간·콜드 스타트를 무시한 설계.** 영상 변환·대량 메일 발송 같은 오래 걸리는 일을 함수 하나에 몰아넣어 "왜 타임아웃이 나죠?"가 됩니다.
- **사용자 입력을 그대로 화면에 꽂는다.** 서버가 돌려준 사용자 입력을 `innerHTML`로 출력하면 XSS 위험. 출력은 기본 `textContent`.

**⑦ 검증하는 법**
1. **요청→응답이 실제로 도는가**: 브라우저 F12 → Network 탭을 열고 기능을 실행해 봅니다. 서버를 부르는 요청이 찍히고, 상태코드가 `200`이면 정상. `404`면 그 경로(주소)가 없는 것, `500`이면 서버 코드가 처리 중 터진 것, 요청 자체가 안 찍히면 애초에 서버를 안 부른 것(앞단 문제).
2. **비밀이 새지 않는가**: F12 → Sources(또는 페이지 소스 보기)에서 비밀 키 문자열(`service_role`, `sk_live_` 등)을 검색해 봅니다. **하나라도 보이면 즉시 폐기·재발급.** 브라우저로 나가는 코드엔 비밀이 없어야 합니다.
3. **콜드 스타트 체감**: 한동안 안 쓰던 서버리스 기능을 처음 호출하면 첫 응답이 살짝 느린지(콜드 스타트), 두 번째부터 빨라지는지 봅니다. 정상 현상이지 버그가 아닙니다.
4. **AI에게 분류를 되물어 확인**: "방금 만든 코드 중 비밀 키를 쓰는 부분이 클라이언트에 있는지 서버에 있는지 표로 보여줘"라고 시켜 교차 점검.

!!! example "💡 예시로 이해하기"
    여러분이 만든 동네 꽃집 예약 사이트가 있다고 해봅시다. 손님이 "토요일 오전 꽃다발 예약" 버튼을 누르면, 브라우저는 서버에 "이 손님이 토요일 오전을 예약하고 싶대요"라는 **쪽지(요청)**를 보냅니다. 서버는 ① 그 시간이 비었는지 데이터베이스를 확인하고(처리) ② 결제 회사에 "3만원 받아주세요"라고 **비밀 키를 써서** 대신 요청한 뒤 ③ "예약 완료, 번호 17번"이라는 **답(응답, 상태코드 200)**을 돌려줍니다. 여기서 결제 비밀 키를 브라우저에 뒀다면? 손님이 F12로 키를 빼내 가게 통장을 마음대로 긁을 수 있습니다. 그래서 결제 호출은 **서버에서만** 합니다. 그리고 이 꽃집은 손님이 24시간 몰려드는 곳이 아니니 **상시 서버를 켜 둘 필요 없이**, "예약 버튼이 눌릴 때만 잠깐 깨는" 서버리스 함수로 충분합니다. 다만 "매일 새벽 3시 예약 현황을 사장님께 문자로" 같은 정기 작업은 함수 하나로 계속 돌리기보다 예약(스케줄)·큐로 따로 빼는 게 안전합니다. 디렉터의 일은 이 한 문장입니다 — **"이건 손님 손이 닿는 브라우저에, 저건 닫힌 주방인 서버에."**
