# API 보안과 레이트리밋 — 남용을 막기

**① 한 줄 정의**
API 보안은 **"누가, 얼마나, 어떤 입력으로 우리 서버를 부를 수 있는가"에 선을 긋는 일**입니다 — 레이트리밋(횟수 제한), CORS(어느 사이트에서 부를 수 있나), 시크릿 관리(비밀 키 숨기기), 인젝션 방어(나쁜 입력 막기), 최소권한(딱 필요한 권한만)이 그 다섯 개의 자물쇠입니다.

**② 왜 중요한가 (디렉터 관점)**
API는 식당으로 치면 **손님이 직접 주방에 대고 외치는 주문 창구**입니다. 화면(프론트엔드)은 예쁘게 꾸민 손님용 메뉴판일 뿐이고, 진짜 음식과 돈과 데이터는 전부 그 창구 뒤에서 오갑니다. 그래서 공격자는 절대 메뉴판을 공격하지 않습니다. 메뉴판을 무시하고 **창구에 직접 대고 외칩니다** — "회원 전체 이메일 다 내놔", "같은 요청 1초에 1만 번", "이름 칸에 `'; DROP TABLE`을 넣어줘".

디렉터가 이걸 알아야 하는 이유는, AI가 만든 코드는 **"정상적인 손님"만 가정**하기 때문입니다. AI에게 "회원가입 API 만들어줘"라고 하면 잘 만듭니다 — 하지만 그건 *착한 사람이 한 번씩 정상 입력으로 부를 때* 잘 도는 코드입니다. 악의적인 1초 1만 번, 빈 입력, 거대한 입력, 남의 데이터를 노린 요청에 대한 방어는 명시적으로 시키지 않으면 거의 빠집니다. 보안은 "추가 기능"이 아니라 **요청이라는 게 원래 신뢰할 수 없는 외부인이 보낸 것**이라는 기본 전제이고, 그 전제를 챙기는 사람이 디렉터입니다. 코드를 못 짜도, "이 API가 남용당하면 누가 어떤 피해를 보는가"를 물을 줄 알면 됩니다.

**③ 비유**
가게 문을 생각하세요. 다섯 개의 장치가 있습니다.

- **레이트리밋** = 회전문. 한 사람이 1초에 100번 들락거리지 못하게 한 번에 한 명씩, 일정 속도로만 통과시킵니다. 폭주(DDoS·무차별 비밀번호 시도·요금 폭탄)를 물리적으로 늦춥니다.
- **CORS** = "어느 동네 사람만 받습니다" 입간판. 우리 가게 주문은 *우리 앱(우리 도메인)* 에서만 받고, 모르는 사이트가 우리 API를 자기 페이지에 끼워 호출하는 걸 브라우저 차원에서 거릅니다.
- **시크릿 관리** = 금고 열쇠. 손님에게 보여줘도 되는 명함(공개 키)과, 절대 새면 안 되는 금고 열쇠(비밀 키)를 구분해서, 열쇠는 카운터 뒤 금고(서버)에만 둡니다.
- **인젝션 방어** = 주문서 양식. 손님이 적어낸 글씨를 *명령*으로 읽지 않고 *글자 그대로의 데이터*로만 다룹니다. "특제소스 추가 그리고 금고 열어" 라고 적어도 '주문 내용'으로만 처리합니다.
- **최소권한** = 직원별 열쇠 꾸러미. 홀 서빙 직원에게 금고 열쇠를 주지 않습니다. 각자 자기 일에 딱 필요한 문만 엽니다.

자물쇠 하나가 아니라 **다섯 개를 겹쳐 거는 것**이 핵심입니다. 하나가 뚫려도 다음 게 막습니다(이것을 '심층 방어'라고 부릅니다).

**④ 최소한 알 것**

다섯 자물쇠를 한 표로:

| 자물쇠 | 막는 것 | 한 줄 핵심 | 디렉터가 물을 질문 |
|---|---|---|---|
| 레이트리밋 | 폭주·무차별 시도·요금 폭탄 | "한 사람이 1분에 N번까지만" 횟수·속도 제한 | "이 API 무한정 부르면 무슨 일 나? 로그인·문자발송·AI호출 같은 비싼 건 제한했나?" |
| CORS | 모르는 사이트가 우리 API 호출 | 허용할 출처(도메인) 목록을 서버가 정함 | "허용 도메인이 `*`(전부)로 열려 있진 않나?" |
| 시크릿 관리 | 비밀 키 유출 | 공개 키는 프론트, 비밀 키는 서버 환경변수에만 | "service_role·결제 비밀 키가 브라우저나 깃허브에 나가 있진 않나?" |
| 인젝션 방어 | SQL·명령·스크립트 주입 | 입력을 '명령'이 아닌 '데이터'로만 다룸(파라미터 바인딩) | "사용자 입력을 그대로 쿼리·HTML·셸에 이어붙이진 않나?" |
| 최소권한 | 권한 과다로 인한 피해 확대 | 각 키·역할에 딱 필요한 권한만 | "이 작업에 이렇게 센 권한이 꼭 필요한가? 더 약한 걸로 되나?" |

키 구분(가장 자주 사고 나는 곳, 반드시 외울 것):

| 종류 | 공개 가능? | 어디에 두나 | 무엇으로 보호하나 |
|---|---|---|---|
| Supabase **anon**(공개/`publishable`) 키 | 🟢 **공개 가능** (브라우저에 나가도 됨) | 프론트엔드 코드 | **RLS(행 수준 보안)** 로 보호 |
| Supabase **service_role**(비밀/`secret`) 키 | 🔴 **절대 비밀** | 서버·n8n 등 백엔드 **환경변수에만** | 애초에 노출 안 함 (RLS도 우회함) |
| 결제사 비밀 키 / API 비밀 키 | 🔴 **절대 비밀** | 서버 환경변수 | 노출 시 즉시 회전(재발급) |

!!! warning "흔한 오해 바로잡기"
    "anon 키 = 비밀번호니까 숨겨야 한다"는 **틀린 말**입니다. anon 키는 브라우저에 나가는 게 정상인 **공개 출입증**입니다. 진짜 보안은 키를 숨기는 게 아니라 **RLS로 '읽기는 누구나, 쓰기·삭제는 권한자만' 규칙을 데이터베이스에 박는 것**입니다. 반대로 **service_role 키는 RLS조차 무시하는 마스터 키**라 절대 프론트·깃허브에 두면 안 됩니다. ([4권 1장](../04-security/01.md) 참고)

레이트리밋의 단위 감각(개념만, 정확한 한도는 서비스 문서 확인 권장):

- **무엇을 셀까**: IP별 / 로그인 사용자별 / API 키별 — 보통 둘 이상을 함께.
- **얼마나**: "분당 60회" 같은 고정 한도, 또는 "토큰 버킷"(평소엔 빠르게, 몰아치면 느리게).
- **비싼 것일수록 빡빡하게**: 로그인 시도·이메일/문자 발송·AI 호출·결제는 **건당 돈·위험**이 크니 일반 조회보다 훨씬 낮게.
- **넘으면**: `429 Too Many Requests` 상태코드로 정중히 거절 + "언제 다시 시도" 안내.

**⑤ AI에게 이렇게 시켜라**

```text
역할: 너는 보안에 깐깐한 백엔드 시니어다.
지금 내 [회원가입 + 로그인 + 문의글 작성] API에 '남용 방어'를 추가하려 한다.
아래 다섯 항목을 빠짐없이 점검·구현하고, 각 항목마다 "왜 필요한지"를
비전공자도 알게 한 줄 주석으로 달아줘.

1) 레이트리밋: IP별 + 사용자별로 건다. 로그인·문자/이메일 발송처럼
   비싸거나 위험한 엔드포인트는 일반 조회보다 훨씬 낮은 한도로.
   한도 초과 시 429 상태코드로 거절하고, 코드에 숫자를 박지 말고
   환경변수/설정으로 조절 가능하게 해줘.
2) CORS: 허용 출처(도메인)를 명시적으로 화이트리스트로만. '*'(전부 허용)는
   금지. 내 프론트 도메인과 로컬 개발 주소만 허용하는 예시로.
3) 시크릿 관리: 비밀 키(service_role·결제 비밀 키 등)는 절대 코드/프론트에
   박지 말고 서버 환경변수에서 읽게. .env.example에는 자리표시자만 넣고,
   .gitignore에 .env가 들어있는지 확인해줘. 공개해도 되는 키와
   숨겨야 하는 키를 표로 구분해줘.
4) 인젝션 방어: 모든 DB 쿼리는 문자열 이어붙이기(concat) 말고
   파라미터 바인딩으로. 사용자 입력을 화면에 출력할 땐 textContent 기준,
   innerHTML은 금지(이유도 설명).
5) 최소권한: 이 작업들에 service_role이 정말 필요한지 다시 따져보고,
   anon + RLS로 될 일은 그렇게. 꼭 필요한 곳에만 강한 권한을 쓰고
   그 이유를 적어줘.

마지막에 '내가 빠뜨린 보안 구멍'이 더 있는지 5개 이내로 지적하고,
각 항목을 내가 어떻게 직접 확인(검증)하는지 절차로 알려줘.
```

> 프롬프트 팁: "정상 입력 말고 **악의적 입력**(빈 값, 10MB짜리 거대 입력, 따옴표·꺽쇠·세미콜론, 1초 1만 번 호출)일 때 어떻게 되는지도 같이 점검해줘"를 덧붙이면, AI가 '착한 손님' 가정에서 벗어납니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **CORS를 `*`로 활짝 열어버림.** AI가 "CORS 에러"를 빨리 없애려고 모든 출처를 허용하는 코드를 자주 냅니다. 에러는 사라지지만 문이 통째로 열립니다. *허용 도메인은 우리 것만* 명시해야 합니다.
- **CORS를 보안 장치로 착각.** CORS는 *브라우저*가 지키는 규칙이라, 브라우저가 아닌 도구(curl·봇·서버)는 무시하고 부를 수 있습니다. CORS는 "다른 사이트가 사용자의 브라우저를 빌려 우리 API를 호출"하는 걸 막을 뿐, **진짜 인증·권한 검사를 대신하지 못합니다.** 인증은 따로([03장](03.md)).
- **레이트리밋을 프론트에만 검.** "버튼을 5초에 한 번만 눌리게" 같은 프론트 제한은 화면 꾸미기일 뿐, 공격자는 API를 직접 부릅니다. **제한은 반드시 서버에서.**
- **service_role 키를 데모 속도 때문에 프론트에 박음.** 가장 흔하고 가장 치명적입니다. 이 키 하나면 RLS를 무시하고 DB 전체를 읽고 지울 수 있습니다. 모은 회원 이메일 전체가 누구나 가져갈 수 있는 상태가 됩니다.
- **문자열 이어붙이기로 쿼리 작성(SQL 인젝션).** `"SELECT * FROM users WHERE name = '" + 입력 + "'"` 같은 코드. 입력에 `' OR '1'='1`을 넣으면 조건이 무너집니다. **반드시 파라미터 바인딩**(자리표시자 `?`/`$1`에 값을 따로 전달)을 쓰게 시키세요.
- **사용자 입력을 `innerHTML`로 출력(XSS).** 입력에 `<script>`가 들어 있으면 다른 사람 브라우저에서 실행됩니다. 출력은 **`textContent` 기본**.
- **에러 메시지에 내부 정보를 토함.** "DB 비밀번호 틀림: 호스트 db-prod-...:5432" 같은 상세 에러를 사용자에게 그대로 보여주면 공격 지도를 그려주는 셈입니다. 사용자에겐 두루뭉술하게, 상세는 서버 로그로만([05장](05.md)).
- **레이트리밋 한도를 코드에 박음.** 환경변수로 빼야 운영 중 조절할 수 있습니다.

**⑦ 검증하는 법**

코드를 못 짜도 디렉터가 직접 확인할 수 있는 절차들입니다.

1. **키 노출 점검(가장 먼저).** 브라우저 F12 → 소스/네트워크에서 `service_role`, `secret`, 결제 비밀 키 문자열이 검색되는지 확인. 깃허브 저장소에서도 `service_role`·`.env` 검색. 하나라도 나오면 **즉시 키 회전(재발급)** ([4권 5장](../04-security/05.md)).
2. **레이트리밋 동작 확인.** 같은 요청을 빠르게 여러 번 보냈을 때 어느 순간 `429`로 거절되는지 본다. (AI에게 "이 한도를 테스트하는 짧은 스크립트와, 정상 사용자가 막히지 않는지 확인하는 법을 줘"라고 시키면 됩니다.) 끝없이 `200`만 나오면 제한이 없는 것.
3. **CORS 확인.** 허용하지 않은 다른 출처에서 브라우저로 호출하면 콘솔에 CORS 차단 에러가 떠야 정상. 그리고 서버 설정에서 허용 출처가 `*`가 아니라 **우리 도메인 목록**인지 눈으로 확인.
4. **인젝션 입력 넣어보기.** 이름·검색 칸에 `'`(따옴표), `<script>alert(1)</script>`, `'; DROP TABLE` 같은 걸 넣어본다. 화면에 `<script>`가 *글자 그대로* 보이면(실행되지 않으면) XSS 방어 OK, 서버가 멀쩡히 거절·저장하면 SQL 방어 OK. 화면이 깨지거나 경고창이 뜨면 위험.
5. **최소권한 되묻기.** "이 기능에 service_role이 꼭 필요해? anon + RLS로는 안 돼?"를 AI에게 물어 *더 약한 권한으로 가능한지* 확인. 대부분 가능합니다.
6. **에러 메시지 점검.** 일부러 잘못된 요청을 보내, 응답에 내부 경로·DB·키 정보가 새어나오는지 본다.

    바이브코딩으로 만든 동네 모임 앱이 입소문을 탔습니다. 어느 새벽, 클라우드에서 "이번 달 문자 발송 요금 38만 원" 알림이 옵니다. 누군가 회원가입 인증문자 API의 주소를 알아내, **레이트리밋이 없는 그 창구에 대고 1초에 수백 번** 아무 번호로 인증문자를 쏘아댄 것입니다. 화면의 "인증요청" 버튼은 5초에 한 번만 눌리게 막아뒀지만, 공격자는 버튼을 누른 게 아니라 API를 직접 불렀습니다. 디렉터는 여기서 세 가지를 시킵니다. (1) 인증문자 같은 *비싼* 엔드포인트에 IP·전화번호별 레이트리밋을 서버에 걸고 한도는 환경변수로 빼기, (2) 한도 초과 시 `429`로 거절, (3) 혹시 service_role 키가 프론트에 박혀 있었는지 즉시 점검·회전. 다음 날 같은 공격이 들어오지만, 이번엔 회전문 앞에서 막혀 요금은 0원입니다. 자물쇠는 화면이 아니라 **창구(API) 바로 뒤**에 달아야 한다는 걸, 38만 원이 가르쳐준 셈입니다.
