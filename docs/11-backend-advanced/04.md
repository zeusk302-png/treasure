# 요청 수명주기와 미들웨어 — 줄 세워 처리하기

**① 한 줄 정의**
요청 하나가 서버에 들어와 응답으로 나갈 때까지는 **여러 검문소를 순서대로 통과하는 여행**이며, 그 검문소 하나하나(인증·로깅·검증 등)를 끼워 넣는 부품이 **미들웨어**입니다.

**② 왜 중요한가 (디렉터 관점)**
미들웨어를 모르면 같은 코드를 **모든 화면마다 복사**하게 됩니다. "로그인 안 한 사람은 막아라"를 페이지 50개에 똑같이 50번 적는 식이죠. 한 곳을 고치면 49곳을 빠뜨리고, 그 틈으로 보안 구멍이 생깁니다. 미들웨어는 이 공통 일을 **요청이 지나가는 길목 한 곳에 한 번만** 설치하는 발상입니다.

디렉터에게 진짜 무기가 되는 지점은 **"순서"**입니다. AI에게 "로그인 검사 붙여줘", "요청 기록(로깅) 남겨줘", "입력값 검사해줘"를 따로따로 시키면 AI는 곧잘 만들어 줍니다. 하지만 **이걸 어떤 순서로 줄 세울지**는 AI가 자주 틀립니다. 인증을 검증보다 뒤에 놓으면 로그인도 안 한 사람의 쓰레기 입력을 서버가 먼저 파싱하느라 일하고, 로깅을 인증보다 앞에 놓으면 누가 접근했는지조차 모른 채 거절당한 요청이 기록에서 빠집니다. 디렉터는 코드를 짜는 사람이 아니라 **"이 검문소들을 이 순서로 세워라"라고 지시하고, 순서가 틀렸을 때 짚어내는 사람**입니다.

**③ 비유**
공항 출국장을 떠올려 보세요. 여행객(요청)은 정해진 줄을 **순서대로** 통과합니다. ① 항공권 확인(이 사람이 올 자격이 있나 = 인증) → ② 짐 검색대(가져온 게 위험물은 아닌가 = 입력 검증) → ③ CCTV·기록 카운터(누가 몇 시에 지나갔나 = 로깅) → ④ 탑승 게이트(진짜 목적지로 보내기 = 실제 처리) → 그리고 같은 통로를 거꾸로 거쳐 비행기에서 내려 짐을 찾고 나옵니다(응답이 나가는 길).

여기서 핵심은 **순서를 바꾸면 공항이 마비된다**는 점입니다. 짐 검색을 항공권 확인보다 먼저 하면 표도 없는 사람의 가방까지 다 뒤지느라 줄이 막힙니다. 보안요원(미들웨어)은 각자 자기 검문소에서 "통과시킬지 / 되돌려보낼지(거절)"만 결정하고, 통과면 다음 검문소로 넘깁니다. 미들웨어 하나가 `next()`(다음으로 넘김)를 호출하지 않으면 그 줄에서 여행객이 그대로 멈춥니다 — 검문소에서 사람을 붙잡아 둔 채 손을 놓아버린 것과 같습니다.

**④ 최소한 알 것**

요청이 거치는 전형적인 흐름과 각 단계에 흔히 끼우는 미들웨어:

| 순서 | 단계 | 끼우는 미들웨어 예 | 하는 일 |
|---|---|---|---|
| 1 | 진입 | CORS·보안 헤더 | 어느 출처의 요청을 받을지, 기본 방어막 |
| 2 | 요청 읽기 | 본문 파서(body parser) | JSON 등 요청 내용을 꺼내 읽기 |
| 3 | 기록 | 로깅 | 누가·언제·무엇을 요청했는지 남김 |
| 4 | 신원 확인 | 인증(authentication) | "이 사람 누구야?" 로그인 여부 확인 |
| 5 | 권한 확인 | 인가(authorization) | "이 사람이 이걸 해도 돼?" 권한 확인 |
| 6 | 입력 검증 | 검증(validation) | 들어온 값이 형식·범위에 맞나 |
| 7 | 핵심 처리 | 라우트 핸들러 | 진짜 일(DB 조회·저장 등) |
| 8 | 마무리 | 에러 처리·응답 후 로깅 | 실패 수습, 응답 시간 기록 |

- **미들웨어 = 요청과 응답 사이에 끼우는 함수**. "받은 요청을 보고 → 뭔가 하고 → 다음으로 넘기거나(`next`) 여기서 응답을 끝낸다"가 전부입니다.
- **파이프라인(pipeline) = 미들웨어를 줄 세운 통로**. 위에서 아래로 순서대로 통과합니다.
- **순서 규칙(외워둘 큰 틀)**: 🟢 *값싸고 빠른 거절을 앞으로*. 인증·권한처럼 "할지 말지"를 가르는 검문은 비싼 일(DB·외부 호출) 앞에 두는 게 기본. 단, **로깅은 "거절된 요청도 남기고 싶으냐"에 따라** 인증 앞/뒤가 갈립니다(보안 감사를 원하면 앞쪽에도 최소 기록).
- **에러 처리 미들웨어는 보통 맨 끝**에 둡니다. 앞 단계 어디서든 터진 에러가 마지막 그물로 떨어지게 하기 위함입니다.
- **전역(global) vs 라우트별(route-level)**: CORS·로깅처럼 모든 요청에 거는 건 전역, "관리자 페이지에만 권한 검사"처럼 일부에만 거는 건 라우트별로 끼웁니다.

**⑤ AI에게 이렇게 시켜라**

```text
역할: 너는 Express(또는 내가 쓰는 백엔드 프레임워크) 백엔드 설계를 돕는 시니어 개발자다.

상황: 회원이 글을 쓰는 API(POST /posts)를 만들고 있다. 이 요청이 들어와
응답으로 나갈 때까지 거치는 미들웨어 파이프라인을 설계해줘.

요구사항:
1) 다음 미들웨어를 '실행 순서대로' 나열하고, 각각이 왜 그 위치에 있는지
   한 줄씩 이유를 달아줘: 보안 헤더, CORS, 요청 본문 파서, 로깅,
   인증(로그인 확인), 인가(이 사용자가 글 쓸 권한 있나), 입력 검증, 실제 처리, 에러 처리.
2) 순서를 바꾸면 어떤 문제가 생기는지(예: 인증을 검증 뒤로 옮기면) 2~3개 예시로 설명해줘.
3) 비싼 작업(DB 접근) 앞에서 값싼 거절(인증 실패)이 먼저 일어나도록 배치했는지 확인해줘.
4) 에러 처리 미들웨어를 왜 맨 끝에 두는지 알려줘.

출력: 먼저 '순서 표'로 보여주고, 그다음 각 단계의 짧은 코드 골격을 주석과 함께 줘.
주석은 '무엇을 하는지'뿐 아니라 '왜 이 순서·이 위치인지'를 비전공자가 알게 한국어로 달아줘.
보안: 비밀키는 코드에 박지 말고 환경변수로, 사용자 입력은 검증 단계에서 거른다는 전제로 짜줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **순서를 섞어 만든다.** AI는 "인증 붙여줘", "검증 붙여줘"를 각각은 잘하지만, 한꺼번에 시키면 검증을 인증보다 앞에 두거나, 로깅을 인증 뒤에만 둬서 거절된 접근이 기록에서 빠지는 배치를 곧잘 내놓습니다. **순서를 명시적으로 묻고 이유를 받아내세요.**
- **`next()`를 빠뜨려 요청이 멈춘다.** 미들웨어에서 다음으로 넘기는 호출(`next()`)을 안 하면 응답이 영영 안 와서 화면이 빙글빙글 돕니다. AI 코드에서 흔한 누락입니다.
- **에러를 그냥 삼킨다.** 중간 미들웨어에서 에러가 나도 마지막 에러 처리로 넘기지 않고 조용히 무시해, 사용자에겐 200(정상)인데 실제론 저장이 안 된 상태가 됩니다.
- **인증과 인가를 한 덩어리로 본다.** "이 사람 누구야(인증)"와 "이 사람이 이걸 해도 돼(인가)"는 다른 검문소입니다. 로그인은 됐지만 남의 글을 지우려는 경우를 인가 단계에서 막아야 하는데, AI가 인증만 걸고 끝내는 경우가 많습니다.
- **무거운 일을 검문 앞에 둔다.** 본문을 통째로 파싱하거나 DB를 조회한 뒤에야 "그런데 로그인 안 했네"라고 거절하면 서버가 헛일을 합니다. 값싼 거절을 앞으로.
- **로깅에 민감정보를 그대로 남긴다.** 비밀번호·토큰·결제정보가 로그에 찍히면 그 자체가 유출 통로입니다. 로깅 미들웨어가 민감 필드를 가리는지(마스킹) 확인하세요.

**⑦ 검증하는 법**

- **브라우저 F12 → Network 탭**에서 한 요청을 클릭해 상태코드와 응답 시간을 봅니다. 로그인 안 한 상태로 보호된 API를 호출했을 때 **빠르게 401/403으로 거절**되면(긴 시간 끌다 거절이 아니라) 값싼 거절이 앞에 잘 배치된 신호입니다.
- **순서 점검표로 눈검사**: ① 거절(401/403)이 무거운 작업보다 먼저 일어나는가 ② 거절된 요청도 로그에 남는가 ③ 잘못된 입력이 핵심 처리 전에 막히는가 ④ 일부러 에러를 내봤을 때(존재하지 않는 글 요청 등) 화면이 멈추지 않고 친절한 에러 응답이 오는가.
- **로그 파일/콘솔 확인**: 요청 한 번에 "들어옴 → 인증 → 처리 → 나감(소요 ms)" 흐름이 순서대로 찍히는지 봅니다. 순서가 뒤죽박죽이면 파이프라인 배치가 틀린 것입니다.
- **AI에게 셀프 점검 시키기**: "방금 만든 미들웨어 순서가 'OWASP·일반 모범사례' 기준으로 인증→인가→검증 순서가 맞는지, 거절이 비싼 작업보다 앞인지 표로 점검해줘"라고 되물어 교차 확인합니다. *(보안 모범사례는 시점에 따라 갱신되니 1차 출처 확인 권장.)*

!!! example "💡 예시로 이해하기"
    회원제 커뮤니티에 "글 삭제" 버튼을 만들었다고 해봅시다. 어떤 사용자가 주소창에 직접 `DELETE /posts/777`을 날립니다. 미들웨어 파이프라인이 제대로 줄 세워져 있다면 이 요청은 이렇게 흘러갑니다. **로깅**이 "익명 IP가 777 삭제 시도"를 먼저 기록하고 → **인증**이 "로그인 토큰이 없네" 하고 **401로 즉시 되돌려** 보냅니다. 서버는 DB 근처에도 가지 않았습니다(값싼 거절). 만약 이 사람이 로그인은 한 상태라면 인증은 통과하지만, 다음 검문소인 **인가**가 "이 글 주인이 아니네" 하고 **403으로 막습니다**. 반대로, 누군가 순서를 잘못 짜서 **검증·DB 조회를 인증보다 앞**에 뒀다면? 서버는 로그인도 안 한 사람의 요청으로 DB에서 777번 글을 끌어오고 한참 일한 뒤에야 "아 참, 로그인 안 했지"라며 거절합니다. 같은 결과(거절)지만 한쪽은 문 앞에서 돌려보내고, 다른 쪽은 집 안까지 들였다가 내쫓는 셈입니다. 디렉터가 "검문소 순서를 인증→인가→검증→처리로 세워라"는 한마디를 할 수 있느냐가 이 차이를 만듭니다.
