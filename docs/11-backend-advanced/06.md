# 비동기 작업과 큐 — 느린 일은 나중에

**① 한 줄 정의**
비동기 작업과 큐(queue)는 **이메일 발송·이미지 변환처럼 오래 걸리는 일을 사용자 앞에서 끝까지 처리하지 않고**, "접수했어요"라고 즉시 답한 뒤 **뒤편에서 차례로(백그라운드) 처리**하는 방식입니다.

**② 왜 중요한가 (디렉터 관점)**
초보가 만든 백엔드가 "잘 되다가 사람 몰리면 멈춰요"라고 하는 사고의 절반은 여기서 납니다. 회원가입 버튼을 눌렀는데 **환영 이메일이 다 나갈 때까지** 화면이 빙글빙글 돌고, 이미지 한 장 올릴 때마다 **변환이 끝날 때까지** 다른 손님까지 같이 기다리는 구조. 디렉터가 "이 작업은 손님 앞에서 끝낼 일인가, 줄 세워 뒤에서 할 일인가?"를 구분할 줄 알면, AI에게 "이건 비동기로 큐에 넣어" 한마디로 설계 방향을 잡아줄 수 있습니다. 즉 **응답 속도·안정성·실패 복구**라는 세 가지 품질을 코드 한 줄 안 짜고도 지휘하는 무기입니다. 그리고 이 개념은 7권 자동화(n8n 워크플로우, 웹훅, 크론)와 한 몸입니다 — 자동화란 결국 "느린 일을 사람 손 떠나서 뒤에서 돌리는 것"이니까요.

**③ 비유**
점심시간 분식집을 떠올려 보세요. 손님이 김밥을 시킬 때마다 주인이 그 자리에서 다 말아줄 때까지 다음 손님이 못 주문하면 줄이 문밖까지 늘어집니다. 똑똑한 가게는 **주문을 받자마자 전표를 주방 꽂이에 꽂고(큐에 넣고) "5분 뒤 나와요" 하고 다음 손님을 받습니다.** 주방은 전표를 **꽂힌 순서대로** 처리하고, 손님은 진동벨(웹훅·알림)이 울리면 받으러 옵니다. 전표를 떨어뜨려도(작업 실패) 다시 꽂으면(재시도) 되고, 같은 전표가 실수로 두 장 꽂혀도 김밥이 두 줄 나가지 않게 표시(멱등성)해 둡니다. **큐 = 주문 전표 꽂이**, **비동기 = "지금 당장 안 받아도 되는 일은 전표로 미뤄두기"**, **워커(worker) = 전표를 처리하는 주방장**입니다.

**④ 최소한 알 것**

| 용어 | 한 줄 뜻 | 분식집 비유 |
|---|---|---|
| 동기(sync) | 끝날 때까지 손님 앞에서 기다리게 함 | 김밥 다 말 때까지 줄 막힘 |
| 비동기(async) | "접수했어요" 즉시 답하고 뒤에서 처리 | 전표 꽂고 다음 손님 받음 |
| 큐(queue) | 처리할 작업을 줄 세워 둔 목록(먼저 온 게 먼저) | 주문 전표 꽂이 |
| 워커(worker) | 큐에서 작업을 꺼내 실제로 처리하는 일꾼 | 전표 보고 김밥 마는 주방장 |
| 웹훅(webhook) | 작업/외부 서비스가 "다 됐다"고 먼저 알려주는 신호 | 진동벨, 주방의 "나왔습니다" |
| 재시도(retry) | 실패한 작업을 잠시 뒤 다시 시도 | 떨어뜨린 전표 다시 꽂기 |
| 지수 백오프 | 재시도 간격을 1초·2초·4초로 점점 늘림 | 바쁠 땐 텀 두고 다시 부르기 |
| 멱등성(idempotency) | 같은 작업이 두 번 처리돼도 결과는 한 번과 같게 | 같은 전표 두 장 와도 김밥 한 줄만 |
| 데드레터 큐(DLQ) | 끝내 실패한 작업을 따로 모아 두는 곳 | "이건 도저히 안 돼" 보류함 |

**언제 큐로 미뤄야 하나 (판단 기준)**

- 🟢 메인 — **이메일/문자 발송**, **이미지·동영상 변환**, **PDF 생성**, **AI(LLM) 호출**, **결제 후처리**(영수증 발송·정산), **대량 데이터 내보내기**. 공통점: 외부 서비스에 의존하거나 시간이 길고, 손님이 결과를 *즉시* 볼 필요는 없음.
- 🟡 대안 — 작고 빠른 일(로그인 검증, 글 한 건 저장)은 굳이 큐 필요 없음. 그냥 요청 안에서 처리.
- 🔵 나중에 — 처음엔 무료 호스팅의 간단한 백그라운드 기능으로 시작하고, 트래픽이 커지면 전용 큐(아래 ⑧)로 옮겨도 됨.
- ⚪ 몰라도 됨 — Kafka 같은 대규모 이벤트 스트리밍은 1인 개발자 단계에선 과합니다.

**웹훅을 한 번 더** — 웹훅은 "내가 자꾸 물어보는(폴링)" 대신 **상대가 끝나면 나에게 신호를 밀어 넣어 주는(push)** 방식입니다. 결제사가 "진짜 돈 들어왔다"고 알려주거나, 이미지 변환 서비스가 "변환 끝났다"고 알려줄 때 씁니다. 큐로 미룬 느린 일의 **완료를 알리는 단짝**이 바로 웹훅입니다.

**⑤ AI에게 이렇게 시켜라**

```text
[역할] 너는 백엔드 설계를 도와주는 시니어 개발자야. 나는 비전공 디렉터라
코드를 직접 짜기보다 옳은 구조인지 판별하고 싶어.

[상황] 회원가입 시 '환영 이메일 발송'과 '프로필 이미지 썸네일 변환'을 하는데,
지금은 회원가입 요청 안에서 둘 다 동기로 처리해서 가입 버튼이 5~10초 멈춰.
가끔 이메일 서버가 느리면 타임아웃 에러까지 나.

[해줘]
1) 이 두 작업을 백그라운드 큐로 미루는 구조를, 코드 짜기 전에 '글과 그림(흐름도 글 설명)'으로 먼저 설명해줘.
2) 사용자에겐 "가입 완료, 이메일은 곧 도착"이라고 즉시 응답하도록 설계해줘.
3) 작업이 실패하면 어떻게 되는지(재시도 횟수·간격=지수 백오프, 끝내 실패하면 데드레터 큐),
   그리고 같은 가입이 중복 호출돼도 이메일이 두 번 안 나가게(멱등성) 막는 방법을 포함해줘.
4) 내가 쓰는 스택(예: Next.js + Supabase, 또는 n8n 자동화)에서 가장 간단히 시작하는 방법과,
   나중에 트래픽 커지면 옮길 전용 큐 후보를 1~2개만 알려줘. (가격·버전은 '확인 권장'으로)
5) 마지막에 '디렉터가 점검할 체크리스트 5줄'로 정리해줘.

코드를 줄 땐 비전공자가 이해하게 한 줄씩 주석으로 '왜 그렇게 했는지'까지 설명해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **무거운 일을 요청 안에서 끝까지 처리** — AI는 별다른 지시가 없으면 이메일·이미지 변환을 그냥 동기로 짭니다. 결과: (1) 화면 오래 멈춤, (2) **타임아웃**(서버가 정해진 시간 안에 못 끝내 강제 종료, 무료 호스팅은 보통 10초~수십 초 제한 — 정확한 한도는 **확인 권장**), (3) 사람 몰리면 무너짐.
- **재시도 설계 누락** — "큐에 넣었다"까지만 하고 *실패하면 어떻게 되는지*를 안 짭니다. 메일 서버가 잠깐 먹통일 때 영영 안 나가거나, 반대로 **무한 재시도로 폭주**(백오프 없음)합니다.
- **멱등성 무시** — 웹훅은 현실에서 **중복으로 옵니다**(결제사가 같은 알림을 두세 번 보냄). AI는 "한 번만 온다"고 가정해 짜서 **이메일이 두 번 가거나 결제가 중복 처리**됩니다. "같은 작업 ID는 두 번 처리하지 마"를 명시해야 합니다.
- **웹훅 서명 검증 누락** — 웹훅 주소는 외부에 열려 있어 아무나 가짜 신호를 쏠 수 있습니다. **서명(secret) 검증**을 빼면 "결제됐다"는 거짓 신호로 공짜 주문이 가능. 비밀키는 코드/깃허브에 박지 말고 환경변수로(공개해도 되는 Supabase anon 키와 달리, 웹훅 시크릿·service_role 키는 **서버에만**).
- **실패를 조용히 삼킴** — 작업이 실패해도 아무도 모름. 끝내 실패한 작업은 **데드레터 큐로 모으고 알림**(슬랙·이메일)을 받도록 해야 사람이 손쓸 수 있습니다.

**⑦ 검증하는 법**

1. **응답 속도 체감** — 브라우저 F12 → Network 탭에서 그 버튼을 눌러 보세요. 잘 미뤘다면 회원가입 응답은 **1초 안쪽**으로 돌아오고, 이메일은 잠시 뒤 도착합니다. 응답에 5~10초가 걸리면 아직 동기로 처리 중인 것.
2. **느림 흉내 내기** — AI에게 "이메일 서버가 느린 상황(5초 지연)을 흉내 내는 테스트를 넣어줘"라고 시켜, 그 상태에서도 **가입 화면은 즉시 응답**하는지 확인. 화면이 같이 멈추면 비동기가 안 된 것.
3. **중복 쏘기** — 같은 웹훅/요청을 **두 번 연속** 보내 보고(또는 AI에게 그런 테스트 요청), 이메일이 **한 번만** 가는지(멱등성) 확인.
4. **재시도 로그** — 일부러 실패시켰을 때(예: 잘못된 메일 주소) 로그에 "1차 실패 → 2초 뒤 재시도 → …"가 찍히고, 끝내 실패한 건이 **데드레터 큐/알림**으로 가는지 확인.
5. **디렉터 질문 한 줄** — "이 외부 서비스가 갑자기 응답 없으면 사용자 화면은 어떻게 되나?" 좋은 답은 *"가입은 되고 이메일만 늦거나 재시도된다"*, 위험한 답은 *"전체가 멈춘다"*.

!!! example "💡 예시로 이해하기"
    수강생 신청 사이트를 만들었습니다. 처음엔 신청 버튼을 누르면 ① DB에 신청 저장 → ② 신청자에게 확인 메일 발송 → ③ 운영자에게 슬랙 알림 → ④ 신청서 PDF 생성, 이 네 가지를 **한 요청 안에서 순서대로** 처리했습니다. 평소엔 멀쩡했는데, 모집 마감 1시간 전 100명이 몰리자 **메일 서버가 느려지면서 신청 버튼이 30초씩 멈추고, 무료 호스팅의 10초 제한에 걸려 타임아웃 에러**가 터졌습니다. 신청은 DB에 저장됐는데 손님 화면엔 "에러"가 떠서, 화가 난 사람들이 **신청 버튼을 두세 번 더 눌렀고** 확인 메일이 사람당 3통씩 나갔습니다. 디렉터는 AI에게 ⑤의 프롬프트로 지시합니다. "①신청 저장만 요청 안에서 즉시 처리하고 '신청 완료'를 1초 안에 응답해라. ②③④는 **큐에 넣어 백그라운드 워커가 처리**하고, 메일·PDF가 실패하면 **2초·4초 간격으로 3번 재시도**, 끝내 실패하면 **데드레터 큐에 넣고 운영자에게 알림**. 같은 신청 ID는 두 번 처리하지 않게 **멱등성**으로 막아라." 다음 마감 날, 200명이 몰려도 신청 버튼은 1초 안에 "완료"를 띄웠고, 메일은 1~2분에 걸쳐 차분히 한 통씩 나갔습니다. 느린 일을 **나중으로 미룬** 덕분에, 가장 바쁜 순간에 사이트가 가장 침착해진 것입니다.
