# 입력 검증과 에러 처리 — 신뢰할 수 없는 입력 다루기

**① 한 줄 정의**
입력 검증은 **서버로 들어오는 모든 데이터를 "일단 의심하고" 형식·범위·권한을 다시 확인하는 일**이고, 에러 처리는 **그 검사에 걸리거나 일이 터졌을 때 일관된 형식으로 정중히 거절·복구하는 일**입니다.

**② 왜 중요한가 (디렉터 관점)**
바이브코딩으로 만든 앱은 화면(브라우저)에서 입력을 한 번 검사합니다. "이메일 형식 맞나요?", "가격이 음수면 안 돼요." — 이게 **클라이언트 검증**입니다. 그런데 여기엔 치명적인 착각이 있습니다. **브라우저는 손님의 영역이라, 손님이 마음대로 뜯어고칠 수 있습니다.** F12(개발자도구)를 열면 "가격 음수 금지" 검사 코드를 지워버리거나, 아예 브라우저를 거치지 않고 서버에 직접 요청을 쏠 수 있습니다(curl·Postman 한 줄이면 됩니다). 그래서 **클라이언트 검증은 '사용자 편의'일 뿐, 보안이 아닙니다.** 진짜 방어선은 **서버에서 한 번 더 검증**하는 것입니다.

디렉터에게 이게 무기가 되는 이유는, AI가 만든 코드를 받았을 때 던질 질문이 명확해지기 때문입니다. "이 검증, 화면에서만 하니 서버에서도 하니?" 한 마디로 가장 흔한 보안 구멍(가격 조작·권한 우회·악성 입력)을 잡아낼 수 있습니다. 또 에러 응답이 **제멋대로면**(어떤 건 영어 문장, 어떤 건 빈 화면, 어떤 건 서버 내부 코드 노출) 사용자도 헷갈리고 프론트엔드도 처리를 못 합니다. 디렉터는 코드를 안 짜도 "들어오는 건 다 의심, 나가는 에러는 한 가지 형식" 이 두 원칙을 지키는지 점검하는 사람입니다.

**③ 비유**
공항 보안검색대를 떠올려 보세요. 비행기 표(예매 사이트)에서 이미 신원 확인을 했더라도, 게이트에 들어가기 전 **공항은 다시 한번 짐을 X-레이로 통과시킵니다.** "예매할 때 확인했잖아요"는 통하지 않습니다. 예매 시스템은 항공사(손님 영역)가 만든 거라 위조될 수 있으니, 진짜 위험구역(비행기) 앞에서는 **공항(서버)이 자기 책임으로 다시 검사**하는 겁니다. 그리고 검색대에 걸렸을 때 직원은 **늘 같은 절차**로 안내합니다 — "이 물건은 반입 금지입니다, 이유는 X, 여기에 버려주세요." 어떤 직원은 소리 지르고 어떤 직원은 그냥 통과시키면 공항은 아수라장이 됩니다. **검증 = 다시 검색, 일관된 에러 응답 = 똑같은 안내 매뉴얼**입니다.

또 하나, 식당 주방(서버) 비유로 보면 입력 검증은 **들어온 식재료 검수**입니다. 손님이 "이 재료로 요리해줘"라며 상한 고기나 돌멩이를 내밀 수 있으니, 주방장은 받자마자 "이건 못 씁니다"라고 돌려보냅니다. 검수 없이 일단 냄비에 넣으면(검증 없이 DB에 저장하면) 나중에 손님 전체가 식중독(데이터 오염·장애)에 걸립니다.

**④ 최소한 알 것**

검증의 두 층 — 둘 다 필요하지만 역할이 다릅니다.

| 구분 | 클라이언트 검증(화면) | 서버 검증(주방) |
|---|---|---|
| 목적 | 사용자 편의(즉시 빨간 글씨) | 보안·데이터 무결성 |
| 신뢰도 | 🚫 못 믿음(손님이 조작 가능) | ✅ 진짜 방어선 |
| 생략하면 | 사용성만 나빠짐 | 보안 사고 직결 |
| 누가 보나 | 사람 눈 | 코드가 자동 검사 |

서버가 반드시 다시 봐야 할 것들:

- **있어야 할 값이 있는가**(필수 항목 누락)
- **형식이 맞는가**(이메일·날짜·전화번호 모양)
- **범위가 맞는가**(나이 0~120, 가격 0 이상, 수량 1~99)
- **권한이 맞는가**(이 사용자가 정말 이 데이터를 바꿀 자격이 있나 — 가장 자주 빠뜨림)
- **너무 크지 않은가**(10MB짜리 글 제목, 100만 자 본문 → 자원 고갈)

검증 라이브러리(개념) — 위 검사를 일일이 if문으로 짜는 대신 **"이 데이터는 이런 모양이어야 한다"는 명세(스키마)를 한 번 적으면 자동으로 검사·거절해주는 도구**입니다.

| 도구 | 환경 | 한 줄 |
|---|---|---|
| **Zod** | TypeScript/JS | 가장 널리 쓰임, 스키마로 타입+검증 동시에 |
| **Yup** | JS | 폼 검증에 많이 쓰던 고전 |
| **Pydantic** | Python | FastAPI의 짝, 파이썬 표준급 |
| **Joi** | Node.js | 서버 검증의 원조격 |

(인기·버전은 시점에 따라 변하니 **최신 표준은 확인 권장**. 우리 스택(Next.js)이라면 보통 **Zod**가 무난한 🟢 메인 선택.)

일관된 에러 응답 형식 — 성공이든 실패든 **항상 같은 모양**으로 답하게 정해둡니다. 예:

```json
{ "ok": false, "code": "INVALID_PRICE", "message": "가격은 0 이상이어야 합니다." }
```

여기에 **상태코드**를 붙입니다. 손님 잘못이면 4xx, 서버 잘못이면 5xx:

| 코드 | 뜻 | 언제 |
|---|---|---|
| 400 | 잘못된 요청 | 형식이 깨짐(JSON 오타 등) |
| 401 | 인증 안 됨 | 로그인 안 한 사람 |
| 403 | 권한 없음 | 로그인은 했지만 자격 없음 |
| 404 | 없음 | 그런 자원이 없음 |
| 422 | 검증 실패 | 형식은 맞는데 값이 규칙 위반 |
| 429 | 너무 많은 요청 | 레이트리밋 초과 |
| 500 | 서버 오류 | 우리 코드/DB가 터짐 |

**⑤ AI에게 이렇게 시켜라**

```text
[역할] 너는 우리 Next.js 앱의 백엔드를 봐주는 시니어 개발자야.

[배경] 사용자가 글을 쓰는 폼이 있어. 제목(필수, 1~100자), 본문(필수, 1~5000자),
가격(0 이상 정수), 카테고리(미리 정한 5개 중 하나)를 받아.

[요청]
1) 이 입력을 받는 API 라우트(app/api/posts/route.ts)를 만들되,
   - Zod 스키마로 서버에서 반드시 다시 검증해줘. (화면 검증은 못 믿는다는 전제)
   - 검증에 걸리면 422 + 일관된 JSON 형식 { ok, code, message }로 거절해줘.
   - 권한 검사도 넣어줘: 로그인 안 했으면 401, 남의 글을 고치려 하면 403.
2) 성공/실패 응답 형식을 한 가지로 통일하고, 그 형식을 주석으로 설명해줘.
3) 예상 못 한 예외는 try/catch로 잡아서 500을 주되, 에러를 '조용히 삼키지' 말고
   서버 로그에는 남기고 사용자에게는 내부 상세(스택·DB 메시지)는 절대 노출하지 마.

[제약] 비전공자가 읽게 각 검증 항목 옆에 "왜 이 검사가 필요한지" 주석을 달아줘.
마지막에 "이 코드가 막아주는 공격/실수"를 3가지로 요약해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **화면 검증만 만들고 끝낸다.** AI에게 "입력값 검증해줘"라고만 하면 브라우저 쪽 빨간 글씨만 붙여놓고 서버는 무방비인 경우가 많습니다. 반드시 **"서버에서 다시(again on the server)"**를 명시하세요.
- **권한 검증을 빼먹는다.** 형식 검증(이메일 모양)은 잘 하는데, **"이 사용자가 이 데이터의 주인이 맞나"**는 자주 누락합니다. 그러면 URL의 글 번호만 바꿔도 남의 글이 수정됩니다(IDOR이라는 고전 취약점).
- **에러를 '조용히 삼킨다'.** `try { ... } catch (e) {}` 처럼 잡기만 하고 아무것도 안 하면, 실패가 며칠 뒤에야 발견됩니다. 로그를 남기고(필요하면 나에게 알림 오게) 사용자에겐 정중히 알려야 합니다.
- **에러 메시지에 내부를 노출한다.** 반대 함정. 사용자 화면에 데이터베이스 에러 전문이나 파일 경로·스택 트레이스를 그대로 뱉으면, 공격자에게 시스템 구조를 알려주는 꼴입니다. **사용자에겐 친절한 한 줄, 로그엔 자세히**가 원칙.
- **에러 응답 형식이 제각각.** 어떤 API는 `{ error: "..." }`, 어떤 건 `{ message: "..." }`, 어떤 건 그냥 빈 200. 프론트가 분기 처리를 못 합니다. **한 형식으로 통일**을 요구하세요.
- **사용자 입력을 그대로 화면에 출력.** 검증을 통과한 글이라도 출력할 땐 `textContent`로(또는 React의 기본 이스케이프) — `innerHTML`로 박으면 사용자가 넣은 `<script>`가 실행되는 XSS가 됩니다. SQL은 문자열을 직접 잇지 말고 **파라미터 바인딩**으로(SQL 인젝션 방지).
- **Supabase RLS와 헷갈림.** 서버 입력 검증과 별개로, DB 단에서는 **RLS(행 수준 보안)**가 "누가 어떤 행을 보고 바꿀 수 있나"를 강제합니다. anon 키는 공개돼도 되지만(브라우저에 나가도 됨), **보호는 RLS가** 합니다. service_role 키는 모든 검증을 우회하므로 **서버에만** 두세요.

**⑦ 검증하는 법**

비전공자도 직접 확인할 수 있는 절차입니다.

1. **화면 검증을 우회해 본다.** F12 → Network 탭에서 정상 요청 하나를 우클릭 → "Copy as cURL"로 복사한 뒤, 값(예: 가격)을 음수나 말도 안 되는 값으로 바꿔 다시 보내봅니다(또는 AI에게 "이 cURL로 가격을 -1로 바꿔 보내는 명령 만들어줘"라고 시킵니다). **서버가 422로 거절하면 합격**, 그냥 저장되면 서버 검증이 없는 것입니다.
2. **남의 데이터 건드리기 테스트.** 로그인한 상태에서 URL이나 요청의 글 번호를 **다른 사람 것으로** 바꿔 수정/삭제를 시도합니다. **403(권한 없음)이 떠야** 정상.
3. **에러 형식 일관성 확인.** 여러 종류의 실패(빈 값, 잘못된 형식, 권한 없음)를 일부러 일으켜 보고, 응답 JSON이 **전부 같은 모양**인지 봅니다.
4. **내부 노출 확인.** 일부러 에러를 내고, 사용자에게 가는 응답에 **DB 메시지·파일 경로·스택**이 섞여 있지 않은지 봅니다(있으면 막아야 함).
5. AI에게 점검을 시킵니다: "방금 만든 API에서 (1)서버 검증이 빠진 항목, (2)권한 검사가 없는 곳, (3)에러를 조용히 삼키는 곳, (4)내부 정보가 노출되는 곳을 찾아 목록으로 보여줘. 아직 고치진 말고."

!!! example "💡 예시로 이해하기"
    중고거래 앱을 만들었다고 합시다. 물건 등록 화면에 "가격은 0원 이상만" 검사를 넣었고, 잘 작동합니다. 그런데 어느 날 한 사용자가 노트북을 **-50만 원**에 올렸고, 누군가 그걸 "구매"하자 시스템이 그 사람에게 50만 원을 **지급**해버렸습니다. 무슨 일이 벌어진 걸까요? 그 사용자는 F12를 열어 화면의 가격 검증 코드를 지운 뒤, 서버에 `가격: -500000`을 직접 보낸 겁니다. 화면(공항 예매)은 통과시켰지만 **서버(공항 검색대)가 다시 검사하지 않았기** 때문에 그대로 들어간 거죠. 만약 서버에 Zod 스키마로 `가격: 0 이상 정수`를 걸어두고 위반 시 422로 거절했다면, 이 요청은 주방 문턱도 못 넘었을 겁니다. "화면에서 막았으니 됐지"가 아니라 **"손님이 직접 주방에 쪽지를 던질 수도 있다"**가 서버 검증의 출발점입니다.
