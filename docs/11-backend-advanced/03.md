# 인증과 인가 심화 — 세션, JWT, 소셜로그인

**① 한 줄 정의**
**인증(Authentication)** 은 "너 누구야?"를 증명받는 일이고, **인가(Authorization)** 는 "그래서 너는 뭘 해도 돼?"를 판정하는 일입니다. 그 사이를 잇는 '신분증'을 어떻게 발급하고 들고 다니느냐가 **세션 vs JWT 토큰**의 갈림길이고, 비밀번호 대신 구글·카카오에게 신원을 대신 확인받는 방식이 **소셜로그인(OAuth)** 입니다.

**② 왜 중요한가 (디렉터 관점)**
로그인은 거의 모든 서비스의 정문입니다. 그리고 정문이 뚫리면 사이트 전체가 뚫립니다. 디렉터가 코드를 직접 짜지 않더라도 이 네 가지 — **인증/인가의 구분, 세션과 토큰의 선택, 소셜로그인 흐름, 비밀번호 해시** — 를 알아야 하는 이유는 분명합니다. AI는 "로그인 기능 만들어줘"라는 한마디에 그럴듯한 코드를 토해내지만, 그 코드가 *비밀번호를 평문으로 저장*하거나 *인가 검사를 프런트엔드(화면)에서만* 하거나 *토큰을 JS가 읽을 수 있는 곳에* 두는 일이 흔합니다. 이건 "버튼 색이 틀렸다" 수준의 실수가 아니라 "금고 문을 안 잠갔다" 수준의 사고입니다. 디렉터의 무기는 **"이 인가 검사는 서버에서 하는 거 맞지?", "비밀번호는 bcrypt로 해시했지?", "이 토큰을 누가 훔치면 어떻게 돼?"** 라고 정확히 되물을 수 있는 능력입니다. 한 번의 올바른 질문이 데이터 유출 사고 하나를 막습니다.

**③ 비유**
회사 건물을 떠올려 보세요. **인증**은 1층 로비에서 사원증을 찍어 "이 사람이 김세영 본인이 맞다"를 확인받는 것입니다. **인가**는 그 사원증으로 *어느 층까지 올라갈 수 있는가* 입니다 — 일반 직원은 5층까지, 임원은 옥상까지. 같은 사람이라도 권한이 다릅니다(인증은 통과했지만 인가에서 막힐 수 있음).

그럼 이 '사원증'을 어떻게 운영할까요? 두 가지 방식이 있습니다.
- **세션 방식**: 로비 경비실에 큰 출입 장부가 있습니다. 손님에게는 번호만 적힌 임시 출입증(쿠키 속 세션 ID)을 줍니다. 손님이 문 앞에 설 때마다 경비가 장부를 뒤져 "3번 = 김세영, 5층까지 OK"를 확인합니다. 장부(서버)가 진실이고, 출입증엔 번호뿐입니다. 경비가 장부에서 줄을 긋는 순간(세션 삭제) 그 출입증은 즉시 무효가 됩니다.
- **JWT 토큰 방식**: 출입증 자체에 "이름: 김세영 / 권한: 5층까지 / 유효기간: 오늘 자정까지"가 적혀 있고, 위조 못 하게 회사 도장(서명)이 찍혀 있습니다. 경비는 장부를 뒤질 필요 없이 도장만 진짜인지 보고 통과시킵니다. 빠르지만, 한 번 발급한 출입증은 유효기간이 끝나기 전엔 회수하기 어렵습니다(이미 손님 손에 있으니까).

**소셜로그인(OAuth)** 은 또 다릅니다. 우리 건물에 들어오려는 손님에게 우리가 직접 신분증을 검사하지 않고, **"옆 건물(구글) 경비한테 가서 본인 확인 도장 받아오세요"** 라고 보내는 것입니다. 손님은 구글 로비에서 인증하고, 구글이 "이 사람 본인 맞음" 도장(인가 코드/토큰)을 찍어 우리에게 돌려보냅니다. 우리는 손님의 구글 비밀번호를 **한 번도 보지 않습니다** — 이게 핵심입니다.

**④ 최소한 알 것**

인증 vs 인가 — 절대 헷갈리면 안 되는 한 쌍:

| 구분 | 인증(Authentication, AuthN) | 인가(Authorization, AuthZ) |
|---|---|---|
| 묻는 것 | "너 누구야?" (신원 확인) | "너 이거 해도 돼?" (권한 확인) |
| 시점 | 로그인할 때 | 로그인 이후 행동마다 |
| 실패 증상 | 401 Unauthorized (로그인 필요) | 403 Forbidden (권한 없음) |
| 예시 | 아이디·비밀번호, 소셜로그인 | "관리자만 삭제 가능", "본인 글만 수정" |
| 흔한 사고 | 비밀번호 평문 저장 | 인가를 화면에서만 검사 (URL로 뚫림) |

세션 vs JWT 토큰 — 신분증을 어디에 저장하느냐:

| 항목 | 세션 방식 | JWT 토큰 방식 |
|---|---|---|
| 진실이 어디 있나 | 서버(장부)에 저장, 쿠키엔 ID만 | 토큰 자체에 정보 담김(서버 저장 X) |
| 강제 로그아웃 | 쉬움 (장부에서 지우면 끝) | 어려움 (유효기간 끝날 때까지 유효) |
| 서버 확장 | 장부 공유 필요(보통 Redis) | 서버가 토큰만 검증하면 됨(무상태) |
| 어울리는 곳 | 일반 웹사이트, 관리자 페이지 | 모바일 앱, 여러 서비스 간 API |
| 주의점 | 장부 동기화 | 토큰 탈취 시 만료 전까지 위험 |

신분증을 '어디에' 보관하느냐 (보안 핵심):

| 저장 위치 | XSS(악성 JS)에 안전? | 추천 |
|---|---|---|
| `HttpOnly` 쿠키 | 안전 (JS가 못 읽음) | 🟢 메인 — 인증 토큰은 여기에 |
| `localStorage` | 위험 (JS가 읽음 → 탈취 가능) | 🔵 가급적 피함 |

비밀번호는 **절대 그대로 저장하지 않습니다**. 한 방향으로만 뭉개는 **해시(bcrypt)** 를 씁니다:

- **평문 저장** = 금고에 비밀번호를 종이로 보관 → DB 한 번 털리면 전원 비밀번호 유출. 🚫 절대 금지.
- **해시 저장** = 비밀번호를 되돌릴 수 없는 지문으로 바꿔 저장. 로그인 시 입력값을 같은 방식으로 뭉개 비교만 함. ✅
- **bcrypt / argon2** = 일부러 느리게 설계된 해시 함수. 해커가 무차별 대입(brute force)으로 풀려 해도 한 번 계산이 느려 시간이 천문학적으로 걸림. (`SHA-256`만 단독으로 쓰는 건 비밀번호용으로는 너무 빨라서 부적합 — 비밀번호엔 bcrypt 계열.)
- **솔트(salt)** = 같은 비밀번호라도 사람마다 다른 양념을 섞어 해시 → 미리 만들어둔 해시 사전(레인보우 테이블)으로 한 번에 못 깸. bcrypt는 솔트를 자동으로 넣어줍니다.

OAuth 소셜로그인 흐름 (한눈에):

1. 사용자가 "구글로 로그인" 클릭 → 우리 사이트가 구글로 보냄
2. 구글 화면에서 사용자가 로그인 + "이 앱에 이메일·이름 제공 동의"
3. 구글이 우리 사이트로 **인가 코드(authorization code)** 를 들려 돌려보냄
4. 우리 **서버**가 그 코드 + 우리 비밀(client secret)을 구글에 보내 **토큰으로 교환**
5. 토큰으로 사용자 정보(이메일 등)를 받아 우리 회원으로 가입/로그인 처리

> 좋은 소식: 위 1~5를 직접 구현하면 함정이 많지만, **Supabase Auth / Clerk / Auth0** 같은 서비스가 이걸 거의 다 대신해 줍니다. 디렉터는 "흐름을 이해하고 옳게 설정됐는지 판별"하면 됩니다.

**⑤ AI에게 이렇게 시켜라**

```text
Next.js + Supabase로 회원 로그인 기능을 만들 거야. 코드를 짜기 전에,
보안 관점에서 다음을 먼저 점검표로 정리해줘. 그다음 그 점검표를
모두 만족하는 코드를 짜줘.

[꼭 지킬 것]
1) 인증(누구인가)과 인가(무엇을 해도 되는가)를 구분해서 설명할 것.
2) 비밀번호 직접 저장 기능은 만들지 말고 Supabase Auth에 위임할 것.
   만약 직접 해시해야 하면 SHA-256 단독이 아니라 bcrypt/argon2를 쓸 것.
3) 인증 토큰은 localStorage가 아니라 HttpOnly 쿠키로 다룰 것
   (JS로 토큰을 읽지 못하게 — XSS로 탈취되면 안 됨).
4) "본인 글만 수정/삭제 가능" 같은 인가 검사는 화면(프런트)이 아니라
   반드시 서버 또는 Supabase RLS(행 수준 보안)에서 강제할 것.
5) 구글 소셜로그인을 붙인다면 OAuth 흐름(인가 코드 → 토큰 교환)을
   한 줄씩 주석으로 설명하고, client secret이 브라우저로 새지 않게 할 것.

각 항목에 대해 "왜 그렇게 해야 하는지" 비전공자가 이해하게 주석으로 풀어줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**
이 주제는 AI가 *그럴듯하지만 위험한* 코드를 가장 잘 만들어내는 영역입니다. 사람이 반드시 점검할 포인트:

- **인가를 화면에서만 검사** — "관리자 메뉴를 숨겼으니 안전하다"는 착각. 버튼을 숨겨도 사용자가 URL을 직접 치거나 API를 직접 호출하면 그대로 뚫립니다. **인가는 반드시 서버(또는 Supabase RLS)에서** 강제해야 합니다. 화면 숨김은 UX일 뿐 보안이 아닙니다.
- **비밀번호 평문/약한 해시 저장** — AI가 `SHA-256`이나 단순 해시로 비밀번호를 저장하는 예시를 주는 일이 있습니다. 비밀번호용으로는 부적합. **bcrypt/argon2** 여야 합니다. (단골 권장: 직접 저장 말고 Supabase Auth에 맡기기.)
- **토큰을 `localStorage`에 저장** — 편해서 AI가 자주 고르지만, 악성 스크립트(XSS) 한 줄이면 토큰을 통째로 훔쳐 갑니다. 인증 토큰은 **`HttpOnly` 쿠키**가 안전합니다.
- **세션과 JWT를 뭉뚱그림** — "JWT 쓰면 보안이 좋아진다" 같은 막연한 설명. JWT는 무상태라 편하지만 **강제 로그아웃이 어렵다**는 트레이드오프가 있습니다. 상황에 맞는 선택을 설명하는지 보세요.
- **소셜로그인의 `client secret`을 브라우저에 노출** — OAuth 토큰 교환(흐름 4단계)은 **서버에서** 해야 합니다. 비밀키가 브라우저 코드에 박히면 누구나 우리 앱 행세를 할 수 있습니다.
- **Supabase 키 오해** — "anon 키는 비밀이니 숨겨야 한다"는 **틀린 말**입니다. **anon 키는 브라우저에 공개돼도 됩니다**(공개 전제로 설계된 키). 진짜 보호는 **RLS(행 수준 보안)** 로 합니다. 반대로 **`service_role` 키는 모든 RLS를 무시하는 만능키라 절대 비밀** — 서버/n8n에서만 쓰고 브라우저엔 절대 노출 금지.
- **사용자 이름·프로필을 화면에 출력할 때** — 로그인한 사용자의 이름 등을 그릴 때 `innerHTML`을 쓰면 이름에 심어둔 `<script>`가 실행될 수 있습니다(XSS). 사용자 입력 출력은 **`textContent`** 가 기본입니다.

**⑦ 검증하는 법**
비전공자도 눈과 개발자도구(F12)만으로 확인할 수 있습니다.

1. **인가가 서버에서 강제되는지** — 로그아웃 상태(또는 일반 사용자)에서 관리자 전용 URL을 주소창에 직접 쳐 봅니다. 화면만 가려져 있고 데이터가 보이면 실패. **403/리다이렉트로 막히면** 성공.
2. **토큰 저장 위치** — F12 → Application(또는 저장소) 탭. 인증 쿠키가 **Cookies**에 있고 `HttpOnly`·`Secure`·`SameSite` 표시가 켜져 있는지 확인. 토큰이 `Local Storage`에 평문으로 있으면 위험 신호.
3. **세션 유지/만료** — 로그인 후 새로고침해도 로그인이 유지되는지, 일정 시간 뒤·로그아웃 후엔 보호 페이지가 막히는지.
4. **소셜로그인 흐름** — "구글로 로그인" 클릭 시 주소창이 잠깐 `accounts.google.com`으로 갔다가 우리 사이트로 돌아오는지(중간에 구글 동의 화면을 거치는지) 눈으로 확인.
5. **AI 답 점검 4종 세트** — AI가 준 인증 코드에 대해 (1) 비밀번호를 bcrypt로 해시했나 (2) 인가를 서버/RLS에서 했나 (3) 토큰을 HttpOnly 쿠키로 뒀나 (4) secret이 브라우저로 새지 않나 — 하나라도 빠지면 "이 4가지를 충족하게 다시 짜줘"로 되돌립니다.

!!! example "💡 예시로 이해하기"
    동네 헬스장 회원 앱을 만든다고 해봅시다. 손님이 **카카오로 로그인**(인증)하면, 앱은 카카오 비밀번호를 한 번도 보지 않고 카카오가 찍어준 "본인 확인 도장"만 받아 회원으로 등록합니다. 이제 손님은 **자기 PT 예약은 잡고 취소할 수 있지만**(인가 OK) **다른 회원의 예약은 못 건드립니다**(인가 거절). 어떤 손님이 "남의 예약도 취소되던데요?"라고 제보합니다. 디렉터는 곧장 코드를 헤집는 대신 묻습니다 — "예약 취소 권한 검사를 *화면에서만* 한 거 아냐? 취소 API를 직접 호출하면 남의 것도 지워지는 거 아냐?" 점검해 보니 정말로 화면에서만 막고 서버 검사가 빠져 있었습니다. Supabase RLS에 "**본인 행만 삭제 가능**" 규칙 한 줄을 추가하자, 화면을 우회해 API를 직접 때려도 서버가 거절합니다. 정문(인증)은 멀쩡했지만 각 방의 자물쇠(인가)가 없었던 것 — 이 둘을 나눠 볼 줄 아는 게 디렉터의 눈입니다.
