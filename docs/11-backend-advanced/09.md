# 백엔드 없이 가기 — BaaS와 직접 서버의 갈림길

**① 한 줄 정의**
BaaS(Backend as a Service, 서비스형 백엔드)는 **데이터베이스·로그인·파일저장·API를 남이 미리 만들어 둔 '완성된 주방'을 빌려 쓰는 것**이고, 직접 서버는 **빈 땅에 주방을 직접 짓는 것**입니다. 이 페이지는 *언제 빌리고 언제 지을지*를 판정하는 갈림길입니다.

**② 왜 중요한가 (디렉터 관점)**
비전공 디렉터에게 이 결정은 **돈·시간·사고 위험을 한꺼번에 좌우하는 가장 큰 갈림길** 중 하나입니다. 직접 서버를 짓는다는 건 단순히 코드를 더 짜는 게 아니라, 그때부터 **로그인 보안, 데이터 백업, 트래픽 폭주 대응, 서버 다운 새벽 호출, 보안 패치**까지 전부 내 책임이 된다는 뜻입니다. 4일 부트캠프를 막 마친 사람이 첫 프로젝트에서 직접 서버부터 짓겠다고 하면, AI는 신나서 Express+PostgreSQL+JWT 풀세트를 토해내지만 그 결과물을 **안전하게 운영할 사람은 없는** 상태가 됩니다.

디렉터의 무기는 "직접 만들 수 있다"가 아니라 **"안 만들어도 되는 걸 알아본다"**입니다. 90%의 초기 서비스(포트폴리오, 문의폼, 방명록, 작은 커뮤니티, 예약, MVP)는 BaaS만으로 충분합니다. 직접 서버가 정말 필요한 신호를 *미리 알아두면*, AI가 과하게 짓는 걸 멈추게 하고 ("이건 Supabase로 충분하지 않아?"), 정말 필요할 때만 ("이 부분만 작은 서버 함수로 빼자") 정확히 시킬 수 있습니다.

**③ 비유**
음식 장사를 시작한다고 합시다. **공유주방을 빌리는 것**이 BaaS입니다. 가스·후드·냉장고·수도·위생 허가가 다 갖춰진 곳에 들어가 내 레시피만 들고 가면 바로 장사가 됩니다. 설비 고장은 건물주가 고치고, 위생 점검도 건물 단위로 통과돼 있습니다. 대신 "여기선 숯불 화덕은 못 놓아요" 같은 **규칙 안에서만** 움직여야 합니다.

**직접 서버를 짓는 것**은 빈 상가를 임대해 주방을 처음부터 짓는 것입니다. 화덕이든 뭐든 원하는 대로 놓을 수 있지만, 배관·전기·위생·소방을 전부 내가 책임지고, 한밤중 냉장고가 멈추면 내가 일어나야 합니다. 미슐랭을 노리는 전문 레스토랑이라면 언젠가 필요하지만, **떡볶이 한 가지 팔아보려는 사람이 첫날부터 할 일은 아닙니다.** 핵심: 대부분은 공유주방으로 시작해, 정말 화덕이 필요해질 때 그때 옮깁니다.

**④ 최소한 알 것**

먼저 용어부터.

| 용어 | 한 줄 뜻 | 비유 |
|---|---|---|
| BaaS | 백엔드(DB·로그인·저장·API)를 통째로 빌려주는 서비스 | 공유주방 |
| 직접 서버 | 내가 코드로 백엔드를 짓고 운영 | 직접 지은 주방 |
| 서버리스 함수 | "이 한 가지 일만 해주는 짧은 서버" 한 조각 | 출장 요리사 한 명 호출 |
| 풀스택 프레임워크 | 프런트+간단 서버를 한 묶음으로 (예: Next.js) | 홀+간이주방 일체형 |

대표 BaaS와 성격(시점성 있는 가격·한도는 **공식 페이지 확인 권장**):

| 도구 | 강점 | 비유 |
|---|---|---|
| Supabase | PostgreSQL 기반·RLS로 보안·SQL 친화·오픈소스 | 표준 규격 공유주방 |
| Firebase | 구글 생태계·실시간 DB·푸시·모바일 강함 | 구글표 올인원 주방 |
| 그 외 | Appwrite, PocketBase, Puck 등 (목적별 다양) | 동네 공유주방들 |

**길라잡이 판정 — 무엇으로 시작할까**

- 🟢 **메인: BaaS로 시작**. 포트폴리오, 문의폼, 방명록, 로그인+CRUD 커뮤니티, 예약, 대부분의 MVP. "데이터 저장 + 로그인 + 파일 업로드"가 필요의 전부라면 BaaS가 정답.
- 🟡 **대안: BaaS + 서버리스 함수 한두 개**. 거의 다 BaaS인데 *딱 한 가지*가 BaaS로 안 될 때(아래 "직접 서버가 필요한 신호") 그 부분만 작은 함수로 뺀다. 통째로 직접 서버를 짓지 않는다.
- 🔵 **나중에: 전용 백엔드 서버**. 트래픽·복잡도가 커져 BaaS의 한계가 *실제로* 느껴진 뒤. 미리 짓지 말고, 아플 때 짓는다.
- ⚪ **몰라도 됨(지금은)**: 쿠버네티스, 마이크로서비스, 직접 DB 튜닝. 첫 서비스에선 이름만 알면 충분.

**직접 서버(또는 서버리스 함수)가 필요해지는 진짜 신호** — 하나라도 강하게 해당하면 검토:

1. **비밀 키를 써야 하는 외부 호출** — 결제(토스/스트라이프), 외부 유료 API, LLM API 호출처럼 **service_role급/비밀 키가 필요한 작업은 브라우저에서 하면 안 됩니다.** 키가 노출되니까. 이 부분은 반드시 서버(또는 서버리스 함수)에서.
2. **신뢰할 수 없는 계산을 서버가 확정해야 할 때** — 게임 점수, 쿠폰 할인 금액, 재고 차감처럼 사용자가 F12로 조작하면 안 되는 값. "최종 판정"은 서버 몫.
3. **복잡한 다단계 트랜잭션/업무 로직** — 단순 CRUD를 넘어 "주문→재고 차감→포인트 적립→알림"을 한 묶음으로 묶어야 할 때.
4. **무거운/오래 걸리는 작업** — 영상 변환, 대용량 배치, 정기 스케줄 작업(자세히는 → [비동기 작업과 큐](06.md)).
5. **세밀한 커스텀 권한·미들웨어** — RLS로 표현하기 어려운 복잡한 인가 규칙(요청 처리 흐름은 → [요청 수명주기와 미들웨어](04.md)).

반대로, **이 정도는 BaaS로 충분**: 회원가입/로그인, 글·댓글·좋아요 CRUD, 이미지 업로드, "내 글만 수정 가능" 같은 기본 권한, 간단한 검색·필터.

**⑤ AI에게 이렇게 시켜라**

```text
[역할] 너는 비전공 1인 개발자를 돕는 시니어 아키텍트야.
[상황] 나는 회원가입/로그인 + 글·댓글·좋아요 CRUD + 이미지 업로드가 있는
작은 커뮤니티 사이트를 만들려고 해. 예상 사용자는 처음엔 수십~수백 명.
나는 서버 운영 경험이 없고 혼자 관리해.

[해줘]
1) 이 요구사항이 Supabase 같은 BaaS만으로 충분한지, 아니면 직접 서버가
   꼭 필요한지 '판정'부터 해줘. 결론을 먼저 한 줄로.
2) 각 기능을 'BaaS로 가능 / 서버리스 함수 필요 / 직접 서버 필요'로 분류한 표.
3) 직접 서버가 필요하다고 판단한 항목이 있으면, 그게 '정말' 필요한 이유와
   대신 서버리스 함수로 처리할 수 있는지도 검토해줘.
4) 보안: anon 키는 어디까지 공개돼도 되는지, RLS를 어떤 테이블에 켜야 하는지,
   service_role 키를 절대 두면 안 되는 곳이 어디인지 명시해줘.

[제약] 처음부터 직접 서버 풀세트(Express+DB+JWT)를 제안하지 마.
나는 운영 부담을 최소화하고 싶어. 꼭 필요한 부분만 최소로.
```

> 팁: "왜 그렇게 판단했는지 한 줄씩 설명해줘"를 붙이면, AI가 과하게 짓는지 점검할 수 있습니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **함정 1: AI가 묻지도 않은 풀스택 서버를 짓는다.** "커뮤니티 만들어줘" 한마디에 Express+PostgreSQL+JWT 인증을 통째로 토해냅니다. 화면은 멀쩡해도, 그걸 **안전하게 운영할 사람이 없으면** 시한폭탄입니다. → 디렉터가 "이거 BaaS로 충분하지 않아?"라고 되물어야 합니다.
- **함정 2: "anon 키는 비밀이니 숨겨야 한다"는 잘못된 설명.** **anon(공개) 키는 브라우저에 나가도 되는 '출입증'입니다.** 진짜 보호는 **RLS(행 수준 보안)를 켜는 것**으로 합니다. AI가 anon 키를 숨기라고만 하고 RLS를 안 켜면, 정작 데이터는 통째로 새어 나갑니다. (인증·인가 자세히는 → [인증과 인가 심화](03.md))
- **함정 3: service_role 키를 프런트/깃허브에 박기.** 빠른 데모를 만들면서 **service_role(진짜 비밀) 키를 브라우저 코드나 깃허브에 넣으면, RLS를 무시하고 전체 데이터를 누구나 가져갈 수 있습니다.** service_role은 **오직 서버/서버리스 함수/n8n 같은 백엔드에서만.** (입력 검증·키 관리는 → [입력 검증과 에러 처리](05.md))
- **함정 4: 비밀 키 외부 호출을 브라우저에서.** LLM·결제 API 키를 프런트에 넣으면 요금 폭탄이 나거나 키가 도난당합니다. 이런 호출은 반드시 서버리스 함수로 한 겹 감쌉니다.
- **함정 5: 사용자 입력을 화면에 그대로 출력.** 댓글·이름 등 사용자 입력을 출력할 때 `innerHTML`을 쓰면 남이 넣은 `<script>`가 실행되는 XSS 위험. 기본은 항상 `textContent`로 출력합니다.

**⑦ 검증하는 법**

1. **RLS 켜졌는지 눈으로 확인** — Supabase 대시보드 → Table Editor에서 각 테이블에 "RLS enabled" 표시가 있는지, Policies 탭에 정책이 실제로 있는지 본다. "다 켰다"는 AI 말이 아니라 화면으로.
2. **로그아웃 상태로 빼가보기** — 로그아웃(혹은 시크릿 창)에서 공개 키만으로 남의 비공개 데이터가 조회되는지 직접 시도. 안 보여야 정상.
3. **개발자도구로 키 점검** — F12 → Sources/Network에서 프런트 코드에 **service_role 같은 비밀 키가 노출됐는지** 검색. 나오면 즉시 회수·교체.
4. **저장 진짜 되는지** — "저장됩니다"라는 말 말고, 실제로 한 건 입력 후 대시보드 테이블에 그 행이 들어왔는지 눈으로 확인.
5. **깃허브 점검** — 커밋된 파일에 `.env`나 비밀 키가 섞여 들어갔는지 확인(`.gitignore`로 막혔는지). 비밀값은 자리표시자(`.env.example`)만 올린다.

!!! example "💡 예시로 이해하기"
    동네 빵집 사장님이 "온라인 주문 받는 사이트 만들어줘"라고 합니다. 신입 디렉터 A는 AI에게 그대로 던졌고, AI는 Express 서버 + 직접 만든 회원 인증 + PostgreSQL 직접 운영 풀세트를 짜줬습니다. 데모는 멋졌지만, 한 달 뒤 서버가 새벽에 멈췄고 아무도 못 일으켰으며 회원 비밀번호 저장이 허술해 식은땀을 흘립니다. 경험 있는 디렉터 B는 먼저 **판정**부터 했습니다. "필요한 건 메뉴 목록(읽기) + 주문 저장(쓰기) + 사장님 로그인. 이건 전부 Supabase로 돼." 그래서 BaaS로 만들고, 단 하나 **카드 결제(비밀 키 필요)**만 서버리스 함수 한 개로 빼냈습니다. RLS로 "메뉴는 누구나 읽기, 주문 생성은 누구나, 주문 조회·관리는 사장님만"을 걸고, service_role 키는 결제 함수에만 두었습니다. 결과: 운영 부담은 거의 0, 보안은 RLS로 보장, 결제만 안전하게 서버 처리. **"다 직접 짓기"가 아니라 "딱 한 군데만 서버"** — 이 한 칸 차이가 새벽에 깨느냐 마느냐를 가릅니다.
