# 결제 연동 개요 — PG사·간편결제, 무엇을 누구에게 시킬까

!!! warning "교육용 안내이며 법정 자문이 아닙니다"
    PG 수수료율·가입 조건·결제 정책은 시점성 정보입니다. **각 PG사(토스페이먼츠/포트원 등) 공식 자료**로 확인하세요(확인 날짜 기록).

**(1) 한 줄 정의**
결제 연동은 카드·간편결제 같은 결제 수단을 PG사(결제대행)나 통합 솔루션(예: 포트원)을 통해 내 사이트에 붙이는 작업으로, 핵심은 "결제가 진짜로 성공했는지"를 어디서 판단하느냐입니다.

**(2) 왜 중요한가(디렉터 관점)**
결제는 돈이 오가는 곳이라 보안 실수가 곧 금전 피해입니다. 가장 위험한 함정은 AI가 **'결제 성공'을 프론트(브라우저)에서 판단하게** 만드는 것입니다. 프론트 값은 사용자가 위·변조할 수 있으므로, 결제 승인은 반드시 **서버에서 PG API로 다시 검증**해야 합니다. 디렉터는 "요청은 클라이언트, 승인 검증은 서버"라는 경계를 알고 검증해야 합니다.

**(3) 비유**
공연장 입장과 같습니다. 손님이 "표 샀어요"라고 말하는 것(프론트 주장)만 믿고 들여보내면 안 되고, 직원이 매표소 시스템에 표 번호를 조회해 진짜 결제됐는지 확인(서버 재검증)한 뒤 들여보내야 합니다.

**(4) 최소한 알 것**

| 항목 | 한 줄 해설 | 판정 |
|---|---|---|
| 서버 재검증 | 결제 성공 판단은 반드시 서버에서 PG API로 재확인 | 🟢메인 |
| 시크릿 키는 서버에만 | PG 비밀 키를 프론트에 노출하면 안 됨(권4 직결) | 🟢메인 |
| 테스트 모드 | 실제 돈 없이 흐름을 검증하는 모드 먼저 사용 | 🟢메인 |
| 가입 선행조건 | 사업자등록 등 선행 조건이 보통 필요 | 🟡대안 |

!!! warning "수수료·조건은 직접 확인"
    "PG 수수료 3.2~3.4%" 같은 수치와 가입 조건은 PG사 공식 가격표로 재확인하세요. 정산 주기·보증보험 요구 등도 함께 확인합니다.

**(5) AI에게 이렇게 시켜라**

```text
Next.js + Supabase 사이트에 결제를 붙이려 한다(포트원/토스페이먼츠 가정).
보안을 최우선으로, 다음 원칙을 지켜 구조를 설계해줘.
1) 결제 '요청'은 클라이언트에서, '승인/성공 판단'은 반드시 서버에서 PG API로 재검증
2) PG 시크릿 키는 절대 프론트에 노출하지 말고 서버 환경변수로만(.env, NEXT_PUBLIC_ 금지)
3) 먼저 '테스트 모드'로 전체 흐름을 검증하는 절차
프론트에서 결제 성공을 판단하는 코드는 절대 만들지 말고, 왜 위험한지 한 줄로 설명해줘.
수수료·가입 조건은 '공식 확인 필요'로 표시해줘.
```

**(6) 흔한 함정·AI가 틀리는 것**
AI는 빠른 데모를 위해 **결제 성공을 프론트에서 판단**하는 코드를 줘 위·변조에 뚫리게 만듭니다. 또 **PG 시크릿 키를 프론트 컴포넌트에 노출**하거나(권4의 service_role 노출과 같은 종류의 사고), 가입 선행조건(사업자등록·심사)을 생략한 채 코드부터 제시합니다.

!!! warning "프론트 결제 판단은 절대 금지"
    "결제창이 성공을 반환했으니 처리 완료"라는 프론트 로직은 조작 가능합니다. 반드시 서버에서 PG의 결제 조회 API로 금액·주문번호·상태를 재검증한 뒤에만 상품/서비스를 제공하세요.

**(7) 검증하는 법**
테스트 모드에서 결제 흐름을 끝까지 돌려봅니다. 브라우저 개발자도구(F12) Network 탭에서 시크릿 키가 노출되지 않는지, 빌드 결과물에 secret 키가 0건인지 확인합니다. 결제 후 서버 로그에서 PG API 재검증 호출이 실제로 일어났는지 봅니다.

**(8) 더 깊이**

- 포트원 개발자 문서 — 1차 출처
- 토스페이먼츠 개발자 문서 — 1차 출처

!!! tip "자기증명 포인트"
    이 사이트는 토스/포트원 테스트 모드로 '요청은 클라이언트, 승인 검증은 서버' 구조를 시연해, 안전한 결제 연동의 경계를 눈으로 보여줍니다.

!!! example "💡 예시로 이해하기"
    AI가 짜준 결제 코드는 결제창이 `{ status: "success" }`를 돌려주면 곧바로 브라우저에서 강의 영상을 풀어주는 구조였습니다. 데모는 잘 돌았죠.
    문제는, 손님이 F12 개발자도구로 그 응답을 `success`로 바꿔치기하면 한 푼도 안 내고 `49,000원`짜리 강의를 가져갈 수 있다는 겁니다. "표 샀어요"라는 말만 믿고 입장시킨 셈이죠.
    올바른 방법은 결제 후 서버가 PG 조회 API로 `주문번호·결제금액·상태`를 다시 확인하고("매표소 시스템 조회"), 49,000원이 실제로 승인됐을 때만 영상을 여는 것입니다. 그리고 PG 시크릿 키는 `NEXT_PUBLIC_` 없이 서버 환경변수로만 둬, 빌드 결과물에서 `grep secret` 검색 시 0건이어야 합니다.
