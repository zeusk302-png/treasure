# 빌드와 번들러 — 왜 코드를 한 번 굽는가

**① 한 줄 정의**
빌드(build)는 **사람이 쓰기 좋은 소스 코드**를 **브라우저가 빠르게 읽기 좋은 배포물(번들)**로 한 번에 번역·압축·포장하는 과정이고, 그 일을 해주는 도구가 **번들러(Vite·esbuild 등)**입니다.

**② 왜 중요한가 (디렉터 관점)**
배포가 빨갛게 실패하는 사고의 절반 이상은 코드를 "쓰다가"가 아니라 **"빌드하다가"** 터집니다. 디렉터가 빌드를 이해하면 에러를 두 칸으로 가를 수 있습니다. "이건 *오븐에 넣기도 전에* 막힌 거야(빌드 에러)" vs "*손님 식탁에서* 음식이 식은 거야(런타임 에러)". 이 한 번의 구분이 우선순위를 바꿉니다. 빌드 에러는 **사용자에게 도달하기 전에** 잡힌 것이라 다행이고, 런타임 에러는 **이미 누군가 보고 있는** 문제라 급합니다.

또 하나, 디렉터가 빌드를 알아야 하는 결정적 이유는 **보안**입니다. AI는 "빠른 데모"라며 API 키를 프론트 코드에 박는 실수를 자주 합니다. 그런데 빌드는 소스를 **그대로** 굽는 게 아니라, `.env`에 든 값을 **빌드 시점에 코드 안으로 박아 넣기도** 합니다. 즉 "어떤 값이 브라우저로 나가는 번들에 섞이고, 어떤 값이 안 섞이는가"를 모르면 비밀 키가 통째로 새어 요금 폭탄을 맞을 수 있습니다. 빌드는 단순한 기술 단계가 아니라 **비밀과 공개를 가르는 관문**입니다.

**③ 비유**
빌드는 **요리책을 출판하는 과정**입니다. 작가(개발자)는 손으로 쓴 원고(소스 코드)를 여러 파일에 나눠 적고, 메모와 주석을 잔뜩 답니다. 하지만 손님(브라우저)에게 손글씨 원고 뭉치를 던질 순 없습니다. 출판사(번들러)가 원고를 모아 **편집(불필요한 공백·주석 제거=압축)**, **번역(최신 문법을 옛 브라우저도 읽는 문법으로=트랜스파일)**, **한 권으로 제본(여러 파일을 묶기=번들링)**, **목차 정리(어떤 조각을 언제 부를지=코드 분할)**를 거쳐 깔끔한 책 한 권으로 인쇄합니다.

이때 "출판 중 오타가 나면 인쇄기 자체가 멈추는 것"이 **빌드 에러**입니다. 반대로 책은 멀쩡히 인쇄됐는데 독자가 12쪽 레시피대로 했더니 소금을 설탕으로 잘못 적은 게 드러나는 것이 **런타임 에러**입니다. 인쇄가 멈췄으면 번역·편집 단계를, 다 읽다가 사고가 났으면 내용(로직)을 의심해야 합니다.

**④ 최소한 알 것**

| 용어 | 한 줄 뜻 | 비유 |
|---|---|---|
| 소스(source) | 사람이 쓰는 원본 코드(여러 파일) | 손으로 쓴 원고 |
| 빌드(build) | 소스 → 배포물로 변환하는 한 번의 작업 | 원고를 책으로 출판 |
| 번들러(bundler) | 빌드를 해주는 도구 (Vite 등) | 출판사 |
| 번들(bundle) | 빌드 결과물(브라우저로 가는 압축된 JS/CSS) | 인쇄된 책 |
| 트랜스파일(transpile) | 최신 문법 → 구형 브라우저용 문법으로 번역 | 어려운 표현을 쉬운 말로 |
| 미니파이(minify) | 공백·주석 제거로 파일 용량 줄이기 | 군더더기 빼고 압축 |
| 코드 분할(code split) | 한 권을 통째로 말고 필요한 장만 따로 | 챕터별 분권 |
| 빌드 에러 | 굽는 도중 멈춤(배포 실패) | 인쇄 중 오타로 정지 |
| 런타임 에러 | 다 구워졌는데 사용자가 쓰다가 터짐 | 책 보다 사고 |

도구 지형(디렉터용 요약):

- 🟢 **Vite** — 요즘 프론트 프로젝트의 사실상 기본 빌드 도구. 개발 중엔 빠르게 미리보기, 배포할 땐 한 번 구워 번들을 만듭니다.
- 🟢 **esbuild** — Vite 내부 등에서 쓰이는 *엄청 빠른* 번역·압축 엔진(고(Go)로 작성돼 매우 빠름). 디렉터는 "Vite가 속도를 esbuild에 빚지고 있다" 정도만 알면 충분.
- 🔵 **Webpack / Turbopack / Rollup** — 더 오래됐거나 특정 프레임워크가 쓰는 번들러. 이름이 로그에 보이면 "아, 번들러구나"라고 알아보면 됩니다.
- ⚪ AOT/JIT, tree shaking 같은 용어 — 몰라도 디렉팅엔 지장 없음. 필요할 때 AI에게 물어보세요.

환경변수(`.env`)와 빌드타임 주입 — **가장 중요한 보안 칸**:

| 구분 | 어디에 두나 | 번들에 섞이나? | 예 |
|---|---|---|---|
| 공개해도 되는 값 | `.env`에 `VITE_` 접두사 | **섞임**(브라우저로 나감) | Supabase URL, Supabase anon 키, 공개 분석 ID |
| 절대 비밀인 값 | 서버 환경변수에만 | **절대 섞으면 안 됨** | service_role 키, 결제 시크릿 키, LLM API 키 |

!!! warning "오해 주의: anon 키는 '비밀'이 아닙니다"
    Supabase **anon 키는 브라우저에 나가도 되는 공개 값**입니다. 보호는 키를 숨겨서가 아니라 **RLS(행 수준 보안)**로 합니다. 반대로 **service_role 키와 결제 시크릿 키는 절대 프론트(번들)에 넣으면 안 됩니다** — 이 값들은 서버(또는 n8n) 환경변수에만 둡니다. Vite에서 `VITE_` 접두사가 붙은 값만 빌드 시점에 번들로 들어간다는 점을 기억하세요. 비밀 값에 실수로 `VITE_`를 붙이면 그대로 새어나갑니다.

**⑤ AI에게 이렇게 시켜라**

```text
내 Vite + Supabase 프로젝트의 환경변수를 점검해줘.

1) .env.example을 만들어줘. 실제 값은 넣지 말고 자리표시자만.
   - 브라우저로 나가도 되는 공개 값(예: Supabase URL, anon 키)에는
     VITE_ 접두사를 붙이고, "공개 OK — 보호는 RLS로 한다"고 주석을 달아줘.
   - service_role 키, 결제 시크릿 키, LLM API 키처럼 절대 비밀인 값은
     프론트에 두면 안 되므로 .env.example에 아예 넣지 말고,
     "이건 서버 환경변수에만 — 번들에 넣지 말 것"이라고 별도 주석으로 경고해줘.

2) .gitignore에 .env가 들어가 있는지 확인하고, 없으면 추가해줘.

3) 마지막으로: 내 소스에서 비밀 값(service_role/시크릿 키 문자열)이
   혹시 프론트 코드나 VITE_ 변수로 새어 들어간 곳이 있는지 찾아서
   목록으로 알려줘. 왜 위험한지 한 줄씩 설명도 붙여줘.
```

빌드 에러가 났을 때:

```text
배포(빌드)가 실패했어. 아래 빌드 로그를 붙여넣을게.
코드를 곧장 고치지 말고, 먼저 이 에러가
(a) 빌드 시점(컴파일/번역 단계) 문제인지
(b) 런타임 시점(실행 중) 문제인지부터 분류해줘.
그다음 로그에서 '실제로 멈춘 첫 번째 에러 줄'이 어디인지 짚고,
어떤 파일·어떤 원인인지, 비전공자가 알아듣게 설명한 뒤
가장 안전한 수정안 한 가지만 제안해줘.

[여기에 빌드 로그 전체 붙여넣기]
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **비밀 키를 프론트에 박음.** AI는 "빠른 데모"라며 service_role·결제 시크릿·LLM API 키를 컴포넌트 코드나 `VITE_` 변수에 넣기도 합니다. 그 값은 빌드 시점에 번들로 들어가 **브라우저에서 그대로 보입니다.** 사람이 반드시 점검할 1순위.
- **빌드 에러 ≠ 런타임 에러를 뭉뚱그림.** AI는 "TS 타입 에러(빌드)"와 "데이터가 비어서 나는 에러(런타임)"를 같은 종류처럼 다루곤 합니다. *문법이 맞는 것과 동작하는 것은 다릅니다.* 빌드가 통과했다고 "코드는 맞다"고 단정하면 안 됩니다.
- **로그의 마지막 줄만 봄.** 빌드 로그는 진짜 원인 아래로 부수적 에러가 줄줄이 딸려 나옵니다. **위에서부터 첫 번째 에러**가 보통 진범입니다.
- **"내 컴퓨터에선 됐는데" 함정.** 로컬에선 멀쩡한데 배포 빌드만 실패하는 흔한 원인은 **환경변수 누락**(서버에 `.env` 값이 안 올라감), 대소문자 다른 파일명(로컬 윈도/맥은 관대, 배포 리눅스는 엄격), 의존성 버전 차이입니다.
- **모든 걸 번들에 다 넣음.** 이미지·큰 데이터를 통째로 묶으면 번들이 비대해져 첫 화면이 느려집니다. "필요한 것만, 나중 것은 나중에(코드 분할)"가 원칙.

**⑦ 검증하는 법**

1. **에러 위치 한 단어로 말하기.** 멈춘 지점이 빌드 로그(예: `Build error`, `Failed to compile`, `Type error`)면 **빌드 시점**, 사이트는 떴는데 버튼·동작에서 콘솔(F12)에 `TypeError: ... undefined`가 뜨면 **런타임 시점**입니다. 한 단어로 분류되면 절반은 해결된 것.
2. **번들에 비밀이 없는지 grep.** 배포된 사이트에서 F12 → **Sources** 탭(또는 Network에서 받은 `.js`)을 열고 `Ctrl+F`로 의심 키워드(예: `service_role`, 결제 시크릿 키의 일부 문자열)를 검색합니다. **0건이어야** 정상. anon 키나 Supabase URL이 보이는 건 정상(공개 값)입니다.
3. **빌드 산출물 폴더 확인.** 빌드 후 생기는 `dist/`(Vite 기준) 안의 파일이 압축된(공백·줄바꿈 없는) 형태인지 보면, "아 소스랑 다른 결과물이 나왔구나"가 눈으로 잡힙니다.
4. **로컬에서 먼저 구워보기.** 배포 전에 로컬에서 빌드 명령(예: `npm run build`)을 돌려보면, Vercel이 빨갛게 되기 전에 같은 에러를 미리 잡을 수 있습니다.

!!! example "💡 예시로 이해하기"
    내일 데모인데 Vercel 배포가 빨간 `Failed to compile`로 멈췄습니다. 패닉에 빠져 코드를 마구 고치는 대신, 디렉터는 먼저 칸을 가릅니다. "빌드 로그에서 멈췄으니 이건 *오븐에 넣기 전* 문제 — 사용자에겐 아직 안 갔다, 다행." 로그를 위에서부터 읽으니 첫 줄이 `Error: Missing environment variable: VITE_SUPABASE_URL`. 로컬에선 `.env` 덕분에 됐지만 **Vercel에 그 값을 안 올린 것**이 원인이었습니다. 코드는 멀쩡했죠. Vercel 설정에 환경변수를 넣고 다시 빌드하니 통과. 같은 김에 F12 Sources에서 `service_role`을 검색해 0건임을 확인하고, anon 키는 보이지만 "이건 공개 값, 보호는 RLS"라며 안심합니다. "배포가 안 돼요"라는 한 덩어리 공포가, `빌드 시점 / 환경변수 누락 / 비밀 유출 0건`이라는 세 문장으로 정리되는 순간 — 문제는 더 이상 무섭지 않습니다.
