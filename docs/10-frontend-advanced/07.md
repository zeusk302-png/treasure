# 접근성(a11y) 심화 — 모두가 쓰는 화면

**① 한 줄 정의**
접근성(a11y, accessibility의 a와 y 사이 글자 11개라서 a11y)이란 **눈이 안 보이거나, 마우스를 못 쓰거나, 색을 구분 못 하는 사람도 내 화면을 똑같이 쓸 수 있게** 만드는 것입니다.

**② 왜 중요한가 (디렉터 관점)**
접근성은 "착한 일"이 아니라 **세 가지 현실적 이유로 반드시 챙겨야 하는 품질 기준**입니다.

첫째, **법**입니다. 한국은 공공기관·일정 규모 이상 사업자에게 웹 접근성을 의무화하고 있고(장애인차별금지법, 국가표준 KWCAG), 해외 진출을 노린다면 미국 ADA·유럽 EAA처럼 더 강한 규제가 기다립니다. 접근성 미준수로 소송·시정명령을 받은 사례가 국내외에 쌓여 있습니다. 디렉터는 "우리 서비스가 법적으로 누구를 배제하고 있지 않은가"를 출시 전에 점검해야 합니다.

둘째, **돈과 사용자 수**입니다. 색약·노안·일시적 손 부상(손목 깁스), 지하철에서 한 손으로 폰 잡은 사람, 밝은 햇빛 아래 화면을 보는 사람 — 이 모두가 "접근성이 나쁘면 떠나는" 사용자입니다. 접근성은 장애인만이 아니라 **모든 사람의 사용 편의(UX)**를 끌어올립니다. 접근성 좋은 사이트는 검색엔진도 더 잘 읽습니다(시맨틱 마크업·alt 텍스트는 SEO와 한 몸).

셋째, **AI는 접근성을 가장 먼저 빠뜨립니다**. AI에게 "예쁜 로그인 화면 만들어줘"라고 하면 화면은 그럴듯하지만 alt 텍스트도, label도, 키보드 포커스도 없는 경우가 태반입니다. 보이는 것만 검수하는 디렉터는 이걸 통과시키고, 출시 후 "스크린리더로 가입이 안 된다"는 항의를 받습니다. 그래서 접근성은 **디렉터가 명시적으로 요구하고 검증해야만 들어오는 품질**입니다.

**③ 비유**
건물 입구를 떠올려 보세요. 계단만 있는 건물은 휠체어·유모차·무거운 짐을 든 사람을 막습니다. 경사로(ramp)를 하나 놓으면 휠체어 이용자뿐 아니라 캐리어 끄는 여행자, 자전거 끄는 사람까지 모두 편해집니다. 접근성은 **소수를 위한 특별 통로가 아니라 모두를 위한 경사로**입니다. 그리고 화면에서 그 경사로 역할을 하는 게 바로 시맨틱 마크업·alt 텍스트·키보드 조작입니다. 건물을 다 짓고 나서 경사로를 끼워 넣으면 비싸고 어색하듯, 접근성도 **처음 설계 때 넣어야 자연스럽고 싸게** 됩니다.

**④ 최소한 알 것**

접근성의 다섯 기둥과 디렉터가 챙길 핵심:

| 기둥 | 무엇인가 | 디렉터가 챙길 한 가지 |
|---|---|---|
| 키보드 내비게이션 | 마우스 없이 `Tab`·`Enter`·`방향키`만으로 모든 기능 사용 | Tab으로 끝까지 눌러봤을 때 못 누르는 버튼·안 보이는 포커스 테두리가 없는지 |
| 스크린리더 | 화면을 음성으로 읽어주는 보조기기(시각장애인용) | 이미지·아이콘 버튼이 "버튼"이 아니라 "장바구니에 담기"처럼 의미로 읽히는지 |
| 시맨틱 마크업 | 의미에 맞는 HTML 태그 사용 | `<div>`로 만든 가짜 버튼이 아니라 진짜 `<button>`·`<nav>`·`<h1>`을 썼는지 |
| ARIA | 시맨틱만으로 부족할 때 보조기기에 역할·상태를 알려주는 추가 속성 | 꼭 필요할 때만 최소로. (먼저 시맨틱 태그로 해결되는지 확인) |
| 색 대비 | 글자와 배경 색의 명암 차이 | 본문 글자가 배경과 충분히 대비되는지(흐린 회색 글자 금지) |

핵심 용어 빠른 사전:

- **시맨틱 마크업(semantic markup)**: 생긴 게 아니라 **뜻**으로 태그를 고르는 것. 제목은 `<h1>~<h6>`, 메뉴는 `<nav>`, 본문은 `<main>`, 버튼은 `<button>`, 링크는 `<a>`. 스크린리더는 이 뜻을 읽어 사용자에게 "여기는 메뉴", "이건 제목"이라고 알려줍니다.
- **alt 텍스트(대체 텍스트)**: 이미지를 못 보는 사람에게 그림을 말로 설명하는 글. `<img src="cat.jpg" alt="창가에 앉아 햇볕 쬐는 고양이">`. 장식용 이미지는 `alt=""`로 비워 "읽지 마"라고 알립니다.
- **label(레이블)**: 입력칸이 무엇을 받는 칸인지 알려주는 이름표. `<label>`을 입력칸과 연결하면 스크린리더가 "이메일, 입력칸"이라고 읽고, 글자를 눌러도 커서가 칸으로 들어갑니다.
- **포커스(focus)**: 지금 키보드 입력이 향하는 곳. Tab으로 이동할 때 **어디에 있는지 보이는 테두리(focus ring)**가 반드시 있어야 합니다. 이걸 디자인 이유로 지워버리면 키보드 사용자는 길을 잃습니다.
- **ARIA(Accessible Rich Internet Applications)**: HTML 기본 태그로 표현 안 되는 역할·상태(예: 펼침/접힘, 로딩 중)를 보조기기에 알려주는 속성 묶음(`aria-label`, `aria-expanded` 등). **"ARIA 없는 게 잘못된 ARIA보다 낫다"**는 게 제1원칙 — 남발하면 오히려 화면이 더 안 읽힙니다.
- **WCAG / KWCAG**: 국제·국내 웹 접근성 표준 지침. 등급은 A < AA < AAA. **실무 목표는 보통 AA**(법적 기준선도 대체로 AA 수준). 구체 수치(대비비율 등)는 표준 문서 확인 권장.

**⑤ AI에게 이렇게 시켜라**

```text
[접근성 포함 요청]
회원가입 폼을 만들어줘. 디자인뿐 아니라 웹 접근성(a11y)을 반드시 지켜줘.
조건:
1. 시맨틱 마크업: 버튼은 <button>, 메뉴는 <nav>, 본문은 <main>으로.
   div로 만든 가짜 버튼/링크 금지.
2. 모든 입력칸에 연결된 <label>을 붙여줘(for/id 연결). placeholder로 label을 대체하지 마.
3. 모든 의미 있는 이미지·아이콘 버튼에 alt 또는 aria-label을 넣어줘.
   장식용 이미지는 alt=""로 비워줘.
4. 키보드만으로 가입 완료까지 가능해야 해(Tab 순서가 자연스럽고,
   포커스 테두리 outline을 절대 지우지 마).
5. 본문 글자와 배경의 색 대비를 WCAG AA 기준으로 맞춰줘
   (흐린 회색 글자 금지). 정확한 대비비율 수치는 표준 확인 권장.
6. ARIA는 시맨틱 태그로 안 되는 경우에만 최소로 써줘.
마지막에 '이 폼이 접근성을 어떻게 충족하는지' 항목별로 한 줄씩 설명해줘.
```

추가로, 이미 만든 화면을 점검시키는 프롬프트도 유용합니다:

```text
[접근성 점검 요청]
아래 HTML의 웹 접근성 문제를 진단해줘. 코드를 바로 고치지 말고,
먼저 (1) 키보드로 못 쓰는 부분 (2) 스크린리더가 의미 없이 읽는 부분
(3) alt/label 누락 (4) 색 대비 의심 지점 (5) 잘못 쓴/남발한 ARIA
다섯 항목으로 나눠 문제 목록을 만들어줘. 그다음 우선순위를 매겨줘.
[여기에 HTML 붙여넣기]
```

**⑥ 흔한 함정 / AI가 틀리는 것**
AI(와 사람)가 접근성에서 가장 자주 저지르는 실수들입니다:

- **`<div>`로 만든 가짜 버튼**: 보기엔 버튼인데 `<div onclick=...>`이라 키보드로 못 누르고 스크린리더가 "버튼"으로 안 읽습니다. 진짜 `<button>`을 써야 클릭·엔터·포커스가 공짜로 따라옵니다.
- **alt 텍스트 누락 또는 무의미**: alt가 없거나 `alt="이미지"`, `alt="image1.png"`처럼 파일명을 넣는 것. 그림이 전하는 **정보**를 적어야 합니다.
- **placeholder로 label 대체**: 회색 안내문(placeholder)은 입력을 시작하면 사라져 무슨 칸인지 잊게 만들고, 스크린리더 지원도 들쭉날쭉합니다. label은 별도로 둬야 합니다.
- **포커스 테두리 제거**: 디자인이 거슬린다고 `outline: none`만 넣고 대체 표시를 안 하면 키보드 사용자는 커서를 완전히 잃습니다. 지우려면 더 예쁜 포커스 스타일로 **대체**해야 합니다.
- **ARIA 남발**: "접근성 좋게 해줘" 하면 AI가 `role`·`aria-*`를 마구 뿌리는데, 시맨틱 태그면 충분한 곳에 ARIA를 덧대면 오히려 보조기기가 혼란스러워합니다. **첫째 규칙: 가능하면 ARIA 대신 올바른 HTML 태그.**
- **색만으로 정보 전달**: "빨간 칸은 오류"처럼 색에만 의존하면 색약 사용자는 못 알아챕니다. 색 + 아이콘 + 글자(예: ⚠ "이메일 형식이 틀렸습니다")를 함께 줘야 합니다.
- **흐린 회색 글자**: 트렌디해 보여서 연한 회색 본문을 자주 쓰는데, 색 대비가 모자라면 노안·햇빛 아래 사용자가 못 읽습니다.

**⑦ 검증하는 법**
코드를 몰라도 비전공자가 할 수 있는 점검 4종 세트:

1. **마우스를 치워라(키보드 테스트)**: `Tab`만 눌러 화면을 끝까지 돌아보세요. 모든 버튼·링크·입력칸에 포커스 테두리가 또렷이 보이고, 순서가 위→아래·좌→우로 자연스러우며, `Enter`로 실제 동작하면 합격입니다. 못 누르는 곳이 있으면 거기가 `<div>` 가짜 버튼일 확률이 높습니다.
2. **스크린리더로 들어라**: 윈도우는 무료 **NVDA**, 맥은 내장 **VoiceOver**를 켜고 화면을 읽혀 보세요. 이미지가 "그래픽"이 아니라 의미로, 버튼이 이름으로 읽히면 좋습니다.
3. **자동 검사 도구를 돌려라**: 크롬 개발자도구(F12) → **Lighthouse** 탭 → Accessibility 점수를 봅니다. 무료 확장 **axe DevTools**나 **WAVE**도 문제 위치를 짚어줍니다. 단, 자동 도구는 전체의 약 일부만 잡으니 1·2번(사람 점검)과 병행하세요.
4. **색 대비를 재라**: 개발자도구의 색 선택기나 "contrast checker" 도구에 글자색·배경색을 넣어 AA 기준 통과 여부를 확인합니다(정확한 합격 비율 수치는 표준 확인 권장).

!!! example "💡 예시로 이해하기"
    카페 예약 사이트를 만들었다고 합시다. 마우스로는 완벽하게 돌아갑니다. 그런데 시각장애인 손님이 NVDA 스크린리더로 들어왔습니다. 날짜 옆 달력 아이콘 버튼은 `<div>`라서 Tab으로 잡히지 않아 건너뛰고, 사진들은 alt가 없어 "그래픽, 그래픽, 그래픽"만 반복되고, "예약하기"는 잡았지만 비활성/활성 상태를 안 알려줘 눌리는지 알 수 없습니다. 결국 예약을 포기합니다. 여기서 디렉터가 한 일은 단 두 가지였습니다 — AI에게 "시맨틱 태그·alt·label·키보드·색 대비를 지키고 항목별로 충족 근거를 설명하라"고 **명시적으로 요구**하고, 받은 화면을 **마우스를 치운 채 Tab으로 끝까지 눌러보고 Lighthouse 점수를 확인**한 것. 보이는 화면만 통과시켰다면 이 손님은 영영 예약하지 못했을 겁니다. 접근성은 "있으면 좋은 것"이 아니라 **이 손님 한 명을 잃느냐 마느냐**의 문제입니다.
