# 상태(state) — 데이터가 화면을 결정한다

**① 한 줄 정의**
**상태(state)는 '지금 이 화면이 어떤 모습이어야 하는가'를 담은 데이터**이고, 그 데이터가 바뀌면 화면은 자동으로 다시 그려집니다. 즉, 화면을 직접 손으로 고치는 게 아니라 **데이터만 바꾸면 화면이 따라온다**가 현대 프론트엔드의 핵심 사고방식입니다.

**② 왜 중요한가 (디렉터 관점)**
비전공 디렉터가 AI에게 "장바구니에 담기 버튼 눌렀는데 숫자가 안 올라가요"라고만 말하면 AI는 버튼 코드만 헤집습니다. 하지만 "장바구니 개수라는 **상태**는 어디에 있고, 담기 버튼이 그 상태를 **갱신**하는지, 헤더의 숫자는 그 상태를 **구독**하는지" 식으로 나눠 물으면 문제의 위치가 단번에 좁혀집니다.

현대 웹앱의 버그는 십중팔구 **"상태"의 문제**입니다. 보이는 게 안 맞는다 = 데이터(상태)가 틀렸거나, 데이터는 맞는데 화면이 안 따라왔거나, 같은 데이터를 두 군데 복사해 둬서 서로 어긋났거나. 이 세 가지로 분류만 할 줄 알아도 디렉터는 AI에게 정확한 질문을 던지고, AI가 내놓은 답이 헛다리인지 아닌지 가려낼 수 있습니다. **"상태를 어디에 두느냐"는 프론트엔드 설계의 절반**입니다 — 코드를 한 줄도 안 짜도, 이 판단만큼은 디렉터가 직접 내려야 합니다.

**③ 비유**
**상태 = 화이트보드, 화면 = 그 화이트보드를 비추는 거울.** 회의실 화이트보드에 "참석자 3명"이라고 적혀 있고, 벽 거울이 그 화이트보드를 그대로 비춥니다. 한 명이 더 들어와 화이트보드 숫자를 4로 고치면, 거울 속 숫자도 저절로 4가 됩니다. 거울을 직접 닦아 4로 만드는 게 아니라(=화면을 직접 조작하는 옛날 방식), **원본인 화이트보드만 고치면 거울이 따라오는 것**(=상태 기반 방식)입니다.

여기서 두 가지가 더 나옵니다. **props는 옆 사람에게 건네는 쪽지**입니다 — "너는 이 숫자만 보여줘"라고 받아 적기만 하고 고치지는 못하는 종이. 그리고 **전역상태(스토어)는 건물 1층 로비의 큰 전광판**입니다 — 모든 층(컴포넌트)이 엘리베이터 타고 내려와 한 번에 같은 정보를 보는, 공유 화이트보드.

**④ 최소한 알 것**

먼저 가장 헷갈리는 **state vs props** 구분부터.

| 구분 | state (상태) | props (속성) |
|---|---|---|
| 비유 | 내 화이트보드(내 것) | 위에서 받은 쪽지 |
| 누가 소유 | 그 컴포넌트 자신 | 부모가 만들어 자식에게 내려줌 |
| 바꿀 수 있나 | 예 (자기가 갱신) | 아니오 (받아서 읽기만, 읽기전용) |
| 흐름 방향 | 안에서 변함 | 위→아래로 흐름(단방향) |
| 예시 | "모달이 열려 있나?", 입력창 글자 | 버튼에 표시할 라벨, 카드에 띄울 제목 |

상태를 둘 위치를 정하는 판단 기준:

- **🟢 메인 — 로컬 상태(컴포넌트 안)**: 그 화면 조각 하나만 쓰는 데이터. 예) 토글 스위치 on/off, 입력창에 친 글자, 아코디언 펼침 여부. **"한 군데서만 쓰면 거기 둔다"**가 기본.
- **🟡 대안 — 들어올리기(lift state up)**: 두 형제 컴포넌트가 같은 데이터를 봐야 하면, 둘의 공통 부모로 상태를 끌어올려 props로 내려준다. 예) 검색창과 결과목록이 같은 '검색어'를 공유.
- **🔵 나중에 — 전역상태(스토어)**: 앱 전체 여러 곳에서 멀리 떨어져 같은 데이터를 봐야 할 때. 예) 로그인한 사용자 정보, 다크모드, 장바구니. 도구로는 Zustand(가벼움)·Redux Toolkit·Jotai, 프레임워크 내장 Context 등 (도구 선택·버전은 확인 권장).
- **⚪ 몰라도 됨(지금은)**: 서버에서 온 데이터(목록·상세)는 사실 '상태'라기보다 '서버 데이터 캐시'라서 TanStack Query(React Query)·SWR 같은 전용 도구로 다루는 게 정석 — 이름만 알아두고 깊이는 나중에.

핵심 원리 세 줄:

- **단방향 데이터 흐름**: 데이터는 위에서 아래로만 흐른다(부모→자식). 자식이 부모 데이터를 바꾸려면 부모가 내려준 '함수'를 호출해 부탁한다. 흐름이 한 방향이라 추적이 쉽다.
- **불변성(immutability)**: 상태를 바꿀 땐 **기존 것을 직접 고치지 말고 새 값으로 통째 교체**한다. 도구가 "어, 값이 바뀌었네?"를 알아채는 방식이라, 배열·객체를 몰래 수정하면 화면이 안 따라오는 대표적 함정이 생긴다.
- **파생값은 상태가 아니다**: 다른 상태로 *계산해 낼 수 있는 값*은 상태로 저장하지 말고 그때그때 계산한다(아래 ⑥ 참고).

**⑤ AI에게 이렇게 시켜라**

```text
React로 만든 우리 쇼핑몰에 '장바구니' 기능을 붙이려고 해. 코드를 주기 전에
'상태(state) 설계'부터 같이 잡아줘.

1) 장바구니 개수/담긴 상품 목록이라는 상태를 '어디에' 두는 게 맞아?
   - 헤더의 장바구니 아이콘(숫자 배지)
   - 상품 카드의 '담기' 버튼
   - 별도 페이지인 '장바구니 페이지'
   이 셋이 같은 데이터를 봐야 하는데, 로컬 상태 / 부모로 들어올리기 /
   전역 스토어 중 무엇이 적절한지, 그 이유를 비전공자도 알게 설명해줘.

2) 추천한 방식으로 갈 때, '담기 버튼을 누르면 헤더 숫자가 즉시 올라가는'
   데이터 흐름을 글로 먼저 그려줘(누가 상태를 갖고, 누가 갱신하고,
   누가 구독하는지). 그 다음에 코드를 줘.

3) 상태를 바꿀 때 배열/객체를 직접 수정하지 말고 새 값으로 교체하는
   '불변성'을 지켜줘. 왜 그래야 하는지 주석으로 한 줄 달아줘.

마지막에, 새로고침하면 장바구니가 날아가는지(메모리 상태)와
유지되는지(localStorage/서버 저장) 중 우리가 뭘 원하는지 나한테 되물어줘.
```

> 프롬프트 팁: "상태 설계부터 글로 잡고 코드는 그 다음에"라고 못 박으면, AI가 곧장 코드부터 쏟아내 엉뚱한 곳에 상태를 박는 사고를 막을 수 있습니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **불필요한 상태(파생값을 상태로 저장)**: 가장 흔한 실수. `items`(상품 목록) 상태가 있는데 `itemCount`(개수)를 **따로 상태로** 또 둡니다. 그러면 상품을 지웠을 때 `items`는 줄었는데 `itemCount`는 안 줄어 숫자가 안 맞는 버그가 납니다. 개수는 `items.length`로 **그때그때 계산**하면 영원히 어긋나지 않습니다. → 점검 질문: *"이 값, 다른 상태로 계산해 낼 수 있는 거 아냐?"*
- **상태 동기화 버그(같은 데이터를 두 곳에 복사)**: 사용자 이름을 헤더에도, 마이페이지에도 각각 별도 상태로 들고 있으면, 이름을 바꿨을 때 한쪽만 갱신돼 어긋납니다. **진실의 원본(single source of truth)은 하나**여야 하고 나머지는 그걸 구독해야 합니다.
- **불변성 위반**: AI가 `state.list.push(x)`처럼 배열을 직접 찔러 넣는 코드를 줄 때가 있습니다. 화면이 안 바뀌면 이걸 의심하세요(새 배열로 교체해야 함).
- **전역상태 남용**: "혹시 나중에 쓸지 모르니"라며 토글 하나까지 전부 전역 스토어에 박습니다. 전역상태는 공유가 진짜 필요할 때만 — 남발하면 추적이 어려워지고 한 곳을 고치면 엉뚱한 데가 깨집니다. **로컬로 충분하면 로컬에.**
- **상태에 비밀값 넣기(보안)**: 프론트 상태/스토어에 든 값은 전부 브라우저에서 들여다보입니다. Supabase **anon 키는 프론트에 둬도 됩니다(공개 가능, 보호는 RLS로)** — 헷갈리지 마세요. 반대로 **service_role 키나 외부 API 비밀키는 절대 프론트 상태에 두면 안 됩니다**(서버/n8n에서만). 또한 사용자가 입력한 글자를 화면에 출력할 땐 `textContent`로 — `innerHTML`은 XSS 위험.

**⑦ 검증하는 법**

1. **React DevTools(브라우저 확장)**로 컴포넌트를 클릭하면 그 컴포넌트의 state·props가 그대로 보입니다. 버튼을 눌러보며 *숫자가 화면에서 올라갈 때 DevTools의 상태값도 같이 올라가는지* 눈으로 확인하세요. 화면은 그대로인데 상태값만 올랐다면 → 화면이 상태를 안 따라오는 문제(불변성·구독 의심).
2. **"진실의 원본 한 개" 테스트**: 같은 정보(예: 사용자 이름)가 두 군데 떠 있다면, 한 곳에서 바꿔보세요. 다른 곳이 **즉시 같이 바뀌면** 상태가 하나로 잘 묶인 것, 한쪽만 바뀌면 복사본이 따로 노는 동기화 버그입니다.
3. **파생값 테스트**: 목록에서 항목 하나를 삭제했을 때 개수·합계 같은 요약 숫자가 *자동으로* 맞아떨어지면 잘 설계된 것. 손으로 별도 갱신해야 한다면 그건 불필요한 상태입니다.
4. AI가 준 코드라면 그대로 물어보세요: *"이 중 진짜 상태로 둬야 하는 값과, 계산으로 대체할 수 있는 값을 구분해줘."*

!!! example "💡 예시로 이해하기"
    카페 주문 화면을 떠올려 봅시다. 손님이 '아메리카노 +' 버튼을 탁 누릅니다. 옛날 방식이라면 개발자가 "버튼 옆 숫자 칸을 찾아 1을 더해 다시 써넣고, 화면 위 총합도 찾아 다시 계산해 써넣고, 결제 버튼의 '2,500원'도 고쳐 써넣고…" 거울을 손으로 일일이 닦아야 합니다. 한 곳을 빠뜨리면 숫자가 어긋나죠. 상태 기반 방식은 다릅니다. 화이트보드(상태)에 적힌 `{ 아메리카노: 1 }`을 `{ 아메리카노: 2 }`로 **딱 한 번** 고치면, 그 화이트보드를 비추는 모든 거울 — 수량 배지, 총합, 결제 금액 — 이 **알아서 동시에** 새 숫자로 바뀝니다. 디렉터가 AI에게 "수량 상태 하나만 진실의 원본으로 두고, 총합·결제액은 거기서 계산해서 보여줘"라고 시키는 순간, '숫자가 따로 논다'는 버그 자체가 생길 수 없는 구조가 됩니다.
