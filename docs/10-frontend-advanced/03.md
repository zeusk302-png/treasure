# 디자인 시스템과 토큰 — 한 번 정해 일관되게

**① 한 줄 정의**
디자인 시스템은 **색·간격·글자 크기 같은 디자인 결정을 '토큰(이름 붙인 값)'으로 한 번 정해 두고, 화면 곳곳에서 그 이름만 불러 쓰게 만드는 규칙집**입니다. 그래서 버튼 하나, 제목 하나가 페이지마다 제각각이 아니라 **한 몸처럼** 보입니다.

**② 왜 중요한가 (디렉터 관점)**
AI에게 "여기 버튼 만들어줘"를 열 번 시키면, 사람이 손대지 않는 한 **열 개의 미묘하게 다른 버튼**이 나옵니다. 파란색이 `#2563EB`였다가 `#1E6FEB`였다가, 모서리가 둥글었다가 각졌다가, 여백이 12px였다가 16px였다가. 하나하나는 멀쩡해 보여도 모아 놓으면 "어딘가 어설픈 사이트", 즉 **아마추어 냄새**가 납니다. 이걸 사람이 매번 눈으로 잡으려면 끝이 없습니다.

디렉터의 무기는 **"값을 직접 보지 말고, 규칙을 정해 AI에게 그 규칙을 강제"** 하는 것입니다. "파란색은 항상 `--color-primary` 토큰을 써. 새 색을 발명하지 마"라고 한 번 정해 두면, 이후 모든 화면이 자동으로 통일됩니다. 더 큰 이득은 **변경**입니다. 브랜드 색을 바꿔야 할 때, 디자인 시스템이 있으면 토큰 한 줄(`--color-primary`)만 고치면 사이트 전체가 따라 바뀝니다. 없으면 수백 군데에 흩어진 `#2563EB`를 일일이 찾아 고쳐야 하고, AI에게 시켜도 몇 개는 반드시 빠집니다. **"한 곳을 고치면 전체가 바뀐다"** — 이게 디자인 시스템이 디렉터에게 주는 시간과 일관성입니다.

**③ 비유**
프랜차이즈 카페를 떠올려 보세요. 서울 지점이든 부산 지점이든 간판 초록색, 컵 로고 위치, 직원 앞치마 색이 똑같습니다. 각 지점 사장이 "오늘은 간판을 좀 더 진한 초록으로 해볼까?" 하고 마음대로 정하지 못합니다. 본사가 **브랜드 매뉴얼**에 "초록색 = 펜톤 3425C"라고 딱 한 번 정해 놓고, 모든 지점이 그 **이름**을 따르기 때문입니다. 토큰은 이 매뉴얼의 한 줄("초록색 = 펜톤 3425C")이고, 디자인 시스템은 매뉴얼 전체입니다. 신입 알바(=AI)가 새로 와도 매뉴얼만 주면 어느 지점에서 일하든 똑같은 결과를 냅니다. 매뉴얼이 없으면? 알바마다 자기 취향대로 칠해서 "같은 브랜드 맞아?" 소리가 나오죠.

**④ 최소한 알 것**

**(1) 토큰의 종류 — 무엇을 이름 붙여 두는가**

| 토큰 종류 | 정하는 것 | 예시 이름 | 안 정하면 생기는 일 |
|---|---|---|---|
| 색(color) | 주색·보조색·배경·텍스트·경고색 | `color-primary`, `color-danger` | 비슷한 파란색이 수십 종 난립 |
| 간격(spacing) | 여백·요소 사이 거리 | `space-2`, `space-4` | 어떤 곳은 13px, 어떤 곳은 17px |
| 타이포(typography) | 글자 크기·굵기·줄간격 | `text-lg`, `font-bold` | 제목 크기가 페이지마다 제각각 |
| 둥글기(radius) | 모서리 둥근 정도 | `radius-md` | 버튼마다 모서리가 다름 |
| 그림자(shadow) | 떠 보이는 음영 | `shadow-card` | 카드 입체감이 들쭉날쭉 |

핵심은 **"값(13px)이 아니라 이름(`space-3`)을 쓴다"** 입니다. 이름을 쓰면 나중에 그 이름이 가리키는 값만 바꿔도 전부 따라옵니다.

**(2) 토큰을 적용하는 두 흐름**

| 접근 | 무엇인가 | 비유 | 누가 정하나 |
|---|---|---|---|
| 디자인 토큰 정의 | 색·간격 등을 이름=값으로 선언 (CSS 변수, Tailwind 설정 등) | 브랜드 매뉴얼 작성 | 디렉터(또는 디자이너) |
| 유틸리티 CSS(Tailwind) | 토큰을 `class`로 바로 갖다 붙이는 방식 | 매뉴얼 색을 골라 칠하기 | AI가 코드에서 |
| 컴포넌트 라이브러리(shadcn/ui 등) | 토큰을 따르는 버튼·카드를 미리 만들어 둔 부품 상자 | 본사가 보내준 완제품 컵·간판 | 가져다 조립 |

**(3) Tailwind / 유틸리티 CSS 한 입**
`<button class="bg-primary text-white px-4 py-2 rounded-md">` 처럼, **이미 정의된 토큰 이름을 클래스로 붙여** 스타일을 입히는 방식입니다. `px-4`는 "좌우 여백 = `space-4` 토큰", `bg-primary`는 "배경 = 주색 토큰"을 뜻합니다. 장점은 **"손으로 임의의 값을 못 쓰게"** 되어 자연히 토큰만 쓰게 되는 것 — 즉 일관성이 강제됩니다. (`bg-[#2563EB]` 같은 임의값 문법도 있지만, 이건 "매뉴얼 무시하고 내 맘대로 칠하기"라 가능하면 막아야 합니다.)

**(4) 컴포넌트 라이브러리(shadcn/ui 등) 한 입**
버튼·입력창·모달처럼 자주 쓰는 부품을, **이미 디자인 토큰을 따르도록 만들어 둔 묶음**입니다. 처음부터 "버튼을 어떻게 둥글릴까"를 고민하지 않고 검증된 부품을 가져다 씁니다. shadcn/ui는 그중에서도 "부품 코드를 내 프로젝트 안으로 복사해 와서 내가 토큰을 고쳐 쓰는" 방식이라 자유도가 높습니다. (라이브러리마다 철학·라이선스·버전이 다르니 **공식 문서로 현재 사용법 확인 권장**.)

> 길라잡이: 🟢 **토큰부터 정하기**(색·간격·타이포 한 묶음) 🟢 **Tailwind로 토큰만 쓰기** 🟡 **컴포넌트 라이브러리는 필요해질 때 도입** 🔵 **디자인 토큰을 Figma·코드 자동 동기화하는 도구는 나중에** ⚪ **토큰 이론(원자 디자인 등) 용어 암기는 몰라도 됨**

**⑤ AI에게 이렇게 시켜라**

```text
역할: 너는 우리 사이트의 디자인 시스템을 지키는 프론트엔드 개발자야.

먼저 아래 디자인 토큰을 프로젝트에 한 곳(예: Tailwind 설정 또는 CSS 변수)에 정의해줘.
임의의 색·간격·글자크기를 코드에 직접 쓰지 말고, 반드시 이 토큰 이름만 사용해.

[디자인 토큰]
- color-primary: #2563EB (주 버튼·링크)
- color-danger: #DC2626 (삭제·경고)
- color-text: #1F2937 / color-muted: #6B7280
- 간격 단위: 4px 배수만 사용 (space-1=4, space-2=8, space-4=16 ...)
- 글자: 본문 16px, 제목 24/20/18, 굵기는 normal/medium/bold만
- 모서리: radius-md(8px) 기본
- 다크모드: 색은 토큰을 통해서만 바꾸고, 컴포넌트 코드는 안 건드리게

요청:
1) 위 토큰을 정의하는 파일을 만들고, 어디에 정의했는지 알려줘.
2) 그다음 '로그인 버튼' 컴포넌트를 만들되, #파란색 같은 값을 직접 쓰지 말고
   반드시 토큰(클래스/변수)으로만 스타일을 입혀줘.
3) 왜 그 토큰을 골랐는지 한 줄씩 주석으로 설명해줘. (비전공자가 읽게)

앞으로 새 UI를 만들 때마다 이 토큰을 우선 사용하고,
토큰에 없는 새 값이 꼭 필요하면 '새 토큰을 추가하자'고 먼저 나에게 제안해.
임의값(예: bg-[#1E6FEB])은 쓰지 마.
```

이 프롬프트의 핵심은 두 가지입니다. (1) **토큰을 먼저 한 곳에 정의**하게 하고, (2) "임의값 금지, 없으면 새 토큰을 제안하라"는 **규칙을 명시**해 AI가 매번 색을 새로 발명하는 걸 막는 것. 디렉터는 픽셀을 보지 않고 **이 규칙이 지켜졌는지**만 봅니다.

**⑥ 흔한 함정 / AI가 틀리는 것**

- **색을 매번 새로 발명한다.** 토큰을 정해 줘도, 다음 요청에서 슬그머니 `bg-[#1E6FEB]`나 `style="color:#2462eb"` 같은 **임의값**을 박습니다. 한 글자 차이라 눈으로 잡기 어렵습니다 → 임의값을 쓰지 말라고 매번 못 박고, 검증 단계에서 임의 색상 코드를 검색하세요.
- **토큰을 정의만 하고 안 쓴다.** Tailwind 설정에 토큰을 멋지게 적어 놓고, 정작 컴포넌트에는 옛날 하드코딩 값을 그대로 둡니다. "정의했으니 된 것 아닌가?"는 착각 — **실제로 그 이름이 쓰였는지**가 중요합니다.
- **간격이 토큰을 벗어난다.** 색은 잘 지키면서 여백은 `mt-[13px]`처럼 어중간한 값을 씁니다. 4px 배수만 쓰라고 명시해야 합니다.
- **다크모드/접근성 대비를 깨뜨린다.** 예쁜 회색 텍스트를 골랐는데 배경과 대비가 약해 안 보이는 경우. 색 토큰은 **대비(명암 차)도 함께** 검증해야 합니다(접근성은 ⑧ 참고).
- **라이브러리 버전·API를 옛것으로 답한다.** shadcn/ui 등은 설치법·명령이 자주 바뀝니다. AI가 주는 명령이 지금도 맞는지 **공식 문서로 확인 권장**.
- (보안 곁가지) 디자인과 무관해 보여도, 사용자 입력을 화면에 넣을 땐 `textContent`로. 멋진 컴포넌트라도 `innerHTML`로 사용자 글을 넣으면 XSS 위험은 그대로입니다.

**⑦ 검증하는 법**

1. **눈 검증 — 나란히 놓기.** 같은 역할의 요소(예: 주요 버튼)를 여러 페이지에서 캡처해 나란히 붙여 보세요. 색·둥글기·여백이 **똑같으면** 일관성 합격, 미묘하게 다르면 어딘가 토큰을 안 쓴 곳입니다.
2. **코드 검색 — 임의값 사냥.** 프로젝트에서 색상 코드(`#`로 시작하는 6자리)와 임의값 클래스(`-[`)를 검색합니다. 토큰 정의 파일 말고 **컴포넌트 코드에 날색이 박혀 있으면** 그게 어긴 자리입니다. AI에게 "이 프로젝트에서 토큰을 안 쓰고 직접 색·간격을 박은 곳을 전부 찾아 목록으로 줘"라고 시키면 빠릅니다.
3. **변경 테스트 — 한 곳만 바꿔 보기.** `color-primary` 토큰 값 하나만 빨강으로 바꿔 보세요. **모든 주 버튼·링크가 빨강으로 바뀌면** 토큰이 제대로 연결된 것. 일부만 바뀌면, 안 바뀐 곳이 토큰을 안 쓴 곳입니다.
4. **대비 도구.** 브라우저 개발자도구(F12)의 접근성/대비 검사나 색 대비 검사 도구로, 텍스트가 배경에서 충분히 읽히는지 확인합니다.

!!! example "💡 예시로 이해하기"
    수료 동기가 만든 쇼핑몰을 열어 보니, 메인 페이지 '구매' 버튼은 짙은 파랑에 모서리가 둥글고, 상세 페이지 '구매' 버튼은 살짝 다른 파랑에 모서리가 각졌습니다. 둘 다 멀쩡해 보이지만 같이 보면 "급조한 느낌"이 납니다. 원인은 단순합니다 — AI에게 버튼을 두 번 따로 시켰고, 매번 색·둥글기를 새로 정한 것. 해결도 단순합니다. `color-primary`와 `radius-md` 토큰을 한 번 정의하고, AI에게 "앞으로 모든 버튼은 이 토큰만 써, 임의값 금지"라고 시킨 뒤 두 버튼을 다시 만들게 하면 둘이 똑같아집니다. 나중에 브랜드 색을 초록으로 바꿀 때도 토큰 한 줄만 고치면 두 페이지의 버튼이 동시에 초록으로 바뀝니다. **디렉터가 픽셀을 일일이 맞추는 게 아니라, "한 번 정하고 규칙을 강제"하는 순간 일관성은 공짜로 따라옵니다.**
