# 프론트 성능 — Core Web Vitals와 체감 속도

**① 한 줄 정의**
프론트 성능은 "사이트가 **얼마나 빨리 보이고(LCP), 안 흔들리고(CLS), 잘 반응하는가(INP)**"를 사용자가 느끼는 그대로 측정·개선하는 일이고, 그 핵심 지표 묶음이 구글의 **Core Web Vitals(핵심 웹 지표)** 입니다.

**② 왜 중요한가 (디렉터 관점)**
성능은 "있으면 좋은 것"이 아니라 **돈과 검색 순위에 직결되는 것**입니다. 페이지가 1초 늦게 뜨면 사람들은 뒤로가기를 누르고(이탈률 상승), 장바구니까지 가던 손님이 사라집니다. 구글은 Core Web Vitals를 **검색 순위 신호**로 쓰기 때문에 느린 사이트는 노출에서도 불리합니다.

디렉터에게 더 중요한 건 **"느리다"는 막연한 불평을 숫자로 쪼개는 능력**입니다. 사용자가 "느려요"라고 하면 그건 한 덩어리가 아닙니다. (가) 첫 화면이 늦게 뜨는 것(LCP), (나) 글을 읽으려는데 광고가 끼어들어 화면이 펄쩍 뛰는 것(CLS), (다) 버튼을 눌렀는데 멍하니 반응이 없는 것(INP)은 **원인도 처방도 전혀 다릅니다.** AI에게 "사이트 느린 거 고쳐줘"라고 던지면 엉뚱한 데를 손대지만, "LCP가 4초인데 가장 큰 요소가 히어로 이미지다, 이걸 줄여줘"라고 하면 정확히 처방합니다. 디렉터는 코드를 짜는 사람이 아니라 **느림의 정체를 지목해 주는 사람**입니다.

**③ 비유**
식당에 손님이 들어왔다고 합시다. 성능은 세 가지 체감으로 나뉩니다. **(1) 음식이 언제 나오나(LCP)** — 메인 요리가 늦으면 손님은 "여기 느리네" 합니다. **(2) 자리가 안 흔들리나(CLS)** — 막 수저를 들었는데 종업원이 테이블을 밀어 국이 쏟아지면 짜증이 납니다. 광고·이미지가 뒤늦게 로드되며 본문을 아래로 밀어버리는 게 딱 이겁니다. **(3) 부르면 바로 오나(INP)** — "여기요!" 했는데 한참 뒤에 오면 답답합니다. 버튼을 눌렀는데 화면이 멍 때리는 게 이것이죠.

그리고 **번들 크기**는 "주방이 한 번에 들여놓는 식재료 박스의 무게"입니다. 손님은 떡볶이 하나 시켰는데 주방이 매번 냉장고 전체를 통째로 들고 나오면(거대한 JS 한 덩어리), 정작 떡볶이가 늦게 나옵니다. **코드 분할·지연 로딩**은 "지금 당장 필요한 재료만 먼저, 나머지는 주문 들어올 때 꺼내는" 것입니다.

**④ 최소한 알 것**

핵심 3대 지표(Core Web Vitals):

| 약어 | 뜻 | 무엇을 재나 | 좋음 기준(목표, 확인 권장) |
|---|---|---|---|
| LCP | Largest Contentful Paint | 가장 큰 콘텐츠(보통 히어로 이미지·제목)가 뜨는 시각 | 2.5초 이하 |
| CLS | Cumulative Layout Shift | 로딩 중 화면이 얼마나 펄쩍 뛰나(레이아웃 이동) | 0.1 이하 |
| INP | Interaction to Next Paint | 클릭·입력에 화면이 반응하는 속도 | 200ms 이하 |

> INP는 2024년에 기존 FID(First Input Delay)를 대체한 지표입니다. 옛 글에 FID가 나와도 지금 기준은 INP라고 생각하세요. (정확한 기준 수치는 web.dev에서 확인 권장.)

성능을 개선하는 대표 무기:

- **이미지 최적화** — 가장 효과 큰 한 방. 4MB 사진을 그대로 올리지 말고 **WebP/AVIF** 같은 최신 포맷 + 화면 크기에 맞춘 리사이즈. `width`/`height`를 지정해 CLS도 막음.
- **코드 분할(code splitting)** — 거대한 JS 한 덩어리를 페이지·기능별로 쪼개 **지금 필요한 것만** 내려받음.
- **지연 로딩(lazy loading)** — 화면 밖(스크롤 내려야 보이는) 이미지·컴포넌트는 보일 때 로드. 이미지엔 `loading="lazy"` 한 줄.
- **폰트 최적화** — 웹폰트는 무겁고 늦게 떠 글자가 깜빡임(FOIT/FOUT). `font-display: swap`, 필요한 글자만 추리는 서브셋, 미리 불러오기(`preload`).
- **번들 크기 줄이기** — 안 쓰는 코드 털기(tree shaking), 무거운 라이브러리 가벼운 것으로 교체, 압축(gzip/brotli).
- **측정 도구** — **Lighthouse**(크롬 F12 → Lighthouse 탭)로 점수와 진단을, 실제 사용자 데이터는 **PageSpeed Insights**로 확인.

판단 길라잡이:

- 🟢 **메인**: 이미지 먼저 최적화 + 이미지에 `width/height` 지정 + Lighthouse로 측정. 비전공 디렉터가 얻는 효과가 가장 큽니다.
- 🟡 **대안**: 폰트 `swap`, 화면 밖 이미지 `lazy` — 한 줄짜리 개선들.
- 🔵 **나중에**: 코드 분할·번들 분석 — 사이트가 커지고 JS가 무거워졌을 때.
- ⚪ **몰라도 됨**: 마이크로 단위 수치 튜닝. Next.js·Vercel을 쓰면 `next/image`·자동 코드 분할 등 상당 부분을 프레임워크가 알아서 해줍니다.

**⑤ AI에게 이렇게 시켜라**

```text
내 웹사이트 성능을 개선하고 싶어. 막연히 "빠르게"가 아니라 Core Web Vitals
(LCP, CLS, INP) 기준으로 진단해줘.

1) 먼저 크롬 개발자도구의 Lighthouse로 측정하는 방법을 단계별로 알려줘
   (어느 탭을 누르고, 모바일/데스크톱 중 뭘 봐야 하는지 포함).
2) 측정 결과에서 LCP가 큰 원인 후보(보통 큰 이미지/늦는 폰트)를 어떻게
   찾는지, Lighthouse 화면의 어느 항목을 봐야 하는지 알려줘.
3) 가장 효과 큰 것부터(이미지 최적화 → 폰트 → 코드 분할 순) 처방을 정리해줘.
   각 처방마다 "왜 이게 어느 지표를 좋게 만드는지"를 비전공자가 알게 한 줄로
   설명해줘. 코드를 줄 땐 주석으로 이유까지 달아줘.

조건: 지금 당장 큰 리팩토링 말고, 한 줄~몇 줄로 가능한 것부터 우선순위를 매겨줘.
```

이미지·폰트 처방을 받은 뒤 이어서:

```text
방금 알려준 이미지 최적화를 적용하려고 해. 내 히어로 이미지가 hero.png(약 3MB)야.
이걸 WebP로 바꾸고, <img> 태그에 width/height와 적절한 loading 속성을 넣어줘.
폴드 위(첫 화면)에 보이는 이미지인지 아래에 있는지에 따라 loading 값을 어떻게
다르게 해야 하는지(eager vs lazy)도 이유와 함께 설명해줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **CLS를 잡겠다고 LCP 처방을 내는** 등 지표를 헷갈립니다. "화면이 펄쩍 뛴다"(CLS) 문제에 "이미지 용량을 줄여라"(LCP 처방)를 내놓기도 하죠. 증상→지표 매칭을 사람이 확인하세요.
- **모든 이미지에 `loading="lazy"`를 다는** 실수. 첫 화면(폴드 위)의 히어로 이미지까지 lazy로 하면 오히려 **LCP가 나빠집니다.** 첫 화면 핵심 이미지는 `eager`(또는 lazy 미지정)여야 합니다.
- **이미지에 `width`/`height`를 안 넣어** CLS를 유발. 크기를 모르면 브라우저가 자리를 못 비워 두다가 이미지가 뜨는 순간 본문을 아래로 밀어버립니다. AI가 깜빡 빼먹는 단골입니다.
- **번들을 줄인다며 멀쩡한 기능을 떼어내거나**, "이 라이브러리가 무거우니 직접 구현하라"며 보안·접근성이 검증된 라이브러리를 위험한 자작 코드로 바꾸자고 합니다.
- **숫자에 집착해 실제 체감을 놓침** — Lighthouse 점수 100점에 매달리느라 정작 사용자가 가장 답답해하는 버튼 반응(INP)은 손도 안 대는 경우. 점수는 도구일 뿐, 목표는 사람의 체감입니다.
- **시점성 수치를 단정** — "LCP 기준은 2.5초"처럼 말하지만 기준·도구 가중치는 바뀝니다. 정확한 현재 기준은 web.dev/PageSpeed Insights에서 확인 권장.

**⑦ 검증하는 법**

1. **Lighthouse로 측정**: 크롬에서 F12 → **Lighthouse** 탭 → "Mobile" 선택 → Analyze. Performance 점수와 LCP/CLS/INP(또는 관련 항목) 수치가 나옵니다. (실습 189와 연결.)
2. **개선 전/후를 비교**: 처방을 적용하기 전 점수를 캡처해 두고, 적용 후 다시 측정해 **숫자가 실제로 좋아졌는지** 봅니다. "좋아진 것 같다"가 아니라 수치로 확인하세요.
3. **눈으로 CLS 확인**: 페이지를 새로고침하며 **본문이 펄쩍 뛰는지** 직접 봅니다. 글을 읽으려는데 이미지·배너가 떠서 아래로 밀리면 CLS 문제가 남은 것입니다.
4. **모바일·느린 네트워크로 확인**: F12 → Network 탭에서 "Slow 4G"로 속도를 제한하고 새로고침. 좋은 와이파이에선 안 보이던 느림이 드러납니다. 실제 사용자의 절반 이상이 모바일임을 잊지 마세요.
5. **실사용자 데이터**: PageSpeed Insights에 URL을 넣으면 실험실 점수뿐 아니라 실제 방문자의 Core Web Vitals(있다면)도 보여줍니다.

!!! example "💡 예시로 이해하기"
    카페 사장님이 만든 메뉴 소개 페이지가 "모바일에서 너무 느려요"라는 후기를 받았습니다. 디렉터는 곧장 코드를 고치지 않고 휴대폰 크롬에서 Lighthouse를 돌립니다. 결과: **LCP 4.8초, CLS 0.32, INP 양호.** 두 군데가 빨갛습니다. LCP가 큰 이유를 보니 첫 화면에 깔린 매장 사진이 **5MB짜리 원본 PNG**였습니다. CLS가 높은 건 그 사진에 `width/height`가 없어 뜰 때마다 메뉴 글자를 아래로 밀어내기 때문이었죠. 디렉터는 AI에게 "이 5MB PNG를 WebP로 바꾸고, `width`/`height`를 넣되 첫 화면 이미지라 `loading`은 lazy 말고 그대로 둬"라고 정확히 지시합니다. 적용 후 다시 측정하니 **LCP 1.9초, CLS 0.02.** "느려요" 한 줄이 `첫 화면 5MB 이미지 → 최적화` 한 줄로 좁혀지는 순간, 막연한 불평이 30분짜리 명확한 작업으로 바뀌었습니다.
