# 반응형·레이아웃 심화 — Flex와 Grid, 모바일 퍼스트

**① 한 줄 정의**
반응형 레이아웃이란 **하나의 코드가 폰·태블릿·PC 어느 화면에서도 깨지지 않게** 스스로 배치를 바꾸는 것이고, 그 배치를 짜는 두 도구가 **Flexbox(한 줄/한 칸의 흐름)와 Grid(가로·세로 격자)**, 그 사고법이 **모바일 퍼스트(작은 화면부터 설계)**입니다.

**② 왜 중요한가 (디렉터 관점)**
"PC에선 멀쩡한데 폰에서 글자가 화면 밖으로 삐져나가요", "버튼이 두 줄로 흘러내려요" — 부트캠프 이후 가장 흔하게 마주칠 클레임이 바로 레이아웃 깨짐입니다. 그런데 이건 **기능 버그가 아니라 배치 버그**라서, 원인을 짚는 어휘가 없으면 AI에게 "그냥 예쁘게 고쳐줘"라고만 던지게 되고, AI는 멀쩡한 부분까지 헤집어 새 버그를 만듭니다. 디렉터가 "이건 가로 한 줄 흐름이니 Flex 문제다 / 이건 격자가 안 맞으니 Grid 문제다 / 이건 폰 폭에서만 깨지니 미디어쿼리 분기 문제다"라고 **문제의 종류와 위치를 짚어주면**, 같은 AI가 정확히 그 지점만 고칩니다. 레이아웃 어휘는 코드를 짜는 능력이 아니라 **고장을 분류하는 능력**입니다. 또한 한국 사용자의 절반 이상이 모바일로 들어온다는 현실에서, "모바일 퍼스트"를 모르면 PC에서만 그럴듯하고 정작 대부분의 손님 화면에서 망가지는 사이트를 만들게 됩니다.

**③ 비유**
레이아웃을 **가구 배치**라고 생각해 봅시다. **Flexbox**는 "소파들을 벽을 따라 한 줄로 죽 늘어놓되, 방이 좁아지면 알아서 간격을 줄이고 안 들어가면 다음 줄로 넘기는" 1차원(한 방향) 정리법입니다. **Grid**는 아예 바닥에 **바둑판 모눈을 그려놓고** "여긴 침대, 여긴 책상, 여긴 옷장" 하고 칸 단위로 2차원(가로·세로 동시) 배치하는 방식입니다. 그리고 **모바일 퍼스트**는 "**좁은 원룸을 먼저 완벽하게 꾸민 뒤, 넓은 집으로 이사 가면 가구를 추가**하는" 순서입니다. 반대로 큰 집부터 꾸미고 원룸으로 욱여넣으면 늘 짐이 넘쳐 어딘가 부서집니다.

**④ 최소한 알 것**

먼저 **Flex냐 Grid냐**를 가르는 한 가지 질문: *"한 방향으로만 흐르나, 가로·세로를 동시에 맞춰야 하나?"*

| 구분 | Flexbox (🟢 한 줄/한 흐름) | Grid (🟢 격자/면) |
|---|---|---|
| 차원 | 1차원 (가로 한 줄 또는 세로 한 줄) | 2차원 (가로·세로 동시) |
| 잘 맞는 곳 | 내비게이션 바, 버튼 묶음, 카드 한 줄, 가운데 정렬 | 카드 갤러리, 대시보드, 페이지 전체 골격(헤더·사이드·본문) |
| 사고 방식 | "내용물 크기에 맞춰 알아서 흐르게" | "칸을 먼저 정하고 그 안에 넣기" |
| 한 문장 | 줄 세우기의 달인 | 판 짜기의 달인 |

실무에서는 **둘을 같이** 씁니다: 페이지 전체 뼈대는 Grid로 칸을 나누고, 각 칸 안의 버튼·아이콘 줄맞춤은 Flex로. 둘 중 하나만 골라야 하는 시험이 아닙니다.

**반응형 분기를 만드는 도구**

| 용어 | 뜻 | 비유 |
|---|---|---|
| 뷰포트(viewport) | 사용자가 실제로 보는 화면 영역 | 창문의 크기 |
| `meta viewport` 태그 | 폰이 페이지를 "축소"하지 않고 실제 폭으로 그리게 하는 한 줄 | 창문을 제 크기로 열어두는 빗장 |
| 미디어쿼리(media query) | "화면 폭이 N보다 좁/넓으면 이 스타일" 식의 분기 | **방 전체 크기**에 따라 가구 배치 바꾸기 |
| 컨테이너쿼리(container query) | "이 요소를 담은 **상자** 폭에 따라" 스타일 분기 (비교적 최신, 브라우저 지원 범위 확인 권장) | **방이 아니라 그 안 책장 칸**의 크기에 따라 책 배치 바꾸기 |
| 브레이크포인트(breakpoint) | 배치가 바뀌는 기준 폭 (예: 좁은 폰 / 태블릿 / 넓은 PC) | 가구 배치를 갈아엎는 "집 크기 경계" |

🟢 메인으로 알 것: **모바일 퍼스트 + 미디어쿼리**. 🟡 대안/한 단계 위: **컨테이너쿼리**(같은 카드 컴포넌트를 좁은 사이드바에도, 넓은 본문에도 재사용할 때 진가). 🔵 나중에: 정밀한 Grid 영역 이름 짓기(`grid-template-areas`) 같은 고급 기법.

**모바일 퍼스트가 코드로 뭐가 다른가** — 기본 스타일은 좁은 화면 기준으로 짜고, "화면이 **더 넓어지면**" 조건으로만 살을 붙입니다(`min-width`). 반대(큰 화면 먼저 → `max-width`로 줄이기)는 데스크톱 퍼스트라 부르며, 폰에서 깨지기 쉽습니다.

**⑤ AI에게 이렇게 시켜라**

```text
역할: 너는 시니어 프론트엔드 개발자다. 비전공자인 내가 이해하도록 설명을 곁들여라.

만들 것: 상품 카드 6개를 보여주는 갤러리 섹션.
요구사항(모바일 퍼스트로):
- 기본(좁은 폰, ~480px): 카드 1열로 세로로 쌓기.
- 태블릿(min-width 768px): 2열.
- PC(min-width 1024px): 3열.
- 카드 사이 간격은 일정하게, 카드 안의 '이미지-제목-가격-버튼'은 세로 정렬.

제약:
- 전체 격자(몇 열로 나눌지)는 CSS Grid로, 카드 '내부' 요소 정렬은 Flexbox로 짜라.
  왜 각각을 골랐는지 한 줄 주석으로 설명해라.
- 모바일 퍼스트로 작성하라: 기본 스타일은 좁은 화면 기준,
  넓어질 때만 min-width 미디어쿼리로 열 수를 늘려라.
- <head>에 viewport meta 태그가 있는지 확인하고 없으면 추가하라(이유도 적어라).
- 가로 스크롤이 생기지 않게(요소가 화면 폭을 넘지 않게) 해라.

산출물: index.html + style.css, 그리고 "왜 Grid/Flex를 이렇게 나눴는지" 3줄 요약.
```

막혔을 때 덧붙일 한 줄: *"폰 폭(375px)에서 카드가 화면 밖으로 삐져나간다. 원인을 코드부터 고치지 말고 어떤 속성이 폭을 넘기는지 먼저 짚어줘."*

**⑥ 흔한 함정 / AI가 틀리는 것**

- **viewport 태그 누락**: AI가 만든 페이지에 `<meta name="viewport" content="width=device-width, initial-scale=1">`이 빠지면, 폰이 데스크톱 화면을 통째로 축소해 보여줘서 글씨가 깨알처럼 됩니다. "반응형이 하나도 안 먹어요"의 1순위 원인입니다.
- **데스크톱 퍼스트로 짜놓고 모바일 퍼스트라 우기기**: `max-width`로 줄여나가는 코드를 주면서 모바일 퍼스트라고 설명하는 경우가 잦습니다. 기본 스타일이 좁은 화면용인지(=`min-width`로 키우는지)로 구분하세요.
- **고정 픽셀 폭(width: 1200px)**: 특정 폭을 못 박으면 그보다 좁은 폰에서 반드시 가로 스크롤이 생깁니다. `max-width`+`%`/`fr`/`auto`로 유연하게 가야 합니다.
- **Flex로 2차원 격자를 억지로 흉내**: 카드 갤러리를 Flex `wrap`으로 짜면 줄마다 카드 수가 들쭉날쭉해지기 쉽습니다. "칸을 딱 맞춰야 하는" 격자는 Grid가 정답입니다.
- **컨테이너쿼리를 미디어쿼리인 양 사용**: 컨테이너쿼리는 부모에 `container-type` 지정이 선행돼야 작동하고, 브라우저 지원 범위 확인이 필요합니다(확인 권장). AI가 설정 없이 `@container`만 쓰면 조용히 안 먹습니다.
- **단위 혼동**: `px`(고정)·`%`(부모 대비)·`rem`(루트 글자 크기 배수)·`vw/vh`(화면 폭/높이 %)를 뒤섞어 의도와 다른 크기가 나오기도 합니다.

**⑦ 검증하는 법**

1. **브라우저 개발자도구로 폭 바꿔보기**: F12 → 좌상단의 **모바일/반응형 토글**(기기 모양 아이콘)을 켜고, 폭을 375 → 768 → 1280으로 끌어보세요. 열 수가 1 → 2 → 3으로 바뀌고 어디서도 가로 스크롤이 안 생기면 합격.
2. **창을 직접 좁혀보기**: 브라우저 창 자체를 마우스로 천천히 좁혔다 넓히며 "배치가 끊기지 않고 부드럽게 재배열되는지" 눈으로 확인.
3. **가로 스크롤 검사**: 폰 폭에서 페이지 맨 아래에 가로 스크롤바가 생기면 어딘가 화면보다 넓은 요소가 있다는 신호입니다.
4. **실기기 확인**: 시뮬레이터가 통과해도 실제 폰에서 한 번 더 봅니다(특히 노치/세이프에어리어가 있는 기기). 배포 후 본인 폰으로 열어보는 것이 가장 확실합니다.
5. **viewport 태그 존재 확인**: 개발자도구 Elements 탭에서 `<head>` 안에 viewport meta 한 줄이 있는지 눈으로 점검.

!!! example "💡 예시로 이해하기"
    동네 카페 메뉴 페이지를 만든다고 합시다. 처음엔 PC 화면으로만 보며 "메뉴 카드 4개가 한 줄에 예쁘게 들어간다!" 하고 배포했는데, 다음 날 사장님이 "제 폰으로 보니 카드가 한 칸씩 옆으로 잘려서 가로로 밀어야 보여요"라고 연락이 옵니다. 디렉터는 한 덩어리 "깨졌어요"를 이렇게 쪼갭니다 — F12로 폭을 375px로 줄여보니 카드에 `width: 300px`가 못 박혀 있어 4장이 폰 폭(375px)을 넘김(가로 스크롤의 범인), 그리고 `<head>`에 viewport 태그도 없음. 그래서 AI에게 "카드 폭 고정을 풀고, 전체는 Grid로 폰 1열·태블릿 2열·PC 4열로 모바일 퍼스트 분기해줘. viewport 태그도 추가하고 왜 넣는지 주석 달아줘"라고 정확히 시킵니다. 막연한 "예쁘게 고쳐줘"가 `고정폭 제거 + Grid 반응형 + viewport 추가`라는 세 개의 구체 작업으로 바뀌는 순간, AI는 멀쩡한 색·폰트는 건드리지 않고 깨진 곳만 정확히 고칩니다.
