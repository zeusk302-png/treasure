# 클라이언트 라우팅 — SPA와 MPA, 페이지 전환의 두 방식

**① 한 줄 정의**
'페이지를 넘기는 방식'에는 두 갈래가 있습니다. 링크를 누를 때마다 서버에서 **새 HTML 한 장을 통째로 받아오는 MPA(여러 페이지 앱)**와, 첫 한 장만 받고 그다음부터는 **자바스크립트가 화면 일부만 갈아끼우며 주소만 바꿔치는 SPA(단일 페이지 앱)**입니다. 후자가 화면을 갈아끼우는 기술이 바로 **클라이언트 라우팅**입니다.

**② 왜 중요한가 (디렉터 관점)**
이 선택은 '취향'이 아니라 **체감 속도·검색 노출·버그 종류**를 한꺼번에 결정하는 갈림길입니다. SPA는 첫 진입만 지나면 페이지 전환이 깜빡임 없이 매끄럽지만, 대가로 "새로고침하면 404", "뒤로가기가 안 먹힘", "공유한 링크를 열면 빈 화면", "검색엔진이 내용을 못 읽음" 같은 **특유의 함정**을 달고 옵니다. 디렉터가 이 구조를 모르면, AI가 만들어 준 사이트에서 위 증상이 터졌을 때 "왜 이러지?"만 반복하다 멀쩡한 코드를 헤집게 됩니다. 반대로 "이건 클라이언트 라우팅이라 새로고침 시 서버 폴백이 없어서 그래"라고 한 문장으로 원인을 짚으면, AI에게 정확히 무엇을 고치라고 시킬 수 있습니다. 즉 이 페이지의 지식은 **'전환은 예쁜데 새로고침하면 깨지는 사이트'의 진단서**입니다.

**③ 비유**
MPA는 **종이책**입니다. 다음 장을 보려면 책장을 통째로 넘깁니다 — 매번 새 종이(새 HTML)가 눈앞에 펼쳐집니다. 깔끔하지만 넘길 때마다 잠깐 종이가 펄럭입니다(화면 깜빡임). SPA는 **태블릿 전자책**입니다. 기기(첫 HTML)는 한 번만 켜고, 그다음부터는 같은 화면에서 내용만 슥슥 바뀝니다 — 종이를 새로 가져오지 않으니 매끄럽지만, 대신 기기가 한 번 멈추면(자바스크립트 오류) 책 전체가 먹통이 됩니다.

그리고 **history API**는 이 전자책의 '책갈피 장치'입니다. 화면은 자바스크립트가 갈아끼웠지만, 주소창과 뒤로가기 버튼은 진짜로 페이지를 넘긴 것처럼 보이게 만들어 줍니다. 책갈피를 제대로 안 꽂으면(history API를 안 쓰면) 뒤로가기가 엉뚱한 곳으로 튀거나, 공유한 책갈피(딥링크)를 열었을 때 표지만 나오고 본문이 안 나옵니다.

**④ 최소한 알 것**

| 구분 | MPA (여러 페이지 앱) | SPA (단일 페이지 앱) |
|---|---|---|
| 페이지 전환 | 매번 서버에서 새 HTML 받음 | JS가 화면 일부만 교체 |
| 첫 화면 속도 | 빠름(필요한 것만 받음) | 느릴 수 있음(JS 다 받아야 함) |
| 전환 후 속도 | 매번 깜빡임 | 매끄럽고 빠름 |
| 새로고침/딥링크 | 기본적으로 안전 | 서버 폴백 설정 안 하면 404 위험 |
| SEO(검색 노출) | 유리(HTML에 내용 있음) | 추가 처리 없으면 불리 |
| 대표 예 | 옛날 게시판, 기본 HTML 사이트 | Gmail, 트렐로 같은 웹앱 |

- **클라이언트 라우팅**: 서버 왕복 없이, 브라우저 안 자바스크립트가 URL과 화면을 바꾸는 것.
- **history API**: `pushState`(주소만 새로 쌓기)·`replaceState`(현재 주소 바꾸기)·`popstate`(뒤로/앞으로 갈 때 알림). 새로고침 없이 주소창을 바꾸고 뒤로가기를 자연스럽게 만드는 표준 기능.
- **딥링크(deep link)**: 첫 화면이 아닌 **특정 안쪽 페이지로 바로 가는 링크**(예: `사이트/products/42`). 남에게 공유하거나 북마크할 때의 그 주소.
- **서버 폴백(SPA fallback)**: SPA에서 어떤 주소로 새로고침/직접 진입해도 서버가 일단 `index.html`을 내려주도록 한 설정. 이게 없으면 `/products/42` 새로고침 시 404.
- **현실은 혼합형**: 요즘 Next.js 같은 프레임워크는 **둘의 장점을 합칩니다**. 서버에서 HTML을 미리 만들어 첫 화면과 SEO를 챙기고(서버 렌더링), 그다음 전환은 클라이언트 라우팅으로 매끄럽게. "SPA냐 MPA냐"의 이분법보다 이 혼합형이 오늘날 기본값에 가깝다는 점을 기억하세요.

🟢 **메인(요즘 표준)**: Next.js류 프레임워크의 혼합형(서버 렌더링 + 클라이언트 전환) · 🟡 **대안**: 순수 SPA(로그인 뒤 대시보드처럼 검색 노출이 필요 없는 내부 도구) · 🔵 **나중에**: 직접 history API 만지기(보통 프레임워크가 알아서 처리) · ⚪ **몰라도 됨**: 라우터 라이브러리 내부 구현

**⑤ AI에게 이렇게 시켜라**

```text
[배경] 비전공자가 만드는 사이트야. 회사 소개·블로그·제품 상세가 있고,
검색(구글)에 잘 잡혔으면 좋겠어. 동시에 페이지를 넘길 때 매끄러우면 좋겠고.

[요청] SPA로 전부 만들지 말고, 다음 기준으로 어떤 방식이 맞는지 먼저 정리해줘.
1) 이 사이트는 SPA / MPA / 둘을 합친 방식(서버 렌더링 + 클라이언트 전환) 중 무엇이 맞아?
   - 검색 노출(SEO)이 필요한 페이지와, 필요 없는 페이지를 나눠서 판단해줘.
2) 선택한 방식에서 '새로고침하면 404', '뒤로가기가 안 먹힘', '공유 링크 열면 빈 화면'
   같은 함정이 생기는지, 생긴다면 무엇을 설정해야 막는지 알려줘.
3) 코드를 주기 전에, 위 결정의 근거를 비전공자가 이해하게 한 단락으로 먼저 설명하고,
   그다음 코드를 줘. 코드에는 '왜 이렇게 했는지' 주석을 한국어로 달아줘.
```

```text
[디버깅용] 내 사이트가 첫 화면은 잘 나오는데,
/products/42 같은 안쪽 주소에서 새로고침하면 404가 떠.
이게 클라이언트 라우팅의 '서버 폴백 누락' 문제인지 먼저 진단해줘.
내가 쓰는 배포 환경(예: Vercel / Netlify / 일반 정적 호스팅)을 물어보고,
환경별로 어떤 설정(리다이렉트/리라이트)을 넣어야 모든 경로가
index.html로 폴백되는지 단계별로 알려줘. 코드를 헤집기 전에 설정부터 점검.
```

**⑥ 흔한 함정 / AI가 틀리는 것**
- **무조건 SPA로 만들어 SEO를 죽인다.** "사이트 만들어줘"라고만 하면 AI는 검색 노출이 꼭 필요한 회사 소개·블로그까지 순수 SPA로 만들어, 구글이 빈 화면만 읽고 가게 합니다. **검색에 잡혀야 하는 페이지**는 서버 렌더링(또는 정적 생성)이 필요하다고 명시하세요.
- **서버 폴백을 빼먹는다.** SPA를 만들어 놓고 새로고침/딥링크 시 404가 나는 설정 누락은 AI 산출물의 단골 버그입니다. 첫 화면만 눌러보고 "됐다"고 넘어가기 쉽습니다.
- **history API를 안 써서 뒤로가기가 깨진다.** 화면만 자바스크립트로 바꾸고 주소를 안 바꾸면, 뒤로가기가 사이트 밖으로 튀거나 같은 화면만 반복됩니다.
- **`<a href>` 대신 `<div onclick>`으로 링크를 만든다.** 그러면 새 탭 열기·검색엔진 추적·접근성이 다 깨집니다. 진짜 링크는 앵커 태그로.
- **로그인/장바구니 상태가 새로고침에 날아간다.** SPA에서 화면(상태)에만 담아 둔 데이터는 새로고침하면 사라집니다 — 영구 보존이 필요하면 DB로. (보안 한 줄: Supabase의 anon 키는 **브라우저에 노출돼도 되는 공개 키**이고 보호는 RLS로 합니다. service_role 키는 절대 프론트에 두지 마세요.)

**⑦ 검증하는 법**
1. **딥링크 새로고침 테스트**: 첫 화면이 아니라 **안쪽 페이지**(예: 제품 상세)로 들어간 뒤 브라우저 새로고침(F5)을 누릅니다. 같은 내용이 그대로 나오면 합격, 404가 나면 서버 폴백 누락.
2. **뒤로가기/앞으로가기 테스트**: 여러 페이지를 누벼 보고 뒤로가기를 연타합니다. 누른 순서대로 정확히 되돌아가면 history API가 제대로 동작하는 것.
3. **공유 링크 테스트**: 안쪽 주소를 복사해 **시크릿 창**이나 휴대폰에서 엽니다. 내용이 보이면 딥링크 정상, 빈 화면이면 SPA가 클라이언트에서만 그리고 있다는 신호.
4. **자바스크립트 끄고 보기**(SEO 감 잡기): 개발자도구로 JS를 비활성화하거나, 주소 앞에 검색엔진 시점을 흉내 내 봅니다. 본문 텍스트가 거의 안 보이면 검색엔진도 비슷하게 못 읽습니다 — 서버 렌더링/정적 생성이 필요하다는 뜻.
5. **F12 → Network 탭**: 페이지 전환 시 새 HTML 문서 요청이 매번 뜨면 MPA, 작은 데이터(JSON) 요청만 뜨고 문서 요청이 없으면 클라이언트 라우팅(SPA)으로 도는 것입니다.

!!! example "💡 예시로 이해하기"
    친구에게 만든 쇼핑몰의 인기 상품 주소 `myshop.com/products/42`를 카톡으로 보냈습니다. 그런데 친구가 "링크 눌렀더니 빈 화면 떠"라고 합니다. 디렉터는 당황하지 않고 구조로 진단합니다. "내 컴퓨터에선 홈에서 그 상품을 **눌러서** 들어가니까 멀쩡했는데, 친구는 그 주소로 **바로** 들어갔지." 이게 바로 SPA의 딥링크 함정입니다. 첫 화면은 자바스크립트가 켜진 뒤에야 안쪽 화면을 그리는데, 서버는 `/products/42`라는 주소에 줄 HTML이 없어서 404를 내거나 빈 껍데기만 보낸 겁니다. 원인을 "딥링크 시 서버 폴백 누락"으로 좁히고 나면, AI에게 "Vercel을 쓰는데 모든 경로를 index.html로 폴백하는 설정을 넣어줘" 또는 "이 상품 페이지는 서버에서 미리 HTML을 만들어 검색에도 잡히게 해줘"라고 정확히 시킬 수 있습니다. "빈 화면 떠"라는 막연한 신고가, 한 문장짜리 수리 지시서로 바뀌는 순간입니다.
