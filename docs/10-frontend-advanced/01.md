# 컴포넌트로 생각하기 — UI를 재사용 조각으로 쪼개기

**① 한 줄 정의**
컴포넌트(component)란 **화면을 '버튼·카드·헤더' 같은 재사용 가능한 조각**으로 나눈 것이고, **props(프롭스)**는 그 조각에 **"이번엔 이렇게 보여라"라고 건네는 설정값**입니다.

**② 왜 중요한가 (디렉터 관점)**
비전공 디렉터에게 컴포넌트는 **"같은 걸 한 번만 만들고 여기저기서 재사용한다"**는 사고법 그 자체입니다. AI에게 "장바구니에 상품 카드 30개를 만들어줘"라고 시켰을 때, AI가 *상품 카드 코드를 30번 복사·붙여넣기*로 만들면 — 나중에 "카드에 '품절' 배지를 추가해줘" 한마디에 30군데를 다 고쳐야 하고, 그중 한두 개를 빠뜨리면 **어떤 카드만 배지가 없는 버그**가 생깁니다. 반대로 *상품 카드를 컴포넌트 하나로 만들고 데이터만 30번 흘려보내면*, 고칠 곳은 **딱 한 곳**입니다.

디렉터는 코드를 직접 짜지 않지만, AI가 만든 결과물이 **"복붙 덩어리인가, 재사용 조각인가"를 판별**할 수 있어야 합니다. 이걸 모르면 처음엔 잘 굴러가던 사이트가, 기능을 더할수록 점점 손대기 무서운 '스파게티'가 되는 걸 막지 못합니다. 즉 컴포넌트 사고는 **"AI에게 어떻게 시킬지(분해)"와 "AI 결과가 좋은지(품질 판별)"의 공통 언어**입니다.

**③ 비유**
레고를 떠올려 보세요. 레고는 성(城)을 통째로 깎아 만들지 않습니다. **작은 블록**(2x4 빨강, 1x2 파랑…)을 만들어 두고, 그걸 조립해 성도 만들고 우주선도 만듭니다. 블록 하나의 모양을 개선하면 그 블록을 쓴 모든 작품이 같이 좋아집니다. 컴포넌트가 바로 이 **블록**이고, props는 **"이번 블록은 빨간색, 4칸짜리로"**라고 정해주는 주문서입니다.

또 다른 비유는 **붕어빵 틀**입니다. 틀(컴포넌트)은 하나, 반죽과 속(props)만 바꿔 넣으면 팥붕어빵·슈크림붕어빵이 똑같은 모양으로 무한히 나옵니다. 디렉터가 "붕어빵 100개"를 시킬 때 떠올려야 할 그림은 *붕어빵 100개를 손으로 빚는 것*이 아니라 *틀 1개 + 속 100인분*입니다.

**④ 최소한 알 것**

| 용어 | 한 줄 뜻 | 비유 |
|---|---|---|
| 컴포넌트 | 재사용 가능한 화면 조각(버튼·카드·헤더 등) | 레고 블록 / 붕어빵 틀 |
| props | 컴포넌트에 밖에서 건네는 설정값(텍스트·색·이미지 등) | 붕어빵 속(팥/슈크림) |
| 재사용 | 같은 컴포넌트를 자리만 바꿔 여러 번 사용 | 같은 틀로 100개 |
| 합성(composition) | 작은 컴포넌트를 모아 큰 화면을 조립 | 블록을 모아 성을 만듦 |
| 단일 책임 | 컴포넌트 하나는 한 가지 일만 | 버튼 틀은 버튼만, 카드 틀은 카드만 |

핵심 판단 기준 세 가지:

- **두 번 이상 나오면 컴포넌트 후보.** 화면에 같은 모양이 반복되면(상품 카드, 댓글, 알림 배지) "이건 조각으로 빼자"가 정답입니다.
- **"무엇이 같고 무엇이 다른가"를 먼저 본다.** 카드 30개의 *틀(레이아웃)*은 같고, *내용(제목·가격·이미지)*만 다릅니다. 같은 건 컴포넌트로, 다른 건 props로.
- **조각이 너무 커지면 더 쪼갠다.** 한 컴포넌트가 화면 절반을 차지하고 수백 줄이면, 그건 '거대 블록'이라 재사용도 수정도 어렵습니다(③권의 '거대 컴포넌트' 함정).

> React, Vue, Svelte 같은 도구가 다른 점도 결국 *이 블록을 어떻게 정의하고 props를 어떻게 흘리는가*의 문법 차이일 뿐, **"화면=재사용 조각의 조립"**이라는 사고법은 똑같습니다.

**⑤ AI에게 이렇게 시켜라**

```text
상품 목록 페이지를 만들 거야. 상품 카드를 30개 보여줘야 해.
중요: 카드 30개를 복사-붙여넣기로 만들지 말고,
재사용 가능한 'ProductCard' 컴포넌트 하나를 정의한 뒤
데이터 배열을 map으로 돌려서 렌더링해줘.

요구사항:
- ProductCard가 받는 props: 제목(title), 가격(price),
  이미지 URL(imageUrl), 품절 여부(soldOut, true면 '품절' 배지 표시)
- 카드의 레이아웃/스타일은 한 곳(ProductCard)에만 정의할 것
- 나중에 카드 디자인을 바꾸면 30개가 한꺼번에 바뀌도록 만들 것
- 비전공자가 읽게, props가 무엇이고 왜 이렇게 나눴는지 주석으로 설명해줘
- 사용자 입력(상품명 등)을 화면에 넣을 땐 textContent 방식으로,
  innerHTML로 직접 넣지 마(XSS 위험)
```

이어서 컴포넌트의 효과를 확인하는 후속 프롬프트:

```text
방금 만든 ProductCard에 '할인율' 배지를 추가하고 싶어.
30개 카드를 따로 고치는 게 아니라, ProductCard 한 곳만 수정해서
모든 카드에 반영되는지 보여줘. 어디를 고쳤는지 그 한 곳을 알려줘.
```

**⑥ 흔한 함정 / AI가 틀리는 것**

- **복붙 폭발.** AI는 "카드 30개"를 시키면 *카드 코드를 30번 그대로 펼쳐* 놓는 경우가 흔합니다. 결과물이 길고 똑같은 덩어리가 반복되면 의심하세요. 그 30군데 중 하나만 미세하게 달라도 찾기 힘든 버그가 됩니다.
- **거대 컴포넌트(God 컴포넌트).** 반대로 모든 걸 한 파일·한 컴포넌트에 욱여넣어 수백 줄이 되기도 합니다. 헤더·목록·푸터가 한 덩어리면 재사용이 안 됩니다.
- **props 누락/오타.** props 이름을 `imageUrl`로 정해놓고 어떤 카드는 `imgUrl`로 넘겨 *이미지만 안 뜨는* 식의 실수. 사람이 "30개 다 똑같이 떴나"를 눈으로 봐야 합니다.
- **하드코딩.** props로 받아야 할 값(가격·제목)을 컴포넌트 안에 박아버리면, 재사용해도 늘 같은 값만 나옵니다. "이 조각이 다른 데서도 다른 내용으로 쓰일 수 있나?"를 물어보세요.
- **XSS 함정.** 사용자가 입력한 상품평·이름을 카드에 그릴 때 `innerHTML`로 꽂으면 악성 `<script>`가 실행될 수 있습니다. 출력은 `textContent`가 기본입니다.

**⑦ 검증하는 법**

1. **"한 곳만 고치면 다 바뀌나" 테스트.** AI에게 카드의 글자색이나 배지를 바꾸라고 시켜보세요. *한 곳* 수정으로 모든 카드가 같이 바뀌면 진짜 컴포넌트, 30곳을 다 고치라고 하면 복붙 덩어리입니다.
2. **눈으로 일관성 확인.** 카드 30개가 *모서리·여백·폰트·배지 위치까지 완전히 똑같은지* 봅니다. 어떤 카드만 미묘하게 다르면 복붙의 흔적입니다.
3. **코드 길이 감각.** 화면엔 카드가 30개인데 소스에 카드 모양 정의가 *딱 한 번만* 나오고 나머지는 데이터(배열)뿐이면 잘 나뉜 것입니다.
4. **데이터만 바꿔보기.** AI에게 "상품 데이터를 3개로 줄여봐"라고 하면 카드가 3개로 줄어야 합니다. 화면이 데이터에 따라 자동으로 늘고 주는지 보세요(이게 다음 페이지 '상태'와 이어집니다).

!!! example "💡 예시로 이해하기"
    카페 메뉴판 웹사이트를 만든다고 해봅시다. 메뉴가 20개고, 각 메뉴는 '사진 + 이름 + 가격 + 인기 배지'로 똑같은 모양입니다. 처음엔 AI가 메뉴 칸 코드를 20번 복사해 붙였습니다 — 잘 돌아갑니다. 그런데 사장님이 "가격 옆에 '원' 글자를 넣고, 인기 메뉴엔 불꽃 이모지를 붙여줘"라고 합니다. 복붙으로 만들었다면 20군데를 손으로 고쳐야 하고, 19개만 고치고 1개를 놓치면 *그 메뉴만 옛날 모양*으로 남습니다. 반면 'MenuCard'라는 조각 하나로 만들어 두고 메뉴 데이터 20개만 흘려보냈다면, 고칠 곳은 MenuCard **한 곳**이고 20개 메뉴가 한꺼번에 새 모양으로 바뀝니다. 디렉터가 "복붙 말고 컴포넌트로 만들어줘"라는 한 문장을 처음부터 깔아두면, 미래의 수정 요청 100개가 *100배 수고*가 아니라 *한 번의 수고*로 끝납니다.
