# 키가 새면 어떻게 하나 — 유출 탐지와 키 회전(rotation) 대응 절차

**(1) 한 줄 정의**

키 회전(rotation)은 유출됐거나 의심되는 키를 **즉시 무효화하고 새 키로 교체**하는 절차다. 보안의 핵심은 "절대 안 새게 숨기기"가 아니라 "새도 빠르게 무력화하기"다.

**(2) 왜 중요한가(디렉터 관점)**

비밀은 언젠가 샐 수 있다는 전제로 운영해야 한다. 디렉터가 사고 순간 당황하지 않으려면 "무엇을, 어떤 순서로, 어디서 끊고 갈아끼우는지"를 미리 알아야 한다. 특히 한 번 커밋된 키는 파일을 지워도 **git 기록에 남기 때문에** 단순 삭제로는 끝나지 않는다는 점이 핵심이다.

**(3) 비유**

집 열쇠를 잃어버렸을 때 정답은 "열쇠를 잘 숨겼어야지" 하고 후회하는 게 아니라 **자물쇠 자체를 바꾸는 것(re-key)**이다. 옛 열쇠를 주운 사람이 와도 문이 안 열린다. 키 회전이 바로 자물쇠 교체다.

**(4) 최소한 알 것**

| 있는 것 | 한 줄 해설 | 판정 |
|---|---|---|
| 키 무효화(revoke) | 옛 키를 즉시 못 쓰게 만들기 | 🟢메인 |
| 새 키 재발급 | 무효화와 동시에 새 키 생성 | 🟢메인 |
| 동시 갱신 | Supabase·Vercel 등 여러 곳을 함께 교체 | 🟢메인 |
| 무중단 회전 | 서비스를 멈추지 않고 갈아끼우는 순서 설계 | 🟡대안 |
| git history 정리 | 기록에 남은 키 흔적 처리 | 🟡대안 |

!!! warning "자동 무효화는 시점성 정보"
    "신형 secret 키가 공개 리포에서 발견되면 Supabase가 자동으로 무효화·회전을 안내한다"는 동작은 정책이 바뀔 수 있습니다. 의존하기 전에 Supabase 공식 문서에서 현재 동작과 날짜를 확인하세요. **자동 탐지가 있더라도 그것에만 기대지 말고 수동 회전 절차를 갖추세요.**

**(5) AI에게 이렇게 시켜라**

```text
secret 키가 공개 저장소에 노출됐다고 가정하고 대응 런북을 만들어줘.
1) 가장 먼저 할 일(옛 키 무효화)부터 순서대로, 코딩 지식 없이 따라 할 수 있게.
2) Supabase에서 새 키 발급 → Vercel(또는 배포처) 환경변수 교체 →
   재배포까지의 체크리스트를 단계별로.
3) 서비스가 멈추지 않게(무중단) 갈아끼우는 순서가 있으면 함께.
4) git 기록에 남은 키 흔적을 어떻게 처리하는지(파일 삭제로 안 사라짐) 설명.
각 단계마다 "무엇을 보면 성공인지" 판정 기준을 적어줘.
```

**(6) 흔한 함정·AI가 틀리는 것**

AI는 사후 대응 절차를 체계적으로 주지 않고 "키를 다시 발급하세요" 정도로 끝낸다. 특히 **"커밋 기록에 남은 키는 파일을 지워도 안 사라진다"**는 사실을 빠뜨려, 디렉터가 파일만 삭제하고 안심하게 만든다. 또 여러 서비스(Supabase/Vercel)를 동시에 갱신해야 한다는 점이나 무중단 순서를 놓친다.

**(7) 검증하는 법**

1. 옛 키로 API 호출 시도 → **거부(401/403)** 되면 무효화 성공.
2. 새 키로 정상 동작 확인 후 배포 환경에서도 동작하는지 점검.
3. 공개 저장소 및 git 기록에서 옛 키 문자열 검색 → 흔적 처리 여부 확인.

**(8) 더 깊이**

- Supabase 공식 문서: Rotating/Revoking API Keys (날짜 확인)
- GitHub Docs: Removing sensitive data from a repository (BFG / filter-repo)
- 03번 ".env 제대로"와 한 묶음으로 읽기

!!! example "💡 예시로 이해하기"
    토요일 밤 11시, 지영이 자기 사이드 프로젝트의 `sb_secret_` 키가 공개 저장소에 올라간 걸 발견했다. 당황해서 파일만 지우면 끝일까? 아니다. 순서는 이렇다.
    (1) Supabase 대시보드 → API Keys에서 옛 secret 키를 먼저 `Revoke`로 무효화한다. 이때 옛 키로 API를 호출하면 `401 Unauthorized`가 떠야 성공이다. (2) 곧바로 새 secret 키를 발급받는다. (3) Vercel → Settings → Environment Variables에서 그 값을 새 키로 바꾸고 재배포한다. (4) Supabase와 Vercel 두 곳을 모두 갈아끼웠는지 확인한다 — 한쪽만 바꾸면 서비스가 멈춘다. 깃 기록에 남은 옛 키 문자열은 어차피 무효화돼서 못 쓰지만, 흔적 자체는 `git filter-repo`나 BFG로 따로 지운다.
