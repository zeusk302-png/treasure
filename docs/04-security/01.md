# 공개해도 되는 키 vs 절대 숨길 키 — anon/publishable vs service_role/secret 완전 정정

**(1) 한 줄 정의**

Supabase 같은 서비스의 키에는 두 종류가 있다. 프론트(브라우저)에 박혀 노출돼도 안전한 **공개 출입증**(anon → 신형 `sb_publishable_...`)과, 모든 보안을 우회하므로 절대 서버 밖으로 내보내면 안 되는 **진짜 비밀**(service_role → 신형 `sb_secret_...`)이다.

**(2) 왜 중요한가(디렉터 관점)**

이것은 이 책 전체에서 가장 비싸게 잘못 가르쳐졌던 지점이다. 기존 강의는 anon 키를 "비밀키=집 열쇠"라고 가르쳤는데, 이는 신뢰도를 가장 크게 깎은 오류다. 디렉터가 두 키의 성격을 거꾸로 알면, AI에게 "키를 숨겨줘"라고 시키면서 정작 진짜 비밀(secret)은 프론트에 그대로 두는 정반대의 사고를 낸다. 무엇이 새도 되고 무엇은 절대 안 되는지를 가르는 안목이 보안의 출발점이다.

**(3) 비유**

`publishable` 키는 건물 정문에 붙은 **방문자 출입증**이다. 누구나 볼 수 있고, 봐도 괜찮다. 출입증을 보여줘도 각 사무실 문(=RLS 정책)은 따로 잠겨 있어 권한 없는 방은 못 연다. `secret` 키는 모든 사무실을 다 여는 **건물 관리인의 마스터키**다. 이건 절대 정문에 붙여두면 안 되고, 관리실(서버) 금고에만 둔다.

**(4) 최소한 알 것**

| 있는 것 | 한 줄 해설 | 판정 |
|---|---|---|
| anon / `sb_publishable_` | 프론트에 노출돼도 되는 공개 출입증. RLS가 막아줌 | 🟢메인 |
| service_role / `sb_secret_` | RLS를 우회하는 마스터키. 서버 전용 | 🟢메인(서버에서만) |
| RLS(행 수준 보안) | 공개 키가 안전한 진짜 이유. 다음 페이지 | 🟢메인 |
| `NEXT_PUBLIC_` 접두 규칙 | 이 접두가 붙은 값만 브라우저에 노출됨 | 🟡대안(개념) |

!!! warning "시점성 정보 — 반드시 재확인"
    Supabase의 신형 키 체계(`sb_publishable_` / `sb_secret_`)와 구형 키(anon / service_role) 폐기 시점은 변경될 수 있습니다. 집필·적용 시점에 [Supabase 공식 문서]를 날짜와 함께 확인하세요(예: 2026년 6월 기준).

**(5) AI에게 이렇게 시켜라**

```text
이 프로젝트의 Supabase 키 사용을 점검해줘.
1) 어떤 키가 어디(프론트 컴포넌트/서버 코드/환경변수)에 쓰이는지 목록으로.
2) service_role(또는 sb_secret_) 키가 브라우저로 가는 코드나 NEXT_PUBLIC_ 접두에
   들어간 곳이 단 한 군데라도 있는지 찾아서 표시.
3) 있으면 "치명적 위험"으로 분류하고 서버 전용으로 옮기는 방법을 알려줘.
추정하지 말고, 실제 코드에서 찾은 위치만 파일·줄 단위로 보고해.
```

**(6) 흔한 함정·AI가 틀리는 것**

AI는 빠른 데모를 만들 때 RLS 설정이 번거로우니 그것을 우회하는 **secret 키를 프론트 컴포넌트에 박는** 코드를 자주 준다. 이것이 가장 흔한 Supabase AI 코딩 보안 실패다. 또한 두 키의 이름이 비슷해 거꾸로 설명하거나, "키를 숨기면 안전하다"고 안심시키며 정작 RLS는 언급하지 않는다.

**(7) 검증하는 법**

1. 빌드 산출물(브라우저 개발자도구 F12 → Sources/Network)에서 `sb_secret_` 또는 `service_role` 문자열을 검색한다. **0건**이어야 한다.
2. publishable 키 문자열은 보여도 정상이다. 그 키로 권한 밖 데이터를 읽으려 하면 RLS가 막는지 확인한다.
3. 코드 저장소 전체에서 `service_role`을 검색해 프론트 경로(컴포넌트, 페이지)에 없는지 본다.
