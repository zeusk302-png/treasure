# AI가 만든 코드의 보안을 디렉터가 검증하는 법

**(1) 한 줄 정의**

AI가 만든 코드의 보안 검증이란, '공개/비밀 키 분리 · RLS · 인가 · 의존성 · 에러 노출'이라는 **고정 체크리스트로 AI를 심문하고 증거를 요구하는 루틴**이다.

**(2) 왜 중요한가(디렉터 관점)**

권4의 모든 페이지가 여기서 하나로 모인다. 디렉터는 직접 보안을 구현하지 않는다. 대신 "AI가 그 선을 지켰는지"를 매번 같은 방식으로 검증한다. 검증을 즉흥으로 하면 빠뜨린다. 고정된 체크리스트가 있어야 매번 같은 깊이로 점검할 수 있고, 그 자체가 디렉터의 핵심 역량이 된다(권8 취업 연계에서 회수).

**(3) 비유**

비행기 이륙 전 **체크리스트**와 같다. 베테랑 기장도 외워서 하지 않고 매번 종이 목록을 소리 내 읽으며 하나씩 확인한다. 빠뜨림을 막는 건 기억력이 아니라 고정된 절차다. 보안 검증도 마찬가지다.

**(4) 최소한 알 것 — 디렉터 고정 체크리스트**

| 점검 항목 | 무엇을 보나 | 판정 |
|---|---|---|
| 공개/비밀 키 분리 | secret 키가 프론트/`NEXT_PUBLIC_`에 0건인가(01) | 🟢메인 |
| RLS | 테이블마다 켜졌고 정책이 실제로 막나(02) | 🟢메인 |
| 인가 | 로그인 외에 "본인 것만" 막혔나, UI 가짜 보안 없나(04) | 🟢메인 |
| 의존성 | lock 파일 커밋, 오타 패키지·취약점 없나(07) | 🟢메인 |
| 에러 노출 | 에러에 내부정보 노출/디버그 모드 없나(06) | 🟢메인 |

!!! warning "같은 AI에게 '안전하냐' 묻지 말 것"
    코드를 만든 AI에게 "이거 안전해?"라고 물으면 '안전하다'고 답하기 쉽습니다(자기확인 편향). 검증은 **재현 가능한 증거**(실제 화면·응답·검색 결과)로 하거나, 다른 시각의 점검(별도 세션/도구)을 곁들이세요.

**(5) AI에게 이렇게 시켜라**

```text
아래 5개 항목으로 이 프로젝트 보안을 점검하고, 각 항목마다 "주장"이 아니라 "증거"를 제시해.
1) 공개/비밀 키 분리: secret 키가 프론트나 NEXT_PUBLIC_에 있는지 (파일·줄로)
2) RLS: 각 테이블 활성 여부와 정책을 사람 말로, USING(true) 같은 무의미 정책 표시
3) 인가: 로그인한 사용자가 남의 데이터를 만질 수 있는 경로, UI 가짜 보안 여부
4) 의존성: package-lock 커밋 여부, 오타 패키지, npm audit 결과
5) 에러 노출: 에러에 내부정보 노출/디버그 모드 여부
각 항목을 "통과/위험/확인필요"로 판정하고, 내가 직접 클릭해 확인할 검증 절차를 적어줘.
"안전합니다"라는 말 대신 확인 방법을 줘.
```

**(6) 흔한 함정·AI가 틀리는 것**

AI는 자기가 만든 코드를 "안전하다"고 과신한다. 그리고 같은 AI에게 다시 물으면 또 "안전하다"고 답하는 자기확인 편향이 있다. 실행해 보지도 않고 "처리했습니다"라고 보고하거나, "에러 없음"을 "안전함"과 혼동한다.

**(7) 검증하는 법**

1. 위 5개 항목 각각에 대해 **재현 가능한 증거**(브라우저 검색 0건, RLS 차단 화면, 권한 거부 응답 등)를 직접 확인.
2. 한 항목이라도 '확인필요/위험'이면 통과로 넘기지 않는다.
3. 가능하면 별도 세션이나 도구로 교차 점검해 자기확인 편향을 깬다.
