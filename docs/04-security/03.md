# 환경변수(.env) 제대로 — 무엇을 어디에, 무엇을 절대 커밋 안 하나

**(1) 한 줄 정의**

환경변수(.env)는 키·비밀 값을 코드 본문에 직접 쓰지(하드코딩하지) 않고 별도 파일로 분리해 두는 방식이다. 다만 비밀을 안전하게 하는 것은 `.env` 파일 자체가 아니라 **"그 파일을 깃허브에 안 올리는 것" + "`NEXT_PUBLIC_` 규칙"**이다.

**(2) 왜 중요한가(디렉터 관점)**

이른바 'Tving 사태'의 실제 원인은 흔히 오해하듯 "키를 잘못 만들어서"가 아니다. **키를 `.env`로 분리하지 않고 코드에 하드코딩한 채, 그 코드를 공개 저장소에 그대로 올려 노출한 것**이 진짜 원인이다. 디렉터가 알아야 할 핵심은 "파일을 나눴느냐"가 아니라 "그 파일이 공개 저장소로 새지 않게 막혔느냐", 그리고 "비밀 값에 실수로 공개 접두(`NEXT_PUBLIC_`)를 붙이지 않았느냐"다.

**(3) 비유**

`.env`는 금고 안에 둔 비밀 메모다. 금고에 넣었어도 금고 문을 활짝 열어 길거리(공개 깃허브)에 내놓으면 소용없다. `.gitignore`는 "이 금고는 절대 밖으로 들고 나가지 마"라는 규칙표다. `NEXT_PUBLIC_` 접두는 "이건 일부러 정문 게시판에 붙일 공지"라는 도장이다 — 비밀 메모에 이 도장을 찍으면 안 된다.

**(4) 최소한 알 것**

| 있는 것 | 한 줄 해설 | 판정 |
|---|---|---|
| `.gitignore`에 `.env.local` 등록 | 비밀 파일을 깃에 안 올리는 핵심 장치 | 🟢메인 |
| `.env.example`(자리표시자) | 키 이름만 적은 공개용 견본. 값은 비움 | 🟢메인 |
| `NEXT_PUBLIC_` 접두 | 이게 붙은 값만 브라우저에 노출됨(공개 의도) | 🟢메인 |
| 하드코딩 | 키를 코드에 직접 박기. Tving 사태 원인. 금지 | ⚪몰라도됨(피할 패턴) |

!!! warning "한 번 새면 파일 삭제로 끝나지 않는다"
    하드코딩된 키를 커밋한 적이 있으면 나중에 파일을 지워도 **git 기록(history)에 그대로 남습니다.** 노출이 의심되면 파일 삭제가 아니라 "키 회전(무효화 후 재발급)"이 정답입니다(05번 페이지 참고).

**(5) AI에게 이렇게 시켜라**

```text
이 프로젝트의 비밀 관리 상태를 점검해줘.
1) 코드 어디든 키/토큰/비밀번호가 하드코딩된 곳이 있는지 파일·줄 단위로 찾아줘.
2) .gitignore에 .env.local(과 비밀 .env)이 등록돼 있는지 확인.
3) NEXT_PUBLIC_ 접두가 붙은 환경변수 목록을 뽑고,
   그중 사실은 비밀이어야 하는 값(예: secret 키)이 섞여 있는지 표시.
4) 공개해도 되는 .env.example(값은 자리표시자)을 만들어줘.
추정 말고 실제로 발견한 것만 보고해.
```

**(6) 흔한 함정·AI가 틀리는 것**

AI는 빠른 동작을 위해 키를 **코드에 직접 하드코딩**하거나, `.gitignore`에 `.env`를 넣는 것을 빠뜨린다. 또 secret 키에 실수로 `NEXT_PUBLIC_`을 붙여 브라우저로 새게 만든다. "분리했으니 안전하다"고 보고하지만 정작 공개 저장소로 새는 경로는 점검하지 않는다.

**(7) 검증하는 법**

1. 공개 깃허브 저장소를 열어 `.env.local`이 **안 보이는지** 확인(보이면 즉시 키 회전).
2. 브라우저 F12 → Sources에서 secret 키 문자열 검색 → 0건이어야 함.
3. `git log`로 과거 커밋에 키가 들어간 적 없는지 점검. 있었다면 회전 절차로.
