# RLS(행 수준 보안) — 출입증을 공개해도 안전한 진짜 이유

**(1) 한 줄 정의**

RLS(Row Level Security, 행 수준 보안)는 "이 행(데이터 한 줄)을 누가 읽고/쓸 수 있나"를 DB 자체에 박아 넣는 잠금장치다. 애플리케이션 코드가 아니라 데이터베이스가 직접 막는다.

**(2) 왜 중요한가(디렉터 관점)**

공개 키(publishable)가 안전한 이유는 "키가 비밀이라서"가 **아니라** "RLS가 켜져 있어서"다. 이 한 문장이 권4 전체의 척추다. RLS가 꺼져 있으면 공개 출입증만으로 남의 데이터를 마음껏 읽고 고칠 수 있다. 디렉터의 보안 체크리스트를 단 하나로 줄이라면 "RLS 켜고 정책이 실제로 막는지 검증"이다. 이것은 OWASP 2025의 1위인 Broken Access Control(접근통제 실패)과 정면으로 직결된다.

**(3) 비유**

RLS는 도서관 사물함 시스템이다. 출입증(공개 키)으로 도서관에는 누구나 들어온다. 하지만 사물함은 각자 자기 번호 것만 열린다. 출입증을 잃어버려 남이 주워도, 그 사람은 자기 사물함만 열 수 있다. **잠금장치(RLS)가 출입증이 아니라 사물함 자체에 달려 있기** 때문이다.

**(4) 최소한 알 것**

| 있는 것 | 한 줄 해설 | 판정 |
|---|---|---|
| RLS 활성화(Enable) | 테이블마다 켜야 함. 끄면 공개 키로 다 뚫림 | 🟢메인 |
| 정책(Policy) | "누가 어떤 행을 읽기/쓰기 가능"의 규칙 | 🟢메인 |
| `auth.uid()` | 로그인한 본인 식별자. "본인 것만" 정책의 핵심 | 🟢메인 |
| `USING (true)` | 사실상 전부 열어버리는 무의미 정책. 위험 | ⚪몰라도됨(피할 패턴) |

!!! warning "OWASP 순위는 시점성 정보"
    "Broken Access Control이 OWASP Top 10 1위"라는 진술은 판본(예: 2025판)에 따라 달라질 수 있습니다. 본문에 인용할 때는 OWASP 공식 자료에서 판본과 날짜를 확인해 표기하세요.

**(5) AI에게 이렇게 시켜라**

```text
방금 만든 테이블들에 대해 RLS 상태를 점검해줘.
1) 각 테이블의 RLS가 켜져 있는지(Enabled) 표로 보여줘.
2) 각 정책을 사람 말로 풀어줘: "누가 / 어떤 행을 / 읽기·쓰기·수정·삭제 가능".
3) USING (true) 처럼 사실상 전부 열린 정책이 있으면 위험으로 표시하고,
   "누구나 읽기 + 작성자(auth.uid())만 수정/삭제"처럼 의도에 맞게 좁혀줘.
정책이 실제로 막는지 내가 눈으로 확인할 테스트 방법도 함께 알려줘.
```

**(6) 흔한 함정·AI가 틀리는 것**

AI는 코드나 마이그레이션을 생성할 때 **RLS가 꺼진 채** 테이블을 만들거나, 켜더라도 `USING (true)`처럼 사실상 전부 열린 무의미한 정책을 넣는다. 데모는 "잘 돌아가는 것처럼" 보이지만 실제로는 누구나 남의 데이터를 읽고 고칠 수 있는 상태다. 침묵이 안전을 뜻하지 않는다.

**(7) 검증하는 법**

1. Supabase 대시보드 → Authentication/Table editor에서 각 테이블 RLS가 **Enabled**인지 확인.
2. 다른 사용자(또는 비로그인)로 남의 행을 읽기/수정 시도 → 막히면 정상.
3. "정책을 끈 데모 테이블"과 "정책을 켠 테이블"을 나란히 두고 결과 차이를 직접 본다.

**(8) 더 깊이**

- Supabase 공식 문서: Row Level Security (Policies) — 1차 출처
- OWASP Top 10: Broken Access Control (판본·날짜 확인)
- 이 사이트의 자기증명: 방명록="누구나 읽기+작성자만 수정/삭제", 진도="본인만"

!!! example "💡 예시로 이해하기"
    독서모임 앱에 `reviews`(서평) 테이블이 있다. RLS를 켜고 `auth.uid() = user_id`로 "본인 글만 수정/삭제" 정책을 걸어두면, 회원 B가 자기 화면 주소창을 조작해 `DELETE /reviews/501` (남인 A의 글)을 직접 호출해도 DB가 0행 삭제로 되돌려보낸다. 코드가 아니라 데이터베이스가 막은 것이다.
    그런데 AI가 흔히 만드는 `USING (true)` 정책이 걸려 있었다면, 같은 요청이 그대로 통과해 A의 서평이 지워진다. 화면상으로는 둘 다 "잘 돌아가는 앱"처럼 보이지만, 두 번째는 누구나 남의 글을 지울 수 있는 상태다. 검증할 때는 꼭 B 계정으로 A의 글을 지워보고 막히는지 직접 눈으로 확인한다.
