# 확장 작업 공유 표준 (모든 에이전트 필독)

이 문서는 '여러분을 위한 웹개발 가이드'(treasure, MkDocs Material) 확장 작업에서 **모든 에이전트가 따라야 할 형식·톤·규칙**이다. 산출물의 일관성은 이 스펙 준수 여부로 결정된다.

## 0. 독자와 톤
- 독자: **비전공 청년**(바이브코딩 4일 부트캠프 수료생). 코드를 직접 다 짜기보다 **AI에게 시켜 만들고, 옳은지 판별하는 '디렉터'**.
- 깊이: **'디렉터 깊이'** — 수식·증명 없이, "무엇이 있고 / 왜 중요하고 / 언제 쓰고 / AI에게 어떻게 시키고 / 무엇이 함정인지"를 안다. 폭넓고 친절하게, 분량은 많을수록 좋다.
- 언어: **본문·제목은 한국어**, 폴더/파일 슬러그는 **영어**(우리가 가르치는 규칙). 영어 약어는 한국어 설명을 곁들인다.
- 비유를 적극 사용(예: 서버=주방, DNS=전화번호부, 캐시=자주 쓰는 물건을 책상 위에 둠).

## 1. 본문(가이드) 페이지 형식 — 8칸 표준
새 `docs/<volume>/NN.md` 페이지는 반드시 아래 8칸 + 예시 블록 구조를 따른다. (기존 `docs/02-web-basics/01.md`가 모범)

```
# (제목 — 명사형, 한국어)

**① 한 줄 정의**
(한 문장으로 핵심.)

**② 왜 중요한가 (디렉터 관점)**
(코드를 안 짜는 디렉터에게 왜 이 개념이 무기가 되는지.)

**③ 비유**
(일상 비유 한 단락.)

**④ 최소한 알 것**
(표 또는 불릿. 핵심 용어·구분·판단 기준.)

**⑤ AI에게 이렇게 시켜라**
```text
(복사해서 바로 쓸 수 있는 바이브코딩 프롬프트 예시. 구체적·맥락 포함.)
```

**⑥ 흔한 함정 / AI가 틀리는 것**
(이 주제에서 AI가 자주 저지르는 실수, 사람이 점검할 포인트.)

**⑦ 검증하는 법**
(만든 결과가 옳은지 비전공자가 눈/도구로 확인하는 절차.)

**⑧ 더 깊이**
→ [관련 페이지](상대경로.md) · [관련 페이지](...)
(필요시 *(참고: 1차 출처 — 확인 권장)*)

!!! example "💡 예시로 이해하기"
    (구체적 상황 하나로 위 개념을 체감시키는 한 단락.)
```

- 길라잡이 판정이 필요한 곳엔 **🟢 메인 / 🟡 대안 / 🔵 나중에 / ⚪ 몰라도 됨** 아이콘을 쓴다.
- admonition은 Material 문법(`!!! tip "제목"`, `!!! warning`, `!!! example`)을 쓴다.

## 2. 권(volume) 개요 index.md 형식
`docs/<volume>/index.md`는 아래 형식(기존 `docs/02-web-basics/index.md` 모범):
```
# (권 번호). (권 제목) — (부제)

> (이 권이 채우는 간극 한 문장.)

이 권의 페이지:

1. [페이지 제목](01.md)
2. [페이지 제목](02.md)
...
```

## 3. 실습 README 형식 — 기존 + 신규 공통
`examples/<id>/README.md`는 아래 섹션을 가진다. 기존 실습 강화 시 **없는 섹션만 추가**하고 기존 내용은 보존한다.

```
# 실습 (번호) — (제목)

(한 단락 소개 + 한 줄 그림 + 비유 인용블록)

## 목표
- (불릿 3~5개)

## 따라하는 단계
(단계별, 초보가 그대로 따라할 수 있게)

## 🤖 바이브코딩 프롬프트   ← (신규 필수 섹션)
이 실습을 AI에게 시켜 만들 때 그대로 복사해 쓸 수 있는 프롬프트.
- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  (역할·목표·제약·산출물을 담은 구체 프롬프트)
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  (이어서 시킬 프롬프트)
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  (에러 붙여넣고 단계별 진단 요청 프롬프트)
  ```
> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 좋다.

## 검증법
- (만든 결과가 옳은지 확인하는 절차 불릿)

## 파일 구성
- `파일명` — 설명

## 관련 가이드
- [관련 본문 권/페이지](상대경로) · 관련 실습 (번호)
- (외부 1차 출처 링크)
```

## 4. 코드 주석 표준 — 기능 + "넣은 이유"
모든 예제 코드(`index.html`, `script.js`, `*.sql`, `workflow.json` 외 등)는 **비전공자가 읽고 이해**하도록 주석을 단다. 핵심 원칙:
- **무엇(기능)** 뿐 아니라 **왜(넣은 이유)**를 적는다. 예: `// textContent로 출력 — innerHTML로 하면 사용자가 넣은 <script>가 실행될 수 있어 XSS 위험이라 막는 것`
- 파일 맨 위에 **이 파일이 무엇이고 왜 있는지** 한 블록 요약.
- 비밀값/보안 관련 줄에는 반드시 이유 주석(공개해도 되는 값 vs 숨겨야 하는 값).
- 과하게 모든 줄에 달지 말고, **초보가 막힐 만한 지점**에 집중.
- 기존 모범: `examples/001/index.html`(무엇), `examples/180/index.html`(보안 이유 주석). 강화 시 "왜"를 보강한다.
- 주석은 한국어. 코드 식별자(변수/함수명)는 영어 유지.

## 5. 저장소·링크 규칙
- 실습 코드 링크: `https://github.com/zeusk302-png/treasure/tree/main/examples/<id>`
- 본문↔실습 상대경로: 실습 README에서 본문으로 `../../docs/<volume>/index.md`, 본문에서 실습은 GitHub 링크.
- 본문 페이지끼리 cross-link는 **존재하는 파일만** 건다(깨진 링크 금지). 같은 권 내는 `NN.md`, 다른 권은 `../<volume>/NN.md`.
- 비밀값은 코드에 절대 박지 않는다. `.env.example`(자리표시자) + `.gitignore`. anon 키는 공개 가능, service_role은 비밀.

## 6. 보안 정확성(중요)
- Supabase: **anon 키 = 공개 가능**(브라우저에 나가도 됨), **service_role 키 = 비밀**(서버/n8n만). 보호는 **RLS(행 수준 보안)**로 한다. ("anon=비밀키"는 틀린 설명 — 쓰지 말 것.)
- 사용자 입력 출력은 `textContent`(기본), `innerHTML`은 XSS 위험. SQL은 파라미터 바인딩.

## 7. 마크다운 표 주의 (이번에 실제로 터진 버그)
- 표 셀 안에 HTML 태그 이름을 쓸 땐 **반드시 백틱**으로 감싼다: `` `<title>` ``, `` `<script>` ``. 날것 `<title>`/`<script>`는 RCDATA라 페이지 뒷부분을 통째로 삼켜 렌더링이 깨진다.
- 표 셀 안에는 `|`를 쓰지 않는다(쓰려면 `\|`).

## 8. 산출물 보고 형식(에이전트 → 워크플로우)
schema가 주어지면 그 형식으로, 아니면 **생성/수정한 파일 경로 목록과 한 줄 요약**을 반환한다. 사람용 인사말 없이 데이터만.
