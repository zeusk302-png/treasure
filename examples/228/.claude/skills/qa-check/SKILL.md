# /qa-check — 배포 전 출시 점검 스킬

이 스킬은 웹페이지를 세상에 내보내기 직전에 **항상 똑같은 4가지 항목**을 검수하는 체크리스트입니다.
"점검해줘" 한마디면, 매번 같은 기준으로 같은 순서로 검사해서 표로 보고합니다.

## 언제 쓰나 (트리거)

- 사용자가 "점검해줘 / 배포 전에 확인 / qa 돌려줘 / 내보내기 전에 봐줘"라고 말할 때
- index.html(또는 HTML/CSS/JS)을 배포·커밋·업로드하기 직전일 때

## 점검 대상 (사람이 먼저 알려줄 것)

검사할 파일이나 폴더를 사용자가 지정합니다. 지정이 없으면 현재 폴더의 `index.html`을 기본으로 봅니다.
필요하면 사용자에게 "어떤 파일/폴더를 점검할까요?"라고 한 번 물어봅니다.

## 검사 순서 (이 순서를 지킬 것)

아래 4가지를 **반드시 이 순서대로** 검사하고, 각 항목에 `✅ 통과 / ⚠️ 주의 / ❌ 실패`를 매깁니다.
판정이 애매하면 단정하지 말고 ⚠️로 두고 근거(파일명·줄 번호·이유)를 적습니다.

### 1) 콘솔 에러 (Console errors)

- HTML 안의 `<script>`와 연결된 `.js` 파일을 읽어, 브라우저 콘솔에서 빨간 에러가 날 만한 곳을 찾는다.
- 대표 후보:
  - `<script src="...">` 의 경로가 실제 파일과 다름 (404)
  - `getElementById("x")` 했는데 HTML에 `id="x"`가 없음 → `null` 에러
  - `</script>`, `}`, `)` 등 닫힘 누락(문법 에러)
  - 정의 안 된 함수/변수 호출
- 판정: 에러 가능성이 있으면 ❌, 의심되면 ⚠️, 없으면 ✅. **어느 줄 때문인지** 적는다.

### 2) 비밀키 노출 (Secret keys)

가장 중요한 보안 항목입니다. **공개해도 되는 값과 절대 숨겨야 하는 값**을 구분합니다.

- ✅ 공개돼도 되는 값(프론트엔드 코드에 있어도 정상):
  - Supabase **anon/publishable 키**(공개키) — RLS(행 수준 보안)로 보호되는 전제
  - Supabase **프로젝트 URL**(`https://xxxx.supabase.co`)
- ❌ 절대 코드/깃에 있으면 안 되는 값(노출 시 실패):
  - Supabase **service_role 키**(비밀키) — DB를 통째로 만질 수 있어 RLS를 무시함
  - 결제·이메일·API의 **secret key**, **비밀번호**, **토큰**, `.env`의 비밀값
- 검사 방법: 코드와 텍스트에서 아래 같은 흔적을 찾는다.
  - `service_role`, `sk_live_`, `sk_test_`, `SECRET`, `PASSWORD`, `Bearer ey...`(JWT) 등
  - `eyJ...`로 시작하는 긴 JWT가 있으면 그게 anon(공개)인지 service_role(비밀)인지 사람에게 확인하도록 표시
- 판정: 비밀키가 코드에 보이면 ❌ + "이 값을 코드에서 빼고 회전(재발급)하세요"라고 적는다.
  공개키만 있으면 ✅(단, RLS가 켜져 있는지 사람이 확인하라고 한 줄 덧붙인다).

> 보고서·예시 코드에 비밀값을 그대로 옮기지 말 것. 항상 `YOUR_SERVICE_ROLE_KEY` 같은 **자리표시자**로 가린다.

### 3) 모바일 화면 (Mobile)

- `<head>`에 `<meta name="viewport" content="width=device-width, initial-scale=1">`가 있는지 본다. 없으면 ❌.
- 가로 스크롤을 유발할 만한 요소(고정 큰 `width`, 화면 밖으로 나가는 절대 위치 등)가 있는지 본다.
- 모바일 분기(`@media`)나 반응형 레이아웃(flex/grid의 줄바꿈)이 있는지 본다.
- 판정: viewport 없거나 가로 스크롤 위험이 크면 ❌/⚠️. 근거(어느 속성/줄)를 적는다.

### 4) 이미지 대체 텍스트 (alt)

- 모든 `<img>` 태그에 `alt` 속성이 있는지 센다.
- 의미 있는 이미지인데 `alt`가 비었거나 없으면 ⚠️/❌.
- 판정: "총 N개 중 M개에 alt 없음 — 몇 번째 img"처럼 개수와 위치를 적는다.

## 보고 형식 (이 표로 출력할 것)

```
# /qa-check 결과 — <검사한 파일명>

| 항목 | 상태 | 근거 / 해야 할 일 |
|---|---|---|
| 1. 콘솔 에러 | ✅/⚠️/❌ | (어느 줄, 왜) |
| 2. 비밀키 노출 | ✅/⚠️/❌ | (무엇이 보였나, 자리표시자로) |
| 3. 모바일 화면 | ✅/⚠️/❌ | (viewport 유무 등) |
| 4. 이미지 alt | ✅/⚠️/❌ | (N개 중 M개 누락) |

## 한 줄 결론
배포해도 됨 / 고치고 다시 점검 (❌가 하나라도 있으면 "고치고 다시 점검")
```

## 규칙

- ❌가 하나라도 있으면 결론은 반드시 "고치고 다시 점검"으로 한다.
- 추측으로 단정하지 말고, 애매하면 ⚠️ + 근거를 남긴다.
- 코드를 마음대로 고치지 않는다. **무엇을 왜 고쳐야 하는지**만 알려주고, 고칠지는 사람(디렉터)이 정한다.
- 비밀값은 보고서에 절대 그대로 쓰지 말고 자리표시자로 가린다.
