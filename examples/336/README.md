# 실습 336 — 간단 부하테스트로 한계 감 잡기

내 사이트(또는 API)가 **사람이 몰리면 몇 명까지 버티는지**를 숫자로 확인하는 실습입니다. 평소엔 혼자 눌러 보니 다 빠릿빠릿하지만, 동시에 50명·100명이 들어오면 갑자기 느려지거나 에러가 터질 수 있습니다. 이번에는 **k6**라는 부하테스트 도구로 내 엔드포인트에 가벼운 '가짜 손님 떼'를 보내, **초당 처리량(RPS)**과 **응답시간(특히 p95)**을 측정해 봅니다. (k6 설치가 부담되면 Node 패키지 하나만 설치하면 되는 **autocannon**도 함께 준비해 뒀습니다.)

> 한 줄 그림: **k6가 가짜 손님 N명을 동시에 보냄 → 내 서버가 응답 → k6가 "초당 몇 건 처리했고, 95%는 몇 ms 안에 답했고, 실패는 몇 %"를 표로 정리**

> 비유: 부하테스트는 **개업 전 '모의 손님 리허설'**입니다. 친구 100명을 한꺼번에 가게로 들여보내 "주방이 안 터지나, 줄이 얼마나 길어지나"를 미리 보는 것입니다. 진짜 손님(실사용자)에게 처음으로 터지는 것보다, 리허설에서 미리 터뜨려 보고 고치는 편이 훨씬 안전하겠죠.

> 안전 메모 — 누구를 때려도 되는가
> - **반드시 내 것만 테스트**합니다. 부하테스트는 본질적으로 "짧은 시간에 요청을 퍼붓는" 행위라, **남의 서버에 허락 없이 하면 공격(DoS)으로 간주**될 수 있습니다. 대상은 **내가 만든·내가 권한 가진 주소**로만 두세요.
> - **무료 티어 주의**: 배포된 사이트(Vercel/Render 등)에 세게 때리면 **요청 수가 무료 한도를 깎아먹거나 요금이 나올 수** 있습니다. 처음에는 **로컬에서 띄운 서버**(`http://localhost:3000`)를 대상으로 작게 시작하세요.
> - 비밀값(있다면)은 코드에 박지 말고 `.env`에 두고, `.gitignore`로 깃에서 뺍니다. 이 실습 자체는 비밀값이 거의 없지만, 대상 URL·인증 토큰을 쓸 경우를 위해 견본을 넣어 뒀습니다.

## 목표
- **부하를 숫자로 본다**: 동시 사용자 수(VU)를 늘려 가며 **RPS(초당 처리량)**·**응답시간 p95**·**에러율**이 어떻게 변하는지 직접 관찰한다.
- **'한계점'의 감을 잡는다**: VU를 점점 올리다 보면 응답시간이 갑자기 치솟거나 에러가 나기 시작하는 **무릎(knee) 지점**이 보인다 — 그게 대략 내 한계다.
- **p95가 평균보다 중요한 이유를 이해한다**: 평균은 빠른 사람들에 가려져 좋게 보여도, **느린 5%(p95)**가 실제 사용자 불만의 정체임을 안다.
- **안전하게 측정하는 습관을 들인다**: 내 것만, 작게 시작해서 키우고, 무료 한도를 의식하며 테스트한다.

## 따라하는 단계

### A. 부하를 받을 '대상 서버' 띄우기 (먼저 때릴 대상이 있어야 함)
1. 이 폴더에서 의존성을 설치합니다: `npm install`
2. 연습용 작은 서버를 띄웁니다: `npm start` → 콘솔에 `http://localhost:3000 에서 대기 중` 이 뜨면 성공입니다.
   - 이 서버에는 일부러 두 개의 길이 있습니다: `GET /` (아주 가벼움)과 `GET /slow` (일부러 30~80ms 걸리게 만든 무거운 길). 부하를 줬을 때 둘이 어떻게 다른지 비교하기 위함입니다.
3. (선택) 이미 내가 만든 다른 서버/사이트가 있다면 그 주소를 대상으로 써도 됩니다. 단, **내 것만** 대상으로 하세요.

### B. k6로 부하 주기 (메인 방법)
4. k6를 설치합니다(택1):
   - Windows: `winget install k6 --source winget` (또는 [Chocolatey] `choco install k6`)
   - macOS: `brew install k6`
   - 설치가 어려우면 C단계의 autocannon로 건너뛰어도 됩니다.
5. 부하 시나리오를 실행합니다: `npm run loadtest:k6`
   - 내부적으로 `k6 run load-test.js`가 돕니다. 이 스크립트는 사용자 수를 **0명 → 20명 → 50명**으로 천천히 올렸다가 내리는 단계(ramp)로 짜여 있습니다.
6. 끝나면 k6가 요약표를 보여줍니다. 다음 줄을 찾아 읽습니다.
   - `http_reqs` 옆의 숫자 / 시간 → **초당 처리량(RPS)** 감.
   - `http_req_duration` 의 `avg`(평균)·`p(95)`(상위 5% 느림) → **응답시간**. p95가 평균보다 한참 크면 "가끔 많이 느린 손님"이 있다는 뜻.
   - `http_req_failed` → **에러율**. 0%에 가까워야 정상.
7. **한계를 찾아 봅니다**: `load-test.js` 안 `stages`의 `target` 숫자(20, 50)를 100, 200으로 올려 다시 실행해 봅니다. 응답시간 p95가 갑자기 뛰거나 에러율이 0%를 벗어나기 시작하는 지점이 대략 내 서버의 **한계 감**입니다.

### C. autocannon로 부하 주기 (k6 설치가 어려울 때)
8. autocannon는 이 폴더 `npm install` 때 함께 깔립니다. 바로 실행합니다: `npm run loadtest:auto`
   - 내부적으로 `autocannon -c 50 -d 10 http://localhost:3000/` 가 돕니다(동시연결 50, 10초 동안).
9. 끝나면 autocannon도 비슷한 표를 줍니다: `Req/Sec`(초당 처리량), `Latency`의 `Avg`/`p99`(응답시간), `2xx`/`Non 2xx`(성공/실패 수). k6와 같은 눈으로 읽으면 됩니다.

### D. 가벼운 길 vs 무거운 길 비교
10. 대상 경로를 `/`에서 `/slow`로 바꿔 다시 돌려 봅니다(k6는 `load-test.js`의 `BASE_URL`/경로, autocannon는 명령 끝의 URL을 `.../slow`로). 같은 사용자 수인데도 **무거운 길은 RPS가 낮고 p95가 크게** 나옵니다 — "느린 코드 한 줄이 처리량을 어떻게 깎아먹는지"가 숫자로 보입니다.

  ```text
  제약/요청:
  - 대상 서버는 의존성 없는 Node 내장 http 모듈로 server.js 하나에 만들어줘. 포트 3000.
  ```

  ```text

  1) "통과 기준(threshold)"을 추가해줘: http_req_duration의 p95가 500ms를 넘거나 http_req_failed가 1%를 넘으면 테스트가 FAIL로 끝나게(thresholds 설정). 이게 왜 CI에서 유용한지 주석으로 설명.
  ```

  ```text

  - 실행한 명령: (예: npm run loadtest:k6)
  - 화면에 뜬 에러/결과: (여기에 그대로 붙여넣기 — 예: dial tcp 127.0.0.1:3000: connect: connection refused / http_req_failed 100%)

  2) URL 오타나 http/https 혼동.
  3) k6가 설치돼 PATH에 있는지(k6 version으로 확인).
  4) 에러율이 높다면 그게 '내 서버가 한계라서'인지 '연결 자체가 안 돼서'인지 구분하는 법.
  ```

> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "p95가 평균보다 왜 중요한지 비전공자가 이해하게 한 줄로 풀어줘"를 덧붙이면 학습에 좋습니다.

## 검증법
- **대상 서버가 응답하는지 먼저 확인**: 브라우저로 `http://localhost:3000/` 을 열어 `{"ok":true}` 가 보이면 부하를 줄 준비가 된 것이다.
- **결과표에 숫자가 찍히는지**: k6 실행 후 `http_reqs`, `http_req_duration`의 `p(95)`, `http_req_failed` 가 0이 아닌 실제 숫자로 나오면 측정이 된 것이다. (autocannon는 `Req/Sec`·`Latency`·`2xx` 칸.)
- **가벼운 길 vs 무거운 길 차이 확인**: `/` 대상일 때보다 `/slow` 대상일 때 **RPS는 낮고 p95는 크게** 나오면, 부하가 코드의 무게를 정확히 잡아낸 것이다.
- **한계 감 확인**: `target`을 키워 가며 돌릴 때, 어느 지점부터 **p95가 급등하거나 `http_req_failed`가 0%를 벗어나면** 그 부근이 내 서버의 한계다. 그 숫자를 메모해 둔다.
- **안전 점검**: 대상 URL이 **내 것(localhost 또는 내 도메인)**인지 다시 확인한다. 남의 주소가 적혀 있으면 안 된다.
- **비밀값 노출 점검**: 토큰을 썼다면 코드 대신 `.env`에만 있는지 확인한다. 이 폴더에서 `grep -nE "Bearer [A-Za-z0-9]{10}|sk-[A-Za-z0-9]" . -r --exclude-dir=node_modules` 를 돌렸을 때 진짜 키가 안 나와야 정상이다.

## 파일 구성
- `server.js` — 부하를 받아 줄 연습용 작은 서버. 가벼운 길(`/`)과 일부러 느린 길(`/slow`)을 둬 비교 학습한다. (Node 내장 모듈만 사용 — 설치 부담 없음.)
- `load-test.js` — k6 부하 스크립트. 사용자 수를 단계적으로 올렸다 내리며 RPS·p95·에러율을 측정하고, 통과 기준(threshold)으로 합격/불합격을 판정한다.
- `package.json` — `npm start`(대상 서버), `loadtest:k6`(k6 실행), `loadtest:auto`(autocannon 실행) 스크립트와 autocannon 의존성.
- `.env.example` — 대상 URL·(선택)인증 토큰 견본. 자리표시자만 들어 있으며, 복사해 `.env`로 만들고 진짜 값은 거기에만 둔다.
- `.gitignore` — `.env`·`node_modules`가 깃에 올라가지 않게 막는다.
