# /deploy — 배포 자동화 스킬 (비밀키 점검 포함)

이 스킬은 내가 만든 사이트를 세상에 내보내는 일을 **항상 똑같은 6단계 순서**로 진행합니다.
"배포해줘" 한마디면, 매번 같은 순서로 점검하고 커밋·푸시한 뒤 **배포 URL**까지 보고합니다.

> 핵심 원칙 — **비밀키가 코드에 보이면 즉시 멈춘다(4단계 진입 금지).**
> 한 번 깃에 올라간 비밀키는 지워도 기록에 남습니다. 그래서 "올리기 전에" 막는 게 유일한 방법입니다.

## 언제 쓰나 (트리거)

- 사용자가 "배포해줘 / deploy / 올려줘 / 푸시하고 배포 / 출시해줘"라고 말할 때
- 작업을 마치고 GitHub에 올려 Vercel로 자동 배포하려 할 때

## 진행 전 확인 (사람이 먼저 알려줄 것)

- 배포할 폴더(저장소). 지정이 없으면 현재 폴더를 기본으로 본다.
- 커밋 메시지로 쓸 "이번에 무엇을 했는지" 한 줄. 없으면 변경 내용을 보고 후보를 제안하고 사람에게 확인받는다.
- 이 스킬은 **사람의 승인 없이는 push까지 가지 않는다.** 5단계(푸시) 직전에 반드시 한 번 확인한다.

## 진행 순서 (이 순서를 반드시 지킬 것)

아래 6단계를 **순서대로** 진행한다. 각 단계가 끝나면 `✅ 통과 / ⚠️ 주의 / ❌ 중단`을 매긴다.
**3단계(비밀키)에서 ❌가 나오면 4단계 이후로 절대 넘어가지 않는다.**

### 1) git 상태 확인 (변경된 게 무엇인지 보기)

- 실행: `git status` 와 `git diff --stat`
- 무엇이 새로 생기고/바뀌고/지워졌는지 사람에게 요약해서 보여 준다.
- 올리면 안 되는 파일이 섞였는지 본다: `.env`, `.env.local`, `node_modules/`, 키가 든 설정 파일 등.
  - 이런 파일이 추적(track)되고 있으면 ⚠️ — `.gitignore`에 넣고 추적에서 빼라고 안내한다.
- 판정: 올릴 변경이 명확하면 ✅. 위험 파일이 섞였으면 ⚠️(또는 ❌).

### 2) 빌드 확인 (깨진 채로 올리지 않기)

- 정적 사이트(순수 HTML/CSS/JS)면 빌드 단계가 없을 수 있다. 그럴 땐 `index.html`이 존재하고 `<script src>`/`<link href>` 경로가 실제 파일과 맞는지만 확인한다.
- 빌드가 있는 프로젝트면 `package.json`의 빌드 명령(`npm run build`)을 실행해 **에러 없이 끝나는지** 확인한다.
- 판정: 빌드 성공 또는 정적 파일 이상 없음이면 ✅. 빌드 실패면 ❌ — "고치고 다시"라고 보고하고 **여기서 멈춘다.**

### 3) 비밀키 점검 (가장 중요 — 여기서 막는다)

배포의 **마지막 안전핀**입니다. 코드·텍스트에서 비밀값 흔적을 찾는다.

- ✅ 공개돼도 되는 값(프론트엔드 코드/깃에 있어도 정상):
  - Supabase **anon / publishable 키**(공개키) — RLS(행 수준 보안)로 보호되는 전제
  - Supabase **프로젝트 URL**(`https://xxxx.supabase.co`)
- ❌ 절대 코드/깃에 있으면 안 되는 값(보이면 즉시 중단):
  - Supabase **service_role 키**(비밀키) — RLS를 무시하고 DB를 통째로 만질 수 있음
  - 결제·이메일·API의 **secret key**, **비밀번호**, **토큰**, `.env`의 비밀값
- 검사 방법: 변경된 파일과 추적 대상 전체에서 아래 흔적을 찾는다.
  - `service_role`, `sk_live_`, `sk_test_`, `SECRET`, `PASSWORD`, `Bearer ey...`(JWT) 등
  - `eyJ...`로 시작하는 긴 JWT가 보이면 anon(공개)인지 service_role(비밀)인지 사람에게 확인하도록 표시한다.
- 판정:
  - 비밀키가 코드/깃에 보이면 **❌ → 즉시 중단.** "이 값을 코드에서 빼서 환경변수(Vercel 환경변수 칸)로 옮기고, 노출된 키는 회전(재발급)하세요"라고 적는다. **커밋·푸시로 넘어가지 않는다.**
  - 공개키만 있으면 ✅(단, "RLS가 켜져 있는지 사람이 한 번 확인하라"는 한 줄을 덧붙인다).

> 보고서에 비밀값을 그대로 옮기지 말 것. 항상 `YOUR_SERVICE_ROLE_KEY` 같은 **자리표시자**로 가린다.

### 4) 커밋 (Conventional Commits 형식)

- 3단계가 ✅/⚠️일 때만 진행한다(❌면 진입 금지).
- `git add` 할 파일을 사람에게 보여 주고 확인받은 뒤 스테이징한다.
- 커밋 메시지는 **Conventional Commits** 형식으로 쓴다: `type: 한 줄 요약`
  - `feat:` 새 기능 / `fix:` 버그 수정 / `docs:` 문서 / `style:` 모양·서식 / `refactor:` 구조 정리 / `chore:` 잡일·설정
  - 예: `feat: 방명록 글쓰기 폼 추가`, `fix: 모바일에서 메뉴 안 닫히던 문제 수정`
- 사람이 준 "이번에 한 일" 한 줄을 알맞은 type에 맞춰 다듬는다.

### 5) 푸시 (사람 승인 후)

- **푸시 직전에 반드시 한 번 더 확인한다**: "이 커밋(`<메시지>`)을 `origin <브랜치>`에 올릴까요?"
- 승인되면 실행: `git push`
- 푸시가 되면 GitHub→Vercel 자동 배포가 트리거된다(자동배포가 연결돼 있다는 전제).

### 6) 배포 URL 보고

- Vercel이 빌드를 끝내면 나오는 **배포 URL**을 사람에게 알려 준다.
  - production 도메인(예: `https://내사이트.vercel.app`)과, 있으면 이번 배포의 preview URL을 함께 적는다.
- 사람에게 **"브라우저로 열어 1분만 직접 확인하세요"**라고 안내한다(첫 화면·콘솔 에러·모바일).

## 보고 형식 (이 표로 출력할 것)

```
# /deploy 결과 — <저장소/폴더 이름>

| 단계 | 상태 | 내용 / 근거 |
|---|---|---|
| 1. git 상태 | ✅/⚠️/❌ | (바뀐 파일 요약, 위험 파일 유무) |
| 2. 빌드 확인 | ✅/⚠️/❌ | (빌드 성공/정적 OK/실패 이유) |
| 3. 비밀키 점검 | ✅/⚠️/❌ | (무엇이 보였나, 자리표시자로) |
| 4. 커밋 | ✅/⏸️ | (커밋 메시지: type: 요약) |
| 5. 푸시 | ✅/⏸️ | (origin/브랜치, 승인 여부) |
| 6. 배포 URL | ✅/⏸️ | (https://... 또는 "대기") |

## 한 줄 결론
배포 완료(URL) / 비밀키 노출로 중단 / 빌드 실패로 중단
```

## 규칙

- **3단계(비밀키)에서 ❌면 절대 커밋·푸시하지 않는다.** 배포 전체를 멈추고 무엇을 빼야 하는지만 보고한다.
- 2단계(빌드)가 실패해도 멈춘다. 깨진 채로 올리지 않는다.
- push는 **사람 승인 후에만** 한다. 승인 전 단계는 표에 `⏸️`로 표시한다.
- 추측으로 단정하지 말고, 애매하면 ⚠️ + 근거를 남긴다.
- 커밋 메시지는 항상 Conventional Commits 형식(`type: 요약`)으로 짧고 명확하게 쓴다.
- 비밀값은 보고서에 절대 그대로 쓰지 말고 자리표시자(`YOUR_SERVICE_ROLE_KEY`)로 가린다.
