# 프론트에 노출된 service_role 키 회수하기 — F12에 그대로 보이는 비밀키

방명록 사이트가 잘 작동은 합니다. 글도 보이고, 글도 써집니다. 그런데 **치명적인 보안 사고**가 숨어 있습니다.
누군가가 "DB를 통째로 관리할 수 있는 **비밀키(service_role)**"를 프론트엔드 코드에 그대로 박아 두었습니다.

문제는, **프론트엔드 코드는 누구나 볼 수 있다**는 점입니다. 방문자가 키보드 `F12`만 누르면 코드가 통째로 보입니다.
즉, 비밀키를 프론트에 두는 순간 그 키는 **전 세계에 공개된 것**과 같습니다.
이 키를 손에 넣은 사람은 RLS(잠금장치)를 **통째로 무시하고** 방명록의 모든 글을 읽고, 수정하고, **전부 삭제**할 수 있습니다.

이 실습은 **"공개돼도 되는 키"와 "절대 숨겨야 하는 키"를 구분하고**, 노출된 비밀키를 회수(제거)한 뒤
공개키(publishable / anon)로 교체하는 보안 디버깅 실습입니다.

> 안심하세요: 이 실습의 코드에 적힌 키 값은 전부 `REPLACE_WITH_...` 같은 **가짜 자리표시자**입니다. 진짜 키가 아닙니다.

## 목표

- **공개돼도 되는 값**과 **절대 숨겨야 하는 값**을 정확히 구분한다.
  - 공개 OK: 프로젝트 URL, `publishable` / `anon` 키
  - 절대 금지: `service_role` / `secret` 키
- **프론트엔드(브라우저) 코드는 비밀이 아니다**는 사실을 몸으로 안다. `F12` → Sources 탭이나 "페이지 소스 보기"로 누구나 통째로 본다.
- `service_role` 키가 왜 위험한지 이해한다. 이 키는 **RLS(행 수준 보안)를 무시**하고 DB의 모든 행을 읽고/쓰고/지운다. (그래서 서버/백엔드의 환경변수에만 둬야 한다)
- 노출된 비밀키를 **제거(회수)**하고, 그 자리에 **공개키로 교체**한다. 공개키가 노출돼도 안전한 이유는 DB에 **RLS** 잠금장치가 걸려 있기 때문임을 안다. (짝꿍 실습 291)

## 따라하는 단계

1. **사고 현장부터 본다.** `broken.html`을 브라우저로 엽니다. 겉보기엔 평범한 방명록입니다. (URL/키가 가짜라 실제 데이터는 안 뜨지만, 코드 구조는 실전과 똑같습니다.)
2. **방문자 시점으로 비밀키를 찾아본다.** 키보드 `F12`(또는 우클릭 → 검사) → **Sources(소스)** 탭을 엽니다.
   - 검색 단축키 `Ctrl + F`(맥은 `Cmd + Opt + F`)로 **`service_role`** 또는 **`secret`** 을 검색합니다.
   - `broken.html` 안에서 `SUPABASE_SERVICE_ROLE_KEY = "..."` 줄이 **그대로 검색됩니다.** → **이 화면이 "before(사고)" 캡처입니다.**
   - 우클릭 → "페이지 소스 보기"로도 똑같이 보입니다. 즉, **이 키는 이미 공개된 것**입니다.
3. **왜 위험한지 코드로 확인한다.** `broken.html`의 이 두 줄이 문제의 핵심입니다.
   - `const SUPABASE_SERVICE_ROLE_KEY = "...";`  ← 비밀키를 프론트에 박음
   - `const db = supabase.createClient(SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY);`  ← 비밀키로 연결 → **RLS가 통째로 무시됨**
   - 이 상태에서는 방문자 아무나 이 키로 `delete()`를 호출해 **남의 글을 전부 지울 수 있습니다.**
4. **비밀키를 회수(제거)한다.** 코드에서 `service_role` 키를 **완전히 지웁니다.** 프론트엔드에는 비밀키를 **단 한 글자도** 남기지 않습니다.
5. **공개키로 교체한다.** 이 폴더의 `index.html`이 정답 버전입니다. 비밀키가 있던 자리에 **`publishable` / `anon`(공개)** 키를 넣었습니다.
   - 실제 값은 Supabase 대시보드 → **Project Settings → API Keys** 의 **"publishable / anon"** 칸에서 복사합니다. (이 칸 값은 공개돼도 됩니다.)
   - `service_role` 칸의 값은 절대 복사해 오지 않습니다. 그건 **서버 환경변수**에만 둡니다. (실습 173, 174)
6. **RLS가 켜져 있어야 진짜 안전하다.** 공개키가 안전한 이유는 DB에 RLS 정책이 걸려 있어서입니다. RLS가 꺼져 있으면 공개키만으로도 위험해집니다. RLS 설정은 짝꿍 실습 **291**에서 다룹니다.
7. **고친 화면을 다시 검사한다.** `index.html`을 열고 다시 `F12` → Sources에서 `service_role` / `secret` 을 검색합니다. 이번엔 **0건**이 나와야 합니다. → **이 화면이 "after(회수 완료)" 캡처입니다.**

## 무엇을 어떻게 고쳤나 (before → after)

| 항목 | 고치기 전 (`broken.html`) | 고친 후 (`index.html`) | 왜 그랬나 |
| --- | --- | --- | --- |
| 사용한 키 | `service_role`(비밀) 키 | `publishable` / `anon`(공개) 키 | 프론트엔드 코드는 누구나 본다 → 공개키만 둔다 |
| 비밀키 위치 | 프론트 `<script>` 안에 박음 | 프론트에서 **완전 제거** | 비밀키는 서버 환경변수에만 (실습 173/174) |
| RLS와의 관계 | RLS를 **무시**함 (관리자 권한) | RLS의 **통제를 받음** (정책 허용 동작만) | RLS가 키 노출을 막아 주는 잠금장치 |
| `F12` Sources 검색 | `service_role` **1건 이상** 노출 | `service_role` / `secret` **0건** | "검색 0건"이 회수 완료의 증거 |

핵심은 코드를 늘린 게 아니라, **노출되면 안 되는 키를 빼고, 노출돼도 되는 키로 바꿔 끼운 것**뿐입니다.
그리고 그게 잘 됐는지는 **추측이 아니라 `F12` Sources에서 직접 검색**해 확인합니다.

### 한 가지 더 알아두기

- **이미 노출된 비밀키는 "제거"만으로 끝나지 않습니다.** 한 번이라도 공개된 키는 깃 기록·캐시·남의 화면에 남았을 수 있으므로, Supabase 대시보드에서 그 키를 **무효화하고 새로 발급(키 회전, rotation)** 해야 진짜 안전합니다. (가이드 `docs/04-security/05.md`)
- `anon`은 옛 이름, `publishable`은 새 이름입니다. 둘 다 **"공개돼도 되는 키"**라는 점은 같습니다. 핵심 구분은 언제나 **공개키 vs 비밀키(service_role/secret)** 입니다.
- 공개키가 안전한 건 **RLS가 켜져 있다는 전제** 하에서입니다. RLS가 꺼져 있으면 공개키만으로도 데이터가 다 털릴 수 있습니다. (짝꿍 실습 291)

## 🤖 바이브코딩 프롬프트

이 보안 디버깅 실습을 AI에게 시켜 만들/고칠 때 그대로 복사해 쓸 수 있는 프롬프트입니다.

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  Supabase 방명록 단일 HTML 파일을 만들어줘. 비전공자 학습용 보안 디버깅 예제야.
  - 한 파일(index.html) 안에 글 목록 보기 + 이름/메시지 입력 + 남기기 버튼.
  - supabase-js는 CDN(<script src=".../@supabase/supabase-js@2">)으로 불러와.
  - SUPABASE_URL과 키는 "REPLACE_WITH_..." 같은 가짜 자리표시자로 둬(진짜 키 절대 넣지 마).
  - 반드시 "공개돼도 되는 키(publishable / anon)"만 createClient에 넣어. service_role 키는 코드 어디에도 쓰지 마.
  - 비전공자도 읽게, 각 줄이 무엇을 하고 왜 그렇게 했는지 한국어 주석으로 한 줄씩 설명해줘.
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  방금 만든 정답 버전(index.html)과 짝이 되는 "고장 난 버전(broken.html)"도 만들어줘.
  - 똑같은 방명록인데, 일부러 service_role(비밀) 키를 프론트 <script>에 박아 둔 "보안 사고" 상태로.
  - 키 값은 시연용 가짜 자리표시자로 두고, 이게 왜 위험한지(F12 Sources/소스 보기로 누구나 본다, RLS를 무시한다)
    주석으로 분명히 설명해줘.
  - 마지막으로 두 파일을 비교하는 before→after 표를 README에 넣어줘:
    사용한 키 / 비밀키 위치 / RLS와의 관계 / F12 검색 결과(1건 이상 vs 0건) 네 항목으로.
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  내 방명록 코드에서 비밀키가 새는지 점검해줘. 아래 코드를 붙여넣을게.
  - createClient에 넘기는 키 변수 이름이 PUBLISHABLE/ANON인지, 아니면 SERVICE_ROLE인지 먼저 확인해줘.
  - service_role이나 secret이라는 단어가 코드 어디에 있는지 전부 찾아서 줄 번호로 알려줘.
  - 비밀키를 어떻게 "완전히 제거"하고 공개키로 바꿔 끼우는지 단계별로 알려줘.
  - 고친 뒤 F12 → Sources에서 service_role 검색이 0건이 되는지 어떻게 확인하는지도 설명해줘.

  [여기에 내 코드 또는 에러 메시지를 붙여넣기]
  ```
> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 좋습니다. 보안 실습이니 "공개돼도 되는 키와 절대 숨겨야 하는 키를 표로 구분해줘"도 함께 시키면 좋습니다.

## 검증법

1. `index.html`을 브라우저로 엽니다. `F12` → **Sources** 탭에서 `Ctrl + F`로 **`service_role`** 검색 → **0건**, **`secret`** 검색 → **0건**이면 회수 성공입니다.
2. `broken.html`도 똑같이 검사합니다. 이쪽은 `service_role`이 **1건 이상** 검색돼야 합니다. (사고 상태 확인)
3. 코드에서 `createClient(...)`에 넘기는 키가 **`PUBLISHABLE` / `ANON`** 이름의 변수인지 눈으로 확인합니다. `SERVICE_ROLE`이라는 단어가 코드 어디에도 없어야 합니다.
4. 제출물 완성: ① 비밀키가 **0건**인 프론트 코드(`index.html`), ② `broken.html`에서 비밀키가 잡히는 **before** `F12` Sources 검색 화면, ③ `index.html`에서 0건이 뜨는 **after** `F12` Sources 검색 화면을 각각 캡처하면 제출물(비밀키 0건 프론트 코드 + F12 Sources 검색 결과 캡처)이 완성됩니다.
