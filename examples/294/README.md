# 실습 294 — 무한루프·무한요청 멈추기: 탭을 멈추게 하는 useEffect/리스너 폭주

화면을 한 번 띄웠을 뿐인데 **F12 → Network(네트워크)** 탭에 요청이 1초에 수십 번 쌓이고,
**Console(콘솔)** 로그가 폭주하다가 결국 **브라우저 탭이 먹통**이 됩니다.

원인은 두 가지입니다. ① `useEffect`에 **의존성 배열을 빼서** "렌더될 때마다" effect가 다시 돌고,
그 안에서 상태를 바꿔 → 또 렌더 → 또 effect → 또 fetch... 하는 **끝없는 고리**가 생겼습니다.
② 자기 자신을 다시 부르는 함수에 **"언제 멈출지"(종료 조건)** 가 없어 영원히 자기를 부릅니다.

이 깨진 코드를 직접 고치며 "무한 반복의 신호"를 알아보고, **종료 조건·의존성 배열·가드**로 멈추는 법을 배웁니다.

> 이건 디버깅(고치기) 실습입니다. 폴더에 **깨진 버전(`broken.html`)** 과 **고친 버전(`index.html`)** 이 함께 들어 있습니다.
> 코드 속 주소(`https://example.invalid/...`)는 **실제 서버가 아닌 가짜 자리표시자**입니다. 진짜 키나 웹훅이 아닙니다.

## 목표

- `useEffect`의 **두 번째 인자(의존성 배열)** 가 무슨 역할인지 안다.
  - 배열을 **아예 빼면** → "렌더될 때마다 매번" 실행 (폭주의 원인)
  - **빈 배열 `[]`** → "처음 한 번만" 실행
  - **`[값]`** → "그 값이 바뀔 때만" 실행
- effect 안에서 `setState`를 하면 왜 무한 고리가 생기는지(렌더 → effect → setState → 렌더 …) 눈으로 확인한다.
- 자기 자신을 부르는 함수(재귀)에는 반드시 **종료 조건**이 필요함을 안다.
- 진행 중인 요청에 **정리(cleanup)/가드**를 넣어, 컴포넌트가 사라진 뒤 늦게 온 응답을 안전하게 무시한다.
- "고쳤다"를 추측이 아니라 **네트워크 탭의 요청 횟수(폭주 → 1번)** 로 증명한다.

## 따라하는 단계

1. **사고 현장부터 본다.** `broken.html`을 브라우저로 엽니다(파일 더블클릭). 화면의 큰 숫자가 **빠르게 치솟습니다**. 곧 탭이 느려집니다.
2. **폭주를 눈으로 확인한다.** `F12`(또는 우클릭 → 검사) → **Network(네트워크)** 탭을 엽니다. `ping?n=...` 요청이 **끝없이** 쌓이는 게 보입니다. → **이 화면이 "before(폭주)" 캡처입니다.** **Console(콘솔)** 탭에는 `fetch 발사!` 로그가 폭주합니다.
3. **탭이 멈추면 그냥 탭을 닫습니다.** 컴퓨터에 해가 가지는 않습니다. (페이지가 너무 무거우면 캡처만 빠르게 한 뒤 닫으세요.)
4. **범인 줄을 찾는다.** `broken.html`의 자바스크립트에서 `❌` 주석을 봅니다. 핵심은 이 `useEffect`입니다.
   - `useEffect(() => { ... });` ← **두 번째 인자(의존성 배열)가 통째로 빠졌습니다.** 그래서 매 렌더마다 실행됩니다.
   - effect 안에서 `setCount(count + 1)` 을 부릅니다 → 렌더가 또 일어나 → effect가 또 돌아 → 무한 고리.
5. **두 번째 범인도 본다.** 함수 `카운트다운(n)` 은 `카운트다운(n - 1)` 로 자기를 다시 부르기만 하고 **멈추는 조건이 없습니다.** (그래서 `broken.html`에선 일부러 호출하지 않고 모양만 둡니다.)
6. **고친 버전을 연다.** `index.html`을 엽니다. 숫자가 폭주하지 않고, 초기 데이터는 "완료! 요청은 단 1번만 나갔습니다"로 한 번만 바뀝니다. `✅` 주석에서 바뀐 핵심을 확인합니다.
   - `useEffect(() => { ... }, []);` ← **빈 배열 `[]` 추가** → "처음 한 번만" 실행.
   - `if (n <= 0) return;` ← 재귀에 **종료 조건** 추가 → 무한 재귀가 아님.
   - `let 살아있음 = true; return () => { 살아있음 = false; clearTimeout(...) };` ← **정리/가드** → 늦게 온 응답을 안전하게 무시.
   - 숫자를 올리고 싶을 땐 effect가 아니라 **버튼 클릭(사용자 이벤트)** 으로만 `setState` 합니다(`안전카운터`).

## 무엇을 어떻게 고쳤나 (before → after)

| 항목 | 고치기 전 (`broken.html`) | 고친 후 (`index.html`) | 왜 그랬나 |
| --- | --- | --- | --- |
| `useEffect` 의존성 | 배열 **없음** → 매 렌더 실행 | 빈 배열 **`[]`** → 처음 1번 | 배열이 effect의 "언제 실행할지"를 정한다 |
| effect 안 `setState` | `setCount`로 또 렌더 유발 | effect에선 안 함 / 버튼에서만 | 렌더→effect→setState 고리를 끊음 |
| 자기 호출(재귀) | 종료 조건 **없음** | `if (n <= 0) return;` | 멈추는 지점이 있어야 끝난다 |
| 진행 중 요청 | 정리 없음 | `cleanup` + `살아있음` 가드 | 사라진 뒤 늦게 온 응답을 무시 |
| 네트워크 요청 수 | **폭주(끝없음)** | **딱 1번** | "고쳤다"의 진짜 증거 |

핵심은 코드를 늘린 게 아니라, **"언제 멈추고 언제 다시 할지"를 명시**해 준 것뿐입니다.

## 🤖 바이브코딩 프롬프트

이 디버깅 실습(무한루프·무한요청 멈추기)을 AI에게 시켜 만들거나 고칠 때 그대로 복사해 쓸 수 있는 프롬프트입니다.

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  너는 React 입문용 데모를 만드는 강사야. 빌드 없이 브라우저에서 바로 도는
  단일 index.html 한 파일을 만들어줘. 조건:
  - React 18 + ReactDOM + Babel standalone 을 unpkg CDN으로 불러와 (설치/빌드 없음).
  - "초기 데이터 1번만 불러오기" 컴포넌트 한 개와, "버튼 누른 만큼만 +1 되는 카운터"
    컴포넌트 한 개를 만들어.
  - 초기 데이터는 진짜 서버 대신 setTimeout 0.4초로 가짜 fetch 를 흉내 내.
  - 화면은 흰 카드 안에 큰 숫자/상태 텍스트가 보이는 단정한 디자인으로.
  - 비전공자가 읽을 수 있게, 각 부분이 "무엇을 하고 왜 그렇게 했는지" 한국어 주석으로 설명해줘.
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  방금 만든 데모에 "무한루프/무한요청을 막는 안전장치"를 명시적으로 넣어줘:
  1) 초기 데이터 useEffect 의 두 번째 인자에 빈 의존성 배열 [] 을 넣어 "처음 한 번만"
     실행되게 하고, 왜 배열을 빼면 매 렌더마다 돌아 폭주하는지 주석으로 설명해줘.
  2) effect 안에서는 setState 로 또 렌더를 유발하지 말고, 숫자는 버튼 클릭 이벤트로만 올리게 해줘.
  3) 진행 중인 요청에 정리(cleanup) 함수와 살아있음 가드를 넣어, 컴포넌트가 사라진 뒤
     늦게 온 응답을 무시하게 해줘(setTimeout 은 clearTimeout 으로 취소).
  4) 자기 자신을 부르는 카운트다운(n) 함수에는 if (n <= 0) return; 종료 조건을 넣어줘.
  바꾼 줄마다 "무엇을/왜" 주석을 달아줘.
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  내 React 데모를 열면 F12 → Network 탭에 ping 요청이 1초에 수십 번 쌓이고
  콘솔 로그가 폭주하다가 탭이 멈춰. 아래 코드를 줄게.
  [여기에 useEffect 부분 코드 붙여넣기]
  무한 반복이 어디서 시작되는지(렌더→effect→setState→렌더 고리인지, 종료 조건 없는
  재귀인지) 단계별로 짚어주고, "무엇을 한 줄 고치면 멈추는지"를 가장 작은 수정으로 알려줘.
  의존성 배열을 어떻게 바꿔야 하는지도 함께 설명해줘.
  ```
> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 좋습니다. 특히 무한루프는 "가장 작은 수정으로 멈춰줘"라고 못 박아야 AI가 코드를 통째로 갈아엎지 않습니다.

## 검증법

- **네트워크 탭 횟수 비교.** `F12 → Network`에서 `broken.html`은 `ping` 요청이 **끝없이** 쌓이고, `index.html`은 새로고침해도 초기 요청이 **딱 1번**만 나가면 성공입니다. (before/after 두 화면을 캡처하면 제출물 "네트워크 탭 요청 폭주 before/after"가 됩니다.)
- **콘솔 로그 횟수 확인.** `index.html` 콘솔에 `fetch 완료`는 한 번, `카운트다운`은 `3 → 2 → 1 → 발사!` 가 **한 번씩만** 찍혀야 합니다. 같은 로그가 계속 쌓이면 아직 고리가 남아 있는 것입니다.
- **CPU/탭 반응 확인.** `index.html`은 열어 둬도 탭이 멈추거나 팬이 돌지 않습니다. (함정: `broken.html`도 처음엔 "잘 도는 앱"처럼 보입니다. 차이는 시간이 지날수록, 그리고 네트워크 탭에서만 분명해집니다.)
- **일부러 다시 고장 내보기(이해 점검).** `index.html`의 `, []` 에서 `[]` 을 지워 보세요 → 다시 폭주합니다. 확인했으면 되돌리세요. "배열 한 칸"이 멈춤/폭주를 가른다는 걸 체감할 수 있습니다.

> 핵심 한 줄: 잘못은 "기능"이 아니라 **"언제 멈출지 안 정한 것"** 에 있었다. 그래서 고치는 곳도 **종료 조건·의존성 배열·정리(cleanup)** 세 군데뿐이다.

!!! tip "실전 팁"
    - **무한 반복의 신호:** 화면 숫자가 멈추지 않고 오름 · 네트워크 탭 요청이 끝없이 쌓임 · 같은 콘솔 로그가 폭주 · `Maximum call stack size exceeded` 에러 · 탭이 느려지거나 멈춤. 하나라도 보이면 "종료 조건/의존성"을 먼저 의심하세요.
    - **effect 안에서 상태를 바꿀 땐 의존성 배열을 꼭 의식**하세요. 배열을 빼면 거의 항상 무한 고리가 됩니다. "처음 한 번"이면 `[]`, "특정 값이 바뀔 때만"이면 `[그값]` 입니다.
    - **이벤트 리스너·타이머는 켰으면 끄세요.** `addEventListener`/`setInterval`을 effect에서 켰다면, 정리 함수에서 `removeEventListener`/`clearInterval`로 반드시 꺼야 리스너가 겹겹이 쌓이지 않습니다.
    - **무한 재귀 대신 반복문**도 방법입니다. 깊게 자기를 부르면 호출 스택이 넘칩니다. 단순 반복이면 `for`/`while`이 더 안전할 때가 많습니다.
