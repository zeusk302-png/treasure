# 실습 138 — 로그인 안 하면 못 들어가는 보호된 페이지 만들기

지금까지는 로그인 폼을 만들고(132), 세션을 읽고(134·137), 로그아웃까지(136) 만들었습니다. 그런데 한 가지가 빠졌습니다. 누군가 주소창에 `mypage.html`을 직접 쳐서 **로그인도 안 하고 들어오면** 어떻게 막을까요?

이번 실습에서는 보호된 페이지 앞을 지키는 **문지기(라우트 가드, route guard)** 를 만듭니다. 건물 입구의 경비원처럼, 페이지가 열리자마자 "이 사람 로그인했나?"를 검사해서 **출입증(로그인 세션)이 없으면 곧바로 로그인 페이지로 돌려보냅니다.**

핵심은 `auth-guard.js` 한 파일입니다. `await db.auth.getUser()`로 로그인 여부를 확인하고, 로그인 안 했으면 `location.replace("login.html...")`로 쫓아냅니다.

이번 실습의 결과물은 **비로그인 시 차단되는 보호 페이지(`mypage.html`)** 와 **가드 스크립트(`auth-guard.js`)** 입니다.

## 목표
- 페이지가 열리자마자 `getUser()`로 **로그인 여부를 검사하는 문지기 패턴**을 이해한다.
- 로그인 안 한 사람을 `location.replace()`로 **로그인 페이지로 돌려보내(차단)는** 법을 익힌다.
- 검사가 끝나기 전엔 내용을 `hidden`으로 숨겨, 보호 내용이 **잠깐도 깜빡이지 않게** 하는 법을 배운다.
- `?redirect=...`로 **원래 가려던 페이지로 로그인 후 되돌려보내는** 흐름을 만든다.
- '화면을 숨기는 것(가드)'과 'DB 데이터를 지키는 것(RLS)'은 **서로 다른 일**임을 구분한다.

## 따라하는 단계
1. 앞 실습(131·132)에서 만든 **Supabase 프로젝트**와 **테스트 계정**을 그대로 쓴다. (계정이 없으면 대시보드 → Authentication → Users에서 "Auto Confirm User"를 켜고 하나 추가한다.)
2. 대시보드 → **Settings → API**에서 `Project URL`과 `anon`(publishable) 키를 복사한다.
3. `supabase.js` 위쪽의 `SUPABASE_URL`, `SUPABASE_ANON_KEY` 두 값을 내 값으로 바꾼다. (코드에 적힌 `https://여기에-...`, `sb_publishable_...`는 자리표시자다. 두 페이지가 이 파일 하나를 공유하므로 한 번만 바꾸면 된다.)
4. 이 폴더의 파일들을 같은 폴더에 둔 채로 **`mypage.html`을 브라우저로 연다.** 아직 로그인 안 했으므로 곧바로 **`login.html`로 튕겨 나간다.** (주소창이 `login.html?redirect=mypage.html`로 바뀐다.) → 차단 성공!
5. 로그인 폼에 테스트 계정으로 **로그인**한다 → 원래 가려던 **`mypage.html`로 자동 복귀**하고, '나만 볼 수 있는 내용'이 보인다. → 통과 성공!
6. 이제 로그인된 상태에서 `mypage.html`을 다시 열거나 **새로고침(F5)** 해도 통과되는지 확인한다. (세션이 유지되므로)
7. `mypage.html`의 **로그아웃** 버튼을 누른다 → 세션이 지워지고 로그인 페이지로 간다. 다시 `mypage.html`로 들어가려 하면 또 막힌다.

## 🤖 바이브코딩 프롬프트
이 실습을 AI에게 시켜 만들 때 그대로 복사해 쓸 수 있는 프롬프트입니다. 내 상황(파일명·키)에 맞게 한두 군데만 고쳐 쓰세요.

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  너는 초보 친화 웹 강사다. Supabase(@supabase/supabase-js v2, CDN)로
  '로그인 안 하면 못 들어가는 보호된 페이지' 실습을 만들어줘.
  파일을 이렇게 나눠줘:
  - supabase.js : createClient로 db 클라이언트 생성 (URL/anon 키는 자리표시자로 두고, anon은 공개돼도 되는 키라는 주석 달기)
  - auth-guard.js : 페이지가 열리자마자 await db.auth.getUser()로 로그인 검사.
    로그인 안 했으면 location.replace("login.html")로 돌려보내고, 했으면 숨긴 내용을 보여줘.
  - mypage.html : 보호된 내용은 처음엔 hidden, 가드 통과 후에만 표시
  - login.html / login.js : 이메일·비밀번호 로그인 폼
  제약: 비밀값은 코드에 박지 말고 자리표시자, 사용자 입력 출력은 textContent 사용.
  비전공자가 읽을 수 있게 각 줄에 '무엇을/왜' 한국어 주석을 달아줘.
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  방금 만든 가드에 이 두 가지를 추가해줘.
  1) ?redirect=... 흐름: 가드가 막을 때 원래 가려던 주소를 login.html?redirect=... 로 붙여 보내고,
     로그인 성공하면 그 주소로 자동 복귀하게 해줘.
  2) 깜빡임 방지: 가드 검사가 끝나기 전엔 '확인 중' 화면을 보여주고 보호 내용은 hidden으로 숨겨,
     비로그인자가 보호 내용을 단 한 순간도 못 보게 해줘.
  그리고 README에 "이 가드는 화면을 가리는 '편의'일 뿐, 진짜 데이터 보호는 DB의 RLS가 한다"는
  경고를 넣고 그 이유도 설명해줘.
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  로그인했는데도 mypage.html이 계속 login.html로 튕겨나가. 아래를 단계별로 점검해줘.
  - 콘솔에서 await db.auth.getUser() 결과의 data.user가 null인지 아닌지
  - supabase.js의 SUPABASE_URL / SUPABASE_ANON_KEY가 자리표시자 그대로 아닌지
  - 스크립트 로드 순서(supabase.js → auth-guard.js → app.js)가 맞는지
  - 파일을 file:// 로 직접 열어서 생기는 문제인지(로컬 서버로 열어야 하는지)
  원인 후보를 가능성 높은 순서로 정리하고, 각 확인 방법을 한 줄씩 알려줘.
  ```
> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 훨씬 좋습니다.

## 검증법
- **비로그인 상태**(또는 새 시크릿 창)에서 `mypage.html`을 열면, 보호 내용이 **단 한 순간도 보이지 않고** 곧바로 `login.html`로 이동하는가? (가드가 작동한다는 증거)
- 튕겨 나간 주소가 `login.html?redirect=mypage.html`처럼 **복귀 주소를 달고** 있는가?
- 로그인에 성공하면 **원래 가려던 `mypage.html`로 자동 복귀**하는가?
- 로그인된 상태에서 `mypage.html`을 **새로고침(F5)** 해도 계속 통과되는가? (세션 유지)
- 로그아웃 후 `mypage.html`로 다시 들어가려 하면 **또 막혀서** `login.html`로 가는가?
- 개발자도구 → **Console**에서 `await db.auth.getUser()`를 실행하면, 비로그인일 때 `data.user`가 `null`로 나오는가? (가드가 이 값을 보고 막는다)

## 핵심 한 줄
문지기는 "로그인 안 했으면 → 쫓아낸다", 이 한 토막이 전부입니다.
```js
const { data } = await db.auth.getUser();
if (!data.user) {
  location.replace("login.html"); // 로그인 안 함 → 차단
}
```

## ⚠️ 가장 중요한 보안 메모 — 이 가드는 '편의'이지 '진짜 보안'이 아닙니다
이 점을 꼭 이해하고 넘어가세요. 비전공자가 가장 많이 오해하는 부분입니다.

- 이 가드는 **브라우저(JS)에서** 화면을 가립니다. 즉 **눈에 안 보이게** 할 뿐입니다. 작정한 사람은 개발자도구로 `hidden`을 풀거나, 가드 파일을 무시하고 직접 API를 호출해 데이터를 빼낼 수 있습니다. 그래서 가드는 **"평범한 방문자를 깔끔하게 안내하는 편의 기능"** 으로만 봐야 합니다.
- **진짜로 데이터를 지키는 건 DB의 RLS(행 수준 보안)** 입니다. RLS는 **Supabase 서버 쪽에서** 동작하므로 브라우저로 우회할 수 없습니다. 예를 들어 메모 테이블에 `auth.uid() = user_id`(= 지금 로그인한 사람이 그 행의 주인일 때만 읽기 허용) 같은 정책을 걸어두면, 로그인 안 한 사람이 직접 API를 호출해도 **빈 결과만** 돌아옵니다.
- 정리: **가드(JS) = 친절한 안내판, RLS(DB) = 실제 잠금장치.** 둘 다 있어야 좋지만, 둘 중 하나만 골라야 한다면 **반드시 RLS**입니다. 가드만 믿으면 안 됩니다.

## 보안 메모 — anon vs service_role
- 여기 넣는 건 **anon(publishable) 키** 하나뿐입니다. anon 키는 "공개돼도 되는 **출입증**"이라 브라우저·GitHub에 있어도 괜찮습니다. (코드의 `sb_publishable_...`는 자리표시자이니 내 값으로 바꿔 쓰세요.)
- `service_role`(secret) 키는 모든 **RLS를 통째로 우회**하는 마스터키라, 브라우저나 깃허브에 두면 절대 안 됩니다. 오직 서버(n8n·엣지 함수)에서 **환경변수**로만 사용하세요. (브라우저 코드에 들어가는 비밀값은 언제나 자리표시자로 둡니다.)

## getUser() vs getSession() — 가드엔 어느 걸 쓸까?
- `getSession()`은 **브라우저에 저장된 세션 그대로**를 빠르게 돌려줍니다. (네트워크 요청 없음 → 빠르지만, 토큰이 진짜 유효한지까지는 확인 안 함)
- `getUser()`는 그 토큰을 **Supabase 서버에 한 번 물어봐서** "이거 진짜 유효한 사용자 맞아?"를 확인합니다. 만료되거나 위조된 세션을 더 확실히 걸러내므로, 출입을 판단하는 **가드에는 `getUser()`** 가 더 안전합니다. (속도가 중요한 곳에선 먼저 `getSession()`으로 빠르게 거른 뒤 민감한 동작 직전에 `getUser()`로 재확인하는 식으로 섞기도 합니다.)
