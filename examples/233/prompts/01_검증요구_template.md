# 템플릿 1 — 검증 요구 (Verify, don't trust)

> **언제 쓰나요?**
> AI가 코드·설정·계획을 내놓으며 "완벽합니다 / 잘 됩니다"라고 단정할 때.
> AI는 **정답기계가 아니라 '그럴듯함' 확률기계**라서, 안 돌려보고도 "된다"고 자신 있게 말합니다.
> 이 템플릿은 그 단정을 **"증거를 가져와"** 로 되받아칩니다.

---

## 빈칸 채우는 법

아래 `[[...]]` 안만 내 상황에 맞게 바꿔서 통째로 복사해 붙여넣으세요.

- `[[무엇]]` — 검증받고 싶은 대상 (예: 방금 준 회원가입 폼 코드 / Supabase RLS 정책 / Vercel 배포 설정)
- `[[어디서 돌아가나]]` — 실행 환경 (예: 브라우저에서 index.html / Supabase SQL 편집기 / n8n 워크플로우)
- `[[성공의 기준]]` — "이렇게 되면 성공"이라고 내가 정한 것 (예: 빈칸 제출 시 빨간 메시지가 뜬다 / 남의 글은 못 지운다)

---

## 복붙용 프롬프트

```
방금 준 [[무엇]] 이 정말 의도대로 동작하는지 검증하고 싶어.

"완벽하다 / 잘 된다"는 말은 빼고, 증거로 설득해줘. 구체적으로:

1. 이건 [[어디서 돌아가나]] 에서 실행할 거야. 그 환경 기준으로 점검해줘.
2. 내가 생각하는 성공 기준은 이거야: [[성공의 기준]]
   - 이 기준을 만족하는지 "예/아니오"로 먼저 답하고, 그 근거를 줄/설정 단위로 짚어줘.
3. 이게 깨질 수 있는 경우(엣지 케이스)를 3가지 만들어, 각각 어떻게 될지 예측해줘.
   (예: 입력이 비었을 때 / 아주 긴 입력 / 네트워크 실패)
4. 내가 직접 손으로 확인할 "검증 체크리스트"를 5줄 이내로 만들어줘.
   각 줄은 "이렇게 하면 → 이렇게 보여야 정상" 형식으로.
5. 확실하지 않은 부분은 "확실하지 않음"이라고 솔직히 표시해.
   없는 함수·없는 설정·안 돌려본 결과를 "된다"고 단정하지 마.
```

---

## 왜 이렇게 시키나요? (비전공자용)

- AI에게 "검증해줘"만 하면 또 "완벽합니다"라고 합니다. **성공 기준을 내가 못 박아** 줘야 빠져나갈 구멍이 줄어듭니다.
- **"엣지 케이스 3개"** 를 강제하면, 평소엔 잘 되지만 빈칸·긴 입력 같은 데서 깨지는 부분이 드러납니다.
- 마지막엔 **사람이 직접 확인할 체크리스트**를 받습니다. 진짜 검증은 결국 내가 손으로 돌려보는 것이고, AI는 그 길잡이만 줍니다.
