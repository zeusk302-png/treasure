# 템플릿 2 — 비판 리뷰 (칭찬 빼고, 깐깐하게)

> **언제 쓰나요?**
> 내가 만든(또는 AI가 만든) 코드·글·계획을 **냉정하게 두들겨 보고 싶을 때.**
> AI는 기본적으로 사용자에게 친절해서 "좋네요!"부터 합니다.
> 이 템플릿은 칭찬을 막고 **"고쳐야 할 것부터 우선순위로"** 끌어냅니다.

---

## 빈칸 채우는 법

- `[[리뷰 대상]]` — 무엇을 리뷰받나 (예: 아래 붙인 방명록 저장 코드 / 이 랜딩페이지 카피 / 이 폼 검증 로직)
- `[[역할]]` — AI에게 씌울 가면 (예: 깐깐한 시니어 개발자 / 보안 담당자 / 까칠한 카피 에디터)
- `[[우리 스택/맥락]]` — 내 프로젝트 환경 (예: 순수 HTML/CSS/JS + Supabase + Vercel + n8n)

리뷰 대상 코드/글은 이 프롬프트 **아래에 그대로 붙여** 넣으세요.

---

## 복붙용 프롬프트

```
너는 [[역할]] 야. 칭찬·덕담은 빼고, 아래 [[리뷰 대상]] 을 깐깐하게 리뷰해.

[맥락]
- 우리 스택/환경: [[우리 스택/맥락]]

[리뷰 규칙]
- "좋다"는 말 금지. "고쳐야 할 것"부터 심각도 높은 순으로 짚어.
- 각 지적은 "어디(파일·줄 또는 문장)" 를 특정해.
- 각 지적을 한 가지로 분류해: [버그] / [보안] / [개선 제안]
- 각 지적마다 (무엇이 문제 / 그냥 두면 무슨 일이 나나 / 어떻게 고치나)를 1~3줄로.
- 보안은 특히 이걸 봐:
  - 비밀 키(service_role 등)가 프론트엔드 코드에 노출됐는가
    (프론트엔드엔 공개용 anon 키만 써야 하고, DB 테이블엔 RLS가 켜져 있어야 함)
  - 사용자 입력을 그대로 innerHTML에 넣어 XSS 위험이 있는가
- 추측 금지: 없는 줄·없는 함수를 지어내지 마. 모르면 "확실하지 않음"이라고 말해.

[출력 형식]
1. 한 줄 총평 (지금 상태를 한 문장으로)
2. 지적 목록 (심각도 높은 순): 어디 / [분류] / 무엇이·왜·어떻게
3. 한 줄 결론: "이대로 써도 되나?" → 예 / 아니오 / 조건부 예
```

---

## 왜 이렇게 시키나요? (비전공자용)

- **역할(가면)을 씌우면** 답의 결이 바뀝니다. "깐깐한 시니어"라고 하면 더 매섭게 봅니다.
- **분류 + 무엇이·왜·어떻게** 형식을 못 박아야 "이 부분이 좀..." 같은 두루뭉술한 말 대신 **고칠 수 있는 지적**이 나옵니다.
- **보안 항목을 명시**하는 이유: 비전공자가 가장 자주 놓치는 게 보안입니다. 특히 비밀 키 노출과 RLS 누락은 "에러는 안 나지만" 위험합니다.
- 마지막 **"예/아니오/조건부 예"** 한 줄로, 리뷰를 행동(고친다/그냥 쓴다)으로 연결합니다.
