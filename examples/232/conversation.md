# GitHub MCP로 PR을 AI에게 코드리뷰 시킨 대화 캡처 (예시)

> 실제 AI(Claude 등)에 GitHub MCP를 붙이고 [`prompt.md`](prompt.md)의 지시문을 넣었을 때
> 오가는 대화가 어떤 모습인지 보여주는 **예시 기록**입니다.
> 여러분이 직접 했을 때도 이런 흐름(PR 읽기 → 파일:줄 지적 → 인라인 코멘트 → 내 결정 → 반영 커밋)이 나오면 성공입니다.
>
> ⚠️ 아래 내용은 **형식을 보여주기 위한 예시**입니다. 여기 적힌 지적은
> 가상의 PR(방명록 페이지에 Supabase 저장을 붙이는 `#7` PR)에 대한 것입니다.
> **여러분의 리뷰는 여러분의 진짜 PR**에 대한 것이어야 합니다.

---

### 🧑 나 (디렉터) — 0단계: MCP 연결 확인

> GitHub MCP가 연결됐는지 확인하고 싶어. 저장소 "REPLACE_WITH_OWNER/REPLACE_WITH_REPO"에
> 열려 있는 PR 목록을 번호·제목만 보여줘.

### 🤖 AI — MCP로 실제 PR 목록을 읽어옴

> GitHub MCP로 저장소를 조회했습니다. 열린 PR은 다음과 같습니다.
> - **#7** 방명록에 Supabase 저장 기능 추가
> - #5 푸터 디자인 수정
>
> 어느 PR을 리뷰할까요?

→ 진짜 PR 목록을 가져왔으니 **연결 성공**입니다. (가짜 목록을 지어냈다면 MCP 미연결 신호)

---

### 🧑 나 — 1단계: PR #7 코드리뷰 지시 (prompt.md 1단계 붙여넣기)

> 너는 깐깐한 시니어 코드리뷰어야. GitHub MCP로 REPLACE_WITH_OWNER/REPLACE_WITH_REPO 의 PR #7을
> 직접 읽고, 바뀐 파일·줄 중심으로 리뷰해. 각 지적에 파일:줄 + [버그]/[보안]/[개선] 분류 +
> 무엇이·왜·어떻게를 붙여. 우리 스택은 HTML/CSS/JS + Supabase + Vercel + n8n이야.
> (…전체 프롬프트는 prompt.md 참고)

### 🤖 AI — PR을 읽고 파일·줄을 짚어 지적함

> PR #7의 변경분(diff)을 읽었습니다. 칭찬은 빼고 심각도 순으로 갑니다.
>
> **변경 요약 (3줄)**
> - 방명록 입력 폼을 추가하고, 입력한 글을 Supabase `guestbook` 테이블에 저장합니다.
> - 저장한 글을 목록으로 화면에 표시합니다.
> - 변경 파일: `index.html`, `app.js`.
>
> **지적 목록 (심각도 높은 순)**
>
> **1. `app.js:4` — [보안] service_role(비밀) 키가 프론트엔드에 노출됨 (가장 치명적)**
> - (무엇이) `const SUPABASE_KEY = "REPLACE_WITH_SERVICE_ROLE_KEY"` 로, 변수명·주석상 **service_role(비밀) 키**를 브라우저에서 실행되는 `app.js`에 직접 넣었습니다.
> - (왜) service_role 키는 **RLS를 무시하고 테이블 전체를 읽고 지울 수 있는** 마스터 키입니다. 프론트에 넣으면 누구나 브라우저 개발자도구로 꺼내 **모든 방명록을 삭제·도용**할 수 있습니다.
> - (어떻게) 프론트엔는 **anon(공개) 키만** 두세요. `const SUPABASE_KEY = "REPLACE_WITH_ANON_PUBLIC_KEY"`. 비밀 키가 이미 커밋됐다면 **키를 폐기·재발급(rotation)** 하세요.
>
> **2. `index.html` (테이블 생성 SQL 없음) — [보안] RLS가 켜져 있는지 확인 불가**
> - (무엇이) 이 PR엔 `guestbook` 테이블에 **RLS(행 단위 출입 통제)가 켜졌다는 근거가 없습니다.**
> - (왜) RLS가 꺼져 있으면 anon 키만 써도 **누구나 전체 행을 읽거나 지울 수** 있습니다.
> - (어떻게) Supabase에서 `alter table guestbook enable row level security;` 와 "익명 INSERT/SELECT 허용" 정책이 있는지 확인하세요. 없으면 별도 PR로 추가하세요.
>
> **3. `app.js:21` — [보안] 사용자 입력을 innerHTML로 출력해 XSS 위험**
> - (무엇이) `li.innerHTML = row.message` 로, 사용자가 적은 글을 **HTML로 해석**해 화면에 넣습니다.
> - (왜) 누군가 `<img src=x onerror=alert(1)>` 같은 걸 남기면 **다른 방문자 브라우저에서 코드가 실행**됩니다(XSS).
> - (어떻게) `li.textContent = row.message` 로 바꾸세요. 글자는 그대로 보이고, 코드로 실행되진 않습니다.
>
> **4. `app.js:13` — [버그] 저장 성공 여부(error)를 확인하지 않음**
> - (무엇이) `await supabase.from('guestbook').insert(...)` 의 반환값 중 `error`를 확인하지 않습니다.
> - (왜) 저장이 실패해도 사용자에겐 "등록됐다"고 보여, 글이 사라진 줄 모릅니다.
> - (어떻게) `const { error } = await ...` 로 받아 `if (error)` 면 사용자에게 실패를 알리세요.
>
> **5. `index.html:12` — [개선] 입력칸에 `required`가 없어 빈 글도 저장됨**
> - (어떻게) `<input ... required>` 로 빈 제출을 브라우저가 먼저 막게 하세요.
>
> **한 줄 결론: 아니오.** 1번(비밀 키 노출)과 3번(XSS)은 합치기(merge) 전에 반드시 고쳐야 합니다.

### 🧑 나 — 2단계: 보안·버그만 PR에 인라인 코멘트로 달라고 지시

> 방금 [보안]·[버그]로 분류한 것만 GitHub MCP로 PR #7의 해당 파일·줄에 인라인 코멘트로 달아줘.
> [개선]은 코멘트 말고 목록으로만 둬. 단, 달기 전에 무엇을 달지 먼저 보여주고 내 "달아"를 받은 뒤 실행해.

### 🤖 AI — 달 코멘트 목록을 먼저 보여주고 승인을 요청함

> 아래 4개를 인라인 코멘트로 달 예정입니다. (개선 1건은 제외)
> - `app.js:4` [보안] service_role 키 노출 → anon 키로 교체 + 키 재발급
> - 정책 [보안] RLS 활성화 여부 확인 요청
> - `app.js:21` [보안] innerHTML → textContent (XSS)
> - `app.js:13` [버그] insert error 미확인
>
> 이대로 PR에 달까요? "달아"라고 하시면 실행하고, 공식 리뷰는 "변경 요청(request changes)"으로 제출하겠습니다.

### 🧑 나 — 승인

> 응, 달아. 변경 요청으로 제출해줘.

### 🤖 AI — 실제로 인라인 코멘트를 달고 결과를 보고함

> GitHub MCP로 PR #7에 인라인 코멘트 4건을 달고, 리뷰를 "변경 요청"으로 제출했습니다.
> PR 페이지의 "Files changed" 탭에서 각 줄 아래에 코멘트가 보일 겁니다.

---

### 🧑 나 — 3단계: 내 결정 정리 + 과잉 비판 자진 신고 요청

> 단 코멘트를 표로 정리해줘. 그리고 이 PR 규모에 과한 지적이 있으면 솔직히 말해줘.

### 🤖 AI — 표 정리 + 자진 신고

> | 파일:줄 | 분류 | 나의 제안 | 내 결정(직접 채우세요) |
> |---|---|---|---|
> | app.js:4 | 보안 | service_role → anon 키, 키 재발급 | (예: 고친다) |
> | 정책 | 보안 | RLS 활성화 확인 | (예: 고친다) |
> | app.js:21 | 보안 | innerHTML → textContent | (예: 고친다) |
> | app.js:13 | 버그 | insert error 확인 | (예: 고친다) |
> | index.html:12 | 개선 | input에 required | (예: 다음에) |
>
> 솔직히 말하면, **5번(required)** 은 첫 버전엔 과한 지적일 수 있습니다. 다만 한 줄이면 끝나니 같이 해도 부담은 없습니다.
> 1·2·3번은 과장이 아니라 **합치기 전에 꼭 막아야 하는 실제 위험**입니다.

## 만약 AI가 줄 번호를 헷갈리거나 지어내면? (확인 한 마디)

가끔 AI는 "app.js:30에 문제가 있다"고 했는데 그 줄이 실제와 다를 수 있습니다.

> 🧑 "app.js:30이라고 했는데, 그 줄의 실제 코드를 MCP로 다시 읽어서 그대로 인용해줘.
> 줄 번호가 안 맞으면 정정해줘. 추측하지 말고 파일을 다시 봐."

이렇게 **"실제 줄을 다시 인용하라"** 고 시키면 환각(지어낸 줄 번호)을 걸러낼 수 있습니다.

## 이 캡처에서 확인할 점

- AI가 MCP로 **진짜 PR을 읽고**, 가짜 목록을 지어내지 않았다. ✅
- 지적마다 **파일:줄 + [버그]/[보안]/[개선] 분류 + 무엇이·왜·어떻게**가 붙었다. ✅
- **service_role 키 노출 / RLS 누락 / XSS**(보안 핵심)를 정확히 짚었다. ✅
- PR에 **인라인 코멘트를 다는 외부 동작 전에** 사람의 "달아" 승인을 받았다. ✅
- 마지막에 **"예 / 아니오 / 조건부 예"** 결론과 **과잉 비판 자진 신고**가 나왔다. ✅
