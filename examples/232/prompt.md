# 232. "GitHub MCP로 내 PR을 AI에게 코드리뷰 시키기" 지시 프롬프트

> 이 파일은 **AI(Claude 등)에게 그대로 붙여넣는 지시문 모음**입니다.
> 목표는 하나 — 내가 올린 **PR(Pull Request, 변경 제안 묶음)** 을
> AI가 **GitHub MCP를 통해 직접 읽고**, 버그·보안 위험을
> **줄 번호까지 짚어(인라인) 코멘트**로 남기게 만드는 것입니다.
>
> MCP(Model Context Protocol)는 **AI를 바깥 세계(여기선 내 GitHub 저장소)와 잇는 통로(신경계)** 입니다.
> MCP가 없으면 나는 매번 코드를 복사해서 채팅창에 붙여넣어야 합니다.
> GitHub MCP를 연결하면 AI가 **내 PR의 변경된 파일·줄을 스스로 읽고** 리뷰할 수 있습니다.
>
> 이 실습에는 새로 짤 "앱 코드"가 없습니다. **AI에게 정확한 리뷰를 끌어내는 지시 설계**가 곧 실습입니다.

---

## 0단계 — GitHub MCP 연결 준비 (한 번만)

> ⚠️ **보안 주의:** GitHub 연결 토큰(Personal Access Token)은 **비밀값**입니다.
> 이 파일이나 채팅, 깃허브 어디에도 **진짜 토큰을 적지 마세요.**
> 예시는 항상 자리표시자(예: `REPLACE_WITH_YOUR_GITHUB_TOKEN`)로만 둡니다.

1. AI 클라이언트(예: Claude Desktop / Claude Code)의 **MCP 설정**에 GitHub MCP 서버를 추가합니다.
   - 서버 이름(예시): `github`
   - 필요한 비밀값: GitHub Personal Access Token → **환경변수**로만 넣습니다.
     - 예: `GITHUB_TOKEN = REPLACE_WITH_YOUR_GITHUB_TOKEN`
   - 토큰 권한은 **최소만** 줍니다. (해당 저장소의 PR 읽기·코멘트 쓰기 정도. 처음엔 읽기 위주로 시작해도 됩니다.)
2. 설정을 저장하고 AI 클라이언트를 다시 시작합니다.
3. 아래 **연결 확인 프롬프트**로 MCP가 실제로 붙었는지 먼저 확인합니다.

```
GitHub MCP가 연결됐는지 확인하고 싶어.
지금 내 저장소 "REPLACE_WITH_OWNER/REPLACE_WITH_REPO"에 열려 있는
PR(Pull Request) 목록을 번호·제목만 5개 이내로 보여줘.
아직 연결이 안 됐거나 권한이 부족하면, 추측해서 지어내지 말고
"무엇이 안 됐는지"만 정확히 알려줘.
```

> AI가 진짜 PR 목록을 가져오면 연결 성공입니다.
> 만약 그럴듯한 가짜 PR 목록을 지어내면(환각) → MCP가 안 붙은 것이니 0단계를 다시 봅니다.

## 1단계 — AI에게 PR 코드리뷰를 시키는 지시 프롬프트 (그대로 복사해서 붙여넣기)

> 아래의 `REPLACE_WITH_OWNER/REPLACE_WITH_REPO`와 `REPLACE_WITH_PR_NUMBER` 자리에
> **내 저장소 주소**와 **리뷰받을 PR 번호**를 넣으세요.

```
너는 우리 팀의 깐깐한 시니어 코드리뷰어야. GitHub MCP를 써서 아래 PR을 직접 읽고 리뷰해.

[대상]
- 저장소: REPLACE_WITH_OWNER/REPLACE_WITH_REPO
- PR 번호: REPLACE_WITH_PR_NUMBER

[먼저 할 일]
1. 이 PR에서 "바뀐 파일"과 "바뀐 줄(diff)"만 읽어. PR 전체가 아니라 변경분 중심으로 봐.
2. 변경 요약을 3줄 이내로 먼저 말해줘. (무엇을 바꾸려는 PR인지)

[리뷰 규칙]
- 칭찬·덕담은 빼고, "고쳐야 할 것"부터 우선순위 순으로 짚어.
- 각 지적은 반드시 "파일 이름 + 줄 번호"를 붙여 어디인지 특정해.
- 각 지적을 아래 한 가지로 분류해: [버그] / [보안] / [개선 제안]
- 각 지적마다: (무엇이) 무엇이 문제인지 / (왜) 그냥 두면 무슨 일이 나는지 / (어떻게) 1~3줄짜리 수정안(가능하면 고친 코드).
- 우리 스택은 순수 HTML/CSS/JS + Supabase + Vercel + n8n이야.
  특히 보안은 이걸 꼭 봐:
  - service_role(비밀 키)이 프론트엔드 코드/HTML/JS에 노출됐는가
  - 프론트엔 anon(공개 키)만 써야 하고, Supabase 테이블엔 RLS가 켜져 있어야 한다
  - 사용자 입력을 그대로 innerHTML에 넣어 XSS 위험이 있는가
- 확실하지 않으면 "확실하지 않다"고 말해. 없는 줄 번호·없는 함수를 지어내지 마.

[출력 형식]
1. 변경 요약 (3줄)
2. 지적 목록 (심각도 높은 순). 각 항목: 파일:줄 / [분류] / 무엇이·왜·어떻게
3. 한 줄 결론: "이 PR, 지금 합쳐도(merge) 되는가?"를 "예 / 아니오 / 조건부 예"로.
```

## 2단계 — 리뷰를 "인라인 코멘트"로 PR에 직접 남기게 하는 한 마디

채팅으로만 받은 리뷰는 흘러갑니다. 진짜 결과물은 **PR 안에 박힌 코멘트**입니다.
1단계 리뷰가 마음에 들면 아래로 "GitHub에 실제로 코멘트를 달라"고 시킵니다.

```
방금 지적한 것 중 "[버그]"와 "[보안]"으로 분류한 것만,
GitHub MCP로 그 PR의 해당 파일·줄에 "인라인 리뷰 코멘트"로 직접 달아줘.
각 코멘트는 "무엇이 문제 / 왜 / 제안 수정"을 짧게 담아.
[개선 제안]은 코멘트로 달지 말고 목록으로만 남겨둬. (내가 나중에 고를게)

단, 코멘트를 "승인(approve)"이나 "변경 요청(request changes)" 같은
공식 리뷰 상태로 제출하기 전에, 무엇을 달지 먼저 나에게 목록으로 보여주고
내 "응, 달아" 한 마디를 받은 뒤에 실행해.
```

> 왜 한 번 멈추나요? **코멘트를 PR에 다는 것은 되돌리기 번거로운 "바깥 동작"** 입니다.
> AI가 외부 도구(여기선 GitHub)를 실제로 실행할 때는, 실행 전에 **사람 승인 한 단계**를 끼우는 게 안전합니다.

---

## 3단계 — 받은 지적을 "반영 / 반박"으로 결정하고 고친 뒤 커밋하기

AI 리뷰도 **항상 옳은 건 아닙니다.** 무엇을 고치고 무엇을 미룰지는 **사람(디렉터)이 결정**합니다.

```
네가 단 코멘트들을 표로 정리해줘.

| 파일:줄 | 분류 | 너의 제안 | 내 결정(고친다 / 다음에 / 동의 안 함) |

그리고 한 가지만 더: 네가 단 지적 중 "사실 이 PR 규모에선 과한 지적"이
있으면 솔직히 자진 신고해줘. (과한 지적인지 진짜 문제인지는 내가 가린다.)
```

그다음, **내가 "고친다"로 정한 것만** 실제 코드에서 고치고, **반영 커밋**을 만듭니다.
커밋 메시지 예시(직접 작성):

```
fix: 코드리뷰 반영 - service_role 키 프론트에서 제거, anon 키로 교체

- index.html: 노출돼 있던 비밀 키 삭제, 공개(anon) 키로 변경
- 사용자 입력은 textContent로 출력해 XSS 위험 제거
(리뷰 코멘트: PR #REPLACE_WITH_PR_NUMBER 참고)
```

> 고친 커밋을 PR에 push 하면, **"AI가 남긴 리뷰 코멘트 + 그걸 반영한 커밋"** 이 한 PR 안에 함께 남습니다.
> 이게 바로 이 실습의 결과물입니다. (정리본은 같은 폴더의 [`REVIEW.md`](REVIEW.md) 참고)

## 주의 (사람이 직접 검토할 것)

- AI가 짚은 **줄 번호가 진짜 맞는지** 한 번은 사람이 PR에서 직접 확인하세요. (AI는 줄 번호를 헷갈릴 수 있습니다.)
- **보안 지적**(특히 service_role 키 노출, RLS 누락)은 절대 가볍게 넘기지 마세요. 다른 건 미뤄도 보안은 먼저 막습니다.
- AI가 "버그 없음, 완벽함"이라고 단정해도 그대로 믿지 마세요. **"에러 없음"이 "원하는 대로 동작"을 뜻하진 않습니다.**
- 진짜 토큰·키 값을 채팅이나 파일에 적지 마세요. 항상 `REPLACE_WITH_...` 같은 **자리표시자**로 둡니다.

---

## 왜 이렇게 시키나요? (비전공자용 한 줄 정리)

- **MCP**는 AI를 내 GitHub와 잇는 통로입니다. 연결하면 코드를 복붙하지 않아도 AI가 **내 PR을 직접 읽습니다.**
- AI에게 그냥 "리뷰해줘"라고 하면 두루뭉술합니다. **"파일:줄 + 버그/보안/개선 분류 + 무엇이·왜·어떻게"** 형식을 못 박아야 쓸모 있는 리뷰가 나옵니다.
- AI가 PR에 **직접 코멘트를 다는 외부 동작** 전에는, 사람이 **"달아"라고 승인**하는 한 단계를 끼웁니다.
- AI 리뷰는 **초안**입니다. 무엇을 반영할지 결정하고 **고친 커밋**을 남기는 것까지가 디렉터의 몫입니다.
