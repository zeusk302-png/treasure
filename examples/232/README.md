# 232. GitHub MCP로 AI에게 PR 자동 코드리뷰 시키기

## 목표

내가 올린 **PR(Pull Request, "이 부분을 이렇게 바꾸자"고 묶어 올리는 변경 제안)** 을
**GitHub MCP**를 통해 AI(Claude 등)가 **직접 읽고**, 버그·보안 위험을
**줄 번호까지 짚어(인라인) 코멘트**로 남기게 만드는 것이 목표입니다.

- **MCP(Model Context Protocol)** 는 **AI를 바깥 세계와 잇는 통로(신경계)** 입니다.
  여기서는 AI를 **내 GitHub 저장소**에 연결합니다.
- MCP가 없으면 매번 코드를 복사해 채팅창에 붙여넣어야 합니다.
  GitHub MCP를 붙이면 AI가 **내 PR의 바뀐 파일·줄을 스스로 읽고** 리뷰합니다.

이 실습에는 새로 짤 "앱 코드"가 없습니다. **AI에게 정확한 리뷰를 끌어내는 지시 설계**가 곧 실습입니다.
결과물은 **AI가 PR에 남긴 리뷰 코멘트 + 그걸 내가 반영한 커밋**이고, 그 정리본이 [`REVIEW.md`](REVIEW.md)입니다.

이 폴더의 파일은 넷입니다.

- [`prompt.md`](prompt.md) — GitHub MCP 연결 → PR 리뷰 → 인라인 코멘트 → 반영까지, 그대로 붙여넣는 지시 프롬프트
- [`conversation.md`](conversation.md) — AI가 MCP로 PR을 읽고 파일:줄을 짚어 코멘트를 남긴 대화 캡처(예시)
- [`REVIEW.md`](REVIEW.md) — **이 실습의 결과물.** PR 리뷰 코멘트 + 내 결정 + 반영 커밋 정리
- `README.md` — 지금 읽는 이 안내문

## 따라하는 단계

1. **리뷰받을 PR을 준비합니다.** 아무 저장소에서 작은 변경(예: 방명록에 Supabase 저장 추가)을 만들어 **PR을 하나 엽니다.** (PR 만드는 법이 낯설면 아래 "관련 가이드"의 버전관리 심화 글을 먼저 보세요.)
2. **GitHub MCP를 연결합니다.** [`prompt.md`](prompt.md)의 **0단계**대로, AI 클라이언트의 MCP 설정에 GitHub MCP 서버를 추가합니다.
   - 토큰(Personal Access Token)은 **비밀값**이므로 **환경변수로만** 넣고, 어디에도 진짜 값을 적지 않습니다. 예시는 `REPLACE_WITH_YOUR_GITHUB_TOKEN`처럼 자리표시자로 둡니다.
   - 권한은 **최소만** 줍니다(처음엔 읽기 위주로 시작해도 됩니다).
3. **연결을 확인합니다.** 0단계의 "연결 확인 프롬프트"로 **내 저장소의 진짜 PR 목록**이 나오는지 봅니다. 가짜 목록을 지어내면 아직 안 붙은 것입니다.
4. **리뷰를 시킵니다.** [`prompt.md`](prompt.md)의 **1단계 프롬프트**를 복사해 `REPLACE_WITH_OWNER/REPLACE_WITH_REPO`·`REPLACE_WITH_PR_NUMBER`를 내 값으로 바꿔 붙여넣습니다. 핵심 제약은 **"파일:줄 + [버그]/[보안]/[개선] 분류 + 무엇이·왜·어떻게"** 입니다.
5. **인라인 코멘트로 달게 합니다.** 리뷰가 쓸 만하면 **2단계 한 마디**로 "[보안]·[버그]만 PR의 해당 줄에 인라인 코멘트로 달아줘"라고 시킵니다. 단 AI가 **무엇을 달지 먼저 보여주고**, 내 "달아" 한 마디를 받은 뒤 실행하게 합니다. (외부 동작 전 사람 승인)
6. **내 결정을 정리합니다.** **3단계 한 마디**로 지적을 표로 정리시키고, AI에게 **"과한 지적은 자진 신고"** 시킵니다. "고친다 / 다음에 / 동의 안 함" 칸은 **내가 직접** 채웁니다. (대화 예시는 [`conversation.md`](conversation.md))
7. **고치고 커밋합니다.** "고친다"로 정한 것만 실제 코드에서 고치고 **반영 커밋**을 만들어 PR에 push 합니다. 그러면 한 PR 안에 **리뷰 코멘트 + 반영 커밋**이 함께 남습니다.
8. **결과를 옮겨 적습니다.** 받은 코멘트·내 결정·반영 커밋을 [`REVIEW.md`](REVIEW.md)처럼 정리해 저장합니다. 그게 이 실습의 결과물입니다.

## 🤖 바이브코딩 프롬프트

이 실습은 "앱 코드 짜기"가 아니라 **AI에게 정확한 PR 코드리뷰를 시키는 지시 설계**가 핵심입니다.
그래서 아래 프롬프트도 "리뷰 받을거리를 만드는 → 리뷰를 시키는 → 막혔을 때 푸는" 흐름으로 짰습니다.
(원문 그대로 붙여 쓰는 정식 지시문은 [`prompt.md`](prompt.md)에 더 자세히 있습니다. 아래는 그 요약형 복붙판입니다.)

- **1단계(뼈대 만들기)** — GitHub MCP 연결 확인 + 리뷰 대상 PR 고르기:
  ```text
  너는 내 코드리뷰를 도와줄 조수야. 지금 GitHub MCP가 실제로 연결됐는지부터 확인하고 싶어.
  내 저장소 "REPLACE_WITH_OWNER/REPLACE_WITH_REPO"에 열려 있는 PR(Pull Request) 목록을
  번호와 제목만 5개 이내로 보여줘.
  중요: 아직 연결이 안 됐거나 권한이 부족하면 절대 추측해서 지어내지 말고,
  "무엇이 안 됐는지(연결/권한/저장소 이름)"만 정확히 알려줘.
  진짜 목록이 나오면, 그중 리뷰하기 좋은 작은 PR 하나를 추천하고 그 번호를 알려줘.
  ```

- **2단계(기능 추가/개선)** — 고른 PR을 "파일:줄 + 분류" 형식으로 리뷰시키고, 보안·버그만 인라인 코멘트로:
  ```text
  너는 우리 팀의 깐깐한 시니어 코드리뷰어야. GitHub MCP로 아래 PR을 직접 읽고 리뷰해.
  - 저장소: REPLACE_WITH_OWNER/REPLACE_WITH_REPO
  - PR 번호: REPLACE_WITH_PR_NUMBER
  먼저 "바뀐 파일·바뀐 줄(diff)"만 보고 변경 요약을 3줄로 말해줘.
  그다음 칭찬은 빼고 "고쳐야 할 것"을 심각도 높은 순으로 짚되, 각 지적마다
  반드시 (1) 파일 이름:줄 번호 (2) [버그]/[보안]/[개선] 분류 (3) 무엇이·왜·어떻게(수정안 1~3줄)를 붙여.
  우리 스택은 HTML/CSS/JS + Supabase + Vercel + n8n이야. 보안은 특히 이걸 봐:
  service_role(비밀) 키가 프론트에 노출됐는지 / 테이블에 RLS가 켜졌는지 / 사용자 입력을 innerHTML로 넣어 XSS 위험인지.
  마지막에 "이 PR 지금 합쳐도 되나?"를 예/아니오/조건부 예 한 줄로 결론 내.
  리뷰가 끝나면, [보안]·[버그]만 그 PR의 해당 줄에 "인라인 코멘트"로 달 예정이라고 먼저 목록으로 보여주고,
  내가 "달아"라고 하면 그때 GitHub MCP로 실제로 달아. (승인 전엔 실행하지 마.)
  ```

- **막혔을 때(디버깅)** — AI가 줄 번호를 헷갈리거나 가짜 PR을 지어낼 때:
  ```text
  방금 "REPLACE_WITH_FILE:REPLACE_WITH_LINE 에 문제가 있다"고 했는데, 그게 진짜인지 의심돼.
  추측하지 말고 GitHub MCP로 그 PR의 해당 파일을 다시 읽어서, 그 줄의 실제 코드를 그대로 인용해줘.
  줄 번호가 안 맞으면 정정하고, 만약 그 줄/함수가 PR의 변경분에 실제로 없다면 "지적 철회"라고 솔직히 말해.
  그리고 혹시 아까 보여준 PR 목록이 MCP로 진짜 읽어온 게 맞는지(아니면 지어낸 건지)도 다시 확인해줘.
  ```

> 프롬프트 팁: 위 지시 끝에 "코드만 고치라 하지 말고, **왜 그렇게 고쳐야 하는지 비전공자도 알게 한 줄씩 주석/설명으로 풀어줘**"를 덧붙이면, 리뷰가 단순 지적이 아니라 학습 자료가 됩니다.

## 검증법

아래를 모두 만족하면 성공입니다.

- [ ] AI가 MCP로 **내 저장소의 진짜 PR**을 읽었다. (가짜 PR 목록을 지어내지 않았다)
- [ ] 지적마다 **"파일 이름 + 줄 번호"** 가 붙어, 어디가 문제인지 특정됐다.
- [ ] 각 지적이 **[버그] / [보안] / [개선 제안]** 으로 분류됐고, **(무엇이 / 왜 / 어떻게)** 가 붙었다.
- [ ] **보안 핵심**(service_role 비밀 키 노출 / RLS 누락 / 사용자 입력 XSS)을 짚었다.
- [ ] [보안]·[버그] 지적이 **PR의 해당 줄에 인라인 코멘트로 실제로 달렸다.** (채팅에만 머무르지 않았다)
- [ ] 코멘트를 다는 **외부 동작 전에** 내가 "달아"라고 **승인**하는 단계가 있었다.
- [ ] 마지막에 **"예 / 아니오 / 조건부 예"** 한 줄 결론이 나왔다.
- [ ] [`REVIEW.md`](REVIEW.md)에 "고친다/다음에/동의 안 함" **내 결정 칸을 사람이 직접** 채웠고, **반영 커밋**이 남았다.

> 빠르게 자가 점검: PR 페이지의 "Files changed" 탭을 열었을 때 **바뀐 줄 아래에 AI 코멘트가 보이고**, 그 위(또는 새 커밋)에 **내가 고친 흔적**이 함께 있으면 통과입니다.
> AI가 줄 번호를 헷갈린 것 같으면, [`conversation.md`](conversation.md) 맨 아래의 "실제 줄을 다시 인용하라" 한 마디로 환각을 걸러내세요.
