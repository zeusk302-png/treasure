# 실습 160 — 입력하는 동안만 검색하는 디바운스 · 중복요청 막기

검색 버튼 없이, **타이핑을 멈추면 알아서 검색**되는 실시간 도서 검색 페이지를 만듭니다.

이 실습의 진짜 핵심은 한 가지 깨달음입니다.
> **글자를 칠 때마다 검색하면 안 된다.** `어린왕자`를 친다고 `ㅇ → 어 → 어ㄹ → 어린 …` 글자마다 API를 보내면, 단어 하나에 수십 번 서버를 두들깁니다. 무료 API는 **호출 한도(rate limit)**를 넘겨 차단되고, 유료 API라면 그만큼 **요금이 새어 나갑니다.** 그래서 ① 입력이 **멈춘 뒤에만** 한 번 검색하고(**디바운스**), ② 그 사이 새 검색이 출발하면 **먼저 떠난 옛 요청은 취소**합니다.

> 비유: 엘리베이터는 누가 탈 때마다 즉시 출발하지 않습니다. 문이 **잠시 조용해질 때까지** 기다렸다가 한 번에 출발하지요. 디바운스가 바로 그 '조용해질 때까지 기다리기'입니다.

이 데모는 159와 똑같이 **키가 필요 없는 무료 공개 API**만 씁니다.
- **Open Library 검색 API**(`https://openlibrary.org/search.json`): 책을 검색하는 무료 공개 API. 키 없음, 회원가입 불필요.

그래서 **인터넷 연결만 있으면** 그대로 동작합니다. (가입·키·결제 모두 불필요)

## 목표
- **디바운스(debounce)**를 이해한다: 입력이 들어올 때마다 검색을 곧장 하지 않고, `setTimeout`으로 **0.4초 뒤로 예약**한다. 그 안에 또 입력이 오면 `clearTimeout`으로 예약을 취소하고 다시 잡는다 → 결국 **타이핑이 멈춘 순간 딱 한 번만** 실행된다.
- **중복요청(이전 요청) 취소**를 이해한다: 새 검색을 시작하기 직전, 아직 안 끝난 옛 요청을 `AbortController.abort()`로 끊는다. 그래야 느린 옛 응답이 늦게 도착해 새 결과를 **덮어쓰는 경쟁 상태(race condition)**가 생기지 않는다.
- **취소는 오류가 아니다**를 안다: `abort()`로 멈춘 fetch는 `catch`에서 `err.name === "AbortError"`로 떨어진다. 이건 정상 흐름이므로 사용자에게 **빨간 오류를 띄우지 않고 조용히 넘긴다**.
- **rate limit(호출 한도)을 의식**하는 습관을 들인다: '키 입력 횟수'와 '실제 검색 요청 횟수'를 화면 계기판으로 비교해, 디바운스가 호출을 얼마나 줄여 주는지 **눈으로 확인**한다.
- 너무 짧은 검색어(1글자)는 결과가 너무 넓어 검색하지 않는 **최소 글자 수(`MIN_CHARS`)** 가드를 둔다.

## 따라하는 단계
1. 이 폴더의 `index.html`을 더블클릭 → 브라우저에서 열린다. (검색은 인터넷에서 불러오므로 **인터넷 연결이 필요**합니다.)
2. 입력칸에 천천히 **`해리포터`**라고 쳐 본다 → 글자를 치는 동안에는 **"입력이 멈추길 기다리는 중…"**만 뜨고, 타이핑을 멈춘 뒤 **약 0.4초**가 지나면 그제서야 스피너가 돌며 검색된다.
3. 위쪽 **계기판**을 본다 → **키 입력**은 글자 수만큼(예: 4~5회) 올라가지만, **실제 검색 요청**은 **딱 1회**만 올라간다. 이게 디바운스가 한 일이다.
4. 이번엔 **아주 빠르게** `python`을 친 뒤 곧바로 지우고 `java`를 쳐 본다 → 느린 네트워크라면 `python` 요청이 취소되며 **취소된 요청** 숫자가 올라가고, 화면에는 **마지막 검색(`java`)** 결과만 남는다.
5. 입력칸을 **한 글자만** 남기거나 **모두 지워** 본다 → "2글자 이상 입력해 주세요" 또는 "검색어를 입력하면…" 안내가 뜨고, **요청을 보내지 않는다**(계기판의 실제 요청 숫자가 안 올라간다).
6. **예시 칩**(예: `어린왕자`)을 눌러 본다 → 칩은 디바운스를 기다리지 않고 **즉시 검색**한다(이미 '확정된' 검색어이므로).
7. `script.js`를 열고 **디바운스·취소의 핵심 네 곳**을 직접 찾아본다.
   - 디바운스 예약/취소: `clearTimeout(debounceTimer)` → `debounceTimer = setTimeout(() => runSearch(q), DEBOUNCE_MS)`
   - 취소 리모컨 만들기: `const controller = new AbortController()`
   - 옛 요청 끊기: `currentController.abort()` (함수 `cancelInFlightRequest`)
   - fetch에 연결: `fetch(url, { signal: controller.signal })` 와 `catch`의 `if (err.name === "AbortError") return;`
8. AI에게 시켜 보기 (디렉터 연습):
   > "이 `script.js`에서 검색 결과 목록에 **마우스를 올린 책 제목을 입력칸 아래에 미리보기로 표시**하는 기능을 추가해 줘. 단, **기존의 디바운스(`setTimeout`/`clearTimeout`) 흐름, `AbortController`로 이전 요청을 취소하는 구조, `AbortError`를 오류로 취급하지 않는 처리는 그대로 유지**해 줘."

## 검증법
- **천천히** 타이핑할 때, 글자마다 검색이 나가지 않고 **멈춘 뒤에 한 번만** 나가는가? (계기판: 키 입력 ≫ 실제 검색 요청)
- 계기판의 **실제 검색 요청** 숫자가, 같은 단어를 한 번 치는 동안 **1만큼만** 올라가는가?
- 빠르게 단어를 바꿔 치면 **취소된 요청** 숫자가 올라가고, 화면에는 **마지막 검색 결과만** 남는가? (옛 결과가 새 결과를 덮어쓰지 않는가)
- **1글자**거나 **빈 칸**이면 검색을 **보내지 않고** 안내만 뜨는가? (헛된 요청을 막는가)
- 검색이 진행될 때 **스피너가 돌고**, 끝나면 **멈추는가?** (낡은 요청이 끝나며 최신 검색의 스피너를 꺼 버리지 않는가)
- 의미 없는 글자(예: `asdfqwerzxcv`)를 넣으면 "검색 결과가 없어요" **빨간 안내**가 뜨는가? (성공일 땐 초록, 실패일 땐 빨강으로 색이 다른가)
- `F12`(개발자 도구) → **Network 탭**을 열고 천천히 타이핑해 보면, `search.json` 요청이 **글자마다가 아니라 멈춘 뒤에만** 한 줄씩 생기는가? (취소된 요청은 빨간 `(canceled)` 상태로 보인다)
- `F12` → **Console 탭**에서, 취소가 일어나면 `이전 요청을 취소했습니다(정상)` 로그만 뜨고 **화면에는 빨간 오류가 안 뜨는가?** (취소를 오류로 착각하지 않는가)

## 흔한 함정 (검색이 과하거나 결과가 뒤죽박죽일 때 여기부터)
- **디바운스 예약을 안 비움**: `setTimeout`만 새로 잡고 직전 예약을 `clearTimeout`으로 지우지 않으면, 예약이 쌓여 **타이핑한 글자 수만큼 검색이 다 터집니다.** 새 입력마다 반드시 먼저 `clearTimeout(debounceTimer)`를 부릅니다.
- **이전 요청을 안 끊음**: 디바운스로 횟수는 줄어도, 느린 네트워크에서는 요청이 겹칠 수 있습니다. 옛 요청을 `abort()`하지 않으면, 늦게 도착한 옛 응답이 **새 결과를 덮어써** 엉뚱한 책이 보입니다(경쟁 상태). 새 검색 직전에 `cancelInFlightRequest()`로 끊습니다.
- **취소(AbortError)를 오류로 처리**: `abort()`는 일부러 멈춘 것이라 정상입니다. 이걸 `catch`에서 그대로 빨간 오류로 띄우면, 정상 동작인데도 "검색 실패"가 깜빡입니다. `err.name === "AbortError"`면 조용히 `return` 합니다.
- **디바운스 시간이 너무 김/짧음**: 너무 길면(예: 1.5초) 느리게 느껴지고, 너무 짧으면(예: 50ms) 디바운스 효과가 거의 없습니다. 보통 **300~500ms**가 적당합니다(이 실습은 `DEBOUNCE_MS = 400`).

## 공개 API와 비밀값 — 보안 메모
이 실습은 **키가 필요 없는 공개 API**(Open Library)만 써서, 브라우저 코드에 그대로 둬도 안전합니다.
하지만 디바운스가 더 절실해지는 쪽은 오히려 **키가 필요한 유료 검색 API**입니다. 호출 한 번이 곧 비용이니까요. 그래서 원칙을 정리해 둡니다.

- **공개되어도 되는 값**(예: Supabase의 `anon`(공개) 키, 키 없는 Open Library): 브라우저 코드에 들어가도 괜찮습니다. 단, 데이터 보호는 **RLS(행 수준 보안)**가 책임집니다. anon 키만 믿고 RLS를 끄면 누구나 데이터를 읽고 쓸 수 있어 위험합니다.
- **절대 노출하면 안 되는 비밀값**(예: Supabase의 `service_role` 키, 과금되는 유료 검색 API 키): **브라우저 코드에 절대 넣지 않습니다.** 브라우저 코드는 `F12`로 누구나 들여다볼 수 있어, 비밀키를 넣으면 그대로 도둑맞아 **요금 폭탄·데이터 유출**로 이어집니다. `service_role` 키는 RLS를 **무시하고** 모든 데이터에 접근하므로, 오직 서버(또는 n8n 같은 자동화 도구의 자격 증명 저장소)에서만 다룹니다.
- 키가 필요한 검색 API로 바꾼다면: 브라우저 → **내 서버(또는 n8n 워크플로)** → 유료 API 순으로 호출해, 키는 서버 쪽에만 둡니다. 디바운스(브라우저)와 더불어, 서버에도 호출 한도 보호를 둡니다.
- 예제에 적을 때조차 진짜 키 대신 `YOUR_API_KEY` 같은 **자리표시자**만 둡니다.

```js
// 키가 필요한 '유료' 검색 API로 바꾸는 경우 — 이렇게 하면 안 됩니다 (브라우저에 키 노출!)
// const url = "https://api.example.com/books?key=진짜키&q=" + q;  // ❌ 금지

// 올바른 방향: 키는 코드에 넣지 말고 내 서버/n8n을 거쳐 호출합니다.
const API_KEY = "YOUR_API_KEY"; // ← 자리표시자. 실제 비밀키는 절대 브라우저 코드에 넣지 않는다.
// (이 키는 브라우저가 아니라 서버 환경변수에만 존재해야 합니다.)
```

> 정리: **디바운스와 요청 취소는 호출 횟수를 줄여 rate limit·요금을 지키는 첫 번째 방어선**입니다. 공개 API(Open Library)는 브라우저에서 직접 불러도 안전하지만, **키가 붙는 순간 그 호출은 서버(또는 n8n) 뒤로 숨겨야** 합니다.
