# SaaS 대시보드: 로그인해야 보이는 보호된 페이지 만들기

웹 서비스(SaaS)에는 **로그인한 사람만 들어갈 수 있는 화면**이 있죠. 이 실습에서는 그 핵심인 **로그인 게이트(보호 라우트)** 를 만듭니다.

핵심 한 줄: **대시보드 페이지가 열리자마자 "지금 로그인돼 있나?"를 먼저 확인하고, 아니면 로그인 페이지로 돌려보낸다.**

> 비유: 대시보드는 회원 전용 라운지입니다. 입구에 직원(가드 코드)이 서서 **출입증(세션)** 을 확인하고, 없으면 정중히 로비(로그인 페이지)로 안내합니다. 화면에 내용이 잠깐 보였다 사라지는 게 아니라, **확인이 끝날 때까지 문을 아예 안 열어 줍니다.**

## 목표

- "**로그인 안 한 사람은 못 들어온다**"를 직접 만들어 보며 **세션 확인(세션 가드)** 을 익힌다.
- 두 페이지(`login.html` ↔ `dashboard.html`)가 **세션 하나를 공유**하는 흐름을 이해한다. (새로고침·페이지 이동에도 로그인 유지)
- **anon(공개) 키는 브라우저에 둬도 되는 '출입증'** 이고, **service_role(비밀) 키는 절대 프론트에 두면 안 된다**는 원칙을 익힌다.

## 따라하는 단계

1. [supabase.com](https://supabase.com)에서 프로젝트를 만듭니다. (앞 실습에서 한 것과 동일)
2. 왼쪽 메뉴 **Authentication → Providers → Email**이 켜져 있는지 확인합니다. 실습 편의를 위해 **"이메일 인증(Confirm email)"을 꺼 두면** 가입 직후 바로 로그인됩니다.
3. **Settings → API**에서 `Project URL`과 `anon`(공개) 키를 복사합니다.
4. `config.js`를 열고 위쪽 두 값을 내 값으로 바꿉니다.
   - `SUPABASE_URL` → 내 `Project URL`
   - `SUPABASE_ANON_KEY` → 내 **anon(공개) 키** (자리표시자 `sb_publishable_여기에-내-anon-공개키-붙여넣기` 자리)
5. `login.html`을 브라우저로 엽니다. 이메일·비밀번호로 **회원가입 → 로그인**합니다. 성공하면 자동으로 `dashboard.html`로 넘어갑니다.
6. 대시보드에서 **로그아웃**을 누릅니다. 곧바로 로그인 페이지로 돌아갑니다.
7. (게이트 확인) 로그아웃된 상태에서 **주소창에 `dashboard.html`을 직접 입력**해 들어가 봅니다. → 내용이 보이지 않고 즉시 로그인 페이지로 튕겨 나갑니다.

## 🤖 바이브코딩 프롬프트

이 실습을 AI에게 시켜 만들 때 그대로 복사해 쓸 수 있는 프롬프트입니다. 한 번에 다 시키지 말고 **1단계 → 2단계 → (막히면) 디버깅** 순서로 나눠서 시키는 것이 핵심입니다.

- **1단계(뼈대 만들기)** 프롬프트:

  ```text
  너는 프론트엔드 멘토야. 비전공자도 이해할 수 있게 만들어 줘.
  Supabase Auth를 쓰는 정적 웹(빌드 도구 없이 HTML+JS만)으로
  "로그인해야 보이는 보호된 대시보드"를 만들어 줘. 파일 구성은:
  - login.html : 이메일/비밀번호로 회원가입·로그인하는 페이지
  - dashboard.html : 로그인한 사람만 볼 수 있는 페이지(가짜 통계 카드 3장)
  - config.js : SUPABASE_URL, SUPABASE_ANON_KEY 와 createClient 한 곳
  - style.css : 공통 스타일
  제약:
  - Supabase는 CDN(@supabase/supabase-js@2)으로 불러와.
  - 키는 anon(공개) 키만 프론트에 둬. service_role 키는 절대 쓰지 마.
  - 실제 값 대신 "여기에-내-값" 같은 자리표시자를 넣어 줘.
  - 각 줄에 "무엇을 하는지 + 왜 그렇게 했는지"를 한국어 주석으로 달아 줘.
  ```

- **2단계(기능 추가/개선)** 프롬프트:

  ```text
  이제 dashboard.html에 진짜 "로그인 게이트(세션 가드)"를 넣어 줘. 요구사항:
  1) 페이지가 열리면 db.auth.getSession()으로 세션을 먼저 확인해.
  2) 세션이 없으면 본문을 절대 안 보여주고 login.html로 즉시 돌려보내.
     (내용이 깜빡 보였다 사라지지 않게, 처음엔 본문을 display:none으로 숨기고
      세션 확인이 끝난 뒤에만 보여 줘.)
  3) 세션이 있으면 로그인한 사람의 이메일을 화면에 표시해.
  4) 로그아웃 버튼: signOut() 후 login.html로 보내.
  5) onAuthStateChange로 다른 탭에서 로그아웃되면 자동으로 추방되게 해.
  login.html도 이미 로그인된 상태면 자동으로 dashboard.html로 보내 줘.
  ```

- **막혔을 때(디버깅)** 프롬프트:

  ```text
  로그인은 되는데 dashboard.html이 자꾸 login.html로 튕겨. 단계별로 진단해 줘.
  - F12 → Console의 빨간 에러를 그대로 붙여넣을게: (여기에 에러 메시지)
  - config.js의 SUPABASE_URL과 anon 키가 placeholder가 아닌 실제 값인지,
    Supabase 대시보드의 Settings → API 값과 일치하는지 점검 포인트를 알려 줘.
  - getSession()이 null을 주는 흔한 원인(이메일 확인 ON이라 세션이 안 생김,
    persistSession 설정, 다른 도메인/file:// 문제)을 하나씩 짚어 줘.
  추측하지 말고, 내가 직접 확인할 수 있는 순서로 알려 줘.
  ```

> 프롬프트 팁: 끝에 **"코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해 줘"**, **"비전공자가 이해하게 한 줄씩 풀어 줘"**를 덧붙이면 결과를 그대로 베끼지 않고 *이해하며* 배울 수 있습니다.

## 검증법

- **로그인 전 차단**: 로그아웃 상태에서 `dashboard.html`에 직접 접속하면 통계 카드가 보이지 않고 `login.html`로 이동한다.
- **로그인 후 통과**: 로그인하면 대시보드의 통계 카드 3장과 내 이메일(👋)이 보인다.
- **세션 유지**: 대시보드에서 **새로고침(F5)** 해도 로그인 페이지로 튕기지 않고 그대로 머문다. (세션이 브라우저에 저장돼 있기 때문)
- **로그아웃 즉시 차단**: 로그아웃을 누른 직후 `dashboard.html`로 뒤로가기/직접 접속하면 다시 로그인 페이지로 돌아간다.
- **오류 없음**: 정상 흐름에서 F12 → Console에 빨간 오류가 없어야 한다.

> "주소창으로 직접 들어가도 막히는가?"가 이 실습의 핵심 검증입니다. 메뉴에서 링크를 숨기는 것만으로는 보호가 안 됩니다 — 페이지가 **스스로 세션을 확인**해야 진짜 게이트입니다.

!!! note "겉보기 가드 vs 진짜 잠금 (한 단계 더)"
    이 실습의 게이트는 **화면 차원의 보호**입니다 — "로그인 안 하면 이 페이지의 내용을 안 보여 준다." 사용자가 보는 SaaS 화면을 가리는 데는 충분합니다.
    다만 **데이터 자체**(예: 남의 매출 숫자를 DB에서 못 읽게)를 지키려면, 화면 가드만으로는 부족하고 데이터베이스의 **RLS(행 수준 보안)** 가 함께 있어야 합니다. 화면 가드는 "문 앞 안내문", RLS는 "진짜 자물쇠"예요. (RLS는 실습 260 참고)

!!! danger "절대 하지 말 것"
    `config.js`에 넣는 건 **anon(공개) 키**여야 합니다. `service_role`(secret) 키는 **모든 보안을 통째로 우회**하므로 브라우저·GitHub에 두면 누구나 모든 데이터를 보고 지울 수 있습니다. 두 키를 헷갈리는 게 가장 흔한 사고입니다. 비밀 키가 필요한 작업은 반드시 **서버(또는 n8n)** 안에서만 처리하세요.
