# 실습 295 — N+1 쿼리 잡기: 글 50개에 51번 두드리는 느린 목록 고치기

게시판 목록을 만들었더니 화면은 멀쩡한데, **속을 보면 글 50개를 그리려고 서버를 51번이나 두드리고** 있었습니다.
원인은 흔한 실수입니다. 글 목록을 받은 뒤, **글을 하나씩 돌면서 "이 글 작성자가 누구지?"를 매번 따로 물어본** 것이죠.

- 글 목록 받기: **1번**
- 글 50개의 작성자 조회: **50번**
- 합계: **1 + 50 = 51번** ← 이게 바로 **N+1 쿼리** 문제입니다. (글이 N개면 1 + N번)

글이 1000개로 늘면 요청은 1001번이 됩니다. 사용자가 몰리면 목록이 한참 뒤에 뜨고 서버가 비명을 지릅니다.
이 깨진 코드를 직접 보고, **한 번에 몰아서 물어보는 방식**으로 고쳐 51번을 1~2번으로 줄여 봅니다.

> 이건 디버깅(고치기) 실습입니다. 폴더에는 **느린 버전(`broken.js`)** 과 **고친 버전(`index.js`)** 이 함께 들어 있고, 같은 페이지에서 나란히 비교합니다.

## 목표

- "화면이 잘 나온다 ≠ 코드가 잘 짜였다"를 체험한다. **잘못은 화면이 아니라 '요청 횟수'에 숨어 있다.**
- **N+1 쿼리**가 무엇인지(반복문 안에서 매번 따로 조회) 코드로 직접 본다.
- 두 가지 해법을 익힌다:
  - **관계 조회(join)** — `select("...,  authors:author_id ( name )")` 한 줄로 작성자까지 같이 받아 **요청 1번**.
  - **`in` 일괄 조회** — 작성자 id들을 모아 `.in("id", [...])`로 **한 방에** 받아 **요청 2번**.
- 요청 횟수를 **직접 측정**해 51번 → 2번 이하로 줄었음을 숫자로 확인한다.

## 따라하는 단계

1. **테이블 만들기.** Supabase 대시보드 → **SQL Editor** 에 `schema.sql`을 통째로 붙여넣고 **Run**. 작성자 10명 + 글 50개가 생깁니다. (N+1을 재현하려면 글이 작성자보다 훨씬 많아야 해서 50:10으로 만듭니다.)
2. **내 연결값 넣기.** `config.js`를 열어 `SUPABASE_URL`과 `SUPABASE_ANON_KEY`를 내 값(Settings → API)으로 바꿉니다. 이 둘은 **공개해도 되는 `anon`(publishable) 키**입니다. `service_role`(secret) 키는 절대 넣지 마세요.
3. **느린 버전 먼저 보기.** `broken.js`를 읽습니다. `for` 반복문 안에서 `db.from("authors")...single()`로 **글마다 작성자를 따로 조회**하는 부분이 범인입니다.
4. **재현하기.** `index.html`을 브라우저로 열고 **F12로 콘솔을 켠 뒤**, 왼쪽 ❌ "느린 목록 불러오기" 버튼을 누릅니다. → 결과 박스에 **"총 51번 DB 요청"**, 콘솔에 `→ DB 요청 #1 … #51`이 줄줄이 찍힙니다.
5. **고치기.** 오른쪽 ✅에서 "관계 조회로 불러오기"(방법 A)를 누릅니다. → **"총 1번"**. 화면 결과는 ❌와 **똑같은데** 요청은 1번뿐입니다. 핵심은 `index.js`의 이 한 줄:
   ```js
   .select("id, title, authors:author_id ( name )")  // 작성자를 같이 받아옴
   ```
6. **차선책도 보기.** 관계(외래키) 설정이 없을 때를 대비해 "in 일괄 조회로 불러오기"(방법 B)도 눌러 봅니다. → **"총 2번"**(목록 1번 + 작성자 한 방에 1번). `.in("id", 작성자id들)`이 핵심입니다.

## 검증법

- **요청 횟수 숫자 비교(핵심).** 결과 박스에 ❌는 **51번**, ✅ 방법 A는 **1번**, 방법 B는 **2번**이 찍히면 성공입니다. 측정은 `config.js`의 `setupCounter()`가 `fetch`를 감싸 `/rest/v1/`로 가는 요청만 세어 만든 진짜 숫자입니다.
- **콘솔 로그로 교차 확인.** 콘솔에서 `→ DB 요청 #N`이 몇 번까지 찍히는지 셉니다. 느린 버전은 #51까지, 고친 버전은 #1(또는 #2)에서 멈춰야 합니다.
- **네트워크 탭으로 한 번 더.** F12 → **Network** 탭을 열고 버튼을 누르면, `authors?...`로 가는 요청이 느린 버전은 **수십 줄**, 고친 버전은 **0줄 또는 1줄**임을 눈으로 봅니다.
- **화면 결과는 동일한가.** 양쪽 목록의 글 제목과 작성자 이름이 **똑같이** 나오는지 확인합니다. "결과는 같은데 비용만 줄였다"가 이 실습의 핵심입니다.
- **글을 늘려 체감하기(선택).** `schema.sql`의 `generate_series(1, 50)`을 `1, 500`으로 바꿔 다시 Run 하면, 느린 버전은 **501번**으로 폭증하지만 고친 버전은 여전히 **1~2번**임을 확인할 수 있습니다.

> 핵심 한 줄: **반복문 안에서 DB를 부르고 있으면 N+1을 의심하라.** 고치는 법은 언제나 같다 — "하나씩 50번 물어보지 말고, 한 번에 몰아서 물어본다."
