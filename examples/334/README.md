# 실습 334 — 구조화 로깅 + 에러 추적 붙이기

작은 웹서버에 **구조화 로깅**(사람도 읽고 기계도 거를 수 있는 한 줄 JSON 로그)과 **에러 추적**(운영 중 터진 에러를 한곳에 모아 보는 Sentry식 보고)을 붙여 봅니다. 배포한 사이트가 "조용히 잘못되고 있을 때" 그걸 **알아채는 눈**을 다는 것이 목표입니다. 이게 운영의 기초 체력인 **관측성(observability)**입니다.

> 한 줄 그림: **요청이 들어옴 → 서버가 "한 줄 JSON 로그"를 남김(누가·어디로·몇 ms·결과 몇 번) → 에러가 나면 그 에러를 추적 도구로 모아 보고 → 나는 로그를 필터로 걸러 보고, 에러 목록에서 "오늘 47번 난 에러"부터 고친다**

> 비유: 로그는 가게의 **CCTV 녹화**이고, 에러 추적 도구는 **"같은 사고를 모아 정리해 주는 사고 보고서함"**입니다. CCTV(로그)는 모든 걸 다 찍어 두지만 그 자체로는 너무 길어 다 못 봅니다. 보고서함(에러 추적)은 "이 사고가 몇 번, 언제 처음 났는지"를 묶어 줘서 무엇부터 손볼지 알려 줍니다. 둘이 짝을 이뤄야 가게가 조용히 망가지는 걸 막습니다.

> 보안 메모 — 공개해도 되는 값 vs 절대 숨겨야 하는 값
> - **공개되어도 되는 값**: 로그 레벨(`LOG_LEVEL`), 포트(`PORT`) 같은 설정. 비밀이 아니라 동작 옵션일 뿐이라 코드에 둬도 됩니다.
> - **절대 노출하면 안 되는 비밀값**: 에러 추적 도구(Sentry)의 **DSN/토큰**. 이건 "내 프로젝트로 에러를 보낼 수 있는 주소"라, 새면 남이 내 프로젝트에 가짜 에러를 쏟아부을 수 있습니다. 그래서 코드에 박지 않고 **`.env`(또는 호스팅의 환경변수)**에만 둡니다.
> - 이 폴더의 `.env.example`에는 진짜 값이 아니라 **자리표시자**만 있습니다. 진짜 DSN은 복사해 만든 `.env`에만 적고, `.env`는 `.gitignore`로 깃에서 빠집니다.

## 목표
- **구조화 로깅을 이해한다**: `console.log("문장")` 대신 한 줄 JSON(`{"level":"info","msg":"...","requestId":"...","durationMs":12}`)으로 남기면, 도구가 **필드로 걸러** 볼 수 있다는 걸 직접 본다.
- **요청을 끝까지 추적한다**: `requestId`(꼬리표)로 한 요청의 로그와 에러를 **하나로 묶어** 따라간다.
- **에러를 한곳에 모은다**: 라우트마다 try/catch를 흩지 않고, **에러 핸들러 한 곳**에서 잡아 추적 도구로 보고한다.
- **비밀값을 코드 밖에 둔다**: Sentry DSN 같은 비밀값은 `server.js`가 아니라 `.env`/환경변수에서만 읽는다.
- **관측성의 기초를 익힌다**: "느린 요청(durationMs)·에러(level=error)를 숫자로 잡아낸다"는 운영 감각을 만든다.

## 따라하는 단계

### A. 실행 준비
1. 컴퓨터에 **Node.js**가 설치돼 있어야 합니다(`node -v`로 버전이 나오면 OK).
2. 이 폴더(`examples/334/`)에서 의존성을 설치합니다.
   ```bash
   npm install
   ```
3. 설정 견본을 복사해 내 `.env`를 만듭니다. (진짜 비밀값은 여기에만 넣습니다.)
   ```bash
   cp .env.example .env
   ```
   - 처음엔 `SENTRY_DSN`을 **비워 둬도** 됩니다. 그러면 에러가 **콘솔로만** "보고"됩니다(키 없이 실습 가능).

### B. 서버 켜고 로그 구경하기
4. 서버를 켭니다.
   ```bash
   npm start
   ```
   - 터미널에 `{"time":"...","level":"info","msg":"서버 시작됨","port":3000,...}` 같은 **한 줄 JSON**이 뜨면 성공입니다.
5. 다른 터미널(또는 브라우저)에서 아래 주소를 두드려 보고, **켜 둔 터미널에 로그가 한 줄씩 쌓이는지** 봅니다.
   ```bash
   curl "http://localhost:3000/"
   curl "http://localhost:3000/hello?name=세영"
   curl "http://localhost:3000/slow"
   ```
   - `/slow`를 치면 로그의 `durationMs`가 1200쯤으로 크게 찍힙니다. → "느린 요청"을 숫자로 잡는 감각.

### C. 일부러 에러 내고, 추적되는지 보기
6. 일부러 에러를 내는 주소를 칩니다.
   ```bash
   curl "http://localhost:3000/boom"
   ```
   - 화면(응답)에는 `{"ok":false,"error":"서버에서 문제가 발생했습니다."}`만 보입니다(내부 에러를 사용자에게 노출하지 않음).
   - 하지만 **터미널 로그**에는 `level":"error"`인 줄과, 그 아래 **에러 추적 도구로 보고**했다는 줄이 같이 찍힙니다. 둘 다 같은 `requestId`라 한 요청으로 묶입니다.

### D. (선택) 진짜 Sentry 붙이기
7. [sentry.io](https://sentry.io)에서 무료 프로젝트를 만들고 **DSN**을 발급받습니다.
8. 그 DSN을 **`.env`의 `SENTRY_DSN=`** 뒤에 붙입니다. (코드/깃에는 절대 넣지 않습니다.)
9. `npm install @sentry/node` 후, `errorTracker.js` 안의 "진짜 Sentry를 붙일 때(참고)" 주석대로 `Sentry.init` / `Sentry.captureException`을 켜면, `/boom`을 칠 때마다 **Sentry 대시보드에 에러가 모입니다.**

## 🤖 바이브코딩 프롬프트
이 실습을 AI에게 시켜 만들 때 그대로 복사해 쓸 수 있는 프롬프트입니다. (덧붙이면 좋은 말: "코드만 주지 말고 왜 그렇게 했는지 한국어 주석으로 한 줄씩 풀어 줘", "비전공자가 이해하게 설명해 줘")

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  너는 친절한 시니어 백엔드 개발자야. 비전공 초보가 따라할 수 있는 Node.js + Express 데모 서버를 만들어 줘.
  목표: "구조화 로깅"을 직접 눈으로 보게 하는 것.
  요구사항:
  - 별도 logger.js 파일에 구조화 로거를 만들어. console.log 대신 한 줄짜리 JSON으로 찍어야 해.
    각 로그에 time(ISO 시각), level(debug/info/warn/error), msg, 그리고 추가 필드를 담을 수 있게 해 줘.
  - 환경변수 LOG_LEVEL 보다 사소한 로그는 버려서 운영 소음을 줄이게 해 줘.
  - server.js에서 모든 요청을 미들웨어로 한 번에 로그로 남겨. 각 요청에 고유 requestId(UUID)를 붙이고,
    응답이 끝나면 method, path, status, durationMs(처리 시간)를 한 줄 JSON으로 남겨 줘.
  - 라우트는 3개: '/'(정상), '/hello?name=...'(입력 받아 인사), '/slow'(일부러 1초 넘게 지연).
  - 모든 코드에 "무엇을 하는지 + 왜 그렇게 했는지"를 한국어 주석으로 달고, 파일 맨 위에 요약 주석을 넣어 줘.
  - package.json도 만들어서 npm start로 돌게 해 줘.
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  좋아. 이제 여기에 "에러 추적(observability)"을 더해 줘.
  - errorTracker.js 파일을 만들어 captureException(err, context) 함수를 제공해 줘.
    환경변수 SENTRY_DSN이 있으면 추적 도구로 보낸 것처럼 처리하고, 없으면 콘솔로만 보고하게 해서
    키 없이도 실습이 돌아가게 해 줘. (진짜 Sentry 붙이는 법은 주석으로 알려 줘.)
  - server.js에 일부러 에러를 던지는 '/boom' 라우트를 추가하고,
    Express의 4-인자 에러 핸들러(err, req, res, next)를 "맨 마지막"에 하나만 둬서
    모든 에러를 거기서 잡게 해 줘. 거기서 (1) level=error 구조화 로그를 남기고
    (2) captureException으로 추적 도구에 보고하고 (3) 사용자에겐 내부 메시지를 숨기고 일반 안내만 보내 줘.
  - requestId로 요청 로그와 에러 로그가 하나로 묶이게 해 줘.
  - 보안: SENTRY_DSN은 비밀값이니 코드에 박지 말고 process.env로만 읽고, .env.example(자리표시자)과 .gitignore도 만들어 줘.
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  Express 서버에서 에러 핸들러가 안 잡히는 것 같아. /boom 을 쳐도 에러 핸들러의 로그가 안 찍히고,
  대신 기본 에러 페이지가 떠. 아래에 server.js 전체와 터미널에 뜬 에러/스택을 붙일게.
  - 원인을 한 가지로 단정하지 말고, 가능성을 높은 순으로 단계별로 짚어 줘
    (예: 에러 핸들러가 라우트보다 앞에 등록됐는지, 인자가 4개 맞는지, async 라우트의 에러를 next로 넘겼는지).
  - 각 가능성마다 "어떻게 확인하는지"와 "고치는 법"을 비전공자도 따라할 수 있게 알려 줘.
  - 고친 뒤 다시 /boom 을 쳤을 때 무엇이 보여야 정상인지도 알려 줘.

  [여기에 server.js 전체와 터미널 에러를 붙여넣기]
  ```
> 프롬프트 팁: 로그/에러를 붙여넣을 땐 **비밀값(DSN·토큰·실제 사용자 정보)을 지우고** 올리세요.

## 검증법
- **로그가 JSON 한 줄인지 확인**: 켜 둔 터미널의 로그가 `{"time":...,"level":"info",...}`처럼 **한 줄 JSON**으로 찍히는지 본다. (여러 줄로 쪼개지면 수집기가 못 읽는다.)
- **요청이 묶이는지 확인**: `/boom`을 쳤을 때, "요청 처리됨" 로그와 "요청 처리 중 에러" 로그의 **`requestId`가 같은지** 본다. 같으면 한 요청으로 추적되는 것이다.
- **느린 요청이 숫자로 잡히는지**: `/slow`의 로그 `durationMs`가 1200 근처로 크게 찍히는지 본다.
- **에러가 보고되는지**: `/boom`을 친 뒤, 터미널에 "에러 추적 도구로 보고" 줄이 뜨는지(또는 DSN을 넣었다면 Sentry 대시보드에 에러가 쌓이는지) 본다.
- **사용자에게 내부 정보가 안 새는지**: `/boom`의 **응답(화면)**에는 스택이나 내부 메시지가 없고 일반 안내(`서버에서 문제가 발생했습니다.`)만 보이는지 확인한다. (스택은 로그/추적 도구에만 있어야 한다.)
- **비밀값이 코드에 없는지 확인**: 아래를 이 폴더에서 실행하면 **자리표시자만** 나와야 정상이다.
  ```bash
  grep -rnE "https://[a-z0-9]+@[a-z0-9.]*sentry" . --exclude-dir=node_modules
  ```
  → 진짜 DSN이 **안 나와야** 정상이다(진짜 값은 `.env`에만, `.env`는 깃에서 빠진다).

## 파일 구성
- `server.js` — Express 데모 서버. 요청 로그 미들웨어 + 정상/느린/에러 라우트 + 에러 핸들러 한 곳.
- `logger.js` — 구조화 로거. 한 줄 JSON으로, LOG_LEVEL로 소음을 거른다.
- `errorTracker.js` — 에러 추적(Sentry 개념) 모듈. DSN이 없으면 콘솔 보고, 있으면 전송(진짜 붙이는 법은 주석).
- `package.json` — 의존성(express)과 `npm start` 명령 정의.
- `.env.example` — 필요한 설정값 견본(자리표시자만). 복사해 `.env`를 만들고 진짜 DSN은 거기에만 넣는다.
- `.gitignore` — `.env`·`node_modules`가 깃에 안 올라가게 막는다.
