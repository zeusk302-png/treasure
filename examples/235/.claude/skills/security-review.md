# 스킬: security-review (보안리뷰 — 배포 직전 마지막 점검)

> 배포(Vercel push) 직전에 "security-review 스킬로 점검해줘" 한 마디로 부르는, **보안 체크리스트 스킬**입니다.
> 사람(디렉터)이 놓치기 쉬운 키 노출·RLS 누락·입력 검증을 AI가 줄 단위로 짚게 합니다.

## 언제 쓰나
- 배포 전, 또는 PR을 올리기 전. 특히 Supabase·키·사용자 입력이 들어간 변경에서.

## AI가 따라야 할 절차

당신은 보안 리뷰어다. 바뀐 코드와 설정을 읽고, 아래 항목을 **하나씩** 점검해 "통과 / 위험 / 확인필요"로 표시하라. 각 지적에는 **파일 이름 + 줄 번호**와 **(무엇이 / 왜 위험 / 어떻게 고치나)** 를 붙인다.

1. **비밀 키 노출** — `service_role` / `secret` / 토큰 / API 키가 프론트엔드 코드나 깃에 올라갈 파일에 적혀 있지 않은가? (있으면 즉시 [위험])
   - 프론트엔드에 있어도 되는 건 **anon(공개) 키뿐**이다.
2. **RLS** — Supabase의 표에 RLS(행 수준 보안)가 켜져 있는가? 정책 없이 anon 키로 **남의 데이터를 읽거나 지울 수** 있지는 않은가?
3. **.env / 비밀 파일** — `.env`·`*-secret.*`·`*.local`이 `.gitignore`에 들어 있는가? 실수로 커밋되지 않았는가?
4. **사용자 입력(XSS)** — 사용자가 친 글을 `innerHTML`로 그대로 넣지 않는가? `textContent` 또는 이스케이프를 쓰는가?
5. **권한 최소화** — MCP 토큰·DB 연결이 필요 이상으로 강한 권한(쓰기·삭제)을 갖고 있지 않은가?
6. **되돌릴 수 있나** — 이 변경이 잘못됐을 때 되돌릴 방법(브랜치/커밋)이 있는가?

마지막에 **"배포해도 됨 / 고치고 배포 / 배포 보류"** 중 하나로 한 줄 결론을 내라. [위험] 항목이 하나라도 있으면 "배포해도 됨"이라고 하지 마라.

## 제약
- 직접 키를 지우거나 파일을 고치는 **외부 동작은 하지 말고**, 무엇을 고칠지 먼저 보여준 뒤 사용자의 승인을 받는다.
- "문제 없음"이라고 단정하지 말고, 확신이 없는 항목은 "확인필요"로 남긴다. 안 돌려본 것을 "안전하다"고 하지 않는다.

## 복붙용 호출 예시
```
security-review 스킬로 이번 변경(방명록 Supabase 연동)을 배포 전에 점검해줘.
파일:줄 + 통과/위험/확인필요로. 결론 한 줄 포함.
```
