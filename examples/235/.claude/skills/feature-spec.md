# 스킬: feature-spec (기획 — 만들기 전에 사양서부터)

> **스킬이란?** AI에게 시킬 "자주 쓰는 작업 절차"를 파일로 적어 둔 것입니다.
> 매번 길게 설명하지 않고 "feature-spec 스킬로 이 기능 기획해줘" 한 마디면, AI가 아래 절차를 따릅니다.
> (이름과 내용은 내 작업환경에 맞게 바꿔도 됩니다.)

## 언제 쓰나
- 새 기능/페이지를 만들기 **직전**. 코드부터 짜지 말고, 무엇을 만들지 먼저 못 박을 때.

## AI가 따라야 할 절차

당신은 이 프로젝트의 시니어 기획자다. 사용자가 만들고 싶은 기능을 말하면, **코드를 바로 짜지 말고** 아래 형식의 짧은 사양서(스펙)부터 작성하라.

1. **한 줄 목표** — 이 기능이 사용자에게 주는 가치 한 문장.
2. **성공 기준(체크 가능한 것)** — "이렇게 하면 → 이렇게 보여야 정상" 형식으로 3~5개. 애매한 말("잘 된다") 금지.
3. **화면/동작 흐름** — 사용자가 무엇을 클릭/입력하면 무슨 일이 일어나는지 순서대로.
4. **데이터** — Supabase에 어떤 표(테이블)·칼럼이 필요한지. **이 표에 RLS가 필요한가?** (남의 데이터 보호가 필요하면 "필요"라고 적고 정책 한 줄을 제안).
5. **사용할 키** — 프론트엔드에서 쓰는 키는 **anon(공개) 키뿐**이어야 한다. service_role(비밀) 키가 필요한 동작이라면 "이건 프론트가 아니라 n8n/서버에서 처리"라고 명시.
6. **엣지 케이스 3개** — 빈 입력 / 아주 긴 입력 / 네트워크 실패 등에서 어떻게 동작할지.
7. **만들지 않을 것(범위 밖)** — 이번엔 안 할 것들. 욕심 방지.

## 제약
- 스택은 CLAUDE.md를 따른다(HTML/CSS/JS · Supabase · Vercel · n8n · Claude). 새 라이브러리를 끌어오려면 이유와 승인 요청을 먼저 적는다.
- **사양서 단계에서는 코드를 작성하지 않는다.** 사양서를 보여주고 사용자의 "좋아, 이대로 만들어"를 받은 뒤에만 구현으로 넘어간다.
- 비밀 키·웹훅 URL·토큰은 예시에 진짜 값을 쓰지 말고 `REPLACE_WITH_...` 자리표시자로만 표기한다.

## 복붙용 호출 예시
```
feature-spec 스킬로 "방명록에 글쓴이 본인만 자기 글을 삭제할 수 있는 기능"을 기획해줘.
사양서까지만. 코드는 내가 좋다고 한 다음에.
```
