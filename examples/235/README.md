# 235. 스킬·CLAUDE.md·MCP·코드리뷰를 묶은 '내 디렉터 작업환경' 완성하기

앞선 실습들에서 따로따로 배운 네 가지 — **CLAUDE.md(항상 켜진 메모)**, **스킬(자주 쓰는 작업 절차)**, **MCP(AI를 바깥과 잇는 통로)**, **코드리뷰(검증)** — 를 **하나의 작업환경**으로 묶습니다.

이 실습에는 새로 짤 "앱 코드"가 없습니다. 결과물은 **AI가 내 프로젝트에서 일을 시작할 때 자동으로 읽고 따르는 설정 파일 한 세트**입니다. 즉, 매번 채팅창에 "우리 스택은 ~야, 비밀 키 노출하지 마, 기획부터 해" 라고 반복하지 않아도 되도록 **규칙을 한 번 적어 두는 것**이 핵심입니다.

이 폴더의 파일은 다음과 같습니다.

- [`CLAUDE.md`](CLAUDE.md) — AI가 이 폴더에서 일할 때 **가장 먼저 자동으로 읽는 메모.** 스택·보안 규칙·작업 방식을 적어 둡니다.
- [`.claude/skills/feature-spec.md`](.claude/skills/feature-spec.md) — **기획 스킬.** 코드부터 짜지 말고 사양서(스펙)를 먼저 쓰게 합니다.
- [`.claude/skills/security-review.md`](.claude/skills/security-review.md) — **보안리뷰 스킬.** 배포 직전 키 노출·RLS 누락·입력 검증을 줄 단위로 점검합니다.
- [`.claude/mcp.example.json`](.claude/mcp.example.json) — **MCP 연결 설정 예시.** GitHub·Supabase를 AI에 붙이는 설정. 토큰은 모두 자리표시자입니다.
- [`.gitignore`](.gitignore) — 비밀 파일(.env, 진짜 MCP 설정 등)이 실수로 깃에 올라가지 않게 막습니다.

> 이 작업환경의 기본 흐름은 **기획 → 작업 → 보안리뷰 → 배포** 입니다.

## 목표

- CLAUDE.md·스킬·MCP를 **한 폴더에 통합**해, AI가 매번 반복 설명 없이 **내 규칙대로** 일하게 만든다.
- 키가 두 종류임을 명확히 한다: **anon(공개) 키는 프론트엔드에 둬도 되지만 RLS가 켜져 있어야 안전**하고, **service_role(비밀) 키는 절대 프론트엔드·깃·채팅창에 두지 않는다.**
- 모든 비밀값·토큰을 진짜 형식과 닮지 않은 **자리표시자(`REPLACE_WITH_...`, `YOUR_API_KEY`)** 로만 적는 습관을 굳힌다.
- 이 통합 작업환경의 **사용법을 README로 문서화**해, 다음에도(또는 동료도) 같은 방식으로 일하게 만든다.

## 따라하는 단계

1. 이 폴더의 [`CLAUDE.md`](CLAUDE.md)를 열어, **2번(스택)·3번(보안 규칙)을 내 프로젝트에 맞게** 고칩니다. 스택이 다르면 바꾸고, 보안 규칙은 그대로 두는 것을 권합니다.
2. [`.claude/skills/`](.claude/skills/) 안의 두 스킬(`feature-spec`, `security-review`)을 읽어 봅니다. 내 작업에 자주 필요한 절차가 더 있으면 같은 형식으로 파일을 하나 더 추가합니다.
3. **MCP를 연결합니다.** [`.claude/mcp.example.json`](.claude/mcp.example.json)을 `mcp.json`으로 **복사**한 뒤, `REPLACE_WITH_...` 자리에 들어갈 진짜 토큰은 파일에 적지 말고 **운영체제 환경변수**에 넣습니다. (`mcp.json`은 `.gitignore`가 이미 커밋을 막아 줍니다.)
4. AI 클라이언트(Claude 등)를 이 폴더에서 시작해, "지금 적용 중인 규칙(CLAUDE.md)을 한 줄로 요약해줘" 라고 물어 **CLAUDE.md가 실제로 읽혔는지** 확인합니다.
5. **기획을 시킵니다.** `feature-spec` 스킬로 작은 기능 하나(예: "방명록 글 본인만 삭제")를 사양서까지만 만들게 합니다. **코드는 내가 "좋아"라고 한 뒤에만** 진행하게 합니다.
6. **만들고, 배포 전에 보안리뷰를 시킵니다.** 만든 변경에 대해 `security-review` 스킬로 점검시키고, **파일:줄 + 통과/위험/확인필요 + 결론 한 줄**을 받습니다.
7. **사람 승인 후 배포합니다.** 리뷰가 "배포해도 됨"이고 내가 동의하면 main에 push(→ Vercel 자동 배포). 되돌릴 수 없는 동작 전에 **내 승인 한 마디**가 들어갔는지 확인합니다.
8. 위 흐름이 한 번 매끄럽게 돌면, 이 README의 "따라하는 단계"가 곧 **내 운영 표준**이 됩니다. 바뀐 규칙이 있으면 CLAUDE.md와 이 README를 같이 업데이트합니다.

## 검증법

아래를 모두 만족하면 성공입니다.

- [ ] AI에게 물었을 때, 내가 적은 **CLAUDE.md의 규칙(스택·보안)** 을 실제로 요약해 답한다. (메모가 읽히고 있다는 증거)
- [ ] `feature-spec` 스킬을 부르면 AI가 **코드부터 짜지 않고 사양서(성공 기준·엣지 케이스·RLS 필요 여부)** 를 먼저 만든다.
- [ ] `security-review` 스킬을 부르면 지적마다 **파일:줄 + (무엇이/왜/어떻게)** 가 붙고, 마지막에 **"배포해도 됨/고치고 배포/배포 보류"** 결론이 나온다.
- [ ] 이 폴더의 어떤 파일에도 **진짜 비밀 키·토큰·웹훅 URL이 없다.** 전부 `REPLACE_WITH_...` 같은 자리표시자다.
- [ ] **anon(공개) 키와 service_role(비밀) 키의 자리**가 헷갈리지 않게 구분돼 있다. service_role은 프론트엔드 어디에도 없다.
- [ ] `.gitignore`에 `.env`·`.claude/mcp.json`이 들어 있어, 진짜 비밀 파일이 커밋되지 않는다.
- [ ] 배포처럼 **되돌리기 어려운 동작 전에 사람(나)의 승인** 단계가 흐름에 들어가 있다.

> 빠른 자가 점검: 새 채팅을 이 폴더에서 열고 "보안 규칙 알려줘"라고만 쳐 보세요. 내가 CLAUDE.md에 적은 anon/service_role 규칙이 그대로 나오면, 작업환경이 제대로 묶인 것입니다.
