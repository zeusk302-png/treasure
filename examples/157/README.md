# 실습 157 — 응답이 늦거나 끊길 때 타임아웃·재시도 처리 넣기

데이터를 받아오는 일은 **항상 성공하지 않습니다.** 서버가 아주 느릴 수도, 가끔 끊길 수도 있어요.
이번 실습은 앞 실습(156, 로딩·성공·실패 세 가지 상태)에서 **한 걸음 더** 나아가, 두 가지 안전장치를 직접 넣습니다.

1. **① 타임아웃** — 정해진 시간(예: 3초) 안에 응답이 안 오면 **그만 기다리고 포기**합니다.
2. **② 재시도** — 한 번 실패했다고 곧장 에러를 띄우지 않고, **한 번 더 시도**해 봅니다.

> 비유: 전화를 걸었는데 신호만 가고 안 받으면(=느림), 언제까지나 들고 있지 않고 **끊습니다(타임아웃)**.
> 그리고 "한 번 더 걸어볼까?" 하고 **다시 겁니다(재시도)**. 그래도 안 받으면 그때 "연결이 안 되네요"라고 알립니다.

> 디렉터로서 꼭 알아야 할 핵심: AI에게 "데이터 받아와서 보여줘"라고 하면, 대부분 **"서버는 빠르게, 항상 성공한다"**고 가정한 코드를 줍니다.
> 그래서 **타임아웃이 없으면** 서버가 멈췄을 때 화면이 **영원히 '로딩 중…'에 갇힙니다.** (사용자가 가장 많이 떠나는 순간)
> "네트워크는 항상 성공한다는 가정"이 왜 위험한지 직접 눈으로 보고, 안전장치를 챙기는 것이 이번 실습의 한 줄 목표입니다.

> 참고: 진짜로 느린 서버를 구하기는 어렵기 때문에, 이 데모는 **느린/불안정한 서버를 코드로 흉내 냅니다**(`fakeServer`).
> 하지만 **받아오는 쪽 코드(타임아웃·재시도)는 진짜 `fetch`를 쓸 때와 똑같은 구조**입니다. 그대로 가져다 쓸 수 있어요.

## 목표
- **타임아웃**을 `AbortController`로 거는 법을 익힌다.
  - `AbortController`는 진행 중인 요청을 **끊을 수 있는 '리모컨'**이다.
  - `setTimeout`으로 정해진 시간이 지나면 `controller.abort()`(중단!)를 눌러 요청을 끊는다.
  - 시간 안에 응답이 오면 `clearTimeout`으로 타이머를 꺼서, **멀쩡한 요청을 실수로 끊지 않게** 한다. (자주 빠뜨리는 부분)
- **재시도**를 반복문으로 구현한다. 성공하면 **즉시 멈추고**(남은 재시도는 하지 않음), 실패하면 잠깐 쉬었다가 다시 시도한다.
- 실패의 **종류를 구분**한다: 타임아웃(`err.name === "AbortError"`)인지 일반 실패인지에 따라 사용자 안내를 다르게 보여 준다.
- 156에서 배운 **로딩/성공/실패 세 가지 상태 전환(`showState`)과 `try/catch/finally` 구조는 그대로 유지**하면서 그 위에 타임아웃·재시도를 얹는다.

## 따라하는 단계
1. 이 폴더의 `index.html`을 더블클릭 → 브라우저에서 열린다. (이 데모는 가짜 서버를 쓰므로 **인터넷 연결이 필요 없습니다.**)
2. 상황을 **'정상 — 0.4초'**로 두고 **[데이터 받기]**를 누른다 → 로딩이 잠깐 보이고 **초록색 성공 화면**으로 바뀐다.
3. 상황을 **'아주 느림 — 6초'**로 바꾸고(타임아웃은 기본 3초), **[데이터 받기]**를 누른다 → 3초를 기다린 뒤 **타임아웃 안내(빨간 실패 화면)**가 뜬다. (서버는 6초 걸리는데 3초에 끊었기 때문)
4. 같은 '아주 느림' 상태에서 **타임아웃을 8초**로 늘려 다시 눌러 본다 → 이번엔 6초 만에 응답이 와서 **성공**한다. (타임아웃 값에 따라 결과가 달라지는 걸 확인)
5. 상황을 **'불안정 — 첫 시도 실패, 재시도 성공'**으로 바꾸고, **재시도 횟수를 1**로 둔 채 누른다 → 첫 시도가 실패한 뒤 **'1번째 재시도 중…'** 문구가 보이고, 재시도가 **성공**한다.
6. 같은 '불안정' 상태에서 **재시도 횟수를 0**으로 바꿔 누른다 → 재시도를 안 하므로 첫 실패 그대로 **실패 화면**이 뜬다. (재시도가 있고 없고의 차이를 체감)
7. 상황을 **'완전 다운 — 매번 실패'**로 바꾸고 누른다 → 재시도를 다 써도 결국 **실패 화면 + [다시 시도] 버튼**이 뜬다.
8. 카드 아래 **진행 기록(검은 박스)**을 본다 → '첫 시도 시작 → 실패 → 1번째 재시도 시작 → 성공' 같은 **무대 뒤 흐름**이 순서대로 찍힌다.
9. `script.js`를 연다. **두 개의 핵심 도우미**를 찾아본다.
   - `fetchWithTimeout(...)`: `AbortController` + `setTimeout`으로 **한 번의 요청에 시간 제한**을 거는 부분. `finally`의 `clearTimeout`이 안전장치다.
   - `fetchWithRetry(...)`: 반복문으로 **실패하면 한 번 더** 시도하고, 성공하면 `return`으로 즉시 멈추는 부분.
10. AI에게 시켜 보기 (디렉터 연습):
    > "이 `script.js`에서 **재시도 사이의 대기 시간**을 점점 길게(예: 0.6초 → 1.2초 → 2.4초) 늘리는 **지수 백오프(exponential backoff)**로 바꿔줘. 단, 기존의 **타임아웃(`AbortController`)·재시도 구조와 로딩/성공/실패 상태 전환(`showState`)은 그대로 유지**하고, 타임아웃 실패와 일반 실패를 **구분하는 안내**도 그대로 둬."

## 🤖 바이브코딩 프롬프트
이 실습을 AI에게 시켜 만들 때 그대로 복사해 쓸 수 있는 프롬프트입니다. (상황을 구체적으로 줄수록 좋은 코드가 나옵니다.)

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  너는 비전공자에게 친절한 웹 프론트엔드 멘토야. 라이브러리 없이 순수 HTML/CSS/JS 한 세트(index.html, style.css, script.js)로
  '데이터 받아오기' 데모를 만들어 줘. 요구사항:
  - 버튼([데이터 받기]) 하나와, 화면 상태 3개를 만든다: ① 로딩(스피너) ② 성공(초록) ③ 실패(빨강 + [다시 시도] 버튼).
  - 한 번에 한 상태만 보이게 하는 showState(which) 도우미 함수를 둔다.
  - 진짜 느린 서버를 구하기 어려우니, Promise를 돌려주는 가짜 서버 fakeServer(scenario)로 흉내 낸다.
    상황(scenario)은 select로 고르게 한다: 정상(빠름) / 아주 느림(6초) / 불안정(첫 시도 실패) / 완전 다운(매번 실패).
  - 받아오는 흐름은 async/await + try/catch/finally로 짠다(성공 시 성공 화면, 실패 시 실패 화면, finally에서 버튼 다시 활성화).
  - 비전공자가 이해하도록 코드만 주지 말고, 각 줄이 왜 필요한지 한국어 주석으로 설명해 줘. 변수·함수 이름은 영어로.
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  위 데모에 두 가지 안전장치를 추가해 줘. 기존 showState와 try/catch 구조는 그대로 유지하고 그 위에 얹어 줘.
  ① 타임아웃: 정해진 시간(입력칸에서 초 단위로 받기, 기본 3초) 안에 응답이 안 오면 그만 기다리고 포기한다.
     AbortController로 '중단 리모컨'을 만들고, setTimeout으로 시간이 지나면 controller.abort()를 부른다.
     시간 안에 응답이 오면 finally에서 clearTimeout으로 타이머를 꺼서 멀쩡한 요청을 실수로 끊지 않게 한다.
  ② 재시도: 재시도 횟수(입력칸)만큼 반복문으로 '한 번 더' 시도한다. 성공하면 즉시 return으로 멈추고,
     실패하면 잠깐 sleep한 뒤 다시 시도한다. '몇 번째 재시도 중'을 로딩 문구와 진행 기록에 보여 준다.
  실패 종류도 구분해 줘: 타임아웃(err.name === "AbortError")이면 "응답이 너무 늦어…", 그 외엔 일반 실패 안내로.
  추가/수정한 줄마다 '무엇을 하고 왜 그렇게 했는지' 주석을 한국어로 달아 줘.
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  '아주 느림(6초)' 상황에서 타임아웃을 3초로 두고 [데이터 받기]를 눌렀는데, 3초가 지나도 실패 화면으로 안 넘어가고
  계속 로딩에 갇혀 있어. 아래 내 코드와 콘솔에 찍힌 에러를 줄게.
  무엇이 원인인지 1) AbortController/setTimeout이 제대로 연결됐는지 2) abort 신호가 reject로 이어지는지
  3) catch가 AbortError를 잡는지 순서대로 짚어 주고, 비전공자도 알아듣게 한 줄씩 풀어서 설명해 줘.
  [여기에 script.js 코드와 F12 콘솔 에러 메시지를 붙여넣기]
  ```
> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 좋습니다.

## 검증법
- **'아주 느림'(6초) + 타임아웃 3초**로 누르면, **3초쯤 뒤에** 실패 화면으로 넘어가는가? (영원히 로딩에 갇히지 않는가)
- 같은 '아주 느림'에서 **타임아웃을 8초**로 늘리면 이번엔 **성공**하는가? (타임아웃 값이 결과를 바꾸는가)
- **'불안정' + 재시도 1**이면 **자동으로 한 번 더 시도해서 성공**하는가? 진행 기록에 `1번째 재시도 시작`이 찍히는가?
- **'불안정' + 재시도 0**이면 재시도 없이 **바로 실패**하는가? (재시도의 효과가 보이는가)
- **'완전 다운'**은 재시도를 다 쓰고도 **실패 화면**으로 끝나는가? 무한 로딩에 빠지지 않는가?
- 타임아웃으로 실패했을 때 사용자에게 보이는 문구가 **"응답이 너무 늦어…(타임아웃)"**로, 일반 실패와 **다르게** 나오는가?
- `F12`(개발자 도구) → **Console 탭**을 열고 실패를 일으키면, 자세한 원인이 `받아오기 최종 실패: ...`로 **콘솔에만** 찍히는가? (화면에는 친절한 한국어 한 줄만)

## 공개 API와 비밀값 — 보안 메모
이 데모는 **가짜 서버(`fakeServer`)**를 쓰므로 외부 API도, 비밀값도 없습니다. 그래도 진짜 API로 바꿀 때를 위해 원칙을 정리해 둡니다.

- **공개되어도 되는 값**(예: Supabase의 `anon`(공개) 키): 브라우저 코드에 들어가도 괜찮습니다. 단, 데이터 보호는 **RLS(행 수준 보안)**가 책임집니다. (anon 키만 믿고 RLS를 끄면 누구나 데이터를 읽고 쓸 수 있어 위험합니다.)
- **절대 노출하면 안 되는 비밀값**(예: Supabase의 `service_role` 키, 유료 API 키): **브라우저 코드에 절대 넣지 않습니다.** `service_role` 키는 RLS를 **무시하고** 모든 데이터에 접근할 수 있으므로, 오직 서버(또는 n8n 같은 자동화 도구의 자격 증명 저장소)에서만 다룹니다.
- 예제에 적을 때조차 진짜 키 대신 `YOUR_API_KEY` 같은 **자리표시자**만 둡니다.

```js
// 타임아웃·재시도 구조를 '진짜 fetch'로 바꾸면 아래처럼 됩니다.
// 키가 필요한 API라면, 키는 코드에 넣지 말고 서버(또는 n8n)를 거쳐 부릅니다.
const API_KEY = "YOUR_API_KEY"; // ← 자리표시자. 실제 비밀키는 절대 코드에 넣지 않는다.

async function fetchWithTimeout(url, timeoutMs) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);
  try {
    const res = await fetch(url, { signal: controller.signal }); // 가짜 서버 → 진짜 fetch로 교체
    if (!res.ok) throw new Error("상태코드 " + res.status);
    return await res.json();
  } finally {
    clearTimeout(timer); // 성공·실패와 상관없이 타이머는 반드시 끈다.
  }
}
```
