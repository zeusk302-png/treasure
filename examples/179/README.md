# 깨진 배포 일부러 만들고 Instant Rollback으로 즉시 되돌리기

배포를 자주 하다 보면 언젠가 **사이트를 깨뜨리는 변경**을 올리게 됩니다. 이때 가장 빠르고 안전한 대응은 *"코드를 급하게 다시 고치는 것"* 이 아니라, **직전의 멀쩡했던 버전으로 즉시 되돌리는 것** 입니다. Vercel은 배포할 때마다 **과거 버전을 지우지 않고 그대로 보관**하기 때문에, 문제가 생기면 클릭 한 번으로 예전 정상 배포를 다시 라이브(Production)로 올릴 수 있습니다. 이 기능이 **Instant Rollback(즉시 되돌리기)** 입니다.

이 실습의 **결과물(Deliverable)** 은 두 가지입니다: **롤백으로 정상화된 사이트**, 그리고 **복구 절차 메모**(`recovery-notes.md`). 즉 "사이트를 살린 행동"과 "다음에 또 당황하지 않도록 적어 둔 절차서"를 함께 남깁니다.

이 폴더의 `index.html` 은 실제 Vercel 대시보드를 흉내 낸 **연습판(시뮬레이터)** 입니다. 설치 없이 더블클릭으로 열려서, "정상 → 고장난 배포 올리기 → 깨진 화면 확인 → 직전 버전으로 롤백 → 정상 복구" 흐름을 손으로 한 번 따라가 볼 수 있습니다. 그다음 진짜 Vercel에서 똑같이 해 봅니다.

> 비전공자 눈높이 한 줄 요약: 배포는 **사진 여러 장이 쌓인 앨범**과 같습니다. 방금 찍은 사진(새 배포)이 잘못 나왔다면, 사진을 다시 보정하느라 진땀 빼지 말고 **바로 전에 잘 나온 사진을 "대표 사진"으로 도로 바꾸면(롤백)** 됩니다. 잘못 나온 사진의 보정(코드 수정)은 그다음에 천천히 해도 됩니다.

## 목표

- **Instant Rollback이 무엇인지** 이해한다: 코드를 고치지 않고, Vercel이 보관 중인 **과거의 정상 배포**를 다시 Production으로 승격(promote)시켜 즉시 복구하는 기능.
- **"빌드 성공 ≠ 정상 작동"** 을 체감한다: 문법 오류가 아닌 오타(`getElementById` → `getElementByID`)는 빌드를 통과해 `Ready`로 배포되지만, **실행되는 순간 페이지가 멈춘다.** 그래서 `Ready` 배포라도 롤백이 필요한 상황이 생긴다.
- 장애 대응 순서 **"사이트부터 살리고(롤백) → 원인은 그다음에 고친다"** 를 몸에 익힌다. 원인 수정은 새 브랜치 → Preview → PR 검토 후 Merge(실습 176·177)로 안전하게.
- **복구 절차 메모(runbook)** 를 남기는 습관을 들인다. 실제 사고는 당황스러우니, 미리 적어 둔 절차서를 그대로 따라 읽는 것이 가장 안전하다.
- (보안 원칙) 롤백은 **코드 배포 버전만** 되돌린다. 환경변수는 별개이므로, 깨진 배포에 **비밀값(`service_role` 키)** 이 끼어 있었는지는 따로 점검한다. 공개 가능한 값(anon 키·도메인)과 비밀값을 구분하고, 비밀값은 코드 대신 Vercel 환경변수에 두며 `.gitignore`로 `.env`를 막는다(자리표시자는 `.env.example`).

## 따라하는 단계

### A. 연습판으로 흐름 감 잡기 (이 폴더의 화면)

1. `examples/179/` 폴더의 `index.html` 을 브라우저로 엽니다. (더블클릭으로 열립니다.)
2. 맨 위 **"0) 지금 손님에게 보이는 화면"** 액자를 봅니다. 지금은 정상 화면(v3)이 보입니다. 그 아래 상태줄에 *"현재 라이브: v3 (정상)"* 이 떠 있습니다.
3. **"1) 일부러 깨진 변경을 라이브에 올리기"** 의 diff를 읽습니다. `getElementById` 가 `getElementByID`(대문자 D)로 바뀐 **오타 한 줄**임을 확인합니다.
4. 빨간 **"고장난 v4를 Production에 배포하기"** 버튼을 누릅니다. 터미널에 *Build completed — Ready* 가 뜨지만(빌드는 통과), 0번 액자가 **어두운 에러 화면**으로 바뀌고 상태줄이 *"v4 (깨짐)"* 으로 변합니다. → **빌드는 됐는데 사이트가 깨진** 상황입니다.
5. **"2) Vercel 대시보드 — 배포 목록"** 을 봅니다. 맨 위 v4에 빨간 **Current(라이브)** 배지가 붙어 있고, 그 아래 정상 배포 **v3** 에는 **"이 버전으로 롤백"** 버튼이 있습니다.
6. **v3 줄의 "이 버전으로 롤백"** 버튼을 누릅니다. 터미널에 *Production now points to v3* 가 흐르고, 0번 액자가 다시 **정상 화면**으로 복구되며 Current 배지가 v3로 옮겨 갑니다.
7. 맨 아래 **"3) 결과물"** 칸에서 *정상화된 라이브 + (코드 수정 0줄) + 복구 절차 메모* 가 나타나는지 봅니다. **"처음부터 다시"** 로 흐름을 한 번 더 반복해 순서를 몸에 익힙니다.

### B. 진짜 Vercel에서 하기

> 전제: 앞 실습(170)대로 **GitHub 저장소가 Vercel에 연결돼 자동 배포 중**이고, Production이 정상으로 떠 있어야 합니다.

8. (고장 만들기) 로컬에서 JS 한 줄을 일부러 오타로 바꿉니다. 예: `document.getElementById("app")` → `document.getElementByID("app")`. 커밋해 **main에 push** 합니다. (연습이니 실제 서비스 말고 연습용 프로젝트에서 하세요.)
9. Vercel이 자동으로 새 배포를 만들고 **Production으로 승격**합니다. **Production 주소**(`https://<프로젝트>.vercel.app`)를 열어 화면이 깨졌는지(흰 화면/콘솔 에러) 확인합니다.
10. **Vercel 대시보드 → 프로젝트 → Deployments** 로 갑니다. 맨 위가 방금 올린 깨진 배포입니다.
11. **직전의 멀쩡했던 배포 줄**을 찾습니다. 그 줄 오른쪽 **`⋯`(더보기) → `Instant Rollback`**(메뉴에 따라 `Promote to Production`) 을 누릅니다.
12. 확인 창에서 승인하면, **재빌드 없이** 그 과거 배포가 즉시 다시 라이브가 됩니다. (보통 수 초)
13. **Production 주소를 강력 새로고침**(Ctrl+Shift+R)해 **정상 화면이 돌아왔는지** 확인합니다. 이게 첫 번째 결과물입니다.
14. (선택, CLI) 터미널을 쓴다면 같은 동작을 명령으로 할 수 있습니다.
    ```bash
    vercel rollback              # 직전 정상 배포로 되돌리기
    vercel rollback <배포-URL>   # 특정 과거 배포로 되돌리기
    ```
15. (원인 고치기) 사이트가 정상화된 뒤, 8번의 오타를 제대로 고칩니다(`getElementById`). 이번엔 main에 바로 올리지 말고 **새 브랜치 → Preview 확인 → PR 검토 후 Merge**(실습 176·177)로 안전하게 다시 배포합니다.
16. (메모 남기기) `recovery-notes.md` 의 "사고 기록" 표를 **이번 사고 내용으로 채워** 저장합니다. 이게 두 번째 결과물(복구 절차 메모)입니다.

## 검증법

1. **연습판 검증**: "고장난 v4 배포" 버튼을 누르면 0번 액자가 에러 화면으로 바뀌고, v3 줄의 "롤백" 버튼을 누르면 다시 정상 화면으로 돌아오며 Current 배지가 v3로 옮겨 가고 맨 아래 결과 칸이 나타나면 성공입니다.
2. **결과물 1 — 정상화된 사이트**: 진짜 **Production 주소를 새로고침**했을 때, 롤백 전에는 깨진 화면, 롤백 후에는 정상 화면이 보여야 합니다. 이 **"전/후 차이"** 가 핵심 증거입니다.
3. **결과물 2 — 복구 절차 메모**: `recovery-notes.md` 의 사고 기록 표(발생 시각·증상·깨진 배포·원인·복구 방법·재발 방지)가 채워져 있으면 됩니다.
4. **롤백 동작 확인**: Vercel Deployments 목록에서 **과거 배포 줄에 다시 `Current`(또는 Production) 표시**가 붙고, 맨 위 깨진 배포에서는 그 표시가 사라졌는지 확인합니다. (재빌드가 새로 생기지 않고 "라이브 포인터"만 옮겨졌다는 점이 포인트)
5. **흔한 실수 점검**:
   - **롤백했는데 화면이 그대로 깨져 보임** → 브라우저 캐시일 수 있으니 **강력 새로고침**(Ctrl+Shift+R)을 하세요. 그래도 그대로면 Deployments에서 Current가 정말 정상 배포로 옮겨졌는지 다시 봅니다.
   - **롤백 메뉴(⋯)가 안 보임** → 그 줄이 Preview 배포이거나 이미 Current인 경우입니다. **Production 환경의 과거 `Ready` 배포** 줄에서 `⋯`을 누르세요.
   - **롤백만 하고 끝냄 → 다음 배포 때 또 깨짐** → 롤백은 코드를 고치지 않습니다. 정상화 후 반드시 **원인(오타)을 고쳐 다시 배포**(15번)해야 재발하지 않습니다.
   - **잘못해서 또 다른 과거 버전으로 되돌림** → 괜찮습니다. 다시 원하는 배포 줄에서 롤백하면 됩니다. 롤백은 몇 번이고 다시 할 수 있습니다.
6. **보안/노출 점검(필수)**: 롤백은 **코드 배포 버전만** 되돌립니다. 환경변수(Supabase 키 등)는 별개로 관리되므로, 깨진 배포의 코드/diff에 **`service_role` 같은 비밀값이 들어 있지 않았는지** 따로 확인합니다. anon(공개) 키나 도메인은 노출돼도 괜찮지만, secret 키는 RLS를 무시하는 마스터 키라 한 번 올라갔다면 롤백과 무관하게 **키를 폐기·재발급**해야 합니다. 코드에 올리는 환경 견본은 **자리표시자만 든 `.env.example`** 뿐이어야 합니다.
