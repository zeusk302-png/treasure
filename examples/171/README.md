# Vercel Deployments 탭에서 배포 성공/실패 읽는 법 익히기

지난 실습(`examples/170`)에서 "글자 한 줄을 고치고 `git push`만 하면 Vercel이 알아서 다시 배포한다"는 자동배포를 체험했습니다. 그런데 막상 해 보면 **"분명히 고쳐서 올렸는데 사이트에 반영이 안 돼요"** 같은 일이 자주 생깁니다. 이럴 때 당황하지 않으려면 **Vercel의 Deployments(배포 기록) 탭**을 읽을 줄 알아야 합니다. 이번 실습의 목표는 코드를 짜는 게 아니라, **배포가 성공했는지(초록 Ready) 실패했는지(빨강 Error)를 한눈에 읽고, 실패했을 때 어디(빌드 로그)를 봐야 하는지 판단하는 눈**을 기르는 것입니다.

> 비전공자 눈높이 한 줄 요약: **Deployments 탭 = 택배 배송 추적 화면**입니다. 내가 보낸 코드(택배)가 지금 **배송 중(Building)**인지, **배송 완료(Ready, 초록)**인지, **배송 실패(Error, 빨강)**인지를 알려 주는 화면이에요. 실패하면 "왜 실패했는지 적힌 영수증" = **빌드 로그(Build Logs)**를 열어 보면 됩니다.

이번 실습의 결과물은 작동하는 웹페이지가 아니라, **여러분이 직접 Vercel 화면을 보며 채우는 체크리스트 + 스크린샷 메모**입니다. 그 양식이 같은 폴더의 **`CHECKLIST.md`** 파일에 들어 있습니다. 화면을 보면서 빈칸을 채우고, 시키는 지점마다 스크린샷을 찍어 끼워 넣으면 이번 실습이 끝납니다.

## 목표

- Vercel **Deployments** 탭을 찾아 들어가서 **배포 기록(여러 줄)** 을 읽는다.
- 각 배포 줄의 **상태 배지**를 구분한다: **Ready**(초록=성공), **Error**(빨강=실패), **Building/Queued**(진행 중), **Canceled**(취소됨).
- 각 배포 줄에 붙은 **커밋 해시**(예: `a1b2c3d`)와 **커밋 메시지**, **브랜치**(보통 `main`), **언제(시간)** 를 읽어, "어떤 코드가 지금 떠 있는지" 추적한다.
- 어떤 줄이 **Production(실서비스)** 인지, 어떤 줄이 **Preview(미리보기)** 인지 구분한다.
- 배포가 **Error**일 때 그 줄을 눌러 **Build Logs(빌드 로그)** 위치를 찾고, 빨간 에러 메시지가 어디에 나오는지 안다.
- 위 내용을 `CHECKLIST.md`에 적고 **스크린샷 4장**(목록 화면 / Ready 배지 / 커밋 해시 / 빌드 로그)을 남겨, "반영이 안 될 때 어디를 봐야 하나"를 스스로 판단할 수 있게 된다.

## 준비물 (이번 실습 전에 끝나 있어야 함)

1. `examples/169`·`170`을 끝내서, 내 GitHub 저장소가 **Vercel에 연결(Connected)** 되어 있고 `프로젝트이름.vercel.app` 주소가 살아 있어야 합니다. (배포 기록이 최소 한 줄이라도 쌓여 있어야 읽을 게 있습니다.)
2. 가능하면 `examples/170`처럼 **글자 한 줄을 두세 번 고쳐 `git push`** 해서, Deployments에 **줄이 여러 개** 쌓여 있으면 비교하며 읽기 좋습니다.
3. 스크린샷을 저장할 준비. (Windows: `Win + Shift + S`, Mac: `Cmd + Shift + 4`) 찍은 이미지는 이 폴더(`examples/171/`)에 함께 넣으면 됩니다.

> 보안 메모: 이번 실습에는 **비밀값(비밀번호·API 키·토큰)이 하나도 없습니다.** 정적 페이지라 공개돼도 안전합니다. 다만 **스크린샷을 찍을 때 주의**할 점이 있습니다. 나중에 Supabase 등을 붙이면 Vercel **Settings → Environment Variables** 화면에 키가 보이는데, 거기서 **`service_role`(비밀) 키 값이 보이는 화면은 절대 스크린샷으로 남기거나 공유하지 마세요.** 정리하면 — 프런트엔드 코드와 화면에 노출돼도 되는 건 **공개용 `anon` 키**(단, 반드시 **RLS = Row Level Security**를 켜서 테이블 접근을 막아야 함)이고, **`service_role` 키는 RLS를 무시하는 마스터 키**라서 노출되면 데이터 전체가 위험합니다. 그래서 비밀값은 코드가 아니라 **Vercel 환경변수에 `자리표시자`처럼** 넣어 둡니다. (예: `SUPABASE_SERVICE_ROLE_KEY = <여기에_실제_비밀키_절대_공유_금지>`) 이번 실습의 스크린샷 대상은 **Deployments 탭과 빌드 로그**뿐이며, 거기엔 비밀값이 노출되지 않습니다.

## 따라하는 단계

1. 브라우저에서 **https://vercel.com** 에 로그인하고, 대시보드에서 내 프로젝트(예: `my-first-site`)를 클릭합니다.
2. 프로젝트 화면 위쪽 메뉴에서 **Deployments** 탭을 누릅니다. (탭 순서는 보통 *Project · Deployments · Analytics · Settings ...*)
3. **배포 기록 목록**이 위에서 아래로(최신 → 과거) 줄지어 보입니다. 가장 위 줄이 **가장 최근 배포**입니다. → **스크린샷 ①** (목록 전체)을 찍습니다.
4. 맨 윗줄의 **상태 배지** 색과 글자를 확인합니다.
   - 초록 **Ready** = 배포 성공, 지금 인터넷에 떠 있음.
   - 빨강 **Error** = 빌드/배포 실패, 이 버전은 사이트에 반영되지 **않음**.
   - 회색/노랑 **Building**·**Queued** = 아직 작업 중(잠시 기다리면 Ready 또는 Error로 바뀜).
   - **Canceled** = 도중에 취소됨(보통 새 push가 들어와 이전 빌드를 멈춘 경우).
   - → **스크린샷 ②** (상태 배지가 잘 보이게)를 찍습니다.
5. 같은 줄에서 **커밋 정보**를 읽습니다. 보통 한 줄에 **커밋 메시지**(예: "버전 글자 v1→v2 수정") + **짧은 커밋 해시**(예: `a1b2c3d`) + **브랜치 이름**(보통 `main`) + **시간**(예: 3m ago)이 함께 표시됩니다.
   - 커밋 해시는 "이 배포가 정확히 어떤 코드(어떤 commit)로 만들어졌는지"를 가리키는 지문 같은 번호입니다. → **스크린샷 ③** (커밋 해시/메시지 부분)을 찍습니다.
6. **Production / Preview 구분**: `main`(또는 `master`) 브랜치로 올린 배포에는 보통 **Production** 또는 **Current** 같은 표시가 붙고, 이게 진짜 `프로젝트이름.vercel.app` 주소에 반영되는 버전입니다. 다른 브랜치/PR로 올린 건 **Preview**(임시 미리보기 주소)입니다. → "내가 새로고침하는 주소"는 **Production 줄의 상태**를 봐야 한다는 점을 기억하세요.
7. **실패(Error) 줄 깊이 보기** — 빌드 로그 위치 찾기:
   - 목록에서 상태가 **Error**(또는 일부러 만들고 싶다면 다음 단계 참고)인 줄을 **클릭**합니다.
   - 배포 상세 화면이 열리면 **Build Logs**(빌드 로그) 섹션이 보입니다. 여기에 빌드가 한 줄씩 진행된 기록이 나오고, **실패한 지점은 보통 빨간 글씨**로 표시됩니다. (맨 아래쪽의 마지막 빨간 줄이 직접적인 실패 원인일 때가 많습니다.)
   - → **스크린샷 ④** (Build Logs 화면, 빨간 에러 줄이 보이게)를 찍습니다.
8. (선택, 실패를 일부러 만들어 보기) Error 줄이 하나도 없다면, 학습을 위해 일부러 실패를 만들어 봐도 좋습니다. 예: `vercel.json`에 일부러 **잘못된(깨진) JSON**을 넣고 push → 빌드가 Error가 됩니다. 빌드 로그에서 에러 메시지를 확인한 뒤, **반드시 원래대로 되돌려 다시 push**해서 Ready로 복구하세요.
9. 같은 폴더의 **`CHECKLIST.md`** 를 열어, 위에서 읽은 값(상태/커밋 해시/브랜치/시간/Production 여부/로그 위치)을 빈칸에 적고 스크린샷 ①~④를 끼워 넣습니다. → 이 채워진 `CHECKLIST.md`가 이번 실습의 **결과물**입니다.

> 자주 막히는 곳: ① **"반영이 안 돼요"의 1순위 점검** = Deployments 맨 윗줄(Production)이 **Ready**인지 보기. 아직 **Building**이면 그냥 기다리면 되고, **Error**면 반영 자체가 안 된 것이라 빌드 로그를 봐야 합니다. ② **Ready인데도 화면이 그대로**라면 코드가 아니라 **브라우저 캐시** 문제일 수 있습니다 → `Ctrl/Cmd + Shift + R`로 강력 새로고침. ③ **새 배포 줄이 아예 안 생긴다**면, 다른 브랜치에 push했거나(배포 대상은 보통 `main`) Settings → Git에서 저장소 **연결(Connected)** 이 끊긴 경우입니다. ④ **커밋 해시가 내가 방금 올린 것과 다르다**면, push가 다른 브랜치로 갔거나 아직 반영 전입니다.

## 🤖 바이브코딩 프롬프트

이번 실습은 코드를 짜는 게 아니라 **Vercel 화면을 읽고 판단하는 눈**을 기르는 것이라, AI는 "코드 생성기"가 아니라 **옆에서 화면을 같이 읽어 주는 조수**로 씁니다. 아래 프롬프트를 그대로 복사해 쓰되, 빈칸은 내 상황(상태 배지·커밋 해시·에러 메시지 등)으로 바꿔 넣으세요.

- **1단계(뼈대 만들기 — 화면 읽는 법 정리)** 프롬프트:
  ```text
  너는 비전공자에게 배포 도구를 가르치는 친절한 멘토야.
  나는 지금 Vercel 대시보드에서 내 프로젝트의 "Deployments(배포 기록)" 탭을 처음 열어 보는 부트캠프 수료생이야.
  목표: 이 화면의 한 줄(배포 기록 1건)에 보이는 정보가 각각 무엇을 뜻하는지 알고 싶어.
  다음을 표로 정리해 줘:
  1) 상태 배지 종류(Ready / Error / Building / Queued / Canceled) — 각각 색깔과 "지금 사이트에 반영됐는지" 여부
  2) 한 줄에 같이 보이는 항목들(커밋 메시지 / 짧은 커밋 해시 / 브랜치 / 시각 / Production·Preview 표시)이 각각 무슨 의미인지
  제약: 전문용어는 일상 비유(예: 택배 배송 추적)로 풀어서, 한국어로, 비전공자가 한 번에 이해하게 써 줘.
  ```
- **2단계(기능 추가/개선 — 내 화면 진단 시키기)** 프롬프트:
  ```text
  이제 내 실제 화면을 같이 봐 줘. 내 Deployments 맨 윗줄(Production) 정보는 이래:
  - 상태 배지: ______ (예: Ready / Error / Building)
  - 커밋 메시지: ______
  - 짧은 커밋 해시: ______
  - 브랜치: ______
  - 시각: ______
  질문 1) 이 상태면 지금 내 "프로젝트이름.vercel.app" 주소에 내가 올린 코드가 반영돼 있는 거야, 아니야?
  질문 2) 내가 방금 GitHub에 올린 커밋 해시는 ______ 인데, 위 해시와 같은지 비교해서 "내 코드가 떴는지" 판정해 줘.
  질문 3) 다음에 내가 화면에서 추가로 확인하면 좋은 것 1~2가지만 알려 줘.
  ```
- **막혔을 때(디버깅 — 빌드 로그 읽기)** 프롬프트:
  ```text
  내 Vercel 배포가 빨간 "Error"로 떴어. 그 줄을 클릭해서 Build Logs(빌드 로그)를 열었더니
  아래 빨간 줄이 보여. 이게 무슨 뜻이고, 내가 무엇을 고쳐야 하는지 비전공자가 알아듣게 단계별로 설명해 줘.
  그리고 고친 뒤 어떻게 다시 배포해서(보통 git push) Ready로 되돌리는지 순서도 알려 줘.

  --- 빌드 로그 에러 (여기에 빨간 줄을 그대로 붙여넣기) ---
  ______
  ```
> 프롬프트 팁: 답을 받으면 **"왜 그렇게 판단했는지 한 줄씩 풀어서 설명해 줘"**, **"내가 다음에 똑같은 상황을 혼자 점검할 체크 순서로 정리해 줘"**를 덧붙이세요. 화면을 읽는 실습이라 코드 주석 대신 **'판단 근거'를 말로 풀게 시키는 것**이 학습에 가장 좋습니다.

## 검증법

1. **상태 읽기 확인**: Deployments 맨 윗줄의 배지가 **Ready / Error / Building** 중 무엇인지 말로 설명할 수 있고, 그게 "지금 사이트에 반영됐다/안 됐다/작업 중이다" 중 무엇을 뜻하는지 답할 수 있으면 됩니다.
2. **커밋 추적 확인**: 방금 GitHub에서 올린 커밋의 짧은 해시(예: `a1b2c3d`)와 Deployments 맨 윗줄에 표시된 해시가 **같은지** 비교해 봅니다. 같으면 "내가 올린 그 코드가 떠 있다"는 뜻입니다. (GitHub 저장소 → Commits에서도 같은 해시를 볼 수 있습니다.)
3. **Production 구분 확인**: 어느 줄이 `프로젝트이름.vercel.app` 주소에 실제로 반영되는 **Production** 줄인지 가리킬 수 있으면 됩니다.
4. **빌드 로그 위치 확인**: "배포가 Error면 어디를 클릭해 어떤 화면을 봐야 하나?"라는 질문에 **"그 배포 줄을 클릭해서 Build Logs를 본다"** 라고 답하고, 실제로 그 화면을 열어 빨간 에러 줄을 짚을 수 있으면 됩니다.
5. **결과물(체크리스트) 확인**: `CHECKLIST.md`의 빈칸이 모두 채워져 있고 스크린샷 ①~④가 끼워져 있으면, 이번 실습의 결과물이 완성된 것입니다.
6. **(보너스) 판단력 확인**: 누군가 "사이트에 수정이 반영이 안 돼요"라고 물으면, **① Deployments 맨 윗줄 상태가 Ready인지 → ② 커밋 해시가 맞는지 → ③ 강력 새로고침**의 순서로 점검하라고 안내할 수 있으면 이번 실습의 진짜 목표(판단력)를 달성한 것입니다.
