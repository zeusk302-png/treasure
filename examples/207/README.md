# 필수값 검증 후 응답(Respond to Webhook) 돌려주기

앞 실습(205·206)에서는 폼에서 들어온 내용을 슬랙·시트로 흘려보냈습니다. 그런데 한 가지 빠진 게 있었습니다. **들어온 데이터가 제대로 된 값인지 확인하는 일**입니다.

예를 들어 누군가 이메일 칸을 비워둔 채 폼을 보냈다면, 그 문의에는 답장할 주소가 없습니다. 이런 데이터는 받아 봐야 소용이 없으니, **n8n이 받자마자 "이메일이 비었네요"라고 알려주고 거절**하는 게 좋습니다. 반대로 이메일이 잘 들어왔으면 "정상 접수됐습니다"라고 알려줍니다.

이번 실습의 핵심은 두 가지입니다. ① **들어온 값이 비었는지 검사(검증)하는 갈림길(IF 노드)** 을 두는 것, ② 그 결과에 따라 **프런트(폼·앱)에게 성공/실패를 JSON으로 돌려주는 것**(Respond to Webhook)입니다. 폼은 이 응답을 받아 "접수 완료" 또는 "이메일을 입력하세요" 메시지를 사용자에게 보여줄 수 있습니다.

> **이 워크플로우는 노드 4개입니다.**
> `입력 받기 (Webhook)` → `이메일 칸이 비었나? (IF)` → (참이면) `성공 응답` / (거짓이면) `실패 응답`
>
> 비유하자면 우체국 창구입니다. ① 손님이 서류를 낸다(Webhook) → ② 직원이 "필수 칸이 채워졌나?" 확인한다(IF) → ③-A 다 채워졌으면 "접수증"을 준다(성공 응답) / ③-B 빈 칸이 있으면 "이건 못 받아요"라며 돌려준다(실패 응답). IF 노드에서 길이 **위(참/true)와 아래(거짓/false) 두 갈래**로 갈라지는 것이 이번 실습의 새로운 부품입니다.

## 목표

- n8n **IF 노드**로 들어온 값(이메일)이 비었는지 검사하고, 검사 결과에 따라 흐름을 **두 갈래로 분기**하는 법을 익힌다.
- **Respond to Webhook** 노드를 분기마다 하나씩 두어, 성공이면 `ok:true`, 실패면 `ok:false` 처럼 **서로 다른 JSON 응답과 상태 코드(200/400)** 를 프런트에 돌려주는 법을 익힌다.
- 자동화가 데이터를 받아만 두는 게 아니라, **"잘 받았다/못 받았다"를 호출한 쪽에 되돌려주는 왕복(요청→응답)** 구조를 이해한다.

## 따라하는 단계

1. **n8n에 로그인**합니다. (n8n Cloud 또는 직접 설치한 n8n 모두 가능)
2. 화면 오른쪽 위 **`...`(점 3개) → `Import from File`** 을 눌러 이 폴더의 **`workflow.json`** 을 불러옵니다. 노드 4개가 나타나고, `IF` 노드에서 길이 위·아래 두 갈래로 갈라져 있는 게 보입니다.
3. **`입력 받기 (Webhook)` 노드를 더블클릭**합니다. 설정은 이미 되어 있어 바꿀 필요는 없지만, 다음 두 값을 확인하세요.
   - **`HTTP Method`**: `POST` (데이터를 담아 보내는 방식)
   - **`Respond`(응답 방식)**: `Using Respond to Webhook Node` 로 되어 있어야 합니다. 이래야 마지막에 우리가 직접 만든 응답이 돌아갑니다.
   - 노드 위쪽의 **`Test URL`(테스트용 주소)** 을 복사해 둡니다. 검증할 때 이 주소로 데이터를 보낼 겁니다. (예: `https://내n8n주소/webhook-test/validate-email`)
4. **`이메일 칸이 비었나? (IF)` 노드를 클릭**해 봅니다. 여기가 이번 실습의 핵심입니다.
   - 조건은 **"`{{ $json.body.email }}` 값이 비어 있지 않다(`is not empty`)"** 로 설정돼 있습니다.
   - 이 조건이 **참(true)** 이면 흐름이 **위쪽(true) 갈래** 로, **거짓(false)** 이면 **아래쪽(false) 갈래** 로 흘러갑니다. n8n의 IF 노드는 항상 위가 true, 아래가 false 입니다.
5. **`성공 응답 돌려주기 (Respond to Webhook)` 노드를 클릭**합니다. (IF의 true 갈래에 연결돼 있습니다.)
   - `Respond With`: `JSON`, 응답 내용은 `{ ok: true, message: '입력이 정상적으로 접수되었습니다.', email: ... }` 입니다.
   - `Response Code`(상태 코드)는 **`200`**(성공)으로 되어 있습니다.
6. **`실패 응답 돌려주기 (Respond to Webhook)` 노드를 클릭**합니다. (IF의 false 갈래에 연결돼 있습니다.)
   - 응답 내용은 `{ ok: false, message: '이메일은 필수 항목입니다.' }`, `Response Code`는 **`400`**(잘못된 요청)으로 되어 있습니다. 프런트는 이 400을 보고 "실패"로 처리하면 됩니다.
7. 캔버스 아래 **`Listen for test event`(또는 `Test workflow`)** 를 눌러 n8n을 "대기" 상태로 만든 뒤, 다음 검증법으로 실제 데이터를 보내 두 갈래가 모두 작동하는지 확인합니다.

## 검증법

3단계에서 복사한 **Test URL**로 데이터를 두 번 보내, 성공/실패 두 경우가 다르게 응답하는지 확인합니다. (아래 명령어의 `https://YOUR-N8N-HOST/...` 부분은 **본인 n8n의 Test URL로 바꿔** 주세요. 진짜 주소는 비밀이 아니므로 노출돼도 괜찮습니다.)

1. **성공 경우 — 이메일이 채워졌을 때 (200, `ok:true`):**
   ```bash
   curl -X POST "https://YOUR-N8N-HOST/webhook-test/validate-email" \
     -H "Content-Type: application/json" \
     -d '{"email": "hong@example.com"}'
   ```
   이렇게 응답이 돌아오면 성공입니다.
   ```json
   {"ok":true,"message":"입력이 정상적으로 접수되었습니다.","email":"hong@example.com"}
   ```
   n8n 캔버스에서는 `Webhook → IF → 성공 응답` 으로 **위쪽 갈래**에 초록 체크가 떠야 합니다.

2. **실패 경우 — 이메일을 비웠을 때 (400, `ok:false`):**
   ```bash
   curl -i -X POST "https://YOUR-N8N-HOST/webhook-test/validate-email" \
     -H "Content-Type: application/json" \
     -d '{"email": ""}'
   ```
   응답 첫 줄에 `HTTP/.. 400` 이 보이고, 본문이 아래처럼 오면 성공입니다. (`email` 키 자체를 아예 빼고 보내도 동일하게 400이 나와야 정상입니다.)
   ```json
   {"ok":false,"message":"이메일은 필수 항목입니다."}
   ```
   n8n 캔버스에서는 `Webhook → IF → 실패 응답` 으로 **아래쪽 갈래**에 초록 체크가 떠야 합니다.

3. **두 갈래가 모두 도는지 확인(가장 중요):** 1번은 위쪽, 2번은 아래쪽으로 흘러야 합니다. 만약 비운 이메일인데도 `ok:true`가 온다면, IF 노드의 조건이 잘못된 것입니다. 조건이 `email` 이 **`is not empty`** 인지 다시 확인하세요.

> **참고:** Test URL(`/webhook-test/...`)은 `Listen for test event`를 누른 뒤 **한 번만** 받습니다. 다시 보내려면 버튼을 또 눌러야 합니다. 실제 운영에서 계속 받으려면 워크플로우를 **`Active`(활성)** 로 켜고, 주소의 `webhook-test` 를 `webhook` 으로 바꾼 **Production URL** 을 쓰면 됩니다.

## 핵심만 짚기 (디렉터 관점)

- **검증은 가능한 한 입구에서.** 잘못된 데이터를 받아 슬랙·시트로 흘려보낸 뒤 치우는 것보다, IF 노드로 입구에서 한 번 걸러주는 게 훨씬 깔끔합니다. 칸이 여러 개라면 IF 조건에 줄을 추가해 한꺼번에 검사할 수 있습니다.
- **응답은 약속(계약)입니다.** 프런트와 백엔드(n8n)는 "성공이면 `ok:true`, 실패면 `ok:false` 와 400" 처럼 **모양을 미리 약속**해 둡니다. 이 약속이 곧 API입니다. 그래서 성공/실패 응답의 키 이름(`ok`, `message`)을 일관되게 맞추는 게 중요합니다.
- **IF는 갈림길 부품입니다.** 이번엔 이메일 유무로 갈랐지만, "금액이 1만원 넘으면", "관리자가 보냈으면" 같은 조건으로도 똑같이 분기할 수 있습니다.

## 보안 — 어떤 값이 비밀이고, 어디에 넣나

이 실습에는 외부 서비스 토큰(슬랙·시트 등)이 없어서 **금고(`Credentials`)에 넣을 비밀값은 없습니다.** 하지만 입력을 외부에서 받는 워크플로우이므로 짚어둘 점이 있습니다.

- **공개돼도 되는 값:** Webhook 주소(`/webhook/validate-email`), 응답 JSON의 문구. 주소가 알려져도 누군가 데이터를 보내볼 수 있을 뿐, IF 노드가 형식을 검사하므로 잘못된 값은 400으로 거절됩니다. (Supabase로 치면 브라우저에 노출돼도 되는 **`anon`(공개) 키** 와 같은 성격입니다.)
- **새면 안 되는 비밀값(이 워크플로우엔 없지만 원칙):** 만약 여기에 슬랙 토큰이나 DB 키를 붙인다면, 그 값은 **절대 노드 파라미터나 `workflow.json`에 직접 적지 말고** n8n의 **`Credentials`(자격증명) 금고** 에만 저장해야 합니다. 이런 비밀값은 Supabase의 **`service_role`(비밀) 키** 처럼 다뤄야 하며, DB에 직접 쓰는 자동화라면 테이블에 **RLS(Row Level Security)** 를 켜서 키가 새더라도 함부로 읽고 쓰지 못하게 막아 둬야 합니다.

> **그래서 이 파일에는 비밀값이 하나도 들어 있지 않습니다.** 입력 검증과 응답 반환만 하기 때문입니다. 나중에 이 워크플로우에 슬랙·시트를 붙일 때, 그 토큰은 반드시 금고로 가야 한다는 점만 기억하세요.

> **한 줄 원칙:** 입력은 입구(IF)에서 검증하고, 비밀값(토큰·키)은 노드가 아니라 `Credentials` 금고에. 응답의 모양은 프런트와 미리 약속한다.
