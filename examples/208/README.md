# IF 노드로 조건 분기 처리하기 (긴급이면 슬랙, 아니면 메일)

앞 실습(207)에서는 IF 노드로 "이메일 칸이 비었나?"를 검사해 받을지 말지를 갈랐습니다. 이번에는 한 걸음 더 나아가, **들어온 데이터의 내용에 따라 처리하는 길 자체를 다르게** 만들어 봅니다.

상황은 이렇습니다. 문의 폼에 "문의 유형"을 고르는 칸이 있다고 합시다. 누군가 **`긴급`** 으로 보냈다면 담당자가 바로 봐야 하니 **슬랙으로 즉시 알림**을 쏘고, 그냥 `일반` 문의라면 급하지 않으니 **담당자 메일함으로 조용히 전달**하면 충분합니다. 같은 폼으로 들어온 문의라도 **내용에 따라 알림 경로가 갈라지는 것**, 이것이 이번 실습의 핵심입니다.

> **이 워크플로우는 노드 5개입니다.**
> `문의 받기 (Webhook)` → `문의 내용 정리하기 (Set)` → `문의 유형이 긴급인가? (IF)` → (참이면) `긴급: 슬랙 알림` / (거짓이면) `일반: 메일 전달`
>
> 비유하자면 우편물 분류대입니다. ① 우편물이 들어온다(Webhook) → ② 보낸 사람·내용을 정리한다(Set) → ③ "이거 긴급 표시 붙었나?"를 확인한다(IF) → ③-A 긴급이면 **빨간 바구니(슬랙)** 로 / ③-B 아니면 **일반 바구니(메일)** 로 넣는다. IF 노드에서 길이 **위(참/true)와 아래(거짓/false) 두 갈래**로 갈라지고, 갈래마다 **서로 다른 부품(슬랙·메일)** 이 붙는 것이 이번 실습의 새로운 점입니다.

## 목표

- n8n **IF 노드**로 들어온 값(문의 유형)이 특정 값(`긴급`)과 같은지 검사하고, 결과에 따라 흐름을 **두 갈래로 분기**하는 법을 익힌다.
- 분기된 **각 갈래에 서로 다른 동작**(true → 슬랙 알림, false → 메일 전달)을 연결해, 워크플로우가 상황에 맞게 다르게 행동하도록 **가지치기**하는 법을 익힌다.
- IF 노드는 항상 **위쪽 출력이 true, 아래쪽 출력이 false** 라는 규칙을 이해한다.

## 따라하는 단계

1. **n8n에 로그인**합니다. (n8n Cloud 또는 직접 설치한 n8n 모두 가능)
2. 화면 오른쪽 위 **`...`(점 3개) → `Import from File`** 을 눌러 이 폴더의 **`workflow.json`** 을 불러옵니다. 노드 5개가 나타나고, `IF` 노드에서 길이 위·아래 두 갈래로 갈라져 위쪽은 슬랙, 아래쪽은 메일로 이어진 게 보입니다.
3. **`문의 받기 (Webhook)` 노드를 더블클릭**합니다. `HTTP Method`가 `POST`로 되어 있는지만 확인하세요. 노드 위쪽의 **`Test URL`(테스트용 주소)** 을 복사해 둡니다. (예: `https://내n8n주소/webhook-test/inquiry-route`)
4. **`문의 내용 정리하기 (Set)` 노드를 클릭**해 봅니다. 들어온 데이터에서 `이름·이메일·문의유형·메시지·받은시각`을 꺼내 깔끔한 형태로 정리합니다. 칸이 비어 있으면 `'이름 없음'`, 유형이 없으면 `'일반'` 처럼 기본값이 들어가도록 해 두었습니다.
5. **`문의 유형이 긴급인가? (IF)` 노드를 클릭**합니다. 여기가 이번 실습의 핵심입니다.
   - 조건은 **"`{{ $json.문의유형 }}` 값이 `긴급` 과 같다(`is equal to`)"** 로 설정돼 있습니다.
   - 이 조건이 **참(true)** 이면 흐름이 **위쪽(true) 갈래**(슬랙)로, **거짓(false)** 이면 **아래쪽(false) 갈래**(메일)로 흘러갑니다. n8n의 IF 노드는 **항상 위가 true, 아래가 false** 입니다.
6. **`긴급: 슬랙으로 즉시 알림 (Slack)` 노드를 클릭**합니다. (IF의 true 갈래에 연결돼 있습니다.)
   - 빨간 사이렌(:rotating_light:) 이모지와 함께 문의 내용을 슬랙 채널로 보내도록 문구가 준비돼 있습니다.
   - 동작시키려면 **자격증명(Slack 봇 토큰)** 과 **채널 ID** 가 필요합니다. (아래 "보안" 항목 참고. 지금 당장 연결이 어렵다면 7번처럼 이 노드를 잠시 꺼두고 분기만 확인해도 됩니다.)
7. **`일반: 담당자 메일로 전달 (Gmail)` 노드를 클릭**합니다. (IF의 false 갈래에 연결돼 있습니다.)
   - 받는 사람이 `support@example.com` 으로 되어 있습니다. **본인이 받을 메일 주소로 바꿔** 주세요.
   - 동작시키려면 **Gmail 자격증명(OAuth2)** 연결이 필요합니다.
   - (자격증명 연결 전에 분기만 먼저 확인하고 싶다면, 슬랙·메일 노드를 각각 클릭하고 키보드 `D` 를 눌러 **잠시 비활성화(Deactivate)** 한 뒤 8번을 실행하세요. IF가 어느 갈래로 가는지 색으로 바로 보입니다.)
8. 캔버스 아래 **`Listen for test event`(또는 `Test workflow`)** 를 눌러 n8n을 "대기" 상태로 만든 뒤, 다음 검증법으로 데이터를 두 번 보내 두 갈래가 모두 작동하는지 확인합니다.

## 검증법

3단계에서 복사한 **Test URL**로 데이터를 두 번 보내, 긴급/일반 두 경우가 서로 다른 갈래로 흐르는지 확인합니다. (아래 명령어의 `https://YOUR-N8N-HOST/...` 부분은 **본인 n8n의 Test URL로 바꿔** 주세요. n8n 주소 자체는 비밀이 아니므로 노출돼도 괜찮습니다.)

1. **긴급 경우 — 위쪽(true) 갈래, 슬랙으로:**
   ```bash
   curl -X POST "https://YOUR-N8N-HOST/webhook-test/inquiry-route" \
     -H "Content-Type: application/json" \
     -d '{"name":"홍길동","email":"hong@example.com","type":"긴급","message":"서버가 멈췄어요!"}'
   ```
   n8n 캔버스에서 `Webhook → Set → IF → 슬랙` 으로 **위쪽 갈래**에 초록 체크가 떠야 합니다. (슬랙을 연결했다면 채널에 빨간 사이렌 알림이 도착합니다.)

2. **일반 경우 — 아래쪽(false) 갈래, 메일로:**
   ```bash
   curl -X POST "https://YOUR-N8N-HOST/webhook-test/inquiry-route" \
     -H "Content-Type: application/json" \
     -d '{"name":"김영희","email":"kim@example.com","type":"일반","message":"이용 시간이 궁금합니다."}'
   ```
   이번엔 `Webhook → Set → IF → 메일` 으로 **아래쪽 갈래**에 초록 체크가 떠야 합니다. (Gmail을 연결했다면 7번에서 지정한 주소로 메일이 도착합니다.)

3. **두 갈래가 갈리는지 확인(가장 중요):** 1번은 위쪽(슬랙), 2번은 아래쪽(메일)으로 흘러야 합니다. 만약 `긴급` 인데도 메일 쪽으로 간다면, IF 노드의 조건을 다시 보세요. **왼쪽 값이 `{{ $json.문의유형 }}`, 비교 연산이 `is equal to`, 오른쪽 값이 `긴급`** 인지 확인하면 됩니다. (`type` 키를 아예 빼고 보내면 Set 노드가 `'일반'` 으로 채우므로 아래쪽 갈래로 가는 게 정상입니다.)

> **참고:** Test URL(`/webhook-test/...`)은 `Listen for test event`를 누른 뒤 **한 번만** 받습니다. 다시 보내려면 버튼을 또 눌러야 합니다. 실제 운영에서 계속 받으려면 워크플로우를 **`Active`(활성)** 로 켜고, 주소의 `webhook-test` 를 `webhook` 으로 바꾼 **Production URL** 을 쓰면 됩니다.

## 핵심만 짚기 (디렉터 관점)

- **IF는 "길을 나누는" 부품입니다.** 207에서는 받을지 말지를 갈랐고, 이번엔 어느 부서로 보낼지를 갈랐습니다. 조건만 바꾸면 "금액이 1만원 넘으면 결제팀, 아니면 자동 처리", "관리자면 전체 권한, 아니면 읽기만" 처럼 무한히 응용됩니다.
- **위가 true, 아래가 false.** 이 규칙만 외우면 갈래가 헷갈리지 않습니다. 갈래마다 원하는 부품(슬랙·메일·시트·DB 등)을 자유롭게 붙이면 됩니다.
- **갈래가 셋 이상이면?** IF 대신 **Switch 노드**를 쓰면 `긴급/보통/스팸` 처럼 여러 갈래로 한 번에 나눌 수 있습니다. IF는 둘로 나누는 가장 기본 부품이라고 기억하세요.

## 보안 — 어떤 값이 비밀이고, 어디에 넣나

이번 워크플로우는 외부 서비스(슬랙·Gmail) 두 개를 붙이므로 **비밀값을 다루는 첫 자동화**입니다. 원칙을 정확히 지켜야 합니다.

- **공개돼도 되는 값:** Webhook 주소(`/webhook/inquiry-route`), 슬랙 채널 ID(`C0000000000`), 받는 메일 주소. 이런 값은 누가 알아도 그 자체로는 피해가 없습니다. (Supabase로 치면 브라우저에 노출돼도 되는 **`anon`(공개) 키** 와 같은 성격입니다.)
- **절대 새면 안 되는 비밀값:** **슬랙 봇 토큰**과 **Gmail OAuth2 자격증명**. 이 값을 가진 사람은 당신 이름으로 메시지를 보내고 메일을 읽을 수 있습니다. 그래서 이 `workflow.json` 안에는 **진짜 토큰이 한 글자도 들어 있지 않습니다.** 대신 자리표시자만 적어 두었습니다.
  - 슬랙: `"id": "REPLACE_WITH_YOUR_SLACK_CREDENTIAL_ID"`
  - Gmail: `"id": "REPLACE_WITH_YOUR_GMAIL_CREDENTIAL_ID"`
- **그럼 진짜 키는 어디에 넣나?** n8n 화면의 **`Credentials`(자격증명) 금고** 에만 넣습니다. 슬랙 노드를 열고 `Credential to connect with → + Create New` 로 봇 토큰을, Gmail 노드에서 OAuth2 로그인을 한 번 해 두면, 그 비밀값은 금고에 안전하게 저장되고 워크플로우 파일에는 **금고를 가리키는 id만** 남습니다. 그래서 `workflow.json` 을 다른 사람과 공유해도 비밀이 새지 않습니다.

> **service_role 와 같은 급으로 다루세요.** 슬랙 봇 토큰·Gmail 자격증명은 Supabase의 **`service_role`(비밀) 키** 처럼 "이게 새면 끝장"인 값입니다. 코드·메시지·깃 저장소에 절대 붙여넣지 말고, 오직 `Credentials` 금고에만 두세요. 만약 이 워크플로우가 나중에 DB(Supabase 테이블)에 직접 쓰게 된다면, 그 테이블에는 **RLS(Row Level Security)** 를 켜서 키가 새더라도 함부로 읽고 쓰지 못하게 막아 두어야 합니다.

> **한 줄 원칙:** 공개 값(주소·채널ID)은 파일에 적어도 되지만, 비밀값(토큰·자격증명)은 노드가 아니라 `Credentials` 금고에. 파일에는 자리표시자만 남긴다.
