# 실습 142 — 다른 사람 데이터가 진짜 안 보이는지 두 계정으로 검증하기

실습 141에서 만든 **'비밀 메모장'(memos 테이블 + RLS)** 이 정말로 안전한지, 이번에는 **공격자 입장**이 되어 직접 뚫어 봅니다. 계정 A로 만든 메모가 계정 B에서 안 보이는지, 그리고 **화면(UI)을 거치지 않고 코드로 직접** 요청해도 막히는지를 확인합니다.

핵심 질문 한 줄: **"화면에 안 보이는 것"과 "진짜로 못 가져오는 것"은 다릅니다.** 버튼을 숨기는 건 'UI 가짜 보안'입니다. 공격자는 버튼 대신 개발자도구 콘솔에서 데이터베이스에 직접 요청할 수 있으니까요. **진짜 보안은 데이터베이스(RLS)가 막아 주는 것**입니다. 이번 실습은 그 차이를 손으로 때려 보며 검증합니다.

이 폴더의 결과물은 **두 계정으로 직접 공격해 보는 검증 도구 `verify.html`** 과 **단계별로 체크하는 `checklist.md`** 입니다.

## 목표
- 같은 테이블을 공유하는데도 **A의 메모가 B에게 안 보이는지**를 두 계정으로 교차 확인한다.
- **UI를 우회한 직접 시도**(필터 없이 전부 요청 / 남의 id로 조회·삽입 / 남의 행 삭제)가 전부 막히는지 검증한다.
- **'UI 가짜 보안'(버튼 숨기기) vs 'DB 진짜 보안'(RLS)** 의 차이를 체감한다.
- anon(공개) 키가 노출돼도 안전한 이유가 **"키를 숨겨서가 아니라 RLS가 행을 지켜서"** 임을 검증으로 납득한다.
- `service_role`(비밀) 키를 브라우저에 두면 이 모든 방어가 **통째로 뚫린다**는 원칙을 안다.

## 따라하는 단계
1. **검증 대상 준비.** 실습 141을 이미 끝냈다면 `memos` 테이블과 RLS 정책이 그대로 있으니 그걸 씁니다. 안 했다면 Supabase 대시보드 → **SQL Editor**에 이 폴더의 `schema.sql`을 붙여넣고 **[Run]** 하세요.
2. **anon 키 넣기.** 대시보드 → **Settings → API**에서 `Project URL`과 `anon`(publishable) 키를 복사해 `supabase.js`의 두 값(`SUPABASE_URL`, `SUPABASE_ANON_KEY`)을 바꿉니다. 코드의 `https://여기에-...`, `sb_publishable_...`는 **자리표시자**입니다. (※ `service_role` 키는 절대 넣지 마세요.)
3. **테스트 편의 설정(선택).** 대시보드 → Authentication → Providers → Email에서 "Confirm email"을 잠깐 꺼두면 가입 즉시 로그인돼 검증이 빠릅니다. (실서비스에선 켜는 게 맞습니다.)
4. **`verify.html`을 로컬 서버로 엽니다.** (VS Code Live Server 등으로 `http://`로 열기 — 콘솔 실험까지 일관되게 하려고 권장합니다.)
5. **계정 A 준비:** 회원가입/로그인 → 2단계의 "내 메모 1개 추가"로 메모를 2~3개 만듭니다. 결과 로그 맨 위에 표시되는 **A의 `user_id`를 복사**해 둡니다(공격에 씁니다).
6. **계정 B 준비:** 로그아웃 → 다른 계정으로 회원가입/로그인 → 메모를 1~2개 만듭니다.
7. **화면 격리 확인:** B로 로그인한 채 "내 메모 목록 보기" → **A의 메모가 하나도 안 보이는지** 확인합니다.
8. **직접 공격(B 상태):** 3단계 카드에서 5번에 복사한 **A의 user_id를 ②·③ 칸에 붙여넣고** 버튼들을 눌러 봅니다. 결과 로그가 전부 **초록(안전)** 으로 떠야 합니다.
9. **콘솔 공격:** 개발자도구 → Console에서 `await db.from('memos').select('*')` → 내 줄만 옴. 로그아웃 후 같은 명령 → **빈 배열 `[]`**.
10. **위험 체험:** SQL Editor에서 `alter table memos disable row level security;` → 새로고침 후 ① 시도 → 이번엔 **남의 메모까지 새며 빨강(위험)** 표시. 확인 즉시 `alter table memos enable row level security;` 로 **다시 켭니다.**
11. `checklist.md`를 위에서부터 하나씩 체크하며 빠진 검증이 없는지 확인합니다.

## 검증법
- **화면(UI):** B로 로그인했을 때 A의 메모가 **0개**로 안 보이는가? 다시 A로 오면 A 것만 보이는가?
- **한 테이블 증거:** 대시보드 Table Editor → `memos`에 A·B의 줄이 **함께** 들어 있는가? (화면에서만 갈라 보인 것)
- **① 전부 훔쳐보기:** 필터 없이 요청해도 **내 줄만** 돌아오는가? (도구가 자동으로 "남의 줄 0개"를 판정해 초록 표시)
- **② 남의 id 조회:** 남의 user_id로 콕 집어 요청해도 **빈 배열 `[]`** 인가?
- **③ 남 이름으로 작성:** 남의 user_id를 적어 넣으면 **`with check` 정책에 막혀 에러**가 나는가?
- **④ 남의 메모 삭제:** 남의 행 id로 삭제 시도 시 **0줄 삭제**(아무 일도 안 일어남)인가?
- **콘솔:** 로그인 시 내 줄만, **로그아웃 시 `[]`** 가 오는가?
- **RLS 끄기 대조:** RLS를 끄면 ①이 **빨강(위험)** 으로 바뀌고, 다시 켜면 초록으로 돌아오는가? → "막아 주는 주체는 화면이 아니라 RLS"임이 증명됨.

## ⚠️ 보안 메모 — anon(공개) vs service_role(비밀) + RLS
- 브라우저(`supabase.js`)에 넣는 건 **anon(publishable) 키 하나뿐**입니다. anon은 "공개돼도 되는 **출입증**"이라 GitHub·브라우저에 있어도 됩니다. (코드의 `sb_publishable_...`는 자리표시자 — 내 값으로 바꿔 쓰세요.)
- anon 키가 공개돼도 안전한 **진짜 이유는 키를 숨겨서가 아니라 RLS** 때문입니다. 이번 검증이 그걸 증명합니다: 공개 키를 들고 콘솔에서 별짓을 다 해도, 정책이 허락한 **내 행** 말고는 한 줄도 못 가져갑니다.
- `service_role`(secret) 키는 모든 **RLS를 통째로 우회**하는 마스터키입니다. 이걸 브라우저에 두면 위 ①~④ 공격이 **전부 성공**합니다(누구나 모두의 메모를 읽고 지움). **절대 프론트엔드·GitHub에 두지 말고**, 서버(n8n·엣지 함수)에서 **환경변수**로만 쓰세요. 브라우저에 들어가는 비밀값은 언제나 자리표시자로 둡니다.
- 기억할 한 쌍: **인증(로그인) = '누구인지' 확인** / **인가(RLS) = '그 사람이 어떤 행을 봐도 되는지' 결정**. 이번 실습은 그중 **인가**가 진짜 작동하는지 검사하는 것입니다.

## 이 폴더의 파일
- `verify.html` — 두 계정 교차 + 직접 공격을 눌러 보는 검증 도구(결과를 초록/빨강으로 자동 판정)
- `style.css` / `script.js` — 위 페이지의 스타일과 로직
- `supabase.js` — anon 키만 넣는 공통 설정(자리표시자)
- `schema.sql` — 검증 대상 테이블 + RLS 정책(141과 동일)
- `checklist.md` — 단계별 검증 체크리스트(결과물)
