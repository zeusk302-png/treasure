# RLS 검증 체크리스트 — 두 계정 교차 테스트

실습 141의 '비밀 메모장(memos 테이블 + RLS)'이 **진짜로** 남의 데이터를 막는지 확인하는 체크리스트입니다.
계정 두 개(A, B)를 준비하세요. 예: `a@test.com`, `b@test.com` (둘 다 비밀번호는 자리표시자 — 본인이 정한 값).

> 통과 기준: 아래 항목이 **전부 체크**되면 "UI 가짜 보안"이 아니라 "DB 진짜 보안(RLS)"이 작동하는 것입니다.

## 준비
- [ ] Supabase 대시보드 → SQL Editor에 `schema.sql` 실행 (또는 141에서 이미 완료)
- [ ] `supabase.js`의 `SUPABASE_URL` / `SUPABASE_ANON_KEY`를 **anon(공개) 키**로 채움 (service_role 절대 금지)
- [ ] 로컬 서버(Live Server 등)로 `verify.html`을 `http://`로 열기
- [ ] 계정 A로 가입/로그인 → 메모 2~3개 추가
- [ ] 로그아웃 → 계정 B로 가입/로그인 → 메모 1~2개 추가

## 1) 화면(UI) 격리 — 눈으로 보는 검증
- [ ] B로 로그인했을 때 화면(2단계 "내 메모 목록 보기")에 **A의 메모가 하나도 안 보인다**
- [ ] 다시 A로 로그인하면 **A의 메모만** 보이고 B의 메모는 안 보인다
- [ ] 대시보드 → Table Editor → `memos`에는 **A와 B의 줄이 함께** 들어 있다 (한 테이블을 공유한다는 증거)

## 2) 직접 시도(UI 우회) — RLS가 진짜로 막는지 검증
> 계정 A의 `user_id`를 복사해 둔 뒤, **B로 로그인**한 상태에서 시도하세요.
> (A의 user_id는 A로 로그인했을 때 결과 로그 맨 위에 표시됩니다. 복사해 두세요.)

- [ ] **① 전부 훔쳐보기**: "전부 가져오기 시도" → 결과 로그가 **초록(안전)**, 내 메모 개수만 돌아온다 (남의 메모 0개)
- [ ] **② 특정 id로 훔쳐보기**: A의 user_id를 칸에 붙여넣고 시도 → **빈 배열 `[]`**, 초록(안전)
- [ ] **③ 남 이름으로 글 심기**: A의 user_id를 붙여넣고 작성 시도 → **with check 정책에 막혀 에러**, 초록(안전)
- [ ] **④ 남의 메모 지우기**: A의 메모 행 id(숫자)를 넣고 삭제 시도 → **0줄 삭제**, 초록(안전)

## 3) 콘솔 직접 공격 (개발자도구 → Console)
> 공격자는 우리 버튼을 안 쓰고 콘솔에서 직접 칠 수 있습니다. 그래도 막혀야 합니다.

- [ ] B로 로그인한 채 `await db.from('memos').select('*')` → **B의 줄만** 온다
- [ ] **로그아웃** 후 같은 명령 → **빈 배열 `[]`** (익명에게는 통과할 정책이 없음)
- [ ] `await db.from('memos').insert({ content:'몰래', user_id:'<A의 id>' })` → **에러**(with check)

## 4) RLS 끄기 위험 체험 (반드시 되돌리기)
- [ ] SQL Editor에서 `alter table memos disable row level security;` 실행
- [ ] `verify.html` 새로고침 후 ① 시도 → 이번엔 **남의 메모까지 다 보임 = 빨강(위험)** 으로 표시되는 것 확인
- [ ] **즉시** `alter table memos enable row level security;` 로 다시 켜고, ① 시도가 다시 초록(안전)으로 돌아오는지 확인

## 결론(스스로 답해보기)
- [ ] anon(공개) 키가 노출돼도 안전한 이유를 "키를 숨겨서가 아니라 **RLS가 행을 지켜서**"라고 설명할 수 있다
- [ ] `service_role`(비밀) 키를 브라우저에 두면 위 모든 방어가 **통째로 뚫린다**는 걸 안다
- [ ] **인증(로그인 = 누구냐)** 과 **인가(RLS = 그가 뭘 봐도 되냐)** 가 다른 단계임을 구분할 수 있다
