# 지시 프롬프트 — Claude에게 "비밀키 점검 → 커밋 → push"를 시키기

아래 프롬프트를 **그대로 복사**해서 Claude(또는 쓰는 AI)에 붙여넣으세요.
핵심은 AI가 **혼자 다 처리하지 않고**, 위험한 단계(비밀키 점검) 결과를 **먼저 보고**한 뒤,
**내가 "진행해"라고 승인했을 때만** 커밋·push로 넘어가게 만드는 것입니다.

> 이 실습에는 새로 짤 코드가 거의 없습니다. **잘 지시하는 글쓰기**가 곧 실습입니다.
> 실제 비밀키, 토큰, 배포 URL은 **절대 프롬프트에 적지 마세요.** 들어갈 자리는 `<...>` 자리표시자로 둡니다.

---

## 1단계 — 지시 프롬프트 (복사해서 사용)

```text
너는 내 배포 보조 디렉티(deploy 스킬 역할)야. 나는 웹 개발을 막 배우는 비전공자고,
HTML/CSS/JS로 만든 사이트를 GitHub에 push하면 Vercel이 자동으로 배포하는 구조를 쓰고 있어.

지금 작업 폴더에는 내가 방금 수정한 파일들이 있어. 아래 순서를 "이 순서 그대로" 지켜줘.

[1] 비밀키 점검 (가장 먼저, 그리고 이 단계 결과를 먼저 보고만 해)
    - git에 올라갈 변경분(staged + unstaged)에 절대 노출되면 안 되는 값이 섞여 있는지 점검해.
    - 점검 대상 예: Supabase service_role(비밀) 키, 각종 API secret, 비밀번호,
      .env 파일 자체, 토큰처럼 보이는 긴 문자열.
    - 참고: Supabase의 anon(공개) 키는 프론트엔드에 노출돼도 되는 키라 막지 않아도 돼.
      하지만 service_role(비밀) 키는 코드/커밋에 절대 들어가면 안 돼.
    - 점검 결과를 표로 보고해: (파일 / 의심 구간 / 위험도 / 권장 조치).
      위험한 게 있으면 "여기서 멈춤"이라고 말하고, .gitignore와 환경변수로 옮기는 법을 알려줘.
    - 위험한 게 하나도 없으면 "비밀키 점검 통과"라고만 말해.

[2] 커밋 메시지 초안 (아직 커밋하지 마, 초안만 보고해)
    - 변경 내용을 의미 단위로 묶어서 Conventional Commits 형식의 커밋 메시지 초안을 제안해.
      형식: type(scope): 한 줄 요약   (예: feat(hero): 첫 화면 소개 문구 교체)
      쓸 수 있는 type: feat, fix, docs, style, refactor, chore.
    - 한 줄 요약은 한국어로, 50자 이내, 명령형 어미(~추가/~수정/~교체)로.
    - 필요하면 본문에 "무엇을 왜 바꿨는지" 1~2줄을 덧붙여.

[3] 내 승인 대기
    - [1] 점검 결과와 [2] 커밋 초안을 보여준 뒤, "이대로 진행할까요?"라고 묻고 멈춰.
    - 내가 "진행해"라고 답하기 전에는 git add / commit / push를 절대 실행하지 마.

[4] 승인 후 실행 (내가 "진행해"라고 한 다음에만)
    - 실제로 실행할 git 명령을 순서대로 보여주고 실행해:
      git add <변경파일들>
      git commit -m "<승인된 커밋 메시지>"
      git push
    - 푸시가 끝나면 "방금 push로 Vercel 자동 배포가 시작됐다"는 점과,
      내가 어디서 결과를 확인해야 하는지(아래 [5])를 알려줘.

[5] 배포 보고 (마지막)
    - 아래 항목을 채워서 한눈에 보이게 보고해. 실제 값은 내가 확인해서 채울 자리표시자로 둬도 돼.
      · 커밋 메시지:
      · 커밋 해시(짧은): <예: a1b2c3d>
      · push 대상 브랜치: <예: main>
      · Vercel Production URL: <YOUR_PROJECT.vercel.app>
      · 배포 상태 확인 위치: Vercel → 프로젝트 → Deployments 맨 윗줄(Ready/Building/Error)
    - 마지막으로, 배포가 Error로 뜰 경우 어디를 봐야 하는지(Build Logs) 한 줄로 안내해.

규칙:
- 단계를 건너뛰지 마. 특히 [1] 점검과 [3] 승인 대기는 반드시 지켜.
- 비밀값이 의심되면 무조건 멈추고 나에게 물어봐.
- 모든 답변은 한국어로, 비전공자도 알아듣게.
```

## 2단계 — AI가 곧바로 커밋하려 하면 (멈춤 한 마디)

```text
잠깐, 아직 "진행해"라고 안 했어. 먼저 [1] 비밀키 점검 결과와
[2] 커밋 메시지 초안만 보여줘. 커밋·push는 내 승인 다음이야.
```

## 3단계 — 승인 한 마디 (점검·초안이 마음에 들 때)

```text
좋아, 점검 통과했고 커밋 메시지도 그대로 좋아. 진행해.
실행할 git 명령을 보여주고 push까지 한 뒤 [5] 배포 보고를 채워줘.
```

## 자리표시자 안내 (절대 실제 값 금지)

| 자리표시자 | 의미 | 예시(형식만) |
| --- | --- | --- |
| `<YOUR_PROJECT.vercel.app>` | 내 배포 주소 | `my-cafe-site.vercel.app` |
| `<YOUR_SUPABASE_URL>` | Supabase 프로젝트 URL | `https://xxxx.supabase.co` |
| `<YOUR_SUPABASE_ANON_KEY>` | 공개(anon) 키 — 노출돼도 됨 | `eyJ...` (프론트 사용 가능) |
| `<YOUR_SERVICE_ROLE_KEY>` | service_role(비밀) 키 — **절대 커밋·노출 금지** | 환경변수/서버에서만 |

> 다시: **anon(공개) 키**는 프론트엔드에 노출돼도 되지만,
> **service_role(비밀) 키**는 코드·커밋·화면 어디에도 들어가면 안 됩니다.
> 공개 데이터 접근은 RLS(행 수준 보안)로 보호하고, 비밀 키가 필요한 작업은 서버에서만 처리하세요.
