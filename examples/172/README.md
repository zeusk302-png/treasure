# 172. Claude에게 deploy 스킬 지시해 커밋 메시지까지 자동화하기

## 목표

내가 직접 `git` 명령을 외워서 치는 대신, **Claude(또는 쓰는 AI)를 디렉팅**해서
다음 순서를 대신 시키는 법을 익힙니다.

1. **비밀키 점검** — 커밋에 service_role(비밀) 키나 `.env`가 섞이지 않았는지 먼저 확인
2. **의미 단위 커밋** — Conventional Commits 형식(`feat`, `fix`, `docs` …)으로 메시지 작성
3. **push** — GitHub에 올리면 Vercel이 자동 배포
4. **배포 보고** — 커밋 해시·브랜치·결과 URL·상태 확인 위치를 한눈에 보고받기

핵심은 **"위험한 일은 AI가 먼저 보고하고, 내가 승인한 뒤에만 실행하게"** 만드는 디렉터의 통제입니다.
이 실습에는 새로 짤 코드가 거의 없습니다. **잘 지시하는 글쓰기**가 곧 실습입니다.

결과물은 두 파일입니다.

- [`prompt.md`](prompt.md) — AI에게 그대로 붙여넣는 지시 프롬프트(+ 멈춤·승인 한 마디)
- [`deploy-report.md`](deploy-report.md) — AI가 수행한 커밋 1건의 배포 보고(예시 + 내가 채울 빈칸)

## 따라하는 단계

1. 미리 준비: HTML/CSS/JS 사이트가 GitHub 저장소에 있고, Vercel과 연결돼 **push하면 자동 배포**되는 상태여야 합니다. (아직이라면 먼저 [169](../169/README.md)·[170](../170/README.md)를 끝내세요.)
2. 사이트에서 **아주 작은 변경 하나**(예: 첫 화면 소개 문구 한 줄)를 직접 수정하고 저장합니다. 커밋할 "거리"를 만드는 단계입니다.
3. [`prompt.md`](prompt.md)의 **1단계 지시 프롬프트**를 통째로 복사해 Claude에 붙여넣습니다.
4. AI가 **[1] 비밀키 점검 결과(표)** 와 **[2] 커밋 메시지 초안**을 먼저 보여주고 멈추는지 확인합니다. AI가 점검을 건너뛰고 곧장 커밋하려 하면, [`prompt.md`](prompt.md)의 **2단계 멈춤 한 마디**로 다시 잡아줍니다.
5. 점검 결과에 **service_role(비밀) 키나 `.env`** 가 걸리면 멈추고, AI가 알려주는 대로 `.gitignore`·환경변수로 옮긴 뒤 다시 점검을 받습니다. (anon 공개 키는 노출돼도 되므로 막지 않아도 됩니다.)
6. 커밋 메시지 초안이 의미 단위·한국어·50자 이내인지 읽고, 좋으면 [`prompt.md`](prompt.md)의 **3단계 승인 한 마디**("진행해")를 보냅니다.
7. AI가 실행한 `git add → commit → push` 명령과 **[5] 배포 보고**를 받습니다.
8. Vercel → 프로젝트 → **Deployments** 맨 윗줄에서 방금 커밋이 **Ready**로 떴는지 확인하고, [`deploy-report.md`](deploy-report.md)의 "내 보고서(빈칸)"를 실제 값으로 채웁니다.

## 🤖 바이브코딩 프롬프트

이 실습의 결과물은 "코드"가 아니라 **AI를 안전하게 부리는 지시문**입니다. 아래 프롬프트를 그대로 복사해 Claude(또는 쓰는 AI)에 붙여넣으세요. (`prompt.md`에 더 자세한 전체 지시문이 있습니다.)

- **1단계(뼈대 만들기)** — 위험한 일은 먼저 보고하고 멈추는 "배포 보조" 역할부터 세우기:
  ```text
  너는 내 배포 보조 디렉티(deploy 스킬 역할)야. 나는 비전공자고, HTML/CSS/JS 사이트를
  GitHub에 push하면 Vercel이 자동 배포하는 구조를 써.
  지금 작업 폴더에 내가 수정한 파일이 있어. 아래 "순서 그대로" 지켜줘.
  [1] 비밀키 점검: 변경분(staged+unstaged)에 service_role(비밀) 키, .env, API secret,
      토큰 같은 긴 문자열이 섞였는지 점검해서 (파일/의심구간/위험도/조치) 표로 먼저 보고만 해.
      참고: Supabase anon(공개) 키는 노출돼도 되니 막지 말고, service_role(비밀) 키만 막아.
  [2] 커밋 메시지 초안: Conventional Commits 형식(type(scope): 한 줄 요약), 한국어 50자 이내로 제안해.
  여기까지 보여주고 "이대로 진행할까요?"라고 묻고 멈춰. 내가 "진행해"라기 전엔 커밋·push 절대 금지.
  모든 답변은 비전공자도 알아듣게 한국어로.
  ```
- **2단계(기능 추가/개선)** — 점검·초안이 마음에 들면 승인하고 실행+보고까지 시키기:
  ```text
  좋아, 점검 통과했고 커밋 메시지도 그대로 좋아. 진행해.
  실행할 git 명령(git add → commit → push)을 순서대로 보여주며 실행하고,
  끝나면 [5] 배포 보고를 채워줘: 커밋 메시지 / 짧은 해시 / push 브랜치 /
  Vercel Production URL(<YOUR_PROJECT.vercel.app> 자리표시자로 둬도 됨) /
  배포 상태 확인 위치(Vercel → Deployments 맨 윗줄) / Error일 때 볼 곳(Build Logs).
  ```
- **막혔을 때(디버깅)** — AI가 점검을 건너뛰거나 배포가 실패했을 때:
  ```text
  잠깐, 아직 "진행해"라고 안 했어. 먼저 [1] 비밀키 점검 결과 표와 [2] 커밋 메시지 초안만 보여줘.
  커밋·push는 내 승인 다음이야.
  --- (배포가 Error로 떴다면) ---
  Vercel Deployments 맨 윗줄이 Error야. 이 빌드 로그를 붙여넣을게: <Build Logs 에러 줄 붙여넣기>
  무엇이 원인인지 한 줄로 알려주고, 비전공자가 따라할 수 있게 고치는 절차를 단계별로 풀어줘.
  ```
> 프롬프트 팁: "명령만 주지 말고 각 git 명령이 무슨 일을 왜 하는지 한 줄씩 주석으로 설명해줘"를 덧붙이면, 다음엔 직접 칠 때도 이해하며 쓸 수 있습니다.

## 검증법

아래를 모두 만족하면 성공입니다.

- [ ] AI가 **커밋·push보다 먼저** 비밀키 점검 결과(표)와 커밋 메시지 초안을 보고했다.
- [ ] 점검에서 **service_role(비밀) 키·`.env`가 커밋에 섞이지 않았음**을 확인했다. (anon 공개 키는 괜찮다는 것도 구분했다.)
- [ ] 커밋 메시지가 **Conventional Commits 형식**(`type(scope): 요약`)이고, 한 줄 요약이 50자 이내·한국어다.
- [ ] 내가 **"진행해"라고 승인한 뒤에야** 실제 `git push`가 실행됐다.
- [ ] GitHub 저장소 **Commits**에 새 커밋 1건이 보이고, 그 짧은 해시가 Vercel **Deployments** 맨 윗줄 해시와 **같다**.
- [ ] [`deploy-report.md`](deploy-report.md)의 "내 보고서" 빈칸(커밋 메시지·해시·브랜치·URL·상태)이 모두 채워졌다.

> 빠른 자가 점검: 누군가 "수정이 사이트에 반영이 안 돼요"라고 물으면,
> **① Deployments 맨 윗줄이 Ready인지 → ② 커밋 해시가 맞는지 → ③ 강력 새로고침** 순으로
> 점검하라고 안내할 수 있으면, 이번 실습의 진짜 목표(디렉팅 + 판단력)를 달성한 것입니다.
