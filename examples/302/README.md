# 실습 302 — 방명록 입력 이스케이프: `<script>` 글이 실행되지 않게 막기

방명록처럼 **남이 적은 글을 화면에 보여주는 기능**은, 그 글을 어떻게 출력하느냐에 따라 안전할 수도, 통째로 뚫릴 수도 있습니다. 이번 실습에서는 일부러 취약하게 만든 방명록(`broken.html`)에 직접 공격을 넣어 **경고창이 뜨는 것**을 본 뒤, 코드 **딱 한 군데**를 `innerHTML` → `textContent` 로 고쳐 같은 공격이 **글자로만 표시되고 실행되지 않는 것**을 확인합니다.

> 핵심 한 줄: `innerHTML` 은 받은 문자열을 **"HTML 코드로 해석"** 하고, `textContent` 는 **"그냥 글자"** 로만 취급합니다. 사용자 입력은 항상 `textContent` 로 출력하면, `<script>`·`onerror` 같은 게 글에 섞여 들어와도 **코드가 아니라 글자**로만 보입니다. 이것이 가장 기본적인 XSS(크로스 사이트 스크립팅) 방어입니다.

이 폴더의 파일은 셋입니다.

- [`broken.html`](broken.html) — **일부러 XSS에 뚫리게 만든 방명록.** 입력을 `innerHTML` 로 출력합니다. (파일 맨 위 주석에 공격 재현 절차가 있습니다)
- [`index.html`](index.html) — `broken.html` 을 고친 **안전한 버전.** 입력을 `textContent` 로 출력합니다. (무엇을 고쳤는지 주석으로 표시)
- `README.md` — 지금 읽는 이 안내문 (아래에 **원인 → 수정 해설**이 있습니다)

> 이번 실습은 Supabase 키가 필요 없습니다. XSS의 원리는 "입력을 어떻게 화면에 그리느냐"의 문제라, 글을 메모리(배열)에 담아 똑같이 재현할 수 있기 때문입니다. (실제 방명록도 출력 방식만 다를 뿐 원리는 같습니다.)

## 목표
- `innerHTML` 로 사용자 입력을 출력하면 왜 위험한지(= 입력이 코드로 실행됨)를 **직접 공격해 보며** 체감한다.
- 같은 코드를 `document.createElement` + `textContent` 로 바꿔 **입력을 항상 글자로만** 출력하게 고친다.
- "고쳤다"를 말이 아니라 **같은 공격 입력이 경고창 → 글자로** 바뀌는 눈에 보이는 증거로 증명한다.

## 따라하는 단계
1. [`broken.html`](broken.html) 을 브라우저로 엽니다(파일 더블클릭). 평범한 방명록처럼 보입니다.
2. 이름칸에 `공격자`, 내용칸에 아래 한 줄을 **그대로 붙여넣고** [남기기] 를 누릅니다.
   ```
   <img src=x onerror="alert('해킹됨!')">
   ```
3. 글이 등록되는 순간 **`해킹됨!` 경고창이 뜹니다.** 우리가 만든 적 없는 코드가, 남이 적은 글 때문에 실행된 것입니다. (이게 XSS입니다.)
4. (선택) 내용칸에 `<script>alert(document.cookie)</script>` 를 넣어 보면, 실제 공격자가 어떻게 로그인 정보(쿠키)를 빼가는지 감이 옵니다.
5. 이제 [`index.html`](index.html) 을 엽니다. 그리고 **2번과 똑같은 공격 입력**을 다시 넣고 [남기기] 를 누릅니다.
6. 이번엔 경고창이 **뜨지 않고**, 입력한 `<img src=x onerror="alert('해킹됨!')">` 가 **글자 그대로** 방명록에 보이면 성공입니다.
7. 두 파일의 `render()` 함수를 비교해 무엇이 달라졌는지 확인합니다. (`innerHTML = ...` 한 줄 → `createElement` + `textContent` 로 교체)

## 검증법
아래를 모두 만족하면 성공입니다.

- [ ] `broken.html` 에서 `<img src=x onerror="alert('해킹됨!')">` 를 등록하면 **경고창이 실제로 뜬다**(취약점 재현 성공).
- [ ] `index.html` 에서 **똑같은 입력**을 등록하면 **경고창이 안 뜨고**, 그 입력이 **글자 그대로** 화면에 보인다.
- [ ] `index.html` 에서 `<script>alert(1)</script>` 를 넣어도 코드가 실행되지 않고 글자로만 보인다.
- [ ] 고친 `index.html` 코드에 **`innerHTML` 로 사용자 입력을 꽂는 줄이 없다.** (F12 → Sources 또는 에디터에서 `innerHTML` 검색 시 사용자 입력 출력에는 안 쓰임)
- [ ] 정상적인 글(예: 이름 `철수`, 내용 `잘 보고 갑니다!`)도 두 버전 모두에서 멀쩡히 보인다(기능은 그대로).

> 빠른 자가 점검: `index.html` 을 열고 내용칸에 `<b>굵게</b>` 를 넣어 보세요. 글자가 **굵어지지 않고** `<b>굵게</b>` 라는 글자 그대로 보이면, 입력이 코드로 해석되지 않는다는 뜻이니 통과입니다.

## 원인 → 수정 해설 (이 실습의 정답 풀이)

**증상:** 방명록 내용칸에 `<img src=x onerror="alert('해킹됨!')">` 를 넣으면, 글이 등록되는 순간 경고창이 뜬다.

**근본 원인:** `broken.html` 의 `render()` 가 사용자 입력을 `innerHTML` 로 꽂는다.

```js
// broken.html (위험): 사용자 입력을 HTML 코드로 해석해 화면에 꽂는다.
entriesBox.innerHTML =
  '<div class="entry">' +
    '<div class="name">' + item.name + '</div>' +
    '<div class="body">' + item.body + '</div>' +  // ← 여기 item.body 안의 <img>·<script> 가 실행됨
  '</div>';
```

`innerHTML` 은 대입된 문자열을 **"이건 HTML이다"** 라고 보고 태그를 만들어 실행합니다. 그래서 입력에 들어 있던 `<img onerror=...>` 의 `onerror` 가 브라우저에 의해 진짜로 실행됩니다. 공격자가 글 한 줄로 우리 페이지에서 **임의의 자바스크립트**를 돌릴 수 있게 되는 것이죠. 이것이 XSS(크로스 사이트 스크립팅)입니다.

**수정:** HTML 문자열을 만들지 말고, 요소를 만들어 값은 `textContent` 로 넣습니다.

```js
// index.html (안전): 요소를 만들고, 값은 textContent 로 — 무엇을 넣든 '글자'로만 취급.
const body = document.createElement("div");
body.className = "body";
body.textContent = item.body;   // ← 핵심 한 줄: innerHTML 이 아니라 textContent
```

`textContent` 는 대입된 값을 **"전부 글자"** 로만 취급합니다. `<` 와 `>` 도 태그가 아니라 그냥 부등호 글자로 화면에 보입니다. 그래서 같은 공격 입력이 **실행되지 않고 글자로만** 표시됩니다.

**교훈:**
- 화면에 **사용자가 적은 값**을 보여줄 때는 기본을 `textContent`(또는 프레임워크의 안전한 출력)로 두세요. `innerHTML` 에 사용자 입력을 직접 넣는 순간 XSS의 문이 열립니다.
- "입력을 막는다"가 아니라 **"출력할 때 글자로만 그린다"** 가 더 확실한 방어입니다. 입력은 막아도 우회가 많지만, 출력을 `textContent` 로 고정하면 새는 곳이 없습니다.
- AI에게 화면 그리는 코드를 받을 때, 사용자 입력을 `innerHTML`/`element.innerHTML +=` 로 꽂는 패턴이 보이면 의심하고 `textContent` 로 바꾸도록 지시하세요.
