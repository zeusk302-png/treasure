# 실습 291 — RLS 누락으로 남의 데이터가 다 보이는 방명록 잠그기

방명록을 만들었더니, **누구나 남이 쓴 글을 지우고 고칠 수 있는** 상태였습니다.
원인은 **RLS(행 수준 보안)가 꺼져 있거나**, 켜더라도 `USING (true)`처럼 **사실상 다 열린 정책**을 넣었기 때문입니다.
이 깨진 코드를 직접 찾아 고치며, "데이터베이스가 직접 막는다"는 행 수준 보안의 개념을 배웁니다.

> 이건 디버깅(고치기) 실습입니다. 폴더에는 **깨진 버전(`broken.sql`)** 과 **고친 버전(`schema.sql`)** 이 함께 들어 있습니다.

## 목표
- "공개(anon) 키가 안전한 진짜 이유는 키가 비밀이라서가 아니라 **RLS가 켜져 있어서**"임을 체험한다.
- `USING (true)`가 왜 "잠금 효과가 0인 가짜 정책"인지 눈으로 본다.
- "누구나 읽기 + **작성자 본인만** 삭제·수정"을 `auth.uid() = user_id` 정책으로 만들어, 남의 글 삭제가 실제로 막히는 것을 확인한다.

## 따라하는 단계
1. `broken.sql`을 먼저 읽는다. 무엇이 빠졌고(=RLS 켜는 줄), 무엇이 위험한지(=`USING (true)` 삭제/수정 정책) `❌` 주석으로 표시돼 있다.
2. (재현) Supabase 대시보드 → **SQL Editor**에 `broken.sql`을 붙여넣고 실행한다. → 대시보드 Table editor에서 `guestbook` 테이블에 **"RLS Disabled" 빨간 경고**가 보인다. 이게 위험 신호다.
3. (확인) 이 상태에서는 공개 키만으로 **아무 글이나 삭제**가 통과된다. "남의 글도 지워지는" 상태임을 머리로 확인한다.
4. (고치기) `broken.sql` 내용을 지우고, 이번엔 **`schema.sql`** 을 SQL Editor에 붙여넣고 실행한다. 바뀐 핵심 3가지:
   - `alter table guestbook enable row level security;` → **RLS를 켠다.**
   - 작성 정책을 `with check (auth.uid() = user_id)` → **로그인 본인 명의로만 작성.**
   - 삭제·수정 정책을 `using (auth.uid() = user_id)` → **작성자 본인만 지우고 고칠 수 있음.**
5. (검증) 아래 "검증법"대로, **남의 글을 지워보고 막히는지** 직접 확인한다.

## 검증법
- **경고가 사라졌는가?** `schema.sql` 실행 후 Table editor에서 `guestbook`의 "RLS Disabled" 경고가 없어졌는지 본다.
- **남의 글 삭제 시도(핵심).** 계정 A로 글을 하나 남긴다. 다른 계정 B(또는 비로그인)로 그 글을 지우려고 시도한다 → **0행 삭제(막힘)** 가 정상이다. 화면에서 A의 글이 그대로 남아 있어야 한다.
- **본인 글 삭제.** A 계정으로 자기 글을 지운다 → 정상적으로 1행 삭제된다.
- **나란히 비교.** `broken.sql`로 만든 테이블은 누구나 삭제 통과, `schema.sql`로 만든 테이블은 본인만 통과 — 같은 요청을 두 테이블에 보내 결과 차이를 직접 본다. ("화면상으로는 둘 다 잘 도는 앱처럼 보인다"는 점이 함정이다.)

> 핵심 한 줄: 잘못은 **코드**가 아니라 **데이터베이스 정책**에 있었다. 그래서 고치는 곳도 SQL의 RLS 정책이다.

!!! danger "절대 하지 말 것"
    남의 글까지 지워야 하는 관리자 기능이 필요하면 `service_role`(secret) 키를 **서버에서만** 쓴다. 이 키는 RLS를 통째로 우회하므로 **브라우저·GitHub에 절대 두면 안 된다.** 공개해도 되는 건 `anon`(publishable) 키뿐이다.
