# 229. AI에게 보안 체크리스트로 내 Supabase 코드 심문시키기

## 목표

"보안 좀 봐줘"라고 막연히 부탁하면 AI는 매번 다른 곳만 봅니다.
그래서 이번엔 **검사 항목 7개를 사람이 미리 못 박아** 두고,
AI에게 그 항목을 하나도 빠짐없이 **✅(안전)/⚠️(고쳐야 함)/❌(치명적 위험)** 로 판정하게 만듭니다.

핵심은 비전공자가 Supabase에서 가장 자주 당하는 **세 가지 사고**를 고정 항목으로 검증하는 것입니다.

1. **공개키 vs 비밀키 분리** — 비밀키(`service_role` / `sb_secret_`)가 브라우저(프론트)에 박혀 있나?
   (공개키 `anon` / `sb_publishable_`는 화면에 보여도 안전, 비밀키는 절대 안 됨)
2. **RLS(행 수준 보안)** — 프론트가 접근하는 테이블에 RLS가 켜져 있나?
   (안 켜면 공개키만으로 테이블 전체가 털림)
3. **명단 통째 조회 차단** — 이름·전화·이메일 같은 개인정보를 아무나 전체 조회할 수 있게 열어 뒀나?

새로 짤 화면은 없습니다. **검사 항목을 고정해 AI를 검증기로 부리는 질문 설계**가 곧 실습입니다.

이 폴더의 파일은 여섯입니다.

- [`prompt.md`](prompt.md) — AI를 "보안 심사관"으로 세워 7개 항목을 ✅/⚠️/❌로 판정시키는, 그대로 붙여넣는 지시 프롬프트
- [`vulnerable-code.html`](vulnerable-code.html) — **검사할 재료(프론트).** 일부러 비밀키·전체조회·디버그노출 구멍을 넣어 둔 코드
- [`vulnerable-policy.sql`](vulnerable-policy.sql) — **검사할 재료(SQL).** RLS 미설정 + 전체 공개 읽기 정책
- [`SECURITY-REVIEW.md`](SECURITY-REVIEW.md) — **이 실습의 결과물.** 항목별 ✅/⚠️/❌ 리포트 + 내 결정 칸
- [`fixed-policy.sql`](fixed-policy.sql) — **고친 정책.** RLS enable + 본인 행만 읽기/쓰기로 좁힌 SQL
- [`fixed-code.html`](fixed-code.html) — 공개키로 교체하고 본인 행만 조회하도록 고친 프론트
- `README.md` — 지금 읽는 이 안내문

## 이 재료 코드의 함정 (정답표 — 검사 후 맞춰 보세요)

| 곳 | 함정 | 올바른 판정 |
|---|---|:---:|
| `vulnerable-code.html` `SUPABASE_KEY` | 비밀키(`sb_secret_`)를 브라우저 코드에 박음 | ❌ |
| `vulnerable-code.html` `select("*")` | 회원 전체(이름·전화·이메일)를 통째 조회 | ❌ |
| `vulnerable-code.html` `console.log/error` | 전체 데이터·에러 원문을 콘솔에 노출 | ⚠️ |
| `vulnerable-policy.sql` | `enable row level security` 줄이 없음(RLS 꺼짐) | ❌ |
| `vulnerable-policy.sql` `using (true)` | 개인정보 테이블을 아무나 전체 읽기 | ❌ |
| `vulnerable-policy.sql` insert/update/delete | 아무나 쓰기·수정·삭제 가능 | ⚠️ |

## 따라하는 단계

1. 검사할 재료를 준비합니다. 같은 폴더의 [`vulnerable-code.html`](vulnerable-code.html)과 [`vulnerable-policy.sql`](vulnerable-policy.sql)을 쓰거나, **내가 만든 진짜 Supabase 코드와 SQL 정책**을 준비합니다.
2. [`prompt.md`](prompt.md)의 **1단계 지시 프롬프트**를 통째로 복사하고, `[여기에 내 코드를 붙여넣기]` / `[여기에 내 SQL 정책을 붙여넣기]` 자리에 위 두 재료를 넣습니다. 핵심 제약은 **"7개 항목을 하나도 빼지 말고 ✅/⚠️/❌로, 근거는 코드 줄 인용으로"** 입니다.
3. 완성한 프롬프트를 실제 Claude(또는 쓰는 AI)에 붙여넣습니다.
4. AI가 **7개 항목을 표로** 판정했는지 봅니다. 특히 **1번(비밀키가 프론트에 있나)** 과 **3번(RLS가 켜져 있나)** 은 ✅/❌ 중 하나로 확정되어야 합니다.
5. AI가 항목을 건너뛰거나 **"대체로 안전해 보여요"** 로 근거 없이 뭉개면, [`prompt.md`](prompt.md)의 **2단계 한 마디**로 "1~7번 다시, 줄 인용해서"를 요구합니다.
6. 판정이 다 나오면 [`prompt.md`](prompt.md)의 **3단계 한 마디**로 ❌·⚠️만 모아 "고친 정책 표"를 만들게 하고, AI가 준 고친 정책이 **(가) RLS enable (나) 읽기 범위 좁힘 (다) 비밀키 제거** 3가지를 충족하는지 **스스로 자진 보고**하게 합니다.
7. AI가 정리한 것을 [`SECURITY-REVIEW.md`](SECURITY-REVIEW.md)처럼 옮기되, **"내 결정" 칸(지금 고친다 / 다음에)은 내가 직접** 채웁니다.
8. 고친 정책을 [`fixed-policy.sql`](fixed-policy.sql)·[`fixed-code.html`](fixed-code.html)과 비교합니다. **RLS enable과 좁힌 policy가 둘 다 들어 있는지**, 비밀키가 프론트에서 완전히 빠졌는지 사람이 눈으로 확인합니다.

## 🤖 바이브코딩 프롬프트

이 실습은 "AI에게 새 화면을 만들게 하는" 실습이 아니라 **AI를 보안 검증기로 부리는** 실습입니다.
그래서 프롬프트도 "만들어줘"가 아니라 **"고정 체크리스트로 심문해줘"** 형태입니다. 그대로 복사해 쓰세요.

- **1단계(뼈대 만들기 — 검사 틀 세우기)** 프롬프트:
  ```text
  너는 내 Supabase 코드를 검사하는 "보안 심사관"이야.
  내가 줄 [보안 체크리스트] 7개 항목을 하나도 빼지 말고 순서대로 판정해.

  [판정 규칙]
  - 각 항목을 ✅(안전) / ⚠️(고쳐야 함) / ❌(치명적 위험) 중 하나로 표시.
  - 판정 근거는 반드시 "내가 붙여넣은 코드의 어느 줄"인지 인용.
  - 코드에 없어서 모르면 "확인 불가"라고만 적고, 임의로 안전하다고 하지 마.

  [보안 체크리스트] (이 7개를 고정으로)
  1. 비밀키(service_role / sb_secret_)가 브라우저로 가는 코드나 NEXT_PUBLIC_ 에 박혀 있나? (하나라도 있으면 ❌)
  2. 프론트에는 공개키(anon / sb_publishable_)만 쓰고 있나?
  3. 프론트가 접근하는 모든 테이블에 "enable row level security"(RLS)가 켜져 있나? (안 켜졌으면 ❌)
  4. "for select using (true)"처럼 아무나 전체를 읽는 테이블에 개인정보(이름·연락처·이메일)가 있나?
  5. insert/update/delete 정책이 "본인 것만"·"관리자만"으로 좁혀져 있나, 아무나 가능한가?
  6. API 키·URL·비밀번호가 코드에 진짜 값으로 박혀 있나? (자리표시자 YOUR_... 면 안전)
  7. 콘솔/화면에 키·내부 구조·전체 행 데이터를 그대로 뱉는 코드가 있나?

  [출력 형식] 먼저 "항목 | 판정 | 근거(인용) | 한 줄 개선안" 표로 7줄. 칭찬/총평은 맨 마지막 한 줄만.

  [검사할 코드]
  --- 프론트 코드 ---
  [여기에 내 코드를 붙여넣기]
  --- SQL 정책 ---
  [여기에 내 SQL 정책을 붙여넣기]
  ```
- **2단계(기능 추가/개선 — 고친 정책까지 받아내기)** 프롬프트:
  ```text
  이제 위에서 ❌ 와 ⚠️ 로 나온 항목만 모아 아래 표로 정리해줘.
  | 항목 | 판정 | 위험을 한 줄로 | 너의 고친 정책/코드 | 내 결정(지금 고친다 / 다음에) |

  그리고 "고친 SQL 정책"을 제시할 때:
  (가) RLS를 enable 했고
  (나) 읽기를 아무나 전체가 아니라 본인 행만(auth.uid() = user_id)으로 좁혔고
  (다) 비밀키를 프론트에서 완전히 빼고 공개키로 교체했는지
  이 3가지를 네가 스스로 "통과/미통과"로 자진 보고해. 미통과면 그 자리에서 다시 고쳐.
  비밀값은 새로 만들지 말고 YOUR_... 자리표시자로 둬.
  ```
- **막혔을 때(디버깅 — 검사가 헐거울 때 되돌리기)** 프롬프트:
  ```text
  방금 7개 항목 중 일부를 건너뛰었거나, 근거 인용 없이 "대체로 안전해 보인다"고 했어. 규칙 위반이야.
  1~7번을 다시, 하나도 빼지 말고, 각 항목마다 "내 코드의 어느 줄을 보고 그 판정을 내렸는지" 인용해서 적어.
  특히 1번(비밀키가 프론트에 있나)과 3번(RLS가 켜져 있나)은 ✅/❌ 중 하나로 반드시 확정해.
  "아마", "보통은" 같은 말은 금지. RLS만 켜고 정책을 다시 using(true)로 열어 둔 "반쪽 수정"이 아닌지도 같이 확인해.
  ```

> 프롬프트 팁: 고친 정책/코드를 받을 때 **"코드만 주지 말고 왜 그렇게 고쳤는지(특히 RLS와 키 분리가 왜 필요한지) 주석으로 한 줄씩 풀어줘"** 를 덧붙이면, 다음에 직접 검증할 때 판단 근거가 남습니다.

## 검증법

아래를 모두 만족하면 성공입니다.

- [ ] AI가 **7개 항목 전부**를 ✅/⚠️/❌로 판정했다. (건너뛴 항목이 없다)
- [ ] 각 판정에 **"내 코드의 어느 줄을 보고 그렇게 판정했는지"** 근거 인용이 붙어 있다.
- [ ] **비밀키(`sb_secret_`)가 프론트에 있던 것**을 ❌로 정확히 잡아냈다.
- [ ] **RLS가 꺼져 있던 것**을 ❌로 잡아냈고, 고친 정책에 `enable row level security`가 들어 있다.
- [ ] **개인정보 전체 조회(`using (true)`)** 를 ❌/⚠️로 잡고, 본인 행만 읽도록(`auth.uid() = user_id`) 좁혔다.
- [ ] 고친 정책이 RLS만 켜고 다시 `using (true)`로 여는 **반쪽 수정**이 아니다.
- [ ] 비밀값이 코드에 진짜 값이 아니라 **자리표시자(`YOUR_...` / `sb_publishable_...`)** 로 남아 있다.
- [ ] [`SECURITY-REVIEW.md`](SECURITY-REVIEW.md)에 항목 표가 정리되고, **"내 결정" 칸을 사람이 직접** 채웠다.

> 빠르게 자가 점검: 리포트만 보고 **"무엇이 ❌라서 지금 당장 못 고치면 명단이 털리는지"** 가 한눈에 보이면 통과입니다.
> 만약 AI가 비밀키와 RLS를 둘 다 ✅로 통과시켰다면, **검사가 헐거운 것**입니다. [`prompt.md`](prompt.md)의 2단계로 1·3번을 다시 확정시키세요.

## 관련 가이드

- 가이드 본문: [공개해도 되는 키 vs 절대 숨길 키 — anon/publishable vs service_role/secret 완전 정정](../../docs/04-security/01.md)
  체크리스트 1·2번의 근거입니다. **공개키(anon)는 보여도 안전, 비밀키(service_role)는 절대 프론트 금지.** 두 키를 거꾸로 알면 이 실습 전체가 무너집니다.
- 가이드 본문: [RLS(행 수준 보안) — 출입증을 공개해도 안전한 진짜 이유](../../docs/04-security/02.md)
  체크리스트 3·4번의 근거입니다. 공개키가 안전한 이유가 바로 RLS이며, RLS를 켜더라도 정책을 `using (true)`로 열어 두면 똑같이 뚫린다는 점이 핵심입니다.
- 가이드 본문: [AI가 만든 코드의 보안을 디렉터가 검증하는 법](../../docs/04-security/08.md)
  이 실습의 뼈대입니다. AI가 만든 코드를 그대로 믿지 않고 **고정 체크리스트로 심문**해 검증하는 디렉터의 일이 바로 이것입니다.
- 가이드 본문: [믿되 검증하라 — AI 결과물을 받아들이는 기본자세](../../docs/01-mindset/06.md)
  AI가 준 "고친 정책"도 초안입니다. RLS만 켜고 정책은 다시 열어 두는 반쪽 수정이 흔하니, **승인 권한은 디렉터에게** 있습니다.
