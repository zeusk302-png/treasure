# 229. AI에게 "고정 보안 체크리스트"로 내 Supabase 코드를 심문시키는 지시 프롬프트

> 이 파일은 **AI에게 그대로 붙여넣는 지시문**입니다.
> "보안 봐줘"라고 막연히 부탁하면 AI는 그때그때 다른 곳만 봅니다.
> 그래서 이번엔 **검사 항목을 사람이 미리 못 박아** 두고, AI에게
> **그 항목을 하나도 빠짐없이 ✅/⚠️/❌ 로 판정**하게 만듭니다.
> "코드리뷰"를 **보안 관점의 정해진 점검표**로 바꾸는 연습입니다.
>
> 비전공자가 가장 자주 당하는 Supabase 사고 3가지가 검사 항목의 핵심입니다.
> 1) **비밀키(service_role)** 를 프론트(브라우저)에 박아 둠
> 2) 테이블에 **RLS(행 수준 보안)** 를 안 켜서, 공개키만으로 남의 데이터까지 다 보임
> 3) 회원·주문 같은 **명단을 아무나 통째로 조회**할 수 있게 열어 둠
>
> 이 실습에는 새로 짤 화면이 없습니다. **검사 항목을 고정해 AI를 검증기로 부리는 질문 설계**가 곧 실습입니다.

---

## 1단계 — AI에게 보낼 지시 프롬프트 (그대로 복사해서 붙여넣기)

> 아래 프롬프트의 `[여기에 내 코드를 붙여넣기]` 자리에
> 같은 폴더의 [`vulnerable-code.html`](vulnerable-code.html) 와 [`vulnerable-policy.sql`](vulnerable-policy.sql),
> 또는 **내가 만든 진짜 Supabase 코드와 SQL 정책**을 통째로 넣으세요.

```
너는 지금 내 Supabase 코드를 검사하는 "보안 심사관"이야.
아래 [보안 체크리스트]의 7개 항목을 "하나도 빼지 말고, 순서대로" 판정해.

[판정 규칙]
- 각 항목을 ✅(안전) / ⚠️(고쳐야 함) / ❌(치명적 위험) 중 하나로 표시해.
- 판정 근거는 반드시 "내가 붙여넣은 코드의 어느 줄/어느 부분"인지 인용해.
- 코드에 없어서 알 수 없으면 "확인 불가"라고만 적고 임의로 안전하다고 하지 마.
- 칭찬·총평은 맨 마지막에 한 줄만. 항목 판정을 먼저 끝내.

[보안 체크리스트] (이 7개를 고정으로 검사)
1. 키 종류 분리: 비밀키(service_role / sb_secret_)가
   브라우저로 가는 코드(HTML/프론트 JS)나 NEXT_PUBLIC_ 접두에 박혀 있는가?
   → 단 한 곳이라도 있으면 무조건 ❌.
2. 공개키 사용: 프론트에는 공개키(anon / sb_publishable_)만 쓰고 있는가?
3. RLS 활성화: 프론트에서 접근하는 모든 테이블에
   "alter table ... enable row level security" 가 켜져 있는가?
   → 안 켜져 있으면 공개키만으로 전체 데이터가 털리므로 ❌.
4. 읽기(SELECT) 정책 범위: "for select using (true)" 처럼
   아무나 전체를 읽게 열어 둔 테이블에 개인정보(이름·연락처·이메일)가 들어 있는가?
   → 명단이 통째로 노출되면 ⚠️~❌.
5. 쓰기/수정/삭제 정책: insert/update/delete 정책이
   "본인 것만" 또는 "관리자만"으로 좁혀져 있는가, 아니면 아무나 가능한가?
6. 비밀값 노출: API 키·URL·비밀번호 등이 코드에 진짜 값으로 박혀 있는가?
   (자리표시자 YOUR_... 형태면 안전, 진짜 sb_secret_... 값이면 ❌)
7. 에러·디버그 노출: 콘솔/화면에 키나 내부 테이블 구조,
   전체 행 데이터를 그대로 뱉는 코드가 있는가?

[출력 형식]
- 먼저 "항목 | 판정(✅/⚠️/❌) | 근거(인용) | 한 줄 개선안" 표로 7줄.
- 그다음 ❌ 와 ⚠️ 항목만 모아 "고친 SQL 정책"과 "고친 프론트 코드"를 제시.
  (RLS는 enable + 좁힌 policy 까지, 키는 공개/비밀 분리까지)
- 비밀값은 절대 새로 만들어 내지 말고 YOUR_... 자리표시자로 둬.

[검사할 코드]
--- 프론트 코드 ---
[여기에 내 코드를 붙여넣기]
--- SQL 정책 ---
[여기에 내 SQL 정책을 붙여넣기]

7개 항목 표부터 바로 시작해.
```

## 2단계 — AI가 항목을 건너뛰거나 "대체로 안전해 보여요"로 뭉개면 잡는 한 마디

AI는 검사 항목이 많으면 일부를 슬쩍 빼먹거나, "전반적으로 괜찮아 보입니다"로
근거 없이 안심시키려는 버릇이 있습니다. 그러면 아래로 되돌립니다.

```
방금 7개 항목 중 일부를 건너뛰었거나, 근거 인용 없이 "괜찮아 보인다"고 했어.
규칙 위반이야. 1~7번을 다시, 하나도 빼지 말고,
각 항목마다 "내 코드의 어느 줄을 보고 그 판정을 내렸는지"를 인용해서 적어.
특히 1번(비밀키가 프론트에 있는지)과 3번(RLS가 켜져 있는지)은
✅/❌ 중 하나로 반드시 확정해. "아마", "보통은" 같은 말 금지.
```

## 3단계 — 판정을 "고칠 것 / 미룰 것"으로 정리하고 고친 정책을 확정하는 마무리

판정을 다 받았으면, AI가 준 "고친 정책"을 그대로 믿지 말고 **내가 확인**합니다.

```
좋아. 이제 ❌ 와 ⚠️ 로 나온 항목만 모아서 다음 표로 정리해줘.

| 항목 | 판정 | 위험을 한 줄로 | 너의 고친 정책/코드 | 내 결정(지금 고친다 / 다음에) |

그리고 네가 준 "고친 SQL 정책"이 정말로
(가) RLS를 enable 했고 (나) 읽기를 아무나 전체가 아니라 필요한 범위로 좁혔고
(다) 비밀키가 프론트에서 완전히 빠졌는지, 이 3가지를 네가 스스로 다시 점검해서
"통과/미통과"로 자진 보고해. 미통과면 그 자리에서 다시 고쳐.
```

> 주의: AI가 준 "고친 정책"도 **항상 옳은 건 아닙니다.** AI는 RLS를 켰다면서
> 정책을 다시 `using (true)`(아무나 전체)로 열어 두는 등, **반쪽짜리 수정**을 자주 합니다.
> 그래서 마지막엔 사람이 직접 [`fixed-policy.sql`](fixed-policy.sql)처럼
> "RLS enable + 좁힌 policy"가 둘 다 들어 있는지 눈으로 확인해야 합니다.
> **승인 권한은 디렉터(나)에게** 있습니다.

## 왜 이렇게 시키나요? (비전공자용 한 줄 정리)

- "보안 봐줘"는 매번 보는 곳이 달라집니다. **항목을 사람이 고정**하면 AI가 검사기처럼 매번 같은 기준으로 봅니다.
- Supabase 사고의 90%는 **비밀키를 프론트에 둠 + RLS를 안 켬** 둘 중 하나입니다. 그래서 1·3번을 ✅/❌로 못 박게 합니다.
- 공개키(anon)는 화면에 보여도 **정상**입니다. 위험한 건 비밀키(service_role)와 **꺼진 RLS**입니다. 둘을 거꾸로 알면 안 됩니다.
- AI가 준 "고친 정책"도 초안입니다. RLS를 켜고도 정책을 다시 아무나로 열어 두는 반쪽 수정이 흔하니, 사람이 마지막에 확인합니다.
