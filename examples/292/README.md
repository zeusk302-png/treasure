# 실습 292 — 타임존 어긋남 잡기: 한국 자정에 올린 글이 '어제'로 찍히는 버그

댓글 목록을 만들었더니, **한국 시간 7월 1일 0시 30분**에 올린 글이 화면에는 **6월 30일**로 나옵니다.
하루가 어긋난 겁니다. 원인은 데이터베이스가 시각을 **UTC(세계 표준시)** 로 저장하는데,
그 값을 **한국 시간으로 바꾸지 않고 그대로** 화면에 찍었기 때문입니다.

이 깨진 코드를 직접 찾아 고치며, "저장은 UTC로, 표시는 현지(한국) 시간으로"라는 타임존 원칙을 배웁니다.

> 이건 디버깅(고치기) 실습입니다. 폴더에 **깨진 버전(`broken.html`)** 과 **고친 버전(`index.html`)** 이 함께 들어 있습니다.

## 목표
- 데이터베이스의 `created_at`이 왜 **UTC(끝에 `Z`)** 로 저장되는지, 그게 왜 좋은 습관인지 이해한다.
- 날짜 문자열을 `split("T")`로 자르는 것이 왜 위험한지(타임존 정보가 버려진다) 눈으로 본다.
- `new Date(...)`로 UTC를 정확히 해석하고, `toLocaleDateString`/`toLocaleString`에 **`timeZone: "Asia/Seoul"`** 을 줘서 항상 한국 시간으로 보이게 고친다.

## 따라하는 단계
1. `broken.html`을 브라우저로 연다(파일을 더블클릭). 마지막 "현우 / 자정에 첫 댓글!"의 날짜가 **6월 30일**로 나오는지 확인한다 — 이게 재현된 버그다. (이 화면을 캡처해 두면 "어긋난 사례 재현 스샷"이 된다.)
2. `broken.html`의 자바스크립트에서 `❌` 주석을 찾는다. 범인은 이 한 줄이다:
   `const dateText = c.created_at.split("T")[0];` — UTC 문자열을 한국 시간으로 바꾸지 않고 날짜만 잘라 쓴다.
3. 왜 어긋나는지 이해한다: `"2026-06-30T15:30:00Z"`는 UTC로 6/30 15:30 이지만, **한국(UTC+9)으로는 7/1 0:30** 이다. `split`은 이 +9시간을 무시한다.
4. `index.html`(고친 버전)을 연다. 바뀐 핵심 두 가지를 코드의 `✅` 주석에서 확인한다:
   - `new Date(c.created_at)` — 끝의 `Z`를 보고 시각을 **정확히 해석**한다(문자열을 자르지 않는다).
   - `toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul", ... })` — **항상 한국 시간**으로 표시한다.
5. 데이터(`comments` 배열)는 두 파일이 **완전히 똑같다**는 점을 확인한다. 고친 곳은 데이터가 아니라 **'표시하는 방법'** 뿐이다.

## 🤖 바이브코딩 프롬프트
이 실습(타임존 어긋남 버그 잡기)을 AI에게 시켜 만들거나 고칠 때 그대로 복사해 쓸 수 있는 프롬프트입니다.

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  너는 프론트엔드 강사야. 비전공자가 보기 쉬운 "댓글 목록" 한 페이지(HTML 한 파일)를 만들어줘.
  - 댓글 데이터는 자바스크립트 배열로 하드코딩(이름/메시지/created_at).
  - created_at 은 데이터베이스가 저장하는 방식 그대로 UTC(끝에 Z)로 적어줘.
    예: "2026-06-30T15:30:00Z" (한국 시간으로는 7/1 0:30 인 값을 일부러 하나 넣어줘).
  - 일단은 날짜를 created_at.split("T")[0] 로 잘라서 그대로 화면에 출력해줘(고치기 전 '깨진' 상태).
  - 사용자 입력(이름/메시지)은 innerHTML 말고 textContent 로 출력해.
  - 각 줄에 한국어 주석으로 '무엇을/왜' 설명을 달아줘.
  ```
- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  위 댓글 목록의 날짜가 한국 자정 근처 글에서 하루 어긋나는 버그를 고쳐줘.
  - 날짜 문자열을 split 으로 자르지 말고, new Date(created_at) 로 UTC를 정확히 해석해.
  - 화면 표시는 toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul", ... }) 로 '항상 한국 시간'이 되게 해.
  - +9시간을 직접 더하는 손계산은 쓰지 마(서머타임·윤초 때문에 또 다른 버그가 나).
  - 시:분까지 보는 버전(toLocaleString)도 함수로 따로 만들어줘.
  - 왜 split 이 위험하고 왜 timeZone 명시가 필요한지 한국어 주석으로 한 줄씩 설명해줘.
  ```
- **막혔을 때(디버깅)** 프롬프트:
  ```text
  댓글 날짜가 보는 사람마다 다르게 나와. 내 코드는 이거야:
  <여기에 날짜 출력 부분 코드를 그대로 붙여넣기>
  1) 왜 사람마다 다르게 보이는지 원인을 비전공자도 알게 설명해줘.
  2) created_at 값 "2026-06-30T15:30:00Z" 가 한국 시간으로 몇 월 며칠 몇 시인지 계산 과정을 보여줘.
  3) 가장 작은 수정으로 '항상 한국 시간'이 되게 고친 코드와, 고치기 전/후 화면이 어떻게 달라지는지 알려줘.
  ```
> 프롬프트 팁: 마지막에 "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 좋습니다.

## 검증법
- **두 파일 나란히 비교.** `broken.html`은 마지막 댓글이 `2026-06-30`, `index.html`은 `2026년 7월 1일`로 나오면 성공이다. (함정: 두 파일 모두 "잘 도는 앱"처럼 보인다. 날짜 한 칸만 다르다.)
- **시:분까지 확인.** `index.html`의 `formatKoreaDateTime`을 써 보면 마지막 댓글이 `2026년 7월 1일 오전 12:30`으로 나온다 — 한국 자정 직후가 맞다.
- **컴퓨터 시간대를 바꿔도 동일한가?** OS의 시간대를 다른 나라로 바꾼 뒤 새로고침해도, `timeZone: "Asia/Seoul"`을 명시했기 때문에 **항상 한국 시간**으로 똑같이 보여야 정상이다. (`timeZone`을 빼면 보는 사람마다 달라진다.)
- **다른 시각으로 직접 테스트.** `created_at` 값을 `"2026-12-31T15:00:00Z"`로 바꿔 보자 → 한국 시간으로는 다음 해 `2027년 1월 1일`이 떠야 한다. 연말연시·자정 경계에서도 안 어긋나면 통과.

> 핵심 한 줄: 잘못은 **저장된 데이터**가 아니라 **표시 코드**에 있었다. 그래서 고치는 곳도 자바스크립트의 날짜 출력 부분이다.

!!! tip "실전 팁"
    - **저장은 UTC, 표시는 현지 시간** — 이 원칙만 지키면 어느 나라 사용자가 봐도 안 꼬인다. Supabase의 `timestamptz`(`created_at timestamptz default now()`)는 자동으로 UTC로 저장해 주므로 좋은 기본값이다.
    - 직접 `+9시간을 더하는` 식으로 손계산하지 말 것. 서머타임·윤초 같은 예외가 있어 직접 더하면 또 다른 버그가 난다. 브라우저에 `timeZone: "Asia/Seoul"`을 맡기는 게 정답이다.
    - "방금 전", "3시간 전" 같은 상대 시간이 필요하면 `Intl.RelativeTimeFormat`을 쓴다.
