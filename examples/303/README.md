# 실습 303 — 개인정보 최소 수집 폼: 안 쓰는 항목 칼럼째 지우기 (데이터 다이어트)

회원가입 폼을 보면 "이름·이메일·비밀번호"만 있으면 되는데, 어느새 **주민등록번호·생년월일·집 주소·휴대폰·성별**까지 받고 있는 경우가 많습니다. "일단 받아두자", "혹시 나중에 쓸지도"가 쌓인 결과입니다. 그런데 개인정보는 **모으는 순간부터 지켜야 할 책임**이 생기고, 유출되면 가장 큰 피해가 나는 게 바로 이 안 쓰는 민감정보들입니다.

이 실습에서는 비만 폼(Before)을 **꼭 필요한 항목만 남긴 최소 수집 폼(After)** 으로 다이어트하고, 폼뿐 아니라 **데이터베이스 테이블의 칼럼까지 통째로 삭제**해 "받을 자리 자체를 없애는" 진짜 최소 수집을 구현합니다.

> 핵심 한 줄: **"필요 없는 건 처음부터 받지 않는다."** 폼에서만 항목을 지우면 테이블엔 빈 칸으로 남아 언제든 다시 받을 수 있습니다. 받을 곳(칼럼)을 없애야 수집이 원천 차단됩니다.

## 목표
- "이 항목이 없으면 서비스가 동작 안 하나?" 질문으로 **각 입력 항목의 수집 사유**를 따져 유지/삭제를 판정한다.
- 안 쓰는 입력란을 **폼(`index.html`)에서 통째로 제거**해, 민감정보(주민번호·주소 등)를 0건만 받게 만든다.
- DB 테이블에서 안 쓰는 칼럼을 `ALTER TABLE ... DROP COLUMN`으로 **칼럼째 삭제**해, 코드 어디서 실수로 INSERT 해도 들어갈 자리가 없게 한다.
- "모은 만큼 책임이 커진다 → 그러니 덜 모은다"는 **개인정보 최소 수집 원칙**을 폼·스키마·사유표로 증명한다.

## 따라하는 단계
1. `index.html`을 브라우저로 연다. 위쪽 **"고치기 전(Before)"** 폼에 주민번호·생년월일·주소·전화·성별까지 8개 입력란이 있는 것을 본다 — 이게 다이어트 대상이다.
2. `data-audit.md`(수집 항목 사유표)를 열어, 8개 항목을 한 줄씩 보며 **"없으면 서비스가 안 되나?"** 로 🟢유지/🔴삭제를 판정한다. (이름·이메일·비밀번호만 🟢, 나머지 5개는 🔴)
3. `index.html` 아래쪽 **"고친 뒤(After)"** 폼을 본다. 🔴 항목 5개의 `<input>`/`<select>`가 **통째로 지워지고** 주석으로만 "삭제됨" 표시가 남은 것을 확인한다.
4. After 폼에 이름·이메일·비밀번호(자리표시자)를 넣고 **[가입(제출 미리보기)]** 을 누른다. 아래 검은 박스에 서버로 보낼 데이터가 찍히는데, **주민번호·주소 등의 키가 아예 없는지** 눈으로 확인한다.
5. Supabase 대시보드 → **SQL Editor** 를 열고 `schema.sql`의 **1단계**를 실행해 비만 테이블 `members`(민감정보 칼럼 5개 포함)를 재현한다.
6. `schema.sql`의 **2단계**(`drop column` 5줄)를 실행해, 안 쓰는 칼럼을 DB에서 영구 삭제한다.
7. `schema.sql`의 **3단계** 검증 쿼리를 실행해, `members`에 `id·name·email·created_at` 4줄만 남고 민감정보 칼럼은 한 줄도 안 나오는지 확인한다.

## 🤖 바이브코딩 프롬프트
이 실습을 AI에게 시켜 만들 때 그대로 복사해 쓸 수 있는 프롬프트입니다. (개인정보 최소 수집 = "안 쓰는 건 처음부터 받지 않는다"가 이 실습의 핵심)

- **1단계(뼈대 만들기)** 프롬프트:
  ```text
  너는 개인정보 보호에 밝은 웹 프론트엔드 개발자야. 비전공자가 이해할 회원가입 폼 데모를 만들어줘.
  - 목표: "개인정보 최소 수집(데이터 다이어트)"을 한눈에 보여주는 학습용 단일 index.html
  - Before/After 두 개의 <form>을 한 화면에 위아래로 배치해 비교
    · Before: 이름·이메일·비밀번호 + 주민등록번호·생년월일·집 주소·휴대폰·성별까지 8개 입력란 (과수집 나쁜 예시)
    · After: 꼭 필요한 이름·이메일·비밀번호 3개만 남기고, 지운 항목은 HTML 주석으로 "삭제됨" 표시만 남김
  - 각 입력란 옆에 '유지' / '삭제 대상' 배지를 작은 라벨로 표시
  - 제약: 외부 라이브러리·CDN 금지(순수 HTML/CSS/JS), 한 파일로만, 한국어 UI
  - 코드만 주지 말고 왜 그렇게 했는지 한국어 주석으로 한 줄씩 설명해줘.
  ```

- **2단계(기능 추가/개선)** 프롬프트:
  ```text
  방금 만든 폼에 아래 기능을 추가해줘. 기존 구조와 톤은 유지하고 필요한 부분만 더해줘.
  1) After 폼에 '가입(제출 미리보기)' 버튼을 누르면, 서버로 보낼 데이터를 JSON으로 화면 아래 검은 박스에 보여줘.
     - 단, 주민번호·생년월일·주소·전화·성별 키는 payload에 아예 들어가지 않아야 해(입력란 자체가 없으니까).
     - 비밀번호는 평문을 찍지 말고 "(입력됨 — 서버에서 해시 처리)"처럼만 표시해줘.
     - 화면 출력은 innerHTML 말고 textContent로 해줘(사용자가 넣은 <script> 실행 방지).
  2) Supabase용 schema.sql도 만들어줘: 비만 테이블 members를 재현하는 1단계, 안 쓰는 칼럼 5개를 ALTER TABLE ... DROP COLUMN으로 지우는 2단계, 칼럼 목록을 information_schema로 확인하는 3단계 검증 쿼리.
  왜 그렇게 했는지 주석으로 설명해줘.
  ```

- **막혔을 때(디버깅)** 프롬프트:
  ```text
  After 폼을 제출했는데 미리보기 JSON에 phone(또는 resident_no) 같은 키가 아직 보여. 왜 그런지 단계별로 진단해줘.
  - 내 index.html 전체를 붙여넣을게: (여기에 코드 붙여넣기)
  - 확인해줄 것: ①After 폼 안에 해당 input 태그가 정말 지워졌는지 ②submitAfter()의 payload 객체에 그 키가 남아있진 않은지 ③getElementById가 가리키는 id가 맞는지
  - 고친 부분만 보여주고, 왜 그게 문제였는지 비전공자가 이해하게 한 줄씩 풀어서 설명해줘.
  ```

> 프롬프트 팁: "코드만 주지 말고 왜 그렇게 했는지 주석으로 설명해줘", "비전공자가 이해하게 한 줄씩 풀어줘"를 덧붙이면 학습에 훨씬 좋습니다.

## 검증법
- After 폼 제출 미리보기 JSON에 `resident_no`·`birth_date`·`address`·`phone`·`gender` 키가 **하나도 없는가?** (있으면 폼에서 input을 덜 지운 것.)
- `index.html`의 After `<form>` 안에 위 5개 항목의 `<input>`/`<select>` 태그가 **0개인가?** (F12 → Elements에서 `id="formAfter"` 안을 보면 입력란이 3개뿐이어야 한다.)
- `schema.sql` 3단계 쿼리 결과가 **정확히 4줄(id·name·email·created_at)** 인가? `resident_no` 등이 보이면 `drop column`이 안 먹은 것.
- `data-audit.md`의 요약표에서 "민감정보 = 0종", "테이블 개인정보 칼럼 = 2개(이름·이메일)"로 줄었는가?
- 각 🔴 항목마다 **"삭제 이유"가 한 줄씩** 적혀 있는가? (왜 안 받아도 되는지 설명할 수 있어야 진짜 최소 수집이다.)

!!! danger "비밀값·민감정보는 자리표시자로만"
    실습 중 비밀번호 칸에는 **실제로 쓰는 비밀번호를 절대 넣지 마세요.** `index.html`도 가입 미리보기일 뿐, 비밀번호는 평문으로 저장하지 않습니다(실서비스에선 Supabase Auth가 해시로 처리). 그리고 **주민등록번호는 법령상 근거 없이 수집 자체가 원칙적으로 금지**입니다 — 그래서 이번 실습의 1순위 삭제 대상입니다.

!!! warning "폼만 지우면 반쪽짜리 — 칼럼도 지워야 합니다"
    HTML 폼에서 입력란만 없애면, DB 테이블에는 `resident_no` 칼럼이 그대로 남아 "언제든 받을 수 있는 상태"입니다. 다른 화면이나 관리자 도구, AI가 만든 다른 코드가 거기에 값을 넣어버릴 수 있어요. **받을 자리(칼럼) 자체를 `DROP COLUMN`으로 없애야** 수집이 원천 차단됩니다.

!!! tip "최소 수집과 RLS는 한 세트"
    이번 실습이 **"덜 모으기"** 라면, 실습 300·301의 RLS는 **"모은 건 본인만 보기"** 입니다. 둘은 짝입니다 — 안 쓰는 건 처음부터 안 받고(303), 꼭 받아야 하는 건 RLS로 주인만 보게(301) 막으면 유출 위험이 양쪽에서 줄어듭니다.
